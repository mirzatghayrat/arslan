# 0.1.42 — background work beside the conversation, and a quieter chat

Starting point `8594e7be` (0.1.41 merge). Implementation by Claude on branch
`claude/0142-background-work`, per the owner-approved 0.1.42 task brief (kept
outside this repository). Scope: A/B background work with completion criteria
and a checked outcome, C interface subtraction. Nothing else: no Mac control,
no proactive work, no interactive browser, no local model.

## A. A chat answer is not a task awaiting review

- Before: every host answer was recorded as a durable task whose only check
  was `user-review` (evaluator `human`), so every answer ended paused at
  `acceptance_review_required` and the sidebar listed plain answers as tasks.
- Now: a host turn's acceptance is `answer-delivered` (deterministic, text
  minimum 1). An answer that delivers text succeeds; an empty one fails
  `task_validation_failed`. Budget, cancellation and crash recovery unchanged.
- Existing rows are **not** modified. Accepting old answers now would record a
  human review that never happened. The conversation header treats a host task
  whose only check is `user-review` as a chat answer (`shownInHeader`).

## B. Background work

Flow: Arslan calls `start_background_work(goal, criteria)` → the turn ends
with one line → the job runs as its own `CompanionTask` (driver
`background`) with its own budget, beside the conversation → progress card in
the chat → result message in the same conversation.

- Concurrency: at most 3 jobs run at once (`MAX_CONCURRENT`); more queue.
- Criteria (≤ 5): `file_saved` → artifact rule, `sources_read` → research
  sources, `mentions` → text contains; anything else is a model check.
  `answer-delivered` is always the first check, so an empty result never passes.
- Outcome shown: done (validator succeeded) / partial / blocked / stopped;
  interrupted when a restart cut the job short. Only a task the W10 validator
  marked succeeded is shown as done.
- Tools only inside a turn, never inside a job: `start_background_work`,
  `background_status`, `stop_background_work`. A job cannot start jobs or ask
  multiple-choice questions.
- Confirmations from a job (`server/services/approvals.py`): the card is
  broadcast to every tab of the conversation and answered by `call_id`; only a
  reply of the card's own kind resolves it; unanswered → declined after 300 s
  (same as foreground). Stricter than a turn: no session grants, no "remember",
  workspace writes asked once per job, schedules every time, remote commands
  always. Approval is a click; nothing spoken approves anything.
- Migration **0054**: the one-running-task-per-conversation index now excludes
  background tasks (a job runs beside the turn that started it). Two foreground
  turns still cannot run at once (tested on a real SQLite file).
- Migration **0055**: `arslan_messages.job_outcome` (nullable, existing rows
  untouched) so a result keeps its label after reload.
- Reconnect: a tab gets cards of running jobs and still-pending confirmations;
  a finished job is in the history as its labelled result. A job's run is
  registered with `replay=False` — found in the UI harness: without it, a
  reload during a job replayed the job's run as if the chat were busy.
- Restart: jobs live in the process. At boot, after task recovery, every
  interrupted background task is closed as cancelled and its conversation gets
  one plain notice (six languages). Chat turns keep their existing recovery.
- The generic promise guard (which appends "nothing is running in the
  background") stays quiet while a job of that conversation is really running.
- Shell: finishing reports `turn_finished` to the 0.1.41 desktop status
  (notification when the window is hidden); a job's card counts as awaiting
  approval while it waits.
- Voice conversation (V2a): when a job finishes, or stops to ask for a
  confirmation, Arslan says one line. The confirmation is still a click.
- REST: `GET /api/v1/background-jobs`, `POST /api/v1/background-jobs/{id}/stop`.
  There is deliberately no endpoint to create a job.

## UI evidence (isolated harness, synthetic model, temporary data)

`scripts/smoke_app.py` gains `ARSLAN_SMOKE_BACKGROUND=1`: `UI_BG_JOB` starts a
job whose synthetic run takes `ARSLAN_SMOKE_JOB_SECONDS`. Observed in Chrome:
the reply returns at once, a second message is answered while the job works,
the card shows its criterion "not checked yet" → "met" and the outcome, the
sidebar shows "In progress 1" and then nothing, the result carries its label,
a restart during a job posts the interruption notice, and a reload during a
job shows its card without a busy chat. Screenshots at 1280 and 900 wide,
zh/en, light/dark were taken (kept with the private brief, not in the repo).

## Cost

No paid model calls. Everything above ran offline with synthetic adapters.

## No evidence yet, not claimed

- **Whether a real model chooses background work well.** When to call
  `start_background_work`, and the criteria it drafts, come from the tool
  descriptions and system prompt only. No real model has been run on it
  (that needs the owner's per-call authorization).
- A route to an expert still runs in the foreground and holds the
  conversation until it finishes; only Arslan's own work goes to the
  background in this version.
- Two confirmation cards of the same kind (for example two jobs both asking to
  run a command) share one slot in the window; the later replaces the earlier
  on screen, and the earlier is declined after 300 s. Routing by `call_id` on
  the server is tested; the single on-screen slot is not changed.
- Jobs do not survive quitting Arslan or a crash; they are reported as
  interrupted at the next start, not resumed.
- Packaged app: not yet built, signed or fresh-install checked for 0.1.42.
- Voice: the spoken line is tested with a mocked recogniser and speaker; not
  yet heard on a real Mac.
- Linux (secondary platform): saved files are checked only inside Seatbelt, so
  there a turn or job that saved a file stops at "checks not run" instead of
  "done". Found by Linux CI on the M4 recovery eval; the eval now expects it.
