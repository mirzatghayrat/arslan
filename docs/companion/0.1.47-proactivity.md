# 0.1.47 — Proactivity

## What was built

Detect → gate → inbox → (optional quiet notification) → the user decides.

| Layer | File | What it does |
| --- | --- | --- |
| Policy (pure) | `arslan/proactive_policy.py` | The gate every candidate passes: known kind, title and evidence keys from a closed catalog, non-empty evidence, a goal (except the brief), no credential in goal or quotes, not a duplicate, not silenced. Quiet hours, daily notification cap, one brief a day, staleness, the diagnosis spend check. |
| Detectors | `server/services/proactive_detectors.py` | Stopped background jobs, failing/paused scheduled tasks, watched web pages (≥2 changed lines and ≥1 % of the page; one item a day per page), watched folders (inside the workspace; hidden files ignored). No model calls. A watch's baseline moves only after its item is stored. |
| Service | `server/services/proactive_service.py` | Stores items, sends at most one quiet notice per item, builds the brief after the pass's own findings, expires and prunes (bounded tables), accept / snooze / dismiss / silence, watches, the 10-minute loop. |
| Diagnosis (opt-in) | `server/services/proactive_diagnosis.py` | One no-tools call on the summarize model per new problem item, only with a known price, a worst case that fits today's cap and is reserved before the call. Quotes are fenced as data. |
| API | `server/api/proactive.py` | Behind the API token; strict bodies; `accept` runs the stored goal only. |
| Desktop | `desktop/src-tauri/src/resident.rs` | `proactive` notification kind: fixed words only; clicking opens the Inbox (`@inbox`). |
| UI | `web/src/components/proactive/ProactiveInbox.tsx`, `settings/ProactiveSection.tsx`, `settings/ProactiveDiagnosisCap.tsx` | Inbox with Open / Snoozed / Done, sidebar badge, Proactivity settings, the spend cap in Automation. Six languages. |

## Decisions worth knowing

- **Proposals only.** Nothing the detectors find acts. `accept` hands the stored
  goal and criteria to the existing background-job runner, whose confirmations
  (writes, commands, browser and Mac actions) are unchanged.
- **Accept is claimed with one conditional UPDATE**, so two clicks or two windows
  start one job; a job that fails to start gives the item back.
- **No model, no claim.** `accept` asks the same first question
  `llm_factory.build_adapter` asks (a provider config, or the older
  `llm_provider` setting) before claiming, so an item is never consumed by a job
  that cannot run. Found by using it in a browser, not by a test.
- **Text is keys + params.** The backend's key catalog is the gate's allow-list and
  is copied to `web/src/locales/proactive-keys.json`; a Python test fails if the copy
  is stale and a frontend test fails if any key lacks words in any language.
- **Notifications never say what was found**, only that something was: a banner
  can be read on a locked screen.
