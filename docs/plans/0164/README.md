## 4. 合并顺序

**两种情况都一样的（②Main、③Hands 审 #434 后改）：**
- **M64 最先：** SUB3–SUB5 和 STY 都要它的基线。
- **S64-0 补洞紧跟着**，然后 INB1 → INB2。
- **§11 第 3 条（上一版的删除没合完，不开新的子系统）：** C7c、C5b、F5b-2 要在 SUB、Q1、CAP 的新部分之前合，不是「空档里合」。
- CAP1–CAP3 不跑陌生代码，不用等 SBX 或 S2a-3。
- 跑陌生代码的（CAP 的 verify 和插件脚本、CAP5 的命令边界、CAP6b、SUB）都排在 SBX 后面。

**情况 A：#432 不采纳，照 10-22 的顺序。**

```
M64 → S64-0 → INB1 → INB2
C7c、C5b、F5b-2（在任何新子系统之前）
CAP1–CAP3、Q1（Bridge 帧点头后）、STY、INB3–INB9
SBX ──→ S2a-3（Codex 审 rebase 后的头）──→ CAP4 起 ──→ SUB
  └──→ ACM
```

**情况 B：#432 采纳（三层 + 模式）。云端审计（#432 上，Opus 4.8，待复核）的意见：分类器只是「少出卡」的体验层，不是安全边界，必须排在 SBX 之后；S2a-3 的解析器留下（硬规则要靠它，尤其是经系统守护进程在沙箱外生效的那一类命令），只放弃「把清单补全」。**
