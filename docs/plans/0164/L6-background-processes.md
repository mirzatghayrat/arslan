## What it is

A **background process** is a shell command that keeps running after its `run_command` call returns. It gets there one of two ways: the model starts it with `run_command(background: true)`, or **the user moves a running foreground command to the background** with the "Move to background" control (Claude Code's Ctrl+B). Its output goes to a bounded buffer and a log file, and the model and the user can list it, read it, wait for it and stop it. It is the same command, through the same gate, in the same sandbox profile, as a foreground command; only its lifetime is longer, and that lifetime is bounded, recorded and visible.

Today nothing like it exists on purpose, but one exists by accident: `cmd > log 2>&1 &` (or `nohup`, or a dev server) returns at once and leaves its process running, unlisted, unstopped by Stop, by quit or by restart. `run_temp.py:9-13` names this case. L6 replaces the accident with a designed path and then closes the accident (L6-2b).

## Design

**Start.** `run_command` gains `background: boolean` (default false). No new start tool: the one gate, card and sandbox stay the only way a command runs. The call returns after at most 2 s with `{"process": "p3", "state": "running" | "exited", "output": <first lines>, "log": <path>}`; a command that fails at once reads like a failed foreground command. `timeout_s` with `background` means the process's life, a separate range in the schema, 60–28,800 s (see "Limits"): left out, a chat-started process runs until it ends or is stopped, under the ceiling. Where a lower limit applies (a job, an exit-woken turn, outside the sandbox), a request above 7,200 s is **refused** with the limit, not clamped, so the card never shows a life the process won't get.

**Move to background (Q1, decided).** See its own section below. It is the only other way in, and only the user can use it.

**One process tool,** `process(action, id?, until?, wait_s?)`, in a new family `tool_defs/processes.py`:
- `list`: this conversation's processes: id, the card's summary of the command, state, started, how it started (model or moved by the user), time to the ceiling, sandbox and online or offline, listening ports (only if L6-7 is approved), exit code.
- `read`: new output since this conversation's last read (a cursor), at most 30,000 characters (`MAX_OUTPUT_CHARS`, Claude Code's default read-back), repeats folded; more than that says how much was skipped and points at the log for `read_file`.
- `wait`: blocks up to `wait_s` (max 30 s, as Codex) until the process exits or plain text `until` appears (no regex). Counts against the turn's budget.
- `stop`: SIGTERM to the group, 3 s, SIGKILL; recorded as stopped by the model.
- **No input.** stdin stays `/dev/null` (Q2).

**Registry fit (LOOP1).** `process` is one `Tool` with `gate=tool_gates.process_gate` (the id must belong to this conversation; anything else reads as "no such process"; refused in a replay). Offered exactly when `run_command` is, plus `not offer.scheduled`; no new `Offer` field. Traits: `effect="local_write"` with `task_service.effect_of` grading `list`, `read`, `wait` as reads by action (as `run_command` is graded by its command); `parallel=False` (the read cursor is shared state); `outside=False` with `untrusted.counts_as_external` judging per call: `read` and `wait` of a process that started online count as outside content (as `run_command` does at `untrusted.py:93-98`); `replay_safe=False`; `saves=False`. The table dump (`test_loop1_tool_table.py`) changes on purpose in L6-3 and the PR gives both hashes. Successful `list`, `read`, `wait` are not reply steps (like `run_process.JOB_TOOLS`); `stop` is. The move control adds no tool and changes no trait (below).

**Lifetime: per conversation, bounded, never across a restart.**
| Event | What happens |
|---|---|
| Exit | State, exit code and time recorded at once; an exit note posted (see "Exit") |
| `process stop`, the user's Stop on its row or its step | Group stopped, recorded with who stopped it; the model is told when the user stopped it (as Claude Code) |
| The turn that started it is stopped | Its processes stop with it (OpenClaw). Earlier turns' processes, and processes the user moved (new since #839: the user's move is a decision to keep it), keep running |
| A background job or sub-session ends | Its processes stop when its task grants are forgotten (`background_jobs.py:323`) |
| Conversation deleted or archived | Its processes stop (Claude Code's "session ends") |
| Life ceiling or life limit (see "Limits") | Stopped by the keeper at its deadline (and by the server, whichever acts first), recorded as `time_limit`, the model told why; a chat-started one then wakes a turn like any exit, and that turn's starts get the woken-turn limits (below), so the ceiling cannot renew itself |
| A profile input changes (below) | Stopped, recorded as `settings_changed` |
| The outside grant is forgotten, or the shell is switched off | Outside processes of that conversation stop; shell off stops all |
| App quits | All stopped before the proxy shuts down; recorded as `app_quit` |
| Arslan crashes or is killed | The keeper (below) stops the group when the server is gone; the boot pass records `app_restarted` and tells each conversation once |

**State is recorded when it happens.** A row in a new `background_process` table: conversation, run, task or job, turn, origin (`model` or `moved`), command, card summary, sandbox mode, network, the profile fingerprint, log path, then pid, group and the process start time written right after spawn (or at the move), then the end state. **The start-time guard is new code:** nothing on main records a process's start time, and `run_temp._alive` (`:86`) keeps a reused group id rather than telling it apart. Boot reads rows and acts; it never infers state from logs or the transcript. Restart matrix, one test each: crash before spawn (row `starting`, no pid: marked `never_started`); after spawn, before the pid is written (the keeper stops the group; boot marks it `app_restarted`); while running (the keeper stops it; boot finds the group gone, or alive with the same start time and stops it, never a group whose start time differs); after exit before the row update (boot marks `ended_unknown`); **during a move**, row `moving` and the keeper not yet attached (boot stops the group only if its start time matches the row, and marks it `app_restarted`).

**The keeper.** Each background process is watched by a small stdlib-only keeper that Arslan starts (outside the sandbox, like the server; the command inside its profile as today). The keeper holds the read end of a pipe whose write end only the server holds: end of file means the server is gone, by quit or crash, and the keeper stops the group, after checking the group's start time against the one it was given. It holds under seatbelt because the child can signal only its own sandbox (`sandbox_profile.py:173`), not the keeper or the server. For a `background: true` start the keeper launches the command; for a moved command it is attached to the running group at the move. **The keeper also enforces the life limit:** it is given the deadline with the start time (the process's recorded start time plus its limit or the 8 h ceiling, whichever is earlier; for a moved command, measured from its original start, not from the move) and stops the group at that deadline by itself, after the same start-time check, even while the server is alive. The server's own timer records `time_limit` and tells the model; the keeper does not depend on it, so a wedged server or a lost timer cannot stretch the ceiling.

**Limits (revisited against Claude Code, decided 2026-11-11).**
| | Claude Code | Arslan |
|---|---|---|
| Chat-started, in the sandbox (started in a turn the user sent with a message) | No limit in a local session; ends with the session | **No life limit by default**: runs until it exits or is stopped, or a lifetime rule above ends it. **Ceiling 8 h** (28,800 s), enforced by the keeper; `timeout_s` may set a shorter life, 60–28,800 s |
| Moved by the user | Unattended: 30 min from the move; local: no limit | The same as chat-started (the move is the user's act, in any turn); the ceiling counts from the process's original start |
| Started in an exit-woken turn (no human sent it) | Unattended limits | **The job limits:** 30 min default, 2 h max, and **its exit posts the note but wakes no turn** |
| Started by a background job or sub-session | Unattended: 30 min default, 2 h max | 30 min default, 2 h max (1,800 / 7,200 s), and it ends with the job |
| Outside the sandbox | No separate rule | 30 min default, 2 h max, whoever started it |
| Scheduled runs, the heartbeat, a job's wrap-up | Unattended limits | Never started |
| Running at once | No documented cap (unconfirmed) | **8 per conversation, 16 on this Mac**; a start or move over the cap is refused with the list, never by pruning |
| Output | 30,000 characters read back; a saved command result is cut at 64 MiB; a background task's file runs on until the 5 GB kill | 30,000 characters per `read`; 1 MiB head and tail in memory; the log on disk capped at 64 MiB with head and tail kept; never killed for output |
| CPU and processes | Not documented | `nice 10`; a watchdog every 2 s counts each tracked group and stops one above 256 processes (`fork_limit`) |
| Memory pressure | Stops idle background tasks under critical pressure | Not built; the ceiling, the caps and `nice` bound it |

*Why an 8 h ceiling when Claude Code has none locally:* a Claude Code terminal session ends when the user closes it, so "until the session ends" is a working session. Arslan is a menu-bar app that stays up for days and is driven from the phone, and a conversation never ends by itself, so "until the conversation ends" would mean "until the next quit", possibly days, unwatched. 8 h covers a working day's dev server or watch build; a forgotten one cannot run overnight; at the ceiling the exit wakes a turn, so the model says so, and the user's one sentence starts it again. *Why a woken turn gets the job limits, not a card:* a woken turn is sent by no human (Claude Code's notices say the same), and a sandboxed `run` verdict shows no card, so with chat limits a ceiling stop would wake a turn that starts the same command for another 8 h, again and again. Giving its starts the job limits and no wake ends that chain after at most 2 h, without a new card kind or a "same command" matcher that a reworded command could slip past; the user's next message restores chat limits. *Why 8 and 16:* the old 4 is one dev server, one watcher, one test runner and one log tail, with no room left; Claude Code documents no cap, and Codex and Hermes cap at 64. Arslan keeps a cap because each process holds a keeper (one extra small Python process) and a path through the proxy, and refuses rather than prunes, so the cap must be roomy. *Why outside and job processes keep 30 min and 2 h:* outside the sandbox the profile is not the boundary, and a job runs with no one watching; both get Claude Code's unattended numbers.

## Move to background (Q1, decided)

**The control.** A "Move to background" button on a running foreground `run_command` step in a Mac reply, next to its Stop (the mock's state 1). It is the user's, like Claude Code's Ctrl+B: a Mac UI route (`POST /runs/{id}/steps/{step}/background` in the runs router, so behind the same router-level `require_auth` Bearer check as the turn's Stop, `POST /runs/{id}/cancel`, `runs.py:42, :1047`; there is no per-step Stop route on main yet, and L6-6's step Stop is added beside it the same way), not a tool, not a tool argument, not a prompt word. The phone's Bridge maps frames, not routes, and gets no frame for it. The model cannot call it or ask for it to be pressed; a replay cannot reach it; the phone has none (Q6). **Never automatic:** a foreground command that reaches its time limit is stopped, as today.

**What it does.** The command keeps running in the same process and group, under the same seatbelt profile and network mode, with the same verdict and the same card answer. It does not start a new command. The reader that fills `_Capped` hands over to the background buffer and log; a `background_process` row is written with origin `moved` (state `moving`, then `running`), the pid, group and start time; a keeper is attached with its deadline; the background limits apply from the move, measured from the process's original start. **A move racing the foreground time limit:** both take the step's lock; whichever takes it first wins. If the time limit fired first, the move is refused ("already stopping"); if the move commits first, the foreground timer is cancelled. The pending `run_command` call returns at once with `{"process": "p4", "state": "running", "moved_by": "user", "output": <so far>, "log": <path>}`, so the transcript keeps one call and one result, and the model goes on with `process`.

**Re-checked at the move** (one function, `command_gate.background_rules(plan, ctx, origin)`, the same that runs after the verdict for a `background: true` start, so the two ways in cannot drift; with `origin="moved"` it runs every rule except the detaching words, which L6-3 already refused before the command ran):
- The step is still running, belongs to this conversation, and is a chat turn's step (not a job's or a scheduled run's).
- The caps: over 8 here or 16 on the Mac, refused with the list; the button shows why.
- The profile fingerprint: the inputs of the profile it was launched under still equal today's settings; if a sandbox setting changed while it ran, the move is refused ("a sandbox setting changed since it started"), and it finishes as a foreground command.
- Outside the sandbox: a this-time confirmation on the step ("Keeps running outside the sandbox, up to 2 h"), even with the conversation's outside grant, because a long-lived outside process is `hard_rules.NEVER_AUTO`; then the outside limits.

**Not re-checked, on purpose:** the command text and `command_gate.check`'s verdict (the control re-classifies an approved process; re-judging it could only refuse a command that is already running); the card the user answered; the profile (it cannot be rebuilt on a live process: drift is a refusal, above); the network mode (fixed at launch; a later outside read changes nothing, and `counts_as_external` uses the launch's online flag); detaching words (skipped by `background_rules` for a move: refused at start since L6-3).

**LOOP1 fit.** No new `Tool`, no `Traits` change, no `Offer` field: `run_command` keeps `effect="external_write"`, `replay_safe=False`, and the table dump does not move in L6-4b. `CommandPlan.background` stays what the model asked (false); the row's origin records the move. `command_gate` gains no new verdict branch, only the shared `background_rules` that both paths call after a verdict exists. `untrusted.counts_as_external` treats a moved process like any other by its launch's online flag.

## L6-7: loopback listening for dev servers (Q3, pending the user: conflicts with D1)

**Status: pending the user, not decided.** On 2026-11-11 the user asked for L6-7. The card returns it to the user because it conflicts with an earlier decision and with three facts that were not in front of that answer:
1. **The mechanism has been measured, and it fails.** macOS CI run 41002402918 (SBX-2) measured that seatbelt's localhost bind filter also permits wildcard binds ("all-interface bind allowed"; `SBX-sandbox.md:254`, `tests/server/sbx/corpus/README.md:151-152`). Listening was denied on 2026-10-30 for that reason. A loopback-only bind rule, as designed below, cannot be expressed with that filter.
2. **D1 (user, 2026-11-01, `SBX-sandbox.md:278`) moved how listening comes back to NET in v0.1.65**: a per-run listen card (cheap, but it opens every interface for that run) or a Network Extension filter (a per-process boundary in the kernel, but heavy). L6-7 in v0.1.64 would supersede D1; that is the user's call, not this card's.
3. **Taking over another local app's port is a demonstrated residual.** Shown on a Mac with two scratch processes outside any sandbox: on macOS, a process that binds the loopback address with address reuse on a port where another app listens on all interfaces takes that app's local clients; without address reuse the bind fails. A loopback listener can also pre-bind a free fixed port another app (or Arslan, later) expects.

Also residual, if built: inbound connections to a listener never pass the proxy, so they are neither logged nor counted, and every other online sandboxed command, in any conversation, reaches the listener directly over loopback (`sandbox_profile.py:196-207`).

**What ships if the p tests agree with run 41002402918:** not the design below. The only candidate left in v0.1.64 would be the profile's inbound check (allow inbound from loopback only), which has never been run and could at most keep other machines from connecting to a wildcard listener; it would not stop the port takeover in fact 3. Until the user decides, listening stays denied in the sandbox, as today, and a dev server gets the usual outside card.

The design below is kept for that decision; it is not approved.

**What the profile would allow.** For a sandboxed command whose network mode is online (proxy or port 22), the commands profile allows `network-bind` and `network-inbound` for **TCP on the loopback addresses only**, `127.0.0.1` and `::1`, in place of today's blanket deny (`sandbox_profile.py:209`). It applies to foreground and background commands alike, so L6-2's "profile bytes equal to the foreground twin" holds and a dev server the user moves to the background is already listening. Rule order against the blanket deny, and what seatbelt's `localhost` filter really matches for `::1`, `0.0.0.0` and `::`, are proven by p tests, not assumed; if seatbelt cannot tell a loopback bind from a wildcard bind (run 41002402918 says it cannot), L6-7 does not ship.

**What would stay denied.** Bind on `0.0.0.0`, `::`, a LAN or any non-loopback address, so no other machine can connect (stricter than Claude Code's `allowLocalBinding` on macOS); inbound from any other host; UDP bind; Arslan's own ports (the server, the Bridge, the proxy: the existing `denied_ports`), for bind as well as for connect; Bonjour advertising (no mach service is added); outbound beyond today's rules (the proxy only); and **every offline command**: offline stays `network*` denied, because a page in the browser can read a loopback listener (DNS rebinding), which would give a process that saw outside content a way out. Disclosed residual: any local program, including the browser and pages in it, can connect to an online process's loopback port, as with a dev server the user starts in Terminal.

**Port reporting.** The group watchdog (every 2 s, outside the sandbox) lists the tracked group's listening TCP sockets (`lsof -a -g <pgid> -iTCP -sTCP:LISTEN -nP`, or `libproc`) and records them on the row. `process list` returns `ports`; the Running row shows "Listening on 127.0.0.1:5173" with Open, which opens it in the user's browser; the exit note names the ports it had.

**Who, if the user approves.** Codex writes the p tests (127.0.0.1 and ::1 accept a local client; `0.0.0.0`, `::` and the LAN address are refused; another host cannot connect; UDP refused; an Arslan port refused; offline refused; a sandboxed bind of the loopback address beside an unsandboxed all-interfaces listener on the same port, with and without address reuse, for IPv4 and for IPv6), Astra reviews, the user merges.

## Safety model

**Same sandbox, fixed at launch.** A background command runs under exactly the commands profile its foreground twin would get for the same inputs (L6-2 tests the bytes are equal): writes only in the working folder, the run's TMPDIR and caches; Arslan's data, keys and HR-1's run-later files denied by the kernel; network only through the proxy, or none; no listening (L6-7 is pending the user). The profile cannot be tightened on a live process, so anything that would build a different profile now stops it instead (Codex's rule): the fingerprint of the profile's inputs (working folder, folder access, project folders, sandbox on or off, system certificates, trusted devices, shell on or off, and, for online processes, **the denied loopback ports**) is recorded at start and checked on each such settings write and every 10 s as a backstop.

**The denied ports are in the fingerprint.** Proxy mode denies Arslan's own listening ports and the system proxies' loopback ports, read once when the profile is built (`command_sandbox.py:488`, `sandbox_proxy.py:117-126`). That snapshot was accepted when every command lived at most 10 min (`sandbox_proxy.py:18-21`); a background process lives for hours. If the user turns on a local HTTP or SOCKS proxy app after the start, its loopback port is not denied in the running profile, so the process could tunnel through it past the proxy's public-only check and its log. So the 10 s backstop re-reads the listening ports and the system proxies and stops the process, recorded as `settings_changed` (the denied ports), when its denied set no longer covers today's. Cost, disclosed: a listener Arslan itself opens later (a browser tunnel, an OAuth callback) also stops online background processes; L6-4 measures how often, and if it bites, ②Main brings a narrower rule to review instead of dropping the check.

**The seatbelt profile is the containment boundary, not process-group tracking.** Writes are confined to the profile's roots, bind and inbound are denied, the network goes only through the proxy, and signals reach only the same sandbox (`sandbox_profile.py:173`). Group tracking only decides how long a process lives, and what L6 lists and stops. A child that leaves the process group (it calls `setsid` itself, or double-forks) keeps running sandboxed until it exits by itself: Arslan no longer lists it, stops it or times it. **That is a liveness gap, disclosed, not a containment gap.** It is no worse than today's `cmd &` (`run_temp.py:9-13`). Claude Code says it stops detached children at stop and exit; how it finds them is unconfirmed, and matching it is listed for later, not built.

**The gate decides at start, unchanged.** `command_gate.check` runs as for any command: forbid refuses, `ask` shows the card, `run` runs, `unreadable` runs offline in the sandbox, offline after outside content. The card's existing text gains one line, in the server-built summary (LOOP1 d1 #817) or the purpose line before it, with no new field: "Keeps running after this reply until it ends or you stop it, at most 8 h. You can stop it on the Mac or by asking Arslan." (with the job, woken-turn or outside limit where that applies; Q9). Then the background rules, `command_gate.background_rules`, after the verdict:
- **Outside the sandbox:** always the outside card, even with the conversation's grant, and that answer is this time only (it joins `hard_rules.NEVER_AUTO`). An outside background process is stopped when that conversation's outside grant is forgotten too.
- **Nobody to ask** (a scheduled run, the heartbeat): never; not offered and refused. Also refused during a job's wrap-up (`terminal_exec.OFFLINE` set by the loop).
- **Detaching words** at the top level (`&` at the end, `nohup`, `setsid`, `disown`, `tmux`, `screen`): refused with "use background: true instead", so the process stays in the group L6 tracks. **Planned grammar work (L6-3):** a named detaching set in `shell_grammar`. Today `disown` only makes a command not understood (`:88-91`, `:698-699`), and `&` is not named at all.
- **Caps** over the limit: refused with the list.
**Later tool calls** don't run a command, so nothing is re-judged by the command policy; `process_gate` checks ownership, and the fingerprint check runs first, so a stale process is stopped rather than read. With no input there is no second command to judge (Q2).

**Run-later (HR-1).** A background process keeps the commands profile for its whole life, so HR-1's kernel deny on hooks, CI and agent settings holds the whole time, not only at start. Outside the sandbox it keeps the minimal profile and HR-3's rules. A background process never restarts itself or anything else: no launch agents, no durable mode.

**Unattended.** Scheduled runs never start one. A background job may, with the job limits, and its processes end with the job. An exit-woken turn is an ordinary turn: its cards wait for the user, and nothing is approved automatically. But no human sent it, so a background process it starts gets the job limits (30 min default, 2 h max) and its exit wakes nothing: a chain of woken turns cannot keep a command alive past one ceiling plus 2 h.

**Threat cases.**
| Case | What holds |

## Exit

On exit the row is updated, then one note is posted in the conversation: the command's summary, exit code, duration, and the last 5 lines framed as outside content (the S64-0b pattern). ## Method

- **Red first, every PR.** L6-0 (tests only) pins today's leak as strict expected failures with `raises=AssertionError` (`xfail(strict=True)`, the SBX convention): a foreground `sleep 600 >/dev/null 2>&1 &` leaves a live group after the call; Stop does not end it; shutdown does not end it. L6-1 and L6-2b flip them.
- **Tests per PR:** the restart matrix (five moments, a fake server death through the keeper's pipe); the gate table for a background start under each verdict (forbid, ask, run, unreadable, outside with and without a grant, nobody to ask, wrap-up, detaching words, caps); the move table (running chat step, a job's step, over the caps, a sandbox setting changed, outside with and without the this-time yes, the step already ended, a replay); profile bytes equal to the foreground twin with `cmp`; a settings change stops the process within 10 s; the ceiling and the job and outside limits; a `timeout_s` above 7,200 refused for a job, woken-turn or outside start; read is incremental and bounded; wait returns at `until`; a reused pid with a different start time is never killed; a move racing the foreground time limit (both orders).
- **Red tests for the review's blockers (written failing first, in the PR that fixes each):**
  - *Renewal chain (L6-4, L6-5):* a chat-started sandboxed process reaches its ceiling, its exit wakes a turn, and in that turn a `run_command(background: true)` with verdict `run` starts a process with the job limits, and that process's exit wakes no turn.
  - *Keeper enforces the ceiling (L6-1, L6-4):* with the server alive but its limit timer disabled, the keeper stops the group at the deadline from the recorded start time (for a moved command, from its original start); with the start time changed, it stops nothing.
  - *Denied ports in the fingerprint (L6-4):* a fake `scutil` output gains a loopback proxy port after the start, and the online process stops within 10 s, recorded as `settings_changed`; an offline process is not stopped.
- **Mutants (each PR lists which went red):** the ceiling enforced by the server only (keeper deadline removed); a woken turn's start given chat limits, or its exit waking a turn; the denied ports left out of the fingerprint; the move route reachable from outside the Mac UI (a tool call, a Bridge frame, or without `require_auth`); background skips `command_gate`; an outside start or move rides the grant; the move re-runs the gate's verdict, or skips `background_rules`; the move route is reachable from a tool call; the keeper ignores end of file; the fingerprint check removed; the cap pruned instead of refused; the cursor not advanced; the boot pass kills without the start-time check; if L6-7 is approved, its bind rule widened to `*`.
- **Probes** through `scripts/dev/probe.sh`, on a real Mac: start a 5-minute build in the background, quit from the menu, then `pgrep` finds nothing; kill the server with SIGKILL and the keeper stops the group; move a foreground `npm run dev` and see it keep its pid and profile. Real-seatbelt denial for background starts reuses the existing commands-base p tests by parameter, no new probe kind. If the user approves L6-7, its loopback tests are new probes: Codex writes them, Astra reviews (SBX "Who writes what").

## Decided (user, 2026-11-11)

The user decided on 2026-11-11: match Claude Code desktop's background-task experience, with the sandbox as the boundary. The answers:

1. **Move to background:** never automatic. A user-only "Move to background" control on a running foreground command, like Claude Code's Ctrl+B; the model cannot trigger it. It moves the already-approved command into the Running list under the same sandbox and the same verdict, with the background limits from then on (L6-4b, L6-6).
2. **Input to a running process:** no. stdin stays `/dev/null`.
3. **Loopback listening for dev servers: pending the user, not decided.** The 2026-11-11 answer asked for L6-7; it conflicts with D1 (user, 2026-11-01), which moved listening to NET in v0.1.65, with run 41002402918's measurement that the localhost bind filter also allows wildcard binds, and with the port-takeover residual. The facts are in L6-7's section. Until the user decides, there is no listening in the sandbox.
4. **Wake a turn on exit:** yes, one ordinary turn per exit, for chat-started processes (L6-5); a process that a woken turn started gets the job limits and wakes nothing.
5. **Stop what a foreground `&` leaves running:** yes (L6-2b).
6. **A process list on the phone:** not now. No Bridge frame.
7. **Per-process proxy accounting:** no.
8. **The chip:** above the composer, as mocked.
9. **The card's line:** "You can stop it on the Mac or by asking Arslan".

The limits follow Claude Code where safety allows (see "Limits"): no default life limit for chat-started sandboxed processes under an 8 h ceiling that the keeper enforces; 30 min and 2 h for job, woken-turn and outside processes; 8 per conversation and 16 on the Mac.
