## 目标

没有工具调用的回答，一边生成一边显示。守卫全保留（D6），但不再挡住流式（v0.1.63 计划 K-6）。

## 今天的情况（按 `fb6d7230` 亲核）

- **假流式：** 先整段生成，过完检查，再用 `_reveal_streamed`（`server/orchestrator/tool_loop.py:1985-1995`）假打字放出来。
- **守卫不是追加更正，而是让模型再跑一步，或换掉回答**（`:2563-2641`）：
  - 能力否认、没有凭据的说法、空头承诺、协议文字：原话加一条纠正放进轨迹，`continue` 再跑一步（`:2569-2591`）；
  - 实在不行，换成合成或兜底的回答（`:2603-2613`）；
  - 带验收条件的回合：再修一步，或改写回答里的链接（`:2614-2637`；`server/services/task_validation.py:376-395`）。
- **窗口和 iPhone 显示的，都是本回合所有 `stream_chunk` 拼起来的：**
  - 窗口：`web/src/stores/arslanStore.ts:710-716`。语音朗读也是一块一块念（`:714`）。
  - iPhone：`desktop/bridge/Sources/BridgeCore/FrameMapper.swift:70-90`，最终消息就是拼起来的 `reply`。
  - 所以，流出去的话被守卫打回后，窗口和 iPhone 上还留着，语音也念过了；数据库里存的却是改过的回答。诚实类测试会失败。
- **已有的追加做法：** `promise_guard` 把更正当作多一块 `stream_chunk` 发出去，再存「原文 + 更正」（`server/orchestrator/arslan.py:878-884`）。三处显示一致，不改帧。
- **三家供应商：**
  - **OpenAI 兼容：** 已经能读带工具调用增量的流并拼好（`arslan/llm/stream_assembly.py:31-127`），只在 DeepSeek、OpenAI、OpenRouter 上开（`arslan/llm/providers/openai_provider.py:59-65`；`arslan/llm/adapter.py:123-124`）。但拼完整段才交回，文字不会边到边出。
  - **Anthropic：** `chat_stream` 带工具直接报错（`anthropic_provider.py:328-342`）；流式解析只认文字（`:390-394`）。
  - **Gemini：** 同样报错（`gemini_provider.py:158-172`，文件头 `:9` 也写明）；流式只取文字（`:193-232`）。审查说 Gemini 也报错，属实。

## 怎么做（要点）

**选 (b)「先流出去，命中守卫就追加更正」，带一个短的放行窗口。(a)「每步先缓冲」作回退。**

- **为什么不选 (a)「每步先缓冲，确定没有工具调用、过了守卫再放」：**
  - 一步有没有工具调用，要到这一步结束才知道：OpenAI 的 `tool_calls` 增量、Anthropic 的 `tool_use` 块，都可能排在文字后面。
  - 所以 (a) 的首字还是要等整段生成完，和今天差不多（今天只是多了约 0.7 秒的假打字）。达不到 §5.3 第 7 条，也违背 D6「不再拦流式」。
- **为什么选 (b)：** 产品里已经有这个形状（上面的 `promise_guard`），三处显示天然一致，不改帧。
- **放行窗口（短文字仍按 (a) 处理）：**
  - 每一步的文字先攒着，攒满 160 字（同 `_DEFERRAL_MAX`，`tool_loop.py:190`）再开始往外流。
  - 窗口里出现工具调用：攒着的是旁白，照今天发成 `note`（`:2549-2552`），不进回答，也不会被念出来。
  - 窗口里这一步就结束了：整段过全部守卫，打回就照今天再跑一步。空头承诺只查短于 160 字的回答（`:193-195`），所以它总在窗口里判完。
  - 代价：首字比模型首字晚「前 160 字的生成时间」。验收按这个写。
- **出了窗口以后：**
  - **硬规则：** 绝不显示原始工具调用 JSON（`_embeds_protocol`，`:1731`），也不显示 `<agent_status` 回显（`server/orchestrator/agent_status.py:151-154`）。按块检查，命中就停止往外流，剩下的丢掉。
  - **其余守卫：** 这一步结束后照常判。命中时，先追加一行本地化的「更正：……」，再照今天把纠正交给模型跑下一步；下一步的文字接在更正后面流出去。
  - 原来「换掉回答」的地方（`:2603-2613`），改成「更正 + 新回答」接在后面。
  - 文字已经放出去、这一步后来又出了工具调用：文字留在回答里，存下的也一样。
- **一条不变式：** 存下的回答 = 本回合流出去的全部文字（含更正和来源脚注）。`_run_native` 返回的 `final` 就是它。
- **照旧整步缓冲的情况（不是旧路径，长期保留，代码注释写明原因）：**
  - 带验收条件的回合（`:2130-2136`，主要是后台任务）：验收失败会改写已经写出的链接，没法事后追加。开工先核：聊天回合有没有这类验收项。
  - 不支持流式工具调用的端点（`streams_tool_calls()` 为假的本地服务）。
- **出错与截断：**
  - 放出文字之后出错，不自动重发，同 `:2151-2152` 的现有规矩；回答末尾追加一行「回答中断」。
  - 放出文字之后被截断（`length`）：不按 `_recover_truncation`（`:621-655`）提高上限重发整段，只续写。
- **顺序：** 每个 PR 先写测试：用假的流式供应商量首字延迟，确认今天要等整段。

## 验收

- **测试：**
  - 首字延迟 ≤ 模型首字 + 前 160 字的生成时间；
  - 不变式：拼起来的 `stream_chunk` = 存下的回答（Bridge 也是这样拼的）；
  - 窗口内：旁白不进回答；短的空头承诺照旧被打回，一个字都不外流；
  - 窗口外：守卫命中时，原文后面紧跟更正；硬规则命中时，工具调用 JSON 不外流；
  - 出错、截断后，不重发已经流出去的文字；
  - K8b、K8c：同一段回答，流式解析 = 非流式解析（夹具按官方文档的事件格式写）；思考块和签名能原样回传。
- **诚实类测试全过：** `tests/server/` 下的 `test_promise_guard.py`、`test_capability_truth.py`、`test_zero_tool_honesty.py`、`test_malformed_protocol_answer.py`、`test_dsml_leak.py`、`test_native_loop.py`。
  - 窗口内的用例，行为不变；
  - 超过窗口的用例，改成断言「原文 + 更正」。改了哪些，列在 PR 描述里。
- **M1（每个 PR 都贴）：** 每题首字延迟、总时长、成功率不差于 K7 之后。K8a 看 DeepSeek，K8b 看 Claude，K8c 看 Gemini。
- **手动：** 用 Claude 时，没有工具调用的回答边生成边出现，iPhone 上也一样（§5.3 第 7 条）。

## 量级

- 原写的「−500 / +100」不对：守卫全保留，删得很少；三家的流式解析都是新写的。
- 重估（产品代码）：K8a 约 +350 / −50；K8b 约 +300；K8c 约 +200 / −40。合计约 +850 / −90，每个 PR 都在 800 行以内。

## 风险与回退

- **风险：** DeepSeek 一类模型更容易谎称做完了。出了窗口才命中的，用户会先看到错话，再看到更正。按 D6 由跑分决定：哪个模型命中多，就对它打开「整步缓冲」。
- **风险：** iPhone 收到的逐段消息每秒最多一次（`FrameMapper.swift:266-272`），所以是按秒跳着出现。这是现有行为，本卡不改。
- **回退：** 设置项「回答完整生成后再显示」，就是方案 (a)。
- **留着的旧路径（§9），卡里和代码注释都写明：**
  - 「回答完整生成后再显示」设置：**v0.1.64 删**。条件：v0.1.63 的 M1 连续两轮「流式」不差于「缓冲」，且没有因流式问题打开它的问题单。
  - 按模型的「整步缓冲」开关：v0.1.64 的 M1 决定哪个模型关掉；**v0.1.65 复查，全部关掉就删**。
  - `_reveal_streamed`：**K8c 合并时删**（v0.1.63 内）。K8a、K8b 期间只给还不能流的供应商用。
