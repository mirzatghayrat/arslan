## 目标

- **只读工具并行：** 同一批里连续的只读调用同时跑，结果按原顺序记录。今天是逐个跑（`server/orchestrator/tool_loop.py:2388` 的循环）。
- **回合中插话：** 回合进行中发来的消息，在下一个工具边界送达，不再等整个回合结束。

## 今天的情况（按 `fb6d7230` 亲核）

- **回合进行中，四个入口能不能发消息：**
  - **窗口：** 能。发送只拦空消息和附件处理中，不看是否在流式（`web/src/components/OrchestratorChat.tsx:320-322`），走 `user_message` 帧（`web/src/App.tsx:299-311`）。排队时窗口下方有提示（`:1070-1072`）。
  - **iPhone：** 能。手机的 `chat.send` 由 Bridge 原样转成 `user_message`，带 `source: "phone"`（`desktop/bridge/Sources/BridgeCore/FrameMapper.swift:344-345`）。
  - **按住说话：** 只把识别出的文字填进窗口的输入框（`OrchestratorChat.tsx:162-168`），发送走窗口那条路。
  - **灵动岛：** **今天没有发消息的入口。** `web/src/island/feed.ts:91-153` 只有动态、回答卡片、停止任务、Hands 的几个按钮。
- **发来以后：** 每个连接的读取器看到会话的回合锁被占（`server/ws/arslan.py:340-342`），就标记 `_queued`，回一个 `queued` 帧，放进**这个连接自己**的收件箱。等锁空了，作为下一轮跑（`:266-274`）。
  - iPhone 上这时显示「Queued behind the current turn」（`FrameMapper.swift:133-134`）。
  - 正在跑的回合可能在另一个连接上（窗口和 Bridge 各有一个连接），所以插话要能跨连接送到。
- **结论：** iPhone 已经能在回合中发消息，走的是排队路径。插话只改 Mac 服务端，**不用改 Bridge 帧格式。**

## 改哪些文件

- **并行：** `tool_loop.py:2388` 的循环
  - 先分组：连续的、可并行的只读调用一组，用有上限的 `asyncio.gather`；写入、要审批的调用照旧串行。
  - 执行和记录分开：并行执行，按原顺序记录结果、发帧、记进轨迹。
  - **可并行的名单是允许清单**，取 `server/services/task_service.py:37-46` 的 `_READ_TOOLS` 的子集。排除共用一个状态的 `browser_*`、`desktop_*`，以及 `delegate_work`、`update_plan`、`render_chart`。
  - MCP 工具看 `readOnlyHint`（已存库，`server/db/models.py:228-229`）；同一个 MCP 服务器的调用不并行。
  - 网页读取次数等预算，在一组启动前一次扣好，不在并发里各自判断。
- **插话：**
  - `server/ws/arslan.py`：仿照 `_turn_locks`（`:44`），加一个按会话的插话信箱。读取器在回合锁被占、且这个窗口没有卡片在等时，把消息放进信箱，而不是自己的收件箱。
  - `tool_loop.py`：每个工具（或每个并行组）跑完就看一眼信箱。有消息时：
    - 本批还没开始的工具，记一个「已跳过：用户插话」的结果，保证每个调用都有结果；
    - 插话作为 user 文字块，放在本批全部 `tool_result` 之后（K1 的原生协议要求）；
    - 照 `server/orchestrator/arslan.py:513-517` 的写法存成 user 消息，带上来源。手机来的照旧发现有的 `message` 帧。
  - 插话的那个窗口，收到现有的 `dequeued` 帧，加一个 `inserted: true` 字段。网页处理 `dequeued` 的地方（`web/src/stores/arslanStore.ts:1270-1271`）：带这个字段时只标「已插入」，不重置本回合的计时。6 种语言的文案按冲突协议加。
  - Bridge 对 `dequeued` 不处理（`FrameMapper.swift:162-163` 的 `default`），iPhone 不受影响。

## 不许碰

- **Bridge 帧格式**（`desktop/bridge/**`、`server/ws/bridge.py`、`spec/mobile-bridge/**`）。
  - iPhone 上那行「Queued behind the current turn」保留不改。要改手机上的显示，就是改 Bridge：**先停下来，经 ②Main 问 ①iOS。**
- 「卡片等待时打字 = 拒绝 + 备注」的语义（`server/ws/arslan.py:335-339`）照旧。已经当作卡片备注的那条消息，不再插入，照旧排队。

## 怎么做（要点）

1. 先写并行测试：两个慢的只读工具，总用时约等于一个；中间夹一个写工具时，仍按顺序执行；结果在历史里按原顺序。
2. 插话的边界情况：
   - 最后一步已经在出回答（没有工具边界了）：照旧排队，下一轮跑；
   - 回合结束时信箱里还有消息：放回发它的那个连接的收件箱，作为下一轮跑，**只跑一次**。
3. 并行有上限（例如 4），避免一次打开太多网页或文件。
4. 两个回退开关，代码注释写明删除条件（见下文）。

## 验收

- **每个入口一条测试：**
  - **窗口：** 同一个连接，回合中发一条消息；下一次模型请求里就有它；还没开始的工具得到「已跳过」。
  - **iPhone：** 回合在窗口的连接上跑，另一个连接发 `user_message` + `source: "phone"`（和 Bridge 转出来的一样）；下一步就有它；存下的消息带 `phone` 来源。
  - **按住说话：** 网页测试：流式进行中，按住说话的最终文字填进输入框，点发送就发出 `user_message`。服务端那一半由窗口那条测试覆盖。
  - **灵动岛：** 不在本卡，见下面。
- 并行测试、配对测试全过；回合结束时没被取走的插话只跑一次。
- **M1（贴在 PR 里）：** 读 3 个网页 / 文件的题，用时下降（领先路线的目标是 ≥40%）；成功率不降。
- **手动：** 任务进行中从 iPhone 改方向，它下一步就照做（§5.3 第 10 条）。

## 风险与回退

- **风险：** 并行改变工具结果在历史里的出现时机。结果严格按原顺序记录，配对测试覆盖。
- **风险：** 插话和卡片备注抢同一条消息。规则：有卡片在等时，消息只当备注，不插入。
- **回退：** 设置项「工具串行」；插话可以单独关掉，回到排队。
- **留着的旧路径（§9），卡里和代码注释都写明：**
  - 「工具串行」开关：**v0.1.64 删**。条件：v0.1.63 的 M1 连续两轮「并行」不差于「串行」，配对测试一直绿。
  - 「关掉插话」开关：**v0.1.64 删**。条件：M3 第 10 条通过，v0.1.63 没有插话相关的问题单。
