# U10 重跑结果和新基线（A 方案），2026-10-20

U10 定的四件事里 ①②的数字，以及之后 K 线对比要用的新基线。决定和原因见总计划的 U10 和 E25。

## 设置（A 方案）

| 项 | 值 |
|---|---|
| Arslan 怎么起 | `BENCH_SANDBOX=none`：不套 bench 的外层沙箱，Arslan 自己的命令沙箱和产物检查照常工作。`BENCH_FRESH_INSTANCE=1`：每格一个全新实例，跑完就关（#228）。替用户点卡的 bench 程序：凡是要把命令放出沙箱的卡（沙箱外跑、停下后重跑）一律拒（#235） |
| 还在的保护 | `env -i`、bench 自己的 HOME、假 key（真 key 只在计量代理里）、Arslan 自己的命令沙箱（结果里是 `sandbox: workspace`；放出沙箱的卡一律拒）。不在的：Arslan 读文件的工具能按绝对路径读；动作卡（AppleScript、快捷指令、Hands）本来就在所有沙箱之外，只批 T1 的提醒事项脚本和 T12 的合成测试 App |
| Hermes、Claude Code | 照旧套外层沙箱。Claude Code 的临时目录挪进 bench 根目录（#227） |
| 判分 | judge v2。T1 按这一跑开始的日子算；06:00 前开始的，「明早」两种读法都算对（#229） |
| 模型 | DeepSeek：`deepseek-v4-pro`；Claude：`claude-sonnet-5` |

- T2、T3 要联网搜索。**更正（2026-10-20 下午，⓪Plan 复核运行记录）：** 原来这里写「DuckDuckGo 弹人机验证，Arslan 如实说找不到，是环境的限制」。这只对 Claude 成立。在 DeepSeek 上，Arslan 用的是 DeepSeek 自带的搜索，这张表里每一跑都搜成功了（运行记录里全是 `provider=deepseek`）。这张表里 T2、T3 丢分的真实原因：
  - T3 三次都把 6 个数全写对，但文件里没写出处（检查器的 `source: false`），所以都是 2 分；
  - T2 只找到 7–8 条岗位（满分要 10 条），而且三次都没干净收尾（见上面的「等你」）。
  - 所以在 DeepSeek 上，T2、T3 和 Hermes（都是 3/3）的差距在 Arslan 自己身上，不在搜索上。Claude 上的搜索走 DuckDuckGo 抓取、会被拦，这一块由 D5 处理。用户也指出：人机验证用户自己也会碰到，不能只算环境问题。
- T8 缺的那一分，是检查器要求「第二节缩到 60% 以下」；那一节本来只有两条，对两边一样严。

## ① 基线里停在「检查没跑」的格子，重跑

| 构建 | DeepSeek | Claude |
|---|---|---|
| v0.1.62 + D2 | 11/16 通过；「等你」1（T2 第 1 次，验收没过） | 7/12 通过 |
| K1 合并后的 main | 在新基线全套里（见上） | 7/12 通过 |

- 这些格子在 M1B 里全部停在「等你」。
- Claude 没过的 5 格，两个构建一样：
  - T1 两格：osascript 在 Arslan 的命令沙箱里被提醒事项拒（`-10004`）。D4（#231）之后，这算已知失败，不再停在「需要你核对」。「批准了卡片却还在沙箱里跑」是设计问题，等用户定。
  - T8 三格：同上，是 60% 的规则。

**更正（同一晚，③Hands 审 #234 时发现）：** 第一批 A 方案的格子里，替用户点卡的 bench 程序还在批「沙箱外跑」「停下后重跑」的卡，8 条命令因此以用户身份在真磁盘上跑了。查过每一条，都只读写 bench 目录。涉及 4 格：

- 新基线 T2 第 2 次；
- ① DeepSeek 的 T2 第 1、3 次；
- ① Claude（K1 后）的 T1 第 2 次。

#235 修好以后这 4 格重跑，上面的数字已换成重跑的结果：

- 新基线 T2 第 2 次：2 分 → 1 分，多一次「等你」；
- ① DeepSeek 的 T2 第 3 次：原来通过，现在 1 分；
- 另两格结果不变。

这些卡大多是模型想用命令读 Arslan 自己存下的大段工具输出（`<data>/tool_outputs/*.txt`），被 Arslan 自己的沙箱挡住。这是产品上的问题，已交 ②Main 放到合适的卡里。
