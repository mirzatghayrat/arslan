# Research track(调研专线)

这个目录是 **GitHub / 市面产品趋势调研 + Arslan 问题挖掘** 专线的落盘处。
它不打断主线施工(当前:S4.1-C MCP-server)——只登记、只积累证据,由主线按节奏消化。

## 结构

- `BACKLOG.md` — 研究驱动的 backlog 登记簿:每条带来源、代码证据、建议归属(挂到哪个 S4 阶段/parked 项)。
- `YYYY-MM-DD-*.md` — 每轮调研报告:外部趋势雷达 + 代码层问题挖掘 + 与路线图的对照。

## 纪律

1. **登记不插队。** 新发现一律进 `BACKLOG.md`,不直接改主线计划;确实紧急的才单独上报。
2. **问题必须带 file:line 证据。** 纯感觉不落盘。
3. **趋势必须带来源链接。** README 级调研要标注深度,不冒充深读。
4. **每条给出归属建议**(S4.x / P1-P3 / 新 parked 项),让主线消化时零思考成本。
5. 🔴 **任何接入建议必须对照 Arslan 的前缀缓存经济学评一次**(规则见 `BACKLOG.md` R-025)。
   外部项目的解法往往是给**没有前缀缓存**的架构设计的——照搬会把一项已兑现的资产
   (命中率 80.5% → 98.5%)悄悄换掉,而提案里只会看到它省的 token。
   **省的那部分要先扣掉缓存损失再报。** 实例:R-017 的 `toolSearch {defer:'auto'}`
   看起来省上下文,实际每轮换工具集 = 每次请求击穿整个前缀。
6. 🔴 **注册表数量 ≠ 运行时数量。** 说"N 个工具/N 个 server/N 条记忆"之前,先问
   **N 里有多少真的到达了运行时**——中间几乎总有闸门。
   实例:R-017 报的"16 工具/9 toolsets"是注册表计数;实测**打包版库 MCP 工具为 0**,
   dev 库 60 个 MCP 里只有 **1 个** `host_enabled`,真正进 prompt 的是 8 个 schema。
   **规模主张必须量运行时,不能数表。**
