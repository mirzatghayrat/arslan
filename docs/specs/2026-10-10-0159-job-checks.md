## 2. Changes

**A2 — a known, local failure is not an unknown outcome.** `reconciliation_required` means "Arslan does not
know what this action did". A `run_command` that ran and exited with a code (or was refused before running),
and a `write_file`/`edit_file` that returned an error, are known outcomes (`task_service.known_local_failure`),
unless the command matches an outbound rule of the terminal policy (`apple-events`, `shortcuts`, `send-mail`,
`send-message`, `upload`, `remote-shell`, `git-push`, `publish`): there a failure can still have left
something behind elsewhere. Exceptions, cancellations, timeouts and signals (killed commands) and every
other tool keep today's behaviour. Three places carry it:
- the runtime does not set `reconciliation_required` for a known local failure;
- the journal records it as `failed`, not `uncertain` (`task_repository.action_finished`, error code
  `known_local_failure`) — an `uncertain` action made `finish(phase="succeeded")` refuse;
- the same action may be tried again after a known failure (`prepare_action`); before, the model was told
  "this exact action already ran and its outcome is unknown" for a script that had simply exited 1.
Whether the job is done is still decided by its checks; the failed steps show under the reply.
*Changed while building (no guard):* the draft required a deterministic user criterion to pass first. An
inline turn has none (only "answer delivered"), so every turn with a failed probe would have kept "needs
your review" — what the voice-memo turn showed. Not covered: a local script that sends something over the
network itself and then fails is treated as local; the terminal policy cannot see inside a script.

**A1 — `file_saved` looks at the disk.** New rule kind `file_saved` (target = a full path, or a file/folder
name). It passes when a matching file Arslan produced is verified (today's artifact check), or when the
target on disk is a file changed since the task started (mtime or ctime), or a folder with at least
`minimum` (default 1) entries changed since then. A bare name is resolved from the paths the job's own steps
used (`write_file`/`edit_file`/`read_file`/`list_dir` paths, path-like tokens of `run_command`) and from the
workspace and project folders. Read-only, and only inside the folders Arslan may read
(`file_reader.roots()`; hidden and credential-shaped names refused): it can tell no more than `list_dir`
already could. A name that resolves nowhere is `not_run` (`file_target_unresolved`), not `failed`.

**B — `sources_read` counts what Arslan read.** New rule kind `sources_read`: web pages admitted by the
research rules plus local files read with `read_file`, at least `minimum` (default 1); an optional `target`
must appear in one of them. `research_sources` stays web-only for research tasks. The tool description says
what each criterion kind means and asks for a full path for `file_saved`.

The finish-time check now sees the task's own tool calls (`TaskRuntime.trace`): it used to be called with an
empty trace, so a file read or a command could never count there.

Existing tasks keep their stored rules (`artifact`, `research_sources`) and are evaluated as before.

**C — no ghost reply.**
- Server: `journal_snapshots` skips a run whose journal already holds `stream_end` — the answer is in
  `history`; nothing to replay, no `run_in_progress`.
- Window: `history` clears the live stream (`streaming`, `streamingText`, `thinking`, `workStartedAt`, stream
  source); an in-flight run is rebuilt from the replay that follows it.
- Window: a `stream_end` whose `message_id` is already shown adds no second item.
