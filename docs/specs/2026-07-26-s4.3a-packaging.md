## 1. 依赖处置 —— 只做方案 A,零新功能

**唯一动作:**

| 改动 | 位置 |
|---|---|
| `pymupdf` → `pypdfium2` | `pyproject.toml:46`;`server/services/ingest.py:37,41-44` 的 `fitz.open` / `page.get_pixmap` 改 pypdfium2 等价调用 |

| PyInstaller `.spec` 显式排除 | `excludes=["fitz","pymupdf","pytesseract"]` + 产物树 grep 断言 |

**不做**(全部是新功能,各自独立成轮,见 §9):不接视觉通路 · 不接 RapidOCR · 不打包 tesseract 二进制 · 不打包任何本地模型。

### 为什么换 pypdfium2

`pymupdf` 是 **AGPL-3.0**,分发内含它的 `.dmg` = 分发组合作品,传染条款附到整个 app,与 Apache-2.0 冲突。这是本轮**唯一不可协商**的依赖问题。

**证据口径(见 §10 规矩)**:结论取自 wheel 内 `pymupdf-1.28.0.dist-info/COPYING` 首行 `Dual Licensed - GNU AFFERO GPL 3.0 or Artifex Commercial License`。`pip show` 的 `License` 字段与 `Classifier` **全空** —— 只看那两处会得出"未声明许可证"的错误结论。

`pypdfium2`(Google PDFium)= `BSD-3-Clause, Apache-2.0`,栅格化能力与 fitz 等价。**其 `dependency licenses` 一项必须展开**:PDFium 内含第三方代码,实现时取 wheel 内实体 notice 进 `THIRD_PARTY_NOTICES.md`,不得只抄 PyPI 字段。

### v1 首个构建的能力缺口(如实,不得淡化)

| 输入 | v1 首个 dmg |
|---|---|
| 文本层 PDF(绝大多数) | ✅ 正常,走 `pypdf`(BSD) |
| docx / pptx / html / txt / md | ✅ 正常 |
| **扫描版 PDF**(无文本层) | ❌ 读不出 |
| **独立图片附件** png/jpg/webp/gif | ❌ 读不出 |

**缺口窄且已知**,补法排在 §9 的视觉轮。这条要同时出现在:代码注释、README、交付报告、§8 诚实披露 —— 不许变成没人记得的缺口。

### 🔴 测试必须新写,否则改完全绿等于没测

`tests/server/test_ingest_ocr.py` 三处**全是** `monkeypatch.setattr(ingest, "_ocr_pdf", …)`、**从不 import fitz** ⇒ 换 pypdfium2 / 移除 pytesseract **不会让任何现有测试变红**。必须新增能区分 fitz 与 pypdfium2 的测试(见 §7 mutation 6/9)。

### 🔴 三个我们独有、openworker 没有的问题

**(a) `ARSLAN_SECRET_KEY` / `crypto_salt` 配对**
`README.md:103` + `docs/ARCHITECTURE.md:252`:密钥**故意**在数据目录之外,PBKDF2 从 `SECRET_KEY` + 每装一份的 `crypto_salt` 派生。打包版必须:首启在 `~/.arslan/secret_key` 生成并**持久化**;`crypto_salt` 落在数据目录内。**密钥丢失或不配对 ⇒ 所有已存 provider key 永久解不开。** 必须配 UI 备份提示 + README 的"备份是两件东西"。

**(b) `web/scripts/clean-vite.sh` 在仓库外暂存**
`:19` `STAGE="${TMPDIR:-/tmp}/arslan-web-stage"`、`:25` `ln -sfn "$WEB_DIR/src" "$STAGE/src"`。仓库改名/移动后旧 symlink 断链 ⇒ **"标题正常但白屏"**(迁移后已踩一次)。CI 全新 runner 首次必然重建,**但复用缓存时可能拿到陈旧 STAGE**。建链后加自检:`[ -d "$STAGE/src" ] || 整目录重建`。**本轮显式交付项,不是顺带。**

**(c) `ARSLAN_API_TOKEN` / `require_auth`**
桌面版是 127.0.0.1 单用户。首启生成 token 存数据目录的 `api_token`,前端从 Tauri 侧注入。**不得**因"本地所以安全"关掉鉴权 —— 同机其他进程可访问 127.0.0.1。

## 5. 密钥防线(三条,如实写明边界)

1. **CI 跑 gitleaks `detect` —— 全历史模式,不是 `protect`/diff 模式。**
   理由写进 workflow 注释:只扫 diff 的话,一次误提交在后续 PR 里就再也查不出来;而要防的正是"证书曾经进过仓库"这种**一次性事故**。全历史每次重扫 1152 个 commit,慢但正确。
2. **签名材料永不进仓库**:`.p12` / `.mobileprovision` / `AuthKey*.p8` 进 `.gitignore` + pre-commit 拦截。
3. **fork PR 不给 secrets**(§4)。

**必须如实写进 README / SECURITY.md**:GitHub 侧的通用密钥检测(non-provider patterns)**未启用,且本账号无法启用** —— 官方要求 organization-owned + GitHub Team + GitHub Secret Protection。防线靠上述三条,**不是靠 GitHub**。

## 9. 后续轮次登记(本轮不做,但已定序)

### 视觉轮 —— 排 S4.3-a 之后、S4.3-b 发布之前,**必须落地**

- 接 BYOK 视觉通路(Anthropic / OpenAI / Gemini 均原生支持图片输入)。选它不选 RapidOCR:**体积 0**、能力高一个数量级(看懂表格顺序 / 图表 / 手写,而非只认字)、且与市面共识一致(实查:无任何现代 agent 桌面产品打包 tesseract)。
- 改动面(实测):`arslan/llm/adapter.py:72` 的 `chat(system: str, user: str, …)` —— **user 是纯字符串,全仓库零视觉通路**;三个 provider 的 `build_messages`;`ingest` 附件路径;附件 API;前端。
- 🔴 **产品诚实要求**:Arslan 本就用用户自己的 key 把对话发往云端,所以"图片发云"与"文本发云"是**同一个隐私模型,不是新破口** —— 但投喂扫描件时用户可能以为是本地处理,**必须在投喂入口显式告知"这张图会发给你配置的模型"**。这是诚实问题不是技术问题。
- 它一并解决 **"截图投喂第二大脑"** —— Arslan 的核心用例之一,不只是补 OCR 缺口。
- 🔴 **该轮 spec 必须含【可选本地能力,按需下载】机制一节**,详见下方。

### 🔴【可选本地能力,按需下载】—— 视觉轮 spec 的必含节

视觉通路、语音(whisper.cpp)、离线 OCR(RapidOCR / Unlimited-OCR)本质是**同一类东西**。一件件临时做 ⇒ 三套下载逻辑 / 三套校验 / 三套存储管理 / 三套 UI。

**要求**:在接第一个之前先把机制的形状定下来 —— **下载 / 校验 / 存储 / 卸载 / 失败重试 / UI 呈现** —— 第一个功能按它落地。**设计必须能承载后两个,而不是只服务视觉。** 这是把三个功能的成本从 3× 压到约 1.3× 的地方。

### v1.x —— RapidOCR 作为可选下载,不打包

- 不进首发。**~150MB 真实占用**(`rapidocr` wheel 27.3MB + `opencv_python` ~90MB + `onnxruntime` ~30MB,**且都带原生 `.dylib`,会把 ④⑤ 的嵌套 Mach-O 签名坑再引进来一次**)换来的只是"认字";视觉通路 0 体积换来"看懂"。**wheel 的 27MB 是假数字。**
- 但它有视觉通路没有的东西:**全离线** —— local-first 的一张牌,所以留着,定位是"按需下载的可选离线能力"。
- 许可证:`RapidAI/RapidOCR` = **Apache-2.0**(源仓库实查;**PyPI 的 `license` 字段是 `None`,不可作依据**,见 §10)。

### v2 —— Unlimited-OCR

- `baidu/Unlimited-OCR`,3.34B VLM;bf16 6.78GB,社区 MLX 4bit **2.46GB** 可在 Apple Silicon 原生跑。**2.46GB 不能首发。**
- 🔴 **v2 开工前必须重核权重许可** —— 很多标称 MIT 的模型权重实际带使用限制条款,**HF 页面的 license 标签与仓库内实际 LICENSE 文件经常不一致**。本轮查到的 `license: mit` 只是 HF 元数据,**不作为最终依据**。

## 10. 许可证核验规矩(立为制度,写进 THIRD_PARTY_NOTICES 维护流程)

**任何依赖的许可证,以【源仓库 LICENSE】+【wheel 内 LICENSE/COPYING 实体文件】为准。PyPI 的 `license` 字段和 `classifiers` 一律不作为依据。**

已骗过两次,且**方向相反**:

| 包 | PyPI 元数据 | 实际 |
|---|---|---|
| `pymupdf` | `license` 与 `Classifier` **全空** | wheel 内 `COPYING` 首行 = **AGPL-3.0** —— 差点打进发行包 |
| `rapidocr` | `license: None` | 源仓库 = **Apache-2.0** |

⇒ **空字段既不能读成"宽松"也不能读成"严格",它什么都不是。**

**代码与模型权重是两个许可证,必须分开核**(GitHub 仓库 MIT ≠ HuggingFace 权重 MIT)。声明许可时**引证据出处**(哪个文件、第几行),不复述元数据字段。
