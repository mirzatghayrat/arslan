# 实时语音对话(重做 2026-08-24 那份的 ②耳③嘴)

> 状态:**待审**。上一版语音(v0.1.32「朗读回复」)用户明确否掉了:
> 「我想要的也不是读 reply 而是实时交互语音」。这份 spec 不是补丁,是换目标。

## §0 先摆事实:这轮实测掉的四个未知(不是推理,是测出来的)

写这份 spec 之前跑了三组探针。结论直接决定架构,所以放最前面。

| 探针 | 结果 | 后果 |
|---|---|---|
| 真 WKWebView 里 `speechSynthesis` | **有**(用户也听到了声) | 嘴**可以**留在前端 |
| 真 WKWebView 里 `navigator.mediaDevices` | 🔴 **undefined** | |
| ↑ 再加安全上下文 + `WKUIDelegate` 授权 | 🔴 **仍然 undefined** | **耳朵不可能走前端。没有"纯前端实时语音"这条路。** |
| 打包 app 无 usage string 摸麦克风 | 🔴 **被 TCC 硬杀**(崩溃报告点名 `NSMicrophoneUsageDescription`) | 不是"拒绝",是**崩溃** |
| 打包 app 有 usage string、无 entitlement | ✅ **弹框 → 用户点允许 → `capture=running=true`** | `audio-input` entitlement **不需要**(Developer ID 也签不进去) |

🔴 **和「默认可读」那轮的关键区别**:文件夹那次的结论是"没有 OS 同意时刻,安全全压回环模型"。
**麦克风相反 —— OS 同意时刻真实存在**,用户点一次、系统记住、可在系统设置里撤销。
这次可以、也应该**把同意交给 OS**,不要自己发明一套。

## §1 上一版为什么不是用户要的

`v0.1.32` 做的是「回复到达时念出来」。两个问题:

1. **方向错了**。用户要的是"能跟它说话",不是"它把字读出来"。朗读是**单向**的,
   而对话的价值在于**不用打字**——这一半上一版根本没做。
2. **连朗读本身也是坏的**:嗓音跟的是**界面语言设置**(`language=en` → 英文嗓音),
   不是**这段话本身的语言**。用户界面是英文、Arslan 用中文回复 ⇒ 英文嗓音念中文
   ⇒ 用户原话「发出来的声音跟输出内容不相关」。
   (探针里 `getVoices()` 返回 **0** 也印证:嗓音表异步加载,代码从没等它、也从没显式选嗓音。)

## §2 架构:被实测逼出来的形状

```
麦克风 ──► [Rust 壳]  CoreAudio 采集 + AEC + VAD
                │
                │  (说完一句) 文本
                ▼
          [Python sidecar]  现有 tool loop  ← 不动
                │
                │  stream_chunk
                ▼
          [前端]  显示 + 逐句朗读(speechSynthesis)
                │
                └──► 用户一开口 → 立刻闭嘴(barge-in)
```

**为什么采集在 Rust 壳而不是 sidecar**:TCC 的责任进程是 `.app`,usage string 在它的
Info.plist 里,权限属于它。sidecar 是它拉起来的子进程,让子进程去摸麦克风等于把
授权语义搞浑。而且 AEC 是 CoreAudio 的事,壳离得最近。

**为什么 tool loop 一行不改**:语音只是**输入法**和**输出法**。一句说完 = 一条
user message,走的还是今天那条路。这条约束是刻意的——它让语音失败时最坏情况是
"回到打字",而不是"整个 agent 坏了"。

## §3 真正难的不是 ASR,是这三件事

### 3.1 回声(必须先解决,否则后面都免谈)
扬声器放 TTS → 麦克风收回去 → ASR 去转写 **Arslan 自己的声音** → 它跟自己聊起来。
- **方案**:CoreAudio 的 `kAudioUnitSubType_VoiceProcessingIO`(系统自带 AEC,
  FaceTime 用的就是它)。零依赖、零下载。
- **退路**:半双工(说话时静音麦克风)。简单,但**杀死 barge-in**——而 barge-in
  正是"实时"和"对讲机"的分界线。

### 3.2 打断(barge-in)
用户一开口,TTS 必须**立刻**停。这条决定体验是"在对话"还是"在等它念完"。
前端 `speechSynthesis.cancel()` 够快,但需要 Rust→前端一条低延迟通道(现有 WS 可用)。

### 3.3 端点检测(什么时候算说完)
- 静音超时(简单,但停顿久了会被误切)
- VAD + 语义端点(准,复杂)
- **建议 V1 用静音超时,阈值可调**,先出可用的东西。

## §4 三个要你拍板的决策

### 决策 ① ASR 用哪个
| 选项 | 优点 | 代价 |
|---|---|---|
| **A. `SFSpeechRecognizer`(系统自带)** | 零下载、零成本、多语种、on-device | 需要 Swift/ObjC 桥;`NSSpeechRecognitionUsageDescription` 又是一个 TCC 门 |
| **B. 本地模型(SenseVoice)** | **用户在 Cairn 里已经跑通过**、完全可控、中文强 | 要下模型(几十 MB~)、Python 侧推理延迟、打包变大 |
| **C. 云端 ASR** | 最准 | 要花钱、有延迟、**把用户的每一句话送出去** — 与"个人 agent"定位冲突 |

**我的建议:A**。理由是"素人零配置就能用"——不下模型、不配 key、装完就能说话。
B 作为后续可选项(用户已有资产,值得留插槽)。**C 不做。**

### 决策 ② 嘴留前端还是搬原生
- **留前端**(`speechSynthesis`):已证明能出声,改动小。**必须修**:按**文本语言**选嗓音,
  并等 `voiceschanged` 再说话。
- **搬原生**(`AVSpeechSynthesizer`):停得更干脆(barge-in 更可靠)、无嗓音加载竞态,
  但多一个桥。

**我的建议:先留前端 + 修嗓音选择**,把预算花在耳朵和 AEC 上。前端这条已经被真机
证明能出声,是这轮唯一"已知能工作"的部件,没必要先拆它。

### 决策 ③ v0.1.32 那个「朗读回复」开关怎么办
- **保留但改写**:它变成语音模式的一部分,不再是独立开关
- **删掉**:语音模式统管一切

**我的建议:保留开关但修好嗓音 bug**,因为"只想听、不想说"是真实需求(边做事边听),
而且它现在**是坏的**——不修就是留着一个会念错的功能。

## §5 分阶段(每阶段可独立验收)

- **V1a｜能说话**:按住说话(不是常开)→ 转写 → 发送。无 AEC 无 barge-in(按住时不放音)。
  **这一阶段就能验证"素人能不能用嘴使唤它"这个核心假设**,而且绕开了最难的回声问题。
- **V1b｜嘴修好**:按文本语言选嗓音 + 等嗓音表加载。独立于 V1a,可先做。
- **V2｜常开对话**:AEC + VAD + barge-in。这才是"实时交互"。
- **V3｜可选本地 ASR**:SenseVoice 插槽。

🔴 **建议 V1a 先出**:它小、可独立验收,而且如果"按住说话"就已经够用,V2 的复杂度
可能根本不需要花。反过来,先做 V2 再发现方向不对,浪费的是最贵的那部分。

## §6 尚无证据 / 逻辑定不了的

- `SFSpeechRecognizer` 在**打包环境**能不能用、on-device 模式对中文可用性如何 —— **未验**。
  这是 V1a 开工前必须补的第三个探针(和这次麦克风探针同一手法:签名 .app + `open`)。
- `NSSpeechRecognitionUsageDescription` 是**另一个 TCC 门**,缺了大概率同样是崩溃而非拒绝
  —— 按麦克风那次的结果类推,但**没实测过**。
- AEC 在这台机器上的实际消除效果 —— 只能真机听。
- "按住说话够不够用" vs "必须常开" —— **纯产品判断,逻辑定不了,要你说**。
