# Arslan mobile bridge protocol — v1

Status: **formal v1** (2026-10-03). It is the single contract between the Mac Bridge
(`ArslanBridge.app`, this repository) and the iPhone app (`arslan-ios`). Its base is the iOS
team's M1 proposal (`arslan-ios/docs/protocol-m1-proposal.md` and the M0 draft); this
document adopts it, adds the `notify` field to the CloudKit record, and settles the open
points marked "needs Mac confirmation".

Executable form: `spec/mobile-bridge/reference.py` (independent Python oracle). Shared vectors:
`spec/mobile-bridge/vectors/` (regenerated by `make_vectors.py`; `tests/test_mobile_bridge_vectors.py`
fails if they drift). Both apps' CI must pass every vector before a release; the iOS repo keeps a
copy. The first four crypto vectors are byte-identical to the iOS proposal's.

Design background: `Arslan-iOS随身版-设计与施工单-2026-10-03.md` §4–§6 (outside the repo).

## 1. Transport

| Path | Use |
| --- | --- |
| CloudKit private database, zone `ArslanBridge` | v1 main channel: both devices on the same Apple ID; Apple sees ciphertext and metadata only |
| Local network (Bonjour) | later (M3), same packets |

The Mac must be on, online and awake; messages wait in iCloud otherwise.

## 2. CloudKit layout

Container: `iCloud.dev.aralem.arslan` (created by the user in the Apple Developer portal; both
apps list the same identifier in their entitlements; a QR code names it and the phone refuses any
other). Private database, custom zone `ArslanBridge`.

Record type `Envelope`, record name = the envelope id as a lowercase UUID:

| Field | Type | Notes |
| --- | --- | --- |
| `to` | String | recipient device id — Queryable |
| `from` | String | sender device id |
| `seq` | Int64 | sender's sequence number |
| `kind` | String | `msg` / `ack` / `control` (§5.1) |
| `notify` | Int64 | **0 or 1** — asks for a user-visible alert (§5.2) — Queryable |
| `sealed` | Bytes | the SecurePacket JSON (§4.2), ≤ 800,000 bytes |
| `asset` | Asset | an encrypted file (§4.6), when present |
| `createdAt` | Date/Time | kept on retries — Queryable, Sortable |

`to`, `from`, `seq`, `kind` and `notify` duplicate signed header fields so CloudKit can index them;
receivers trust only the signed header inside `sealed`.

Schema (once per container, by the account owner): the profile pins the container to the
**Production** environment, where record types cannot be created on first write. Create the
`Envelope` type with the fields above in CloudKit Console → Development (or import
`spec/mobile-bridge/cloudkit-schema.ckdb` with `xcrun cktool import-schema`), add the indexes
(`recordName` Queryable; `to`, `notify` Queryable; `createdAt` Queryable + Sortable), then
**Deploy Schema Changes** to Production. The zone itself is created by the Bridge at run time.

Subscriptions:
- Mac: zone subscription, silent push; on wake, fetch changes by change token. Fallback poll of zone
  changes every 10 s while a phone is active, else every 60 s (initial values; tune after M1).
- Phone: zone subscription (silent) plus a query subscription `to == <phone id> AND notify == 1` with
  a generic alert, `mutable-content` (the notification extension fetches, verifies, decrypts and,
  if the user allowed it, rewrites the alert).

Clean-up: the receiver sends `ack` after processing; the sender deletes the original record on a
valid `ack`. An `ack` is not acknowledged, so the device that reads it deletes it. A new
`status.snapshot` replaces the one the phone has not acknowledged yet: the Mac deletes the older
record. The Mac deletes envelopes older than 7 days once a day (ten minutes after it starts, then
every 24 hours), whoever wrote them.

## 3. Pairing

### 3.1 The QR code

`arslan://pair?payload=<base64url(JSON)>` (padding optional), exactly one `payload` parameter, at
most 8,192 UTF-8 bytes. JSON fields:

| Field | Constraint |
| --- | --- |
| `v` | 1 |
| `pairing_id` | UUID (lowercase in the code), identifies the one-time code |
| `mac_device_id` | 1–128 UTF-8 bytes |
| `device_name` | 1–256 UTF-8 bytes |
| `signing_public_key`, `exchange_public_key` | standard base64, 32-byte Ed25519 / X25519 public keys |
| `pairing_key` | standard base64, 32 random bytes |
| `container_id` | must equal the container this build is signed for, else `wrong_container` |
| `zone` | `ArslanBridge` |
| `issued_at`, `expires_at` | ISO 8601 UTC; validity ≤ 600 s; `issued_at` may be ≤ 30 s ahead of the phone's clock |

Errors: `pairing_invalid` (bad window), `pairing_expired`, `wrong_container`, `unsupported_version`,
`malformed`.

### 3.2 The handshake

1. The phone pins the Mac's two public keys from the code, creates its own Ed25519 identity, X25519
   exchange key and local storage key (Keychain, `AfterFirstUnlockThisDeviceOnly`, never synced).
2. It sends `pair.request` (kind `control`): body = phone name and public keys; header carries
   `pairing_id` and `signing_key` (the phone's signing public key, so the Mac can verify a sender it
   does not know yet); the HKDF salt is the `pairing_key`.
3. The Mac verifies with the header key (not yet trusted), decrypts with its exchange key and the
   pairing key, checks the body's key equals the header's, then **asks the user on the Mac**. Nothing
   is trusted until both the pairing key and the user's click succeed.
4. The Mac answers `pair.accept` or `pair.reject` under the same `pairing_id` and salt, signed by its
   pinned key. `pair.accept.mac_device_id` and both keys must equal the code's.
5. The Mac persists the code as consumed. A retry of the same request id from the same phone gets the
   same decision; never a second prompt or a second grant. The phone deletes the pairing key after a
   decision and sends nothing else before `pair.accept`.
6. Revocation (Mac settings) sends `device.revoked` and forgets the phone's keys.

### 3.3 Pairing again, removing a phone, device state (added 2026-10-07; additive within v1)

Found on a real iPhone (TestFlight 1.0 (11)): every pairing gives the phone a new device id, and
unpairing on the phone does not tell the Mac. The same phone scanning again became another row in
Settings › iPhone (four "iPhone"s), the Mac kept writing to the old ids, and none of those records was
ever acknowledged: 1,602 stayed in the user's iCloud, and a freshly paired phone paged through them
all looking for its `pair.accept` and timed out.

1. **`pair.request.replaces`** (optional): an array of up to 8 strings — device ids this phone used in
   earlier pairings with this Mac. Only when the user **accepts** the request does the Mac remove each
   of them exactly as Settings › Remove does (item 2), except that it sends them nothing (no
   `device.revoked`: that phone identity is gone). The Mac takes the first 8 entries and skips any
   that is not a string; an id it does not know matches nothing; the requesting phone's own id is
   never removed. A reject removes nothing. A phone that sends no `replaces` pairs as before.
2. **Removing a phone** (Settings › Remove, or `replaces`): the Mac forgets its keys, deletes from the
   zone the records it sent that phone that still wait for its `ack`, and stops waiting for them. On
   Settings › Remove the `device.revoked` it sends first is left for the phone to read (no ack can
   be read from a forgotten key; the 7-day clean-up takes it). The Mac remembers each waiting
   record's recipient (`to`) across restarts, so a removal after a restart still finds them.
2a. **Unpairing on the phone** (added 2026-10-10, iPhone 1.0): before it wipes itself, a paired phone
   sends `device.revoked` with `reason: "unpaired_on_phone"` (phone → Mac, signed with its key) and
   waits a few seconds at most for the upload; offline, it unpairs anyway and the Mac keeps the row
   until Settings › Remove or the next pairing's `replaces`. The Mac removes the **sender** as in item 2,
   sends it nothing back, and acts on nothing else from it in that batch. The body never names another
   phone: a phone can remove only itself. A Mac older than this ignores the message.
3. **At start-up** the Mac deletes the records still waiting for an ack whose recipient is no longer a
   paired phone. Waiting ids remembered before this change carry no recipient: the Mac reads each
   record's `to` from the zone by id (that field only). An id the zone no longer has stops being
   waited for; if the lookup fails, nothing is concluded and nothing is deleted (tried again at the
   next start). A record addressed to a phone that is still paired is never deleted this way.
4. **Device state** in the Bridge's `devices` control frame (§6.1): each item is `device_id`, `name`,
   `paired_at`, `state` and `last_seen?`. `state` is `connecting` while the phone is paired but no
   authenticated message from it has been read yet, and `connected` from the first one (any type,
   acks included). `last_seen` (ISO 8601) is when the Mac last read one, kept to the minute and
   remembered across restarts; absent until then. The Bridge sends a new `devices` frame when a phone
   becomes connected and when its `last_seen` moves on — at most once a minute per phone, not on
   every message.

## 4. Packets

### 4.1 Keys

Per device: an Ed25519 identity key (`Curve25519.Signing`) and an X25519 exchange key
(`Curve25519.KeyAgreement`). CryptoKit primitives only; macOS 11 / iOS 17 (no HPKE). No model API
keys are ever stored or sent by either side.

### 4.2 SecurePacket

`Envelope.sealed` is the UTF-8 JSON

```text
{ "header": { "v", "id", "from", "to", "seq", "kind", "ephemeral", "notify",
              "pairing_id"?, "asset_hash"?, "signing_key"? },
  "sealed": base64(nonce[12] || ciphertext || tag[16]),
  "signature": base64(ed25519 signature[64]) }
```

`v` = 1; `id` UUID; `seq` positive Int64; `kind` ∈ {msg, ack, control}; `ephemeral` = this message's
fresh X25519 public key (standard base64); `notify` boolean. The real type and body exist only in the
encrypted plaintext (§5).

### 4.3 Header bytes

`LP(s) = UInt32BE(len(UTF8(s))) || UTF8(s)`; header bytes are, in order:
`LP("arslan-bridge/v1")`, `LP(decimal v)`, `LP(lowercase id)`, `LP(from)`, `LP(to)`,
`LP(decimal seq)`, `LP(kind)`, `LP(ephemeral base64)`, `LP(lowercase pairing_id or "")`,
`LP(asset_hash base64 or "")`, `LP(signing_key base64 or "")`, `LP("1" if notify else "0")`.
No JSON canonicalisation is involved; every header field is both signed and AEAD-authenticated.

### 4.4 Sealing

1. ECDH: the sender's fresh X25519 private key × the recipient's X25519 public key.
2. HKDF-SHA256 → 32 bytes; salt = the pairing key for `pair.*`, empty otherwise; info =
   UTF-8 `arslan-bridge/v1/message` || `LP(from)` || `LP(to)`.
3. ChaCha20-Poly1305, random 12-byte nonce, AAD = header bytes.
4. Ed25519 signature over `header bytes || sealed` (sealed includes nonce and tag).

Ed25519 verification is compared, not signature bytes: CryptoKit's signatures are valid but need not
equal the deterministic reference signatures in the vectors.

### 4.5 Retries

A retry re-sends the **same persisted packet**: same id, seq, ephemeral key and nonce. Senders
persist the sequence counter and the outgoing queue before any CloudKit write.

### 4.6 Files

At most 20 MiB. Key: the same shared secret and salt with info purpose `arslan-bridge/v1/asset`.
AAD = the header bytes with field 10 (`asset_hash`) empty. `asset = nonce || ciphertext || tag` in
the record's `asset`; the header's `asset_hash` = standard base64 of SHA-256(asset), computed before
the message is sealed and signed. The body must be `file.offer`. The receiver checks the asset hash,
the AEAD, the plaintext size and `body.sha256` before caching or previewing.

### 4.7 Opening (order matters)

shape → recipient (`not_for_me`) → signature (`bad_signature`) → decrypt (`decrypt_failed`) →
plaintext agrees with the header: `v`, `id` (case-insensitive), `from`, `to`, `seq`, and the type's
kind (`header_mismatch`) → asset (`asset_mismatch`). Any failure drops the packet with no partial
effect.

### 4.8 Replay

Per sender, remember the last 1,024 sequence numbers: accept a new one inside the window even out of
order; drop a repeat and anything at or below `highest − 1024`. A duplicate envelope id is not
re-executed, but its `ack` is sent again.

## 5. Messages

Plaintext (compact UTF-8 JSON; receivers ignore key order):

```json
{ "v": 1, "id": "uuid", "seq": 42, "ts": "2026-10-03T12:00:00Z",
  "from": "iphone-…", "to": "mac-…", "type": "chat.send", "body": { } }
```

### 5.1 Kind

`ack` → `ack`; `pair.request`, `pair.accept`, `pair.reject`, `hello`, `device.revoked` → `control`;
everything else → `msg`.

### 5.2 Notify

`notify = 1` only for: `chat.event` with `kind: "message"` and `final: true`, or `kind: "error"`;
`job.event` in a terminal state (`done`, `partial`, `stuck`, `stopped`); `approval.request`;
`approval.result` with outcome `failed` or `expired`; `device.revoked`; `error`. Everything else
(progress, ack, pairing, history, files, snapshots) is 0. The bit reveals "this asks for an alert",
never the content. A lock-screen alert shows generic text unless the user turned content on.

### 5.3 Types and bodies

| Type | Direction | Body (`?` optional) |
| --- | --- | --- |
| `pair.request` | phone → Mac | `device_name`, `signing_public_key`, `exchange_public_key`, `replaces[]?` (≤ 8 earlier device ids, §3.3) |
| `pair.accept` | Mac → phone | `phone_device_id`, `mac_device_id`, `device_name`, `signing_public_key`, `exchange_public_key` |
| `pair.reject` | Mac → phone | `reason` |
| `hello` | both | `app_version`, `protocol_version`, `capabilities[]` |
| `ack` | both | `ids[]` (lowercase envelope ids) |
| `status.snapshot` | Mac → phone | `presence` (online/sleeping/offline), `mascot`, `device_name`, `last_seen`, `jobs[]` (each a `job.event` body: the jobs still running), `waiting_approvals`, `high_risk_mac_only` |
| `conversations.list` / `conversations.result` | phone → Mac / Mac → phone | `limit?` (1–100, default 20) / `conversations[]` (`id`, `title`, `updated_at`; optional `kind`, `state`, `origin`, `preview`, `files`, `job`), most recent first |
| `chat.history` / `chat.history.result` | phone → Mac / Mac → phone | `conversation_id`, `limit` / `conversation_id`, `messages[]` (`id`, `role`, `text`, `ts`, `attachments[]`, `run_id?`) |
| `chat.send` | phone → Mac | `conversation_id?` (absent = the pocket conversation), `text`, `attachments[]`, `client_msg_id` (UUID) |
| `chat.event` | Mac → phone | `conversation_id`, `kind` (message/progress/error), `message_id`, `text`, `final`, `job_id?`, `run_id?` |
| `job.event` | Mac → phone | `id`, `conversation_id`, `state` (running/done/partial/stuck/stopped), `title`, `current_step`, `completed`, `total`, `plan[]`, `summary?`, `files[]`, `run_id?`, `origin?`, `criteria[]?` |
| `approval.request` | Mac → phone | `approval_id`, `action` (the card's `title` when it has one; an app, site or Shortcut card ends it with " (for this task)"), `target`, `risk` (write/send/delete/install/payment/publish; the card's `perm_kind` decides the word first, §5.3), `task_id`, `task_title`, `expires_at` (the card's own) |
| `approval.answer` | phone → Mac | `approval_id`, `decision` (approve/deny), `auth` (`faceid` or `touchid` for approve, `none` for deny; a Mac that counts `touchid` says `touchid` in its hello capabilities, and a phone sends a Touch ID yes only to such a Mac), `ts` |
| `approval.result` | Mac → phone | `approval_id`, `outcome` (done/denied/expired/failed), `detail?` |
| `file.offer` / `file.get` | Mac → phone / phone → Mac | `id`, `name`, `size`, `mime_type`, `sha256` (hex of the plaintext) / `file_id` |
| `run.get` / `run.result` | phone → Mac / Mac → phone | `run_id` / `run_id`, `conversation_id`, `title`, `state` (working/done/failed/stopped), `started_at`, `duration_ms`, `total`, `steps[]`, `files[]` (§5.5) |
| `task.start` / `task.started` | phone → Mac / Mac → phone | `goal`, `criteria[]?` (≤ 3), `client_task_id` (UUID) / `conversation_id`, `job_id`, `client_task_id` |
| `task.stop` | phone → Mac | `job_id`, `conversation_id?` |
| `device.revoked` | Mac → phone; phone → Mac (§3.3 item 2a) | `reason` (`removed_on_mac` / `unpaired_on_phone`) |
| `error` | both | `code`, `message`, `related_id?` (the request it answers) |

Settled here (open in the proposal):
- **`approval.result`** is the business receipt: an `ack` only says "delivered". The phone shows an
  approval as done only after `approval.result` with `done`; a card that expired on the Mac (30 min since
  0.1.61; 5 min before) answers `expired`, which is never a refusal.
- **Deny** carries `auth: "none"`; approving always needs Face ID; voice never approves.
- `status.snapshot` is built by the Mac from the island feed (`/api/v1/island/feed`); the phone never
  calls the Mac's HTTP API. The Mac sends it when the phone says `hello`, when what the phone shows
  changes (mascot, cards waiting, which jobs and their state: at most every 2 s; a job's step or
  progress: at most every 15 s), and otherwise as a heartbeat every 60 s. The phone treats a Mac whose
  `last_seen` is more than 90 s old as offline. `mascot` follows the island: a card waiting →
  `approval`; work in flight → `searching` (web search, page reading, recall, browser) or `working`;
  else what finished in the last minute → `done`, or `stopped` when it failed or a schedule paused;
  else `idle`. The Mac sends `presence: online` only (it cannot speak while asleep or off; `sleeping`
  is reserved), and `high_risk_mac_only: false` until that switch exists.
- `mascot` values: idle, working, searching, approval, question, done, stopped, away (the island's
  states).
- Progress (`job.event` running, `chat.event` progress) is coalesced to at most one per job every
  2 s, newest wins; terminal states are sent at once.
- `chat.send` is executed once per `client_msg_id`; a retry gets the same result.
- `risk` is one of six values and only decides how the phone's card looks; the decision stays on the
  Mac. A command card maps its words (delete → `delete`, install/brew/pip/npm and anything outside the
  sandbox → `install`, push/publish/deploy/upload → `publish`, curl/ssh/mail or another machine →
  `send`, else `write`); writes and schedules are `write`; a website action is `send`. Since 0.1.61 a
  card's `perm_kind` decides first: `money` → `payment`, `send` → `send`, `destructive` → `delete`,
  `outside` → `install`; any other kind keeps the rules above. A `capability` card never reaches the
  phone. `action` is the card's `title` when it has one (the Mac's own words, in English for now),
  and `expires_at` is the card's own. `action` ends with " (for this task)" on a card whose `perm_kind`
  is `app`, `site` or `shortcut`: the phone's yes takes the card's first, narrowest choice, which on
  those cards is the task (the heading is still cut at 200 characters, the words kept whole). A card for
  several apps (`decide_many`) joins their ids; several apps in one card arrive in `target` separated by ", ".
- History ids are the Mac's stored message ids, and the final `chat.event` of a turn uses the same id,
  so the phone can merge the two. Arslan's replies list their run's files as `attachments`.
- Files are a run's artifacts (immutable snapshots, so a reference never goes stale; id =
  the artifact's filename). When a turn ends, the Mac offers its files as `file.offer` without an
  asset; `file.get` answers with a new `file.offer` carrying the encrypted asset (§4.6), sent only
  when the bytes match the reference. Files over 20 MiB are never offered (`too_large`); a file that is
  gone or changed answers `file_unavailable`.

### 5.5 Review and tasks (added 2026-10-04; optional fields, new types — additive within v1)

For "I'm out, the Mac is at home": glance, review fast, hand over a whole task.

- **`status.snapshot.activity`**: today on the Mac — `hours[24]` (per local hour `[chat turns, tasks,
  approvals]`), `done` (runs finished cleanly), `files` (files made), `waiting` (cards open).
- **`conversations.result` items**: `kind` remote/chat/task/scheduled (the pocket conversation is
  `remote` and is titled **Remote** on both sides), `state` idle/working/waiting/done/unfinished/failed
  (`unfinished`: the job ended without getting it done — partly, stuck, out of budget, or by its own
  account; `failed`: stopped), `origin`
  phone/mac (who started it — the Remote trace), `preview` (last message, one line), `files` (count),
  and `job` `{id, step, done, total}` while a background job runs in it.
- **`run_id`** on a reply (`chat.event` final, `chat.history.result` message, `job.event`): the run whose
  steps `run.get` returns.
- **`job.event.criteria[]`**: each acceptance check as `{text, status}`, `status` pending/passed/failed/
  not_reached (a finished job never says pending); `completed` counts the passed ones, `total` all of them.
- **`run.result.steps[]`**: the newest 40 (`total` says how many): `kind` command/edit/write/web/search/
  read/plan/other, `tool`, `ok`, `ms`, `target`, `summary`, `running?`, and by kind:
  `terminal {command, exit, lines[]}` (the last ≤ 60 lines, colour codes removed); `diff {path, added,
  removed, new_file, lines[[op, old_no, new_no, text]]}` with `op` `" "`/`"-"`/`"+"`/`"fold"` (a fold's
  text is the number of unchanged lines hidden; two lines of context around each change; ≤ 160 rows;
  line numbers are within the edited snippet); `file_id` for a new file (fetch with `file.get`).
  The Mac records this review data when each tool finishes, bounded (a few KB per step).
- **`task.start`**: the Mac gives the task its own conversation (`task-…`), stores the goal as the
  phone's message, and runs a background job with the criteria as its acceptance checks; replies
  `task.started`. A retry with the same `client_task_id` gets the same answer and starts nothing new.
  Progress then arrives as `job.event`, the result as a final `chat.event` with `job_id`.
- **`task.stop`** cancels a running job; the phone sees it end as `job.event` `stopped` (pass
  `conversation_id` so the Mac is listening to that conversation).
- When the phone asks for a conversation's history, the Mac starts forwarding that conversation's live
  events (progress, results, background-job cards) too.

### 5.7 Files from the phone, live conversations, delete (added 2026-10-13; optional fields, new types — additive within v1)

For "the same conversations on both sides, files both ways" (iPhone 1.0 final). A Mac without these
answers the new types with `unknown_type`; a phone without them never receives the new events (below).

**Capabilities.** The Mac's `hello.capabilities` add `files_in` (it takes files from the phone),
`partial`, `delete`, `live` and `mac_messages`. The Mac remembers each phone's own `hello.capabilities`
(across restarts) and sends `chat.event` kind `partial` only to a phone that said `partial`, and the
words typed on the Mac (role `user`) only to a phone that said `mac_messages`. A phone that has not
said hello gets neither: today's phone answers an unknown `chat.event` kind with `unknown_type` and
would show the Mac's words as an answer. A phone that sends files says `files_out`.

| Type | Direction | Body (`?` optional) |
| --- | --- | --- |
| `file.offer` (with asset) | phone → Mac | the `FileReference`: `id`, `name`, `size`, `mime_type`, `sha256` (hex of the plaintext); the asset sealed and bound exactly as §4.6 |
| `chat.send` | phone → Mac | as §5.3; `attachments[]` = up to 10 `FileReference`s, each sent first as a `file.offer` with its asset |
| `chat.event` | Mac → phone | as §5.3, plus kind `partial`; on a final `message`: `partial_id?`, `origin?` (`phone`/`mac`); on words typed on the Mac: `role: "user"`, `source: "mac"`; on `error`: `origin?` |
| `file.offer` (reference) | Mac → phone | as §5.3, plus `conversation_id?`, `message_id?`, `run_id?`, `job_id?` |
| `conversation.delete` / `conversation.deleted` | phone → Mac / Mac → phone | `conversation_id` / `conversation_id` |
| `chat.history.result` | Mac → phone | as §5.3, plus `truncated?` (true when older messages were left out); a user message has `source` `phone`/`mac` |

New error codes (may travel in `error`): `too_many_files` (more than 10 attachments), `not_found` (a
conversation the Mac does not have).

- **Files from the phone.** The phone sends each file as `file.offer` with its asset (≤ 20 MiB), then
  the `chat.send` naming them in `attachments`. The Mac opens the asset exactly as the phone opens one
  (§4.7: asset hash, AEAD, plaintext size, `sha256`; a failure drops the packet unacknowledged), saves
  it to the workspace as `Inbox/iPhone/<local YYYY-MM-DD>/<name>` (the name's last path component, no
  leading dots, no control characters or colons, at most 120 characters with its extension kept,
  ` (2)`, ` (3)` … when taken), reads a non-picture's text once (`/api/v1/extract`), and keeps a
  picture's bytes in memory until a message uses them or for 10 minutes. The same file offered again
  is saved once. A phone `file.offer` without an asset answers `malformed`.
- **A message with files.** `chat.send` runs once every referenced file is on the Mac, at most 120 s
  after the Mac received it; then the Mac answers `error` `file_unavailable` with `related_id` = that
  `chat.send` and does not count it as run, so the phone may send the files and the message again.
  A later message to the same conversation waits behind it (order kept); other conversations do not
  wait. More than 10 attachments: `too_many_files`. The message reaches Arslan as one turn, as the web
  composer sends one: the text, a blank line, then one line per file `Attached from iPhone: <name> →
  <saved path>`; pictures (`image/jpeg`, `png`, `gif`, `webp`; ≤ 3.5 MB each and 8 MiB together, so the
  frame stays under the backend's 16 MiB) go to the model as images; other files' text goes in as
  attached context under `=== <name> ===`. A picture not shown or a file whose text could not be read
  says so on its line (`(not shown to the model as a picture; open the file itself)`, `(its text could
  not be read; open the file itself)`): the agent can still open the saved file. `client_msg_id` stays
  once-only.
- **`partial`.** While Arslan writes an answer, `chat.event` kind `partial` carries the whole reply so
  far (`final: false`), at most once a second and only when it changed, under the turn's own
  `message_id` (the id its `progress` and `error` events also use). The final `message` keeps the stored
  message id (history merge, §5.3) and names the partial it replaces in `partial_id`; a final or an
  error ends the conversation's partial. No partials past 100 KB of reply (the final still comes). A
  newer partial, or the turn's final word, takes back a partial the phone has not read yet. `partial`
  never asks for an alert.
- **Words typed on the Mac.** A user message typed in a Mac window reaches the phone as `chat.event`
  `message` with `role: "user"`, `source: "mac"`, `final: true` and the stored message id; never an
  alert. The phone's own words are never sent back. Today's backend sends no frame for a window's own
  words, so the Mac reads the newest stored messages of a linked conversation when a turn starts there
  (a phone's messages are `source: "phone"` in the history, a window's `source: "mac"`).
- **Who started a turn, and who it rings.** A final `message` or `error` carries `origin`: `phone` when
  the phone's words started that turn, `mac` when words typed on the Mac did; absent when unknown (a
  schedule; a Mac not reading the Mac's words). Amending §5.2: a `chat.event` with `origin: "mac"` or
  `role: "user"`, or kind `partial`, never asks for an alert (the user is at the Mac); an unknown
  origin rings as before. A background job's result carries the job's `origin`; `job.event` in a
  terminal state still always rings, the phone's own tasks included.
- **Progress lines.** The backend's "still working" beat becomes a `progress` line `Working…` (only
  inside a turn, never in place of a step held back) and "your message waits for the current turn"
  becomes `Queued behind the current turn`, under the same 2-second rule.
- **The Mac's files, attached to their answer.** A `file.offer` the Mac sends after a turn names
  `conversation_id`, `run_id` and the stored `message_id` of the answer; a background job's files go
  with its result message (`message_id`, `job_id`), or alone (`job_id`, no `message_id`) about 2 s
  after a job that ended without one. A run's files are offered once.
- **`conversation.delete`.** The Mac deletes the conversation as its own window does (`DELETE
  /api/v1/conversations/<id>`; its runs are kept), closes its live link and answers
  `conversation.deleted`. `pocket` (Remote) is never deleted: `malformed`. A conversation the Mac does
  not have: `not_found`. An older Mac answers `unknown_type`.
- **Live conversations.** At start, after each `conversations.list` and on `hello`, the Mac links the
  newest 20 conversations and every one with a running job (never a temporary one), so their answers,
  progress and shared cards (a phone's turn, a background job's, one whose window went away) reach the
  phone without it opening them first. Linking is a read-only socket: it answers nothing and takes no
  turn. A conversation the phone opens stays linked as before; beyond 40 links, ones unused for 15
  minutes that are no longer among the live ones close (never one with a card open).
- **History in one envelope.** The phone may ask for 200 messages and 100 conversations. The Mac keeps
  the history body under 560 KB (the design said 700 KB, but after encryption and base64 a body that
  size cannot fit the 800,000-byte record, §4 `Wire.maxSealedBytes`), dropping the oldest first, and
  then sets `truncated: true`; one message bigger than that keeps its start, cut with `…`.

### 5.4 Error codes

`malformed`, `unsupported_version`, `unknown_type`, `not_for_me`, `bad_signature`, `decrypt_failed`,
`header_mismatch`, `asset_mismatch`, `too_large`, `pairing_invalid`, `pairing_expired`,
`wrong_container`, `not_paired`, `revoked`, `approval_expired`, `rate_limited`, `mac_busy`,
`file_unavailable`. A receiver never answers an `error` with an `error`. Codes in
§4.7 are receiver-side drops and are not sent back (no oracle); the others may travel in `error`.

## 6. Mac side (summary; plan in the design doc §6)

`Arslan.app/Contents/Helpers/ArslanBridge.app`, its own bundle id (`com.arslan.desktop.bridge`), a
Developer ID provisioning profile with iCloud (CloudKit, the container above) and Push. Started by
Arslan, runs with resident mode, quits with it. Talks to the local backend with the existing API
token (handed over on stdin, never in the environment or a file) and same-origin websockets, one
`/ws/arslan/{conversation_id}` per active conversation; cards become `approval.request`, answers become
the existing `confirm_*` / `cancel_*` frames. Its private keys live in its own Keychain items.

### 6.1 Mac-side wiring (proposed; built in the next steps)

- The Bridge has no window (LSUIElement). Pairing prompts and the Settings › iPhone page live in Arslan's
  own window, so the user sees them where everything else is.
- Control channel: the Bridge opens `/ws/bridge?token=…` (same origin, same token rules as `/ws/arslan`).
  The backend relays: "new pairing code" → QR shown in Settings; a pending `pair.request` → a card
  "iPhone 'x' wants to connect" that only a click in Arslan's window can accept (never voice, never the
  phone); device list (with each phone's `state` and `last_seen`, §3.3), revoke; the two switches
  (keep awake while a phone is connected, high-risk only on the Mac).
- Conversation channel: one `/ws/arslan/{conversation_id}` per active conversation, mapped by
  `FrameMapper` (BridgeCore). The pocket conversation (no `conversation_id`) is one fixed conversation
  the Bridge creates on first use.
- The one backend change for messages: a `user_message` frame may carry `source: "phone"`; the message
  is stored and shown with "from iPhone". It is also sent at once, as a `message` frame with
  `source: "phone"`, to every Mac window open on that conversation (the Bridge ignores it).
- Cards of a turn the phone started go to every socket on the conversation: the Bridge's (→
  `approval.request`) and each Mac window's. The first answer from either side decides; the backend
  then broadcasts `card_resolved {call_id, outcome: approved|declined|expired, by?: phone|mac|inbox|island}`, which
  closes the window copies and becomes the phone's `approval.result` (approved → `done`, declined →
  `denied`, expired → `expired`; `detail: "answered_on_mac"` when the Mac answered — a window, the Inbox or the island). The phone's
  `confirm_*` / `cancel_*` frames carry `source: "phone"`; a phone answer to a card the Mac already
  decided is dropped quietly (the phone has its `approval.result`). Background-job cards end with the
  same `card_resolved`. A window's own turn keeps its cards private to that window, as before.
- Keys: the Bridge's identity keys and the paired phones' public keys live in the Bridge's own Keychain
  items; the backend never holds them.

## 7. Versioning

`v` changes only for an incompatible wire change. New optional body fields and new types are
additive within v1; a receiver answers an unknown type with `error` `unknown_type` and an unknown `v`
with `unsupported_version`. `hello` exchanges app and protocol versions and capabilities.
