## 1. 机制（四段，每段一条硬规矩）

### DETECT —— 廉价、常开、去抖
- 信号：run 失败率（复用 runs.py 的现成计算）、同形状错误重复 N 次（去抖：**单次不触发**，
  Sentry Seer 的 10+ 次门槛先例）、MCP 连接持续 failing、工具连续报错降级（PB-3 已有计数）。
- **硬规矩：检测本身零 LLM 调用、零网络。** 纯 SQL/计数，跑在现有 watch_loop 的 tick 里
  （挂 while 体不挂 tick()，D5 教训：tick 第一句是 `_enabled()` 闸）。
- 每个信号带**可修性预判**（规则判断，不是模型判断）：schema 错误=可修，配额耗尽=不可修只通知。

### DIAGNOSE —— 硬预算，强制终态
- 触发后开一次诊断 run：**max N 次派发 + 每 attempt 抓取预算（直接复用 FU-2b 的
  `HERMETIC_FETCH_BUDGET` 机制，新 sentinel `proactive-diagnosis`）+ 强制终态**：
  要么产出提案，要么记录"放弃 + 原因"。**没有第三态**（AutoGPT 的 54% 预算烧在解析引用 =
  没有强制终态的下场）。
- 固定阶段不自由规划：复现证据收集 → 假设 → （可选）GitHub 检索 → 提案草稿。
  每阶段有输出契约，上一阶段的输出是下一阶段的输入。

### PROPOSE —— 可审工件，证据附身
- 提案 = `{症状(带 run id 们), 诊断, 建议动作, 证据链接(GitHub URL 等), 预估影响}`。
- GitHub 检索结果**只作为链接进提案**——人读、人选。**绝不自动 import_skill /
  绝不把搜索结果喂给任何安装通路**（`test_capability_supply_chain.py` 已经钉死签名边界，
  本轮给它加一条：诊断执行器模块不可 import `skill_import`）。
- 提案先过自检（Sweep 先例）：能本地验证的（如"重跑该 run 确认已修"）验完再入箱。

### APPROVE —— 人闸
- 提案入箱等 accept/dismiss。accept 的动作**只能是**：打开某设置页、跳到某文档、
  或触发一个**已在封闭注册表内**的既有操作。没有"accept = 装个新东西"。

## 2. 不做（防蠕变）
自动修复（哪怕"很安全的"）；自动安装任何来源的任何东西；后台自主浏览非 GitHub 站点；
诊断结果直接改设置；把本循环接进进化的自动路径。

## 3. 拍板项 —— **已裁决（用户 2026-08-01）**

| # | 裁决 | 内容 |
|---|---|---|
| ① | **A** | 检测信号首批收三个：run 失败率 · 同形错误去抖 · MCP 持续 failing |
| ② | **A** | **第三个独立箱**（沿"两箱不混"既有裁决，Diagnostics 里加一节） |
| ③ | 见 §3.1 | 预算数值 —— 用户"按你建议"，但**推导推翻了我建议的数字**，见下 |
| ④ | **A** | GitHub **只搜 issues/discussions，不搜代码** |

### ①：三个信号，各自的"可修性预判"是规则不是模型

三个信号共用一条硬规矩（§1 DETECT）：**零 LLM、零网络**，纯 SQL/计数。
它们的差别在**去抖形状**，实现轮不许合并成一个阈值：

| 信号 | 去抖 | 为什么不能只用"次数" |
|---|---|---|
| run 失败率 | 比率 + 最小样本量 | 1/1 失败是 100%，样本量闸是唯一拦得住它的东西 |
| 同形错误 | **同形状**重复 N 次（单次不触发） | 形状相同才说明是系统性的；N 次不同错误只说明今天不顺 |
| MCP failing | **持续**时长 | 一次探测失败可能是网络抖动，时间窗口才区分得开 |

### ②：为什么是第三个箱，不是并进进化收件箱

沿用户既有裁决"两箱不混"。语义不同：进化箱是"**要不要换这个 prompt**"，
本箱是"**系统有病，这是证据**"。混在一起，用户对两种东西的 accept 会变成同一个动作 —— 而它们的
**风险面完全不同**：进化 accept 改的是分身行为，本箱 accept 只能开设置页/跳文档/触发封闭注册表内既有操作（§1 APPROVE）。

### ④：只搜 issues 的真实理由 —— 不是"面窄"，是**证据类型不同**

issues/discussions 是**别人也遇到过**的记录，天然带上下文（复现步骤、维护者回复、是否已修）。
代码搜索返回的是**看起来像方案的片段**，而"看起来像"正是供应链红线要防的那一半。
🔴 与 [[供应链红线]] 的关系要在实现轮写死：**检索面收窄不等于有了执行面**。
issues-only 仍然只是**链接进提案**，人读、人选；诊断执行器模块**不可 import `skill_import`**（§1 PROPOSE 已列）。

### 3.1 ③ 预算：我建议的数字站不住，推导在此

我原话是"抓取沿用 50/attempt，理由按 FU-2b 的推导方式算，不拍脑袋"。
真去推，**那个数字是错的，而且是"只搬数字不搬理由"这一类错**：

`HERMETIC_FETCH_BUDGET = 50` 比 live 的 `LIVE_FETCH_BUDGET = 25` **更大**，
理由写在它自己的注释里（`tool_loop.py:309-317`）：它要罩住
`pairs × 2 arms × (epochs*lr_budget + 1)` —— **一次 attempt 几百次派发**。
> 「25 × 224 不是上限，是个带标签的乘数。」

⇒ **50 不是"宽松度"，是一个极长 attempt 的总额。**
本循环是 **≤6 次派发的 live 路径**（真的出网抓 GitHub）。把 50 搬过来，
等于给每次派发 8 倍于 live 路径的抓取额度，**而理由那一半留在原地没跟过来**。

（数值与推导以对抗核验结果为准，见本节末的核验记录。）

## 4. 验收（写死，实现轮照抄）

**原有四条（不变）**
- 检测零 LLM/零网络有测试（探针：patch 掉 LLM/httpx，检测照常跑）。
  🔴 探针必须**先证明自己能失败**（v0.1.12 干净 runner 先例：先断言"这台机器没有可借的东西"，再作能力声明）。
- 诊断超预算必到终态"放弃+原因"，mutation：删终态逻辑必红。
- 提案箱 accept 不可达任何安装通路（扩展 supply-chain 守卫）。
- 每条提案带 ≥1 个 run id 证据，空证据提案被服务端拒。

**裁决带来的新增四条**
- **①** 三个信号**各自**有去抖测试，且断言要能区分去抖形状：
  给"1 次失败 / 1 次样本"必须**不**触发（比率闸靠样本量拦），给"N 次不同形状错误"必须**不**触发
  （同形闸靠形状拦）。只断言"触发了"的测试对这三条无区分力。
- **②** 第三个箱与进化收件箱**互不串**：断言本箱的 accept 动作集合是**封闭枚举**
  （开设置页 / 跳文档 / 触发注册表内既有操作），且**不含**进化箱的 promote 路径。
- **④** 检索面 issues-only 是**服务端强制**，不是 prompt 里请求：
  断言代码搜索端点不可达（照 `test_capability_supply_chain.py` 的写法），
  mutation：放开代码搜索必红。
- **③** 预算是**派发前**拒绝，不是跑完再算（照 `evolution_watcher` 的 fail-closed 形状）。
  mutation：把闸从"派发前"挪到"派发后"必红 —— 那个 mutation 抓的正是"闸存在但不生效"。
