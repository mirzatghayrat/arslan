01 / プロジェクト概要自然言語を、実際の仕事につなげる

Arslan は、Mac を主な対象とする、ローカルファーストのオープンソース個人用 AI アシスタントです。ユーザーが取り組みたい仕事を伝えると、Arslan がコンテキストを整理し、モデルを呼び出し、ツールを使い、実行過程を記録して、確認できる回答やファイルを届けます。チャット、記憶、ファイル処理、ターミナル、Web、一部のネイティブアプリ操作、バックグラウンドタスクを、一つの作業窓口にまとめています。

作者が AI の支援を受け、いわゆる vibe coding によって、単独で開発と改良を続けているプロジェクトです。本書では、製品の目標から実際のコードの適用範囲までをたどり、設計の理由、動作の仕組み、初期のプロトタイプから v0.1.56 までの変化を紹介します。

タスクを理解する

今回の依頼、最近の会話、使用を許可された個人の記憶、関連資料を合わせて、次に必要な情報とツールを判断します。

実行して結果を観察する

モデルが構造化されたアクションを提案し、コードが引数と権限を検証します。ツールが実際の結果を返し、モデルは続行するか、方法を変えるか、完了するかを判断します。

確認できる成果を届ける

ファイル、ツールの返却値、タスクの状態、出典が、成果の根拠になります。ユーザーは進捗の確認、承認、タスクの停止、既存の記録からの作業再開ができます。

「ローカルファースト」が意味すること

ローカルファーストとは、データの主な保存先と処理の実行場所を指します。デスクトップ UI、ローカルサービス、データベース、ワークスペース、Mac 向けツールは、主にユーザーのマシンで動作します。モデルはユーザーが設定します。クラウドモデルを使う場合、リクエストに含まれる会話、資料の抜粋、使用を許可された記憶は、該当するモデル提供者に送信されます。互換性のあるローカルモデルのエンドポイントにも接続できますが、ツール呼び出しや画像認識の能力は、モデルとサービスの実装に依存します。

そのため、Arslan のアーキテクチャでは、どのマシンで作業が行われ、どの内容がどのモデルのエンドポイントに送られるかという二つの問いに答える必要があります。ローカルデータの永続化、クラウドへの記憶の送信許可、ツールの権限はそれぞれ別の役割を担っており、一つの「ローカル」設定では表せません。

02 / 個人開発とオープンソースAI とともに、一人でアプリをシステムへ育てる

Arslan は、私が AI の支援を受けて単独で開発したプロジェクトです。いわゆる vibe coding にあたります。最初のプロトタイプからその後の各バージョンまで、一貫して私一人で開発を進めてきました。

ここでいう「個人開発」とは、プロジェクト全体を作者が単独で進めており、AI が実装過程の協働ツールであるという意味です。同時に Arslan は、オープンソースのフレームワーク、システム API、外部モデル、サードパーティのコンポーネントを基盤としています。開発方法、プロジェクトの責任、コンポーネントの出所は、それぞれ別の意味を持ちます。以下では、最終的に製品に組み込まれた設計と実装について説明します。

コードの生成から、使える製品の保守へ

コードが動くことは、製品に必要なことのごく一部です。デスクトップアプリでは、サービスの起動方法、ウィンドウの接続方法、古いデータベースの移行方法、プロセス終了後の後処理、システム権限を持つ主体、開発環境のないマシンで配布パッケージが動くかどうかも解決しなければなりません。Agent にはさらに不確実性があります。モデルのタイムアウト、ツール引数の欠落、Web ページの読み取り不足が起こり得ますし、実行の途中でユーザーの承認が必要になることもあります。

こうした課題を受け、Arslan の改良は次第に四つの方向へ進みました。明示的な契約で入力と状態を制約すること、観察可能なツール結果で完了状況を照合すること、権限の境界で実際の副作用を制御すること、そしてテストとリリース時の受け入れ確認で変更の妥当性を確かめることです。AI の支援は実装や原因調査を速められますが、最終的な製品の提供には、これらの制約がそろっている必要があります。

初期の前提を捨てる判断

初期は専門家の分身を中心に機能を組み立てていましたが、後に一つの Arslan へ統合しました。ツールや手順は再利用しながら、ユーザーの入口と主要な実行経路を、実際に生じた課題に合わせて設計し直しています。

改善しなかった結果も残す

レビュー層、経験学習、並列処理を追加しても、必ずしもタスクの結果は改善しません。プロジェクトでは、レビューの失敗、調査タスクでの劣後、学習後も高速化しなかった結果を記録し、次の修正につながる具体的な手がかりとしています。

Python の実行コアを維持する理由

Python はモデル適応、文書処理、Agent ループ、タスクサービスを担当し、既存のエコシステムと実装をそのまま活かせます。Tauri と Rust は、ウィンドウ、プロセスのライフサイクル、ネイティブ連携を担当します。この実行コアを維持する判断は、公開されているアーキテクチャ決定記録に残っています。コアを別の言語へ移行すると、ツール、データ移行、パッケージング、テストの境界が同時に変わるため、「よりネイティブになる」という理由だけでは利点を判断できません。

論理的には層を分けていますが、配備形態は引き続きローカルサービスが中心です。内部の Python モジュールをそれぞれリモートのマイクロサービスにしているわけではなく、動作に Redis、Celery、Kubernetes も必要ありません。Hands、Bridge、MCP サービス、ターミナルの子プロセスは、独立した権限や実行環境が必要な箇所でプロセスの境界を設けています。

固定された依存関係：フロントエンドのロックファイル；デスクトップのロックファイル；Python のロックファイル。設計と帰属：実行コアに関する決定；サードパーティの帰属。

04 / これまでの歩み専門家を生成する仕組みから、仕事を続けられる一つの Arslan へ

Arslan は、作者が AI を活用した vibe coding により、単独で開発を続けているプロジェクトです。その歩みには新機能の追加だけでなく、設計の撤回もあります。実行条件を整える必要がある機能もあれば、複雑さを取り除くべき部分もありました。過去の機能をすべて並べるより、こうした変化を理解するほうが、現在のアーキテクチャをよく説明できます。

この年表には、根拠から確認できる範囲があります。初期の日付は残存する Git コミット、正式バージョンの日付は公開 Release に基づき、すべて北京時間に換算しています。最初のコミット、オープンソース化の準備、リポジトリの公開、初回リリースは、それぞれ別の時点です。現在の記録からは、リポジトリを Public に切り替えた正確な日付は確定できません。現在の公開リポジトリは 2026 年 7 月 26 日に作成されました。

6 月：まず「会話を通じて Agent を生成する」一連の流れを作る

現存する最初のコミットは 2026 年 6 月 7 日のデータモデルです。当時の方向性は Meta-Agent でした。技術に詳しくないユーザーが会話を通じて分野ごとの専門家を作り、その専門家がタスクを遂行するという構想です。その後、モデルアダプター、ツールレジストリ、要件を聞き取る会話の状態機械、テンプレート、Spawn Manager、CLI が加わりました。6 月 8 日には、FastAPI、非同期データベース、認証、WebSocket、React UI が接続され、操作、保存、再接続ができるプロトタイプになりました。

05 / システムアーキテクチャUI、実行、権限は、それぞれ何を担うのか

分かりやすく説明すると、React はユーザーの作業画面、Tauri は macOS とつなぐシェル、Python は仕事を調整するエンジンです。モデルが判断し、ツールが実際に動作し、データベースとディスクが過程と結果を保存します。これらの役割は一つのデスクトップ製品にまとまっていますが、同じプロセスで動くわけではありません。

図 1 · 現在のアーキテクチャ。テキストで表すと、UI ↔ ローカルサービス → 統一 Agent ループ ↔ モデル、実行ループ → ツール → システム／ファイルとなり、状態は SQLite とディスクに保存されます。iPhone は CloudKit を通じて Mac Bridge と通信し、Mac の公開インターネット向け API に直接接続するわけではありません。

起動時にプロセスを接続する仕組み

  1. Tauri が実行ファイル化された Python sidecar を起動し、サービスの準備ができるまで起動画面を表示します。
  2. sidecar はローカルポート 47317へのバインドを優先し、競合時には一時ポートを使います。その後、標準出力で ARSLAN_PORT を返してハンドシェイクします。
  3. デスクトップシェルがポートを受け取ると、システム WebView に、ローカルサービスが提供する React ページを読み込ませます。固定ポートを優先することで、WebKit origin と UI のローカルストレージを安定させます。サーバー側の会話ディレクトリにより、ポートが変わっても履歴を再び見つけられます。
  4. UI は HTTP でリソースを管理し、WebSocket でテキストストリーム、ツール状態、承認、タスクの進捗を受け取ります。ローカル接続でも token と接続元の検証は必要です。
  5. シェルは、ライフサイクルを連動させるために標準入力パイプを保持します。親プロセスの終了で EOF が生じると、sidecar は後処理をして終了できます。出力パイプも継続的に読み取り、ブロックや、接続断後に孤児プロセスが残ることを防ぐ必要があります。

これらの仕組みにより、ウィンドウ、サービス、データベースのライフサイクルを整合させます。HTTP health の成功だけでは、WebSocket、添付ファイル、静的リソース、ネイティブ helper がすべて使えるとは確認できません。リリース時の受け入れ確認では、それぞれ個別に検査します。

06 / 実行ランタイム一つの依頼に、過程と境界と結果を持たせる

Arslan の実行コアは、ユーザーの意図を観察可能な一連の動作へ変えます。コンテキストを準備し、モデルを呼び出し、ツールの要求を検証し、許可された操作を実行し、実際の結果を読んで、続行するか成果を届けるかを判断します。v0.1.56 の既定の入口は統一ループで、EXPERTS_ENABLED=Falseです。メッセージは直接回答処理に入り、長期的な事実の抽出は回答後に行います。過去の専門家システムの互換コードは残っていますが、現在の主要経路では、最初にモデルによるルーティングを行いません。

図 2 · 実行の循環。テキストで表すと、入力 → コンテキスト → モデル → 引数検証 → 許可 → ツール実行 → 結果の返却を繰り返します。モデルが直接回答することもあります。回答と成果物は確認してから届けるか、未完了であることを正確に説明します。禁止や拒否をモデルの意向で上書きすることはできません。

モデルは次の一手を提案し、ランタイムは実行条件を管理する

モデルに見えるツールは、名前、用途、引数 schema の集合です。モデルが構造化された tool_calls を返すと、ランタイムはまず JSON を解析し、引数を検証します。そのうえで、ツールが引き続き利用可能か、現在の予算で実行できるか、ユーザーの許可が必要かを再確認します。組み込みツールはレジストリによって実行関数に対応付けられ、mcp_ で始まるツールは MCP 呼び出しへ渡されます。レジストリに登録されていても、毎回の会話でそのツールが開放されるとは限りません。

重要な境界の一つは応答の完全性です。提供者側の出力長制限でツール呼び出しが途切れた場合、そのバッチは、個々の呼び出しが完結して見えても実行しません。ツール呼び出しを含むモデルの文章は過程の説明としてのみ扱い、最終成果として先に提示することはできません。実行の前後でチェックポイントを記録し、実際のツール結果を、対応する呼び出しの識別情報とともにモデルへ返します。Web ページ、ファイル、外部ツールからの内容は、引き続きデータとして扱います。

したがって、「ファイルを保存しました」という説明には、実際の保存結果と成果物の参照が対応している必要があります。自然言語で約束しただけでは、操作が実行済みになったことにはなりません。ツールの失敗も次の入力に含まれ、ループは経路を調整できますが、同じ権限と予算を引き続き守る必要があります。

「指定したディレクトリを読み、一覧を作成する」例では、まずディレクトリのパスがタスクの入力範囲に入ります。モデルが読み取りを要求し、ツールが実際のファイル情報を返して初めて、一覧を作る根拠が得られます。さらにファイルの移動や削除を求められた場合、ランタイムはその操作に応じて許可を判断します。最終的には、生成済みのファイルを示し、確認結果を説明する必要があります。この過程におけるファイル一覧、操作の応答記録、成果物の参照は、それぞれ異なる証拠の役割を担います。

入口を統一しながら、モデルのプロトコルの違いを保つ

LLMAdapter が統一された呼び出しインターフェースを提供し、各 Provider がリクエスト形式、ストリーミングイベント、ツール呼び出し、usage を扱います。Provider の実装は httpx で HTTP リクエストを送信します。OpenAI 互換エンドポイントにはローカルモデルサービスも設定できます。クラウドモデルを選んだ場合、対応するリクエストのコンテキストは、ユーザーが設定した提供者へ送られます。

一時的な協働 worker とバックグラウンドタスクの役割

delegate_work は、独立した調査を一時的な worker に分担させます。一度に最大 4 件、同時に実行できるのは最大 2 件です。現在、worker に開放しているのは web_search と web_extractだけです。ファイルや個人の記憶への書き込み、再帰的な再委任はできません。主担当が資料を受け取り、照合と統合を行います。この設計は、並列調査の利点を保ちつつ、実行の責任を元のタスクに集約します。

一方、バックグラウンド job は、時間のかかるタスク全体を扱います。独立したコンテキストと予算を持ち、ツールループ、成果物の検査、修正処理を再利用します。進捗はタスクカードを通じて会話に返され、既定では最大 3 件を同時実行します。ネットワーク接続、チャットウィンドウ、バックグラウンド実行はそれぞれ独自のライフサイクルを持つため、会話の切り替えはタスクのキャンセルを意味しません。マシンがスリープしたりプロセスが終了したりしても、バックグラウンド作業がクラウドに引き継がれるわけではありません。

強制上限に達する前に、成果をまとめる

予算では、モデルリクエスト数、ツール呼び出し数、累計 token、実行時間を計測します。soft limit に達したら調査範囲の拡大を止め、既存の成果をまとめる必要があります。hard limit は、消費が際限なく続くことを防ぎます。入れ子の実行と再試行もタスク予算に計上します。また、進展のない繰り返し呼び出しを別途検出し、失敗した同じ経路を何度も試すことを避けます。

タスク、実行の試み、受け入れ判定を別々に記録する

TaskSpec は、指示、入力、範囲、受け入れ項目、予算といったタスクの合意条件を、改訂番号とともに保存します。一つの task に複数の attempt があり、attempt は具体的な一回の実行の試みです。条件の変更、取消後に届く古い結果、再開後の新しい試みの状態を混在させてはいけません。永続化の更新時には attempt の識別情報と row version の両方を確認し、古い実行が新しい状態を上書きすることを防ぎます。

状態意味

受け入れ結果は、合格、失敗、未実施、該当なしなどを区別します。判定には対応する証拠が必要であり、約束した検査を省いたり、すべてをモデルの自己評価だけに頼ったりすることはできません。ファイルの存在、所属タスク、ダイジェストなどは決定論的に検証でき、主観的な品質についてモデルや人の評価を補助的に使います。準備中、実行中、効果不明の操作が残っている場合には、リポジトリ層でもタスクが直接成功状態になることを防ぎます。

タスクの改訂を識別する必要があるのもこのためです。古い要件に対する結果は、新しい要件が満たされた証拠にはなりません。受け入れ確認は、同じ版の合意条件、有効な同一の実行の試み、そのタスクに属する証拠に対応させます。重要な検査を任意に「該当なし」にすることはできず、契約ルールに合う重要度の低い項目に限って、その扱いが可能です。証拠が不足している場合は、未検証または未完了の状態を維持し、追加の確認を待ちます。

既存の証拠から安全に再開する

チェックポイントは、進捗、使用済み予算、証拠、成果物の参照を保存し、実行イベントは UI の再接続後に確認できます。プロセス内の run registry は、実際の非同期タスクとキャンセルの入口を保持し、接続中のウィンドウにイベントを配信します。再接続時にはスナップショットの取得とイベントストリームへの接続を一体で行い、接続の引き継ぎ時にイベントが欠落したり重複したりすることを減らします。

プロセス再起動後、終了していない実行は中断として識別され、ユーザーが明示的に続行します。外部へ送信済みでも応答を受け取れていない操作は、効果が不明です。直接再送せず、先に照合する必要があります。バックアップからの復元では、古い操作許可を失効させ、関連する操作を不確定として記録します。チェックポイントが解決するのは「どこから安全に続けられるか」であり、すでに生じた外部の結果を取り消すものではありません。

停止にも二つの層があります。実行レジストリは待機中または実行中の非同期処理をキャンセルし、永続化された状態は遅れて届く結果の反映を阻止します。外部システムがすでに受け付けた要求について、ローカルの待機をキャンセルしても、相手側が未実行であるとは証明できません。そのため、操作テーブルでは、準備中、開始済み、確認済み、失敗、効果不明、キャンセル済みなどの状態を区別します。復旧処理はまずそれらを確認し、どの手順を再試行できるかを判断します。

ソース：タスクと受け入れ確認の契約；永続化された状態と並行更新の検査；成果物の検証；実行と明示的な続行；接続と実行の分離；バックアップ復元の境界。

プロジェクト：ボード、レベル、証拠を必要とするチェックポイント

0.1.56 以降、プロジェクトはレベルの計画を持ちます。各レベルには明確な達成条件と、いくつかのチェックポイントがあります。種類（ゲーム、アプリ、ウェブサイト、リサーチ、執筆、動画、スキル、旅行、仕事、その他）を選ぶと、モデルを呼び出さずにテンプレートからレベルの下書きが作られます。「Let Arslan refine」を使うと、ユーザー自身のモデルを 1 回だけ呼び出し、ゴールに合わせてレベルを調整します。ユーザーがプロジェクトを作成するまで、何も保存されません。ボードの列（Idea、Shaping、Doing、Done）は現在のレベルから導かれるもので、ドラッグで動かすことはありません。Done と Dropped を設定できるのはユーザーだけです。

Arslan が計画を進めるのは、示せる証拠があるときだけで、対象も現在のレベルに限られます。ファイルを指定したチェックポイントは、そのファイルがプロジェクトフォルダーに現れた時点でチェックが付きます。ユーザー自身の発言の後には、判定役（judge）がそのメッセージが何かの完了を伝えているかを確かめます。プロジェクトの引き継ぎから始めたバックグラウンドジョブは、完了状態で終わったときに対応するチェックポイントにチェックを付けます。小さなチェックは取り消せます。レベルのクリアはカード上の提案として示され、通知や Inbox の項目にはなりません。Arslan が自分でレベルを進めてよいか一度だけ尋ねるのは、10 回続けて推測が正しかった後に限られます。学習した計画のルール、ユーザーのペース、「停滞」のヒントはローカルにとどまり、モデルに届くのはユーザーが自分で始めた下書き作成の要求の中だけです。

ソース：レベル、ボード、提案；ファイル、ユーザーの発言、実行；レベルのテンプレート；計画のルール、ペース、停滞。

07 / データと記憶役立つコンテキストを残し、データの境界も明確にする

Arslan は、主な状態をマシン上の SQLite に保存します。会話、実行記録、タスク、個人の記憶、モデル設定、使用量には、それぞれ対応するデータモデルがあります。ファイルの成果物はディスクに書き込みます。非常に長いツール出力の全文はアプリのデータフォルダーに別途保存され（保持期間は 7 日間）、モデルは結果に示されたパスから分割して読み取ります。そのため、ウィンドウを閉じてもタスクの過程は消えず、「そのとき何を話したか」「実際に何をしたか」「今後何を覚えてよいか」を別々に管理できます。

データへのアクセスには、非同期 SQLAlchemy と aiosqliteを使います。接続では WAL、外部キー検査、5 秒のビジータイムアウトを有効にし、 synchronous=NORMALを設定しています。これらはローカルの単一ユーザー向けアプリに合わせた選択で、配備時の依存を減らし、読み書きが並行する場合の使い勝手を改善します。データディレクトリには協調型のプロセスロックも設け、同じプロトコルを守るインスタンスが同じデータを同時に使うことを防ぎます。

作業用コンテキスト：今回の入力を制御し、元の履歴を残す

モデルが一度に受け取れる量には限りがあるため、Arslan は長さに上限のある逐次更新の要約と最近のメッセージで、作業用コンテキストを構成します。この履歴ウィンドウの既定の推定予算は 3,000 token で、要約そのものにも長さの制限があります。これは履歴を組み立てるための予算であり、モデルリクエスト全体が 3,000 token という意味ではありません。システム指示、ツール schema、資料、結果も別の領域を使います。

会話が長くなると、古いメッセージは要約にまとめ、最近のメッセージは原文を保てます。圧縮が変えるのは次回の入力に含める内容であり、データベース内の完全な会話を削除するわけではありません。圧縮に失敗しても元の記録は残ります。長すぎるツール出力には、別途ディスクへ保存する仕組みがあります。モデルには先頭と末尾の抜粋とファイルパスを渡し、必要に応じて分割して読み取ります。完全な出力は保持ポリシーに従って削除します。

この層構造により、モデルには現在のタスクに必要な情報を優先して見せながら、後の照合に使う元の根拠を残せます。要約は既存の内容を圧縮した表現にすぎず、外部操作の実際の応答記録の代わりにはなりません。

個人の記憶：関連性より先に、利用できるかを判断する

記憶の項目には、種類、範囲、機密度、利用ポリシー、状態、信頼度に関する情報、改訂番号を持たせます。範囲はグローバルまたは特定のプロジェクトで（ほかにドメインや専門家などの内部的な範囲もあります）、各項目には所有者もあります。local_only などの利用ポリシーが、クラウドモデルへの要求に含めてよいかをさらに決定します。各ターンの信頼できるコンテキストは、データベースから会話設定を読み込みます。通常のユーザーテキスト、Web ページ、モデル出力が、これらの権限を勝手に書き換えることはできません。

資料検索：キーワードとベクトルを組み合わせる

知識資料の検索モジュールは、SQLite FTS5 の全文検索と、ベクトルのコサイン類似度検索に対応しています。前者は語句の一致を、後者は embedding を使って意味の近い断片を探します。両方を利用できる場合は、RRF で順位を統合します。RRF が比べるのは順位であり、尺度の異なる生のスコアを直接混ぜません。embedding が未設定、またはベクトルがない場合も、全文検索を利用できます。

検索された断片は出典とともにモデルのコンテキストに入り、モデルが現在の質問と合わせて回答を組み立てます。ここでいう RAG は、この仕組みを指します。記憶 v2 が有効な場合、資料の検索は資料コレクションが紐付けられたプロジェクトでのみ行われます。クラウドモデルを使う場合は、その会話自体のクラウド記憶の許可も有効である必要があります（既定の「Remember me」スイッチは資料を対象にしません）。結果は recall ツールの戻り値としてコンテキストに入ります。基盤モデルの重みを変更する必要はなく、別途配備したベクトルデータベースにも依存しません。個人の記憶 v2 の選択には、主に権限による絞り込み、全文検索、ローカルの関連性ロジックを使います。すべての記憶が同じベクトル処理を通ると解釈することはできません。

経験からの学習：訂正を、レビューできるルールにする

Lesson は、ユーザーの訂正、失敗の後に成功した回避策、マシン環境の特徴を保存します。たとえば、現在の Mac であるコマンドに別の引数が必要なら、出所のある経験として残し、類似タスクの参考にできます。呼び出すのは最大 5 件、合計約 800 文字で、動的な agent status に入れ、固定のシステムプレフィックスには混ぜません。呼び出し、遵守、成功、失敗をそれぞれ計数します。

保存する価値があるか、既存の内容と重複または矛盾するかについては、judgment 層が狭い範囲の判断を提示し、確率と後の結果を記録できます。ユーザーの訂正や、外部コンテンツの影響を受けていない経験は、設定で許可され、有用と判断されれば直接有効にできます。その他のレビューが必要な内容は提案へ送ります。認証情報を含む候補はその場で破棄されます。「推測された機微情報はレビューが必要」というルールは個人の記憶に適用されるもので、経験には適用されません。判断が得られない場合やタイムアウト時には、フォールバック経路があります。

0.1.55 以降、訂正として扱われるのは、会話の中で Arslan が以前に行ったことへの応答だけです。最初のメッセージは依頼であり、訂正にはなりません。同じターンでうまくいったばかりの経路に反する訂正は、すぐには有効にならず、ユーザーの承認を待つ提案になります。また、macOS が権限を拒否した場合のように、ユーザー自身が直す必要のある失敗を、別の経路を取る理由として学習することはありません。Arslan が会話中に記憶を保存したときは、そのことをスレッド内に表示し、Undo で取り消せるようにします。

これらの仕組みは、アプリが保存して呼び出す知識を変更するもので、モデルの重みを学習するものではありません。judgment の有効範囲も用途ごとに異なります。たとえば、ツール承認の判断が shadow モードのときは提案を記録するだけで、実行の可否は引き続き本来の許可フローが決めます。

ソース：資料のハイブリッド検索；経験の抽出と呼び出し；小規模な判断と実行モード。

削除を、要約と古いバックアップにも反映する

記憶を削除すると、システムは deletion epoch を進め、その項目の古い改訂の本文と出所を消去し、すべての会話の逐次要約と、実行記録にキャッシュされたプロンプトを消去します。これにより、古い派生コンテンツが削除済みの記憶を呼び戻すことはありません。削除記録には照合用のコンテンツ指紋（ローカル鍵による HMAC）と範囲などのメタデータだけを残し、削除済みの本文を台帳に再保存することを避けます。suppression 記録は、チャット履歴に残る同じ出所から記憶が再び自動生成されるのを防ぎます。記憶の削除と元の会話の削除は、別々のデータ操作です。

独立した削除台帳と削除マニフェストにより、起動時と復元時にも削除を引き続き適用します。古いバックアップを復元する前には、ストレージの識別情報を検証し、データを有効にする前に、削除情報と照合して一時領域のデータを整理します。これにより、古いバックアップから削除済みの記憶が戻る可能性を抑えます。この保証は復元手順と利用可能な削除記録に依存し、外部に出力済みのすべてのコピーを取り消せるという意味ではありません。

バックアップ内の他の記憶も、すべての利用許可がすぐに復元されるわけではありません。復元処理はそれらをレビュー待ちとして隔離し、利用ポリシーを厳しくし、キャッシュされたコンテキストを消去し、すべての定期タスクを無効にし、会話単位のクラウド利用と機微情報の許可を取り消し、進行中のプロジェクトをアーカイブします。データの復元と利用の再承認を分けることで、古い会話の許可が新しい実行環境で知らないうちに有効になることを防ぎます。

移行を完了してから、アプリがデータを使い始める

現在のデータベース更新は、明示的な移行 runner を使います。schema のバージョン検査、更新前バックアップの準備、不足するテーブルの作成、未実行の移行の順次実行を行い、その後に鍵の互換性処理と記憶 v2 の有効化を行います。不明な schema や新しすぎる schema は拒否し、古いプログラムが新しいデータを不用意に変更することを防ぎます。v0.1.56 の明示的な登録は 0063まで進んでいます。初期の Alembic の履歴を、現在の実行方式と混同しないでください。

記憶 v2 の有効化では、旧来の事実テーブルと学習テーブルを legacy テーブルに改名し、読み取り専用のトリガーを追加します。互換ビューが旧来の読み取り口を新構造に対応付け、全文インデックスもこの過程で作成します。モデルの API キー、MCP の環境変数と OAuth トークン、SSH 鍵などの秘密フィールドには、フィールド単位の Fernet 暗号化（PBKDF2 とインストールごとに独立した salt）を使いますが、通常の会話やタスクのテーブルまで含めたデータベース全体の暗号化ではありません。永続化、秘密情報の保護、バックアップからの復元には、それぞれ固有の境界があります。

08 / ツール、Skill、拡張機能機能を再利用し、実行の境界を保つ

Arslan は、「何ができるか」と「どう行うか」を分けて構成しています。ツールは実際の操作、Skill は手順と参考資料、MCP は外部機能との接続を担い、プラグインのマニフェストがそれらを組み合わせます。モデルが受け取るのは、そのターンで利用できる機能の集合です。ソースのレジストリにツールが存在しても、既定で有効であることや、実行が許可済みであることを意味しません。

拡張サービスは、新たな信頼境界になる

ローカルの stdio MCP は通常、独立したプロセスの起動を伴い、HTTP MCP はリモートサービスへ接続する場合があります。Arslan は、接続、主アシスタントからの利用可否、ツールの公開、認証情報の保存と表示をそれぞれ管理します。プラグインのマニフェストで宣言する HTTP MCP サービスの URL は、HTTPS が必須です。secret スロットはパラメーターの形式を宣言し、実際の認証情報をマニフェストに埋め込みません。設定済みの環境値は暗号化して保存し、読み出して表示するときはマスクします。

これらの制約は、意図しない露出や誤実行の機会を減らしますが、実際の MCP サービスは、与えられたリソースにアクセスし得ます。ツールの出所、必要な権限、リモートへ送られるデータ、操作の副作用は、いずれも拡張機能として説明すべき事項です。

並列調査を残している理由

統一 Agent ループには、制限付きの一時的な読み取り専用 workers が残っています。v0.1.56 では一度に最大 4 件、同時に最大 2 件を実行できます。ツールは検索と Web ページ抽出に限られ、ファイルや個人の記憶へ書き込まず、再帰的に workers を増やすこともできません。主アシスタントが結果を確認して統合します。

この委任は、互いに独立した資料調査を分割するのに適しています。初期の恒久的な専門家の分身とはライフサイクルが異なり、ユーザーが先に専門家チームを選んだり管理したりする必要はありません。また、すべてのメッセージを別の「専門家」に強制的に振り分けるものでもありません。並列化するかどうかは、タスクを有効に分割できるかと、追加の呼び出し費用によって判断します。

バックグラウンド、定期実行、heartbeat

バックグラウンド job は、時間のかかる実行を現在のチャットから切り離し、同じモデル、ツール、受け入れ確認のロジックを再利用します。定期タスクは「いつ開始するか」を永続化します。heartbeat はチェックリストを定期的に確認する用途の一つで、既定では無効であり、確認と提案を担当します。定刻に起動したからといって、提案が承認済みの書き込みやコマンドになるわけではありません。

現在のスケジューリングはローカルサービスが担い、重複実行のスキップ、失敗時の一時停止、再起動時の整理などを処理します。逃した実行回は一つずつ補完せず、同じタスクの前回分が終わっていないときは次の回を重ねて開始しません。個人向けデスクトップアプリに適した動作である一方、常時オンラインのサーバーとは実行条件が異なります。

承認は具体的な操作に紐づけ、バックグラウンドにはすべての便宜的な許可を引き継がない

承認カードは、 call_id と操作の種類に紐づき、種類が異なる返答で別のカードを承認することはできません。Mac のウィンドウとスマートフォンに同時に表示されるカードは、最初の有効な回答を採用し、他の画面へ終了を通知します。回答がなければ 300 秒で期限切れになります。バックグラウンドタスクは、接続のセッション許可を引き継がず、「このコマンドを記憶する」機能も提供しません。0.1.54 以降は、チャットウィンドウの「この会話の残りはサンドボックス外で実行する」もこれに含まれます。ウィンドウで何が許可されていても、バックグラウンドタスクのコマンドはサンドボックス内から始まります。モデルが MCP への接続、リモートマシンの登録、他の実行経路へのアクセスを提案した場合も、提案と実際の接続の有効化は分けて扱います。

外部への副作用についても、要求を送信しただけでは操作の完了にはなりません。タスクの復元時には、結果の分からない実行中の操作を不確定とし、プロセスを再起動したというだけで自動的に再実行しません。ここでの目標は、再試行と復旧の意味を明確にすることであり、任意の外部システムで取り消しができると約束することではありません。

0.1.55 以降、ウィンドウ、バックグラウンドタスク、iPhone のいずれから来た待機中のカードも、すべて一つのキューと Inbox に並び、そこから call_id で回答できます。返答はカード自身の種類から組み立てられるため、そのカードの承認か取り消ししかできず、「これを記憶する」はカード上でしか選べません。Island からも回答できますが、削除、送信、公開、支払い、別のマシンへの到達を伴う手順は除きます。具体的には、削除や送信を行う AppleScript、それらのルールまたは Hermes の危険ルールに該当するターミナルコマンド、サンドボックス外やリモートホスト上の操作、そして検査が把握していない種類のカードです。これらには「Open in Arslan」が表示され、Island のページだけでなくサーバーも、Island からの承認を拒否します。ウィンドウでは ⌘⏎ で許可、Esc で拒否します。単独の ⏎ でカードに回答することはありません。

Inbox と Island からの回答；カードの関連付け、期限切れ、複数端末からの回答；復元時の不確定な副作用；接続の提案と許可の入口。

Hands は、より小さなプロセスにシステム権限を集約する

Accessibility 権限を与える先は、 Arslan Hands.appであり、メインアプリではありません。署名付きの配布版は、保護された Unix socket、起動ごとに生成する token、peer の署名検査を通じて要求を受け付けます。ルールは helper 自体が実行し、下層の agent-desktop が独立してその権限を持つわけではありません。読み取りは会話とアプリの組み合わせで承認します。操作はバックグラウンドタスク内だけで行い、タスクとアプリの組み合わせで承認します。削除、送信、支払い、購入、送金、送信確定などの機微なボタンは、実際のラベルに基づき毎回確認します。パスワードフィールドには入力せず、パスワードマネージャーやシステムのセキュリティ画面などは、禁止アプリの一覧に含めます。

停止操作は停止ラッチを設定し、後続の操作はその検査を通る必要があります。アクティビティ記録には操作の手がかりを残し、入力テキストは長さだけを記録します。制約も公開しています。見えるのは現在の Space のウィンドウに限られ、大きなウィンドウの読み取りには 10–20 秒かかる場合があります。Stop で中断した呼び出しには、対応する trace 行がないことがあり、監査記録はあらゆる中断について完全な証拠を保証するものではありません。

0.1.56 以降、Hands は各要求を最大 1 回だけ実行します。要求 ID に対する応答は 10 分間保持され、同じ ID が繰り返されたときはそこから応答します。バックエンドは、応答を受け取り損ねた場合、操作を再送するのではなく、その応答を取りに行きます。テキストを読み取れないフィールドへの追記は、内容を置き換えるのではなく拒否します。Return キーは、そのフィールドにフォーカスがあるときにだけ押します。送信したものの読み戻せなかった操作は、完了ではなく「sent, not confirmed」（送信済み・未確認）として報告します。

ローカルサービスにも境界があります。配布版では REST と WebSocket のアクセストークンを生成し、インストールの受け入れ確認で未認証の要求が拒否されることを検証します。token を表示する設定エンドポイントは、すでにその token を提示している直接のループバック呼び出し元にだけ token を渡します（0.1.54）。サンドボックス内のコマンドもループバックのソケットを開けるため、ループバックからの接続であることだけでは不十分です。ソースからの開発モードでは、便宜のため localhost から token なしで使える経路を許可しています。「ローカルでのみ待ち受ける」ことと「認証済みである」ことは同じではありません。現在のユーザーと同じ権限で動くホスト環境がすでに侵害されている場合も、ローカルの token 一つで自動的に信頼できる環境になるわけではありません。

QR コードの読み取りは、ペアリングの始まりにすぎない

QR コードには、一回限りの pairing_id、Mac の署名用・鍵交換用の公開鍵、32 バイトのペアリング鍵、固定のコンテナ識別子、有効期限が含まれます。有効期間は最大 600 秒です。スマートフォンは、期限切れ、誤ったコンテナ、制約に合わない内容を拒否し、QR コード内の Mac 公開鍵を固定します。その後、自身の識別用・鍵交換用の鍵を生成し、暗号化されたペアリング要求を送ります。Mac は要求を検証した後もユーザーに提示し、Mac 上でのクリックによって承認または拒否を決めます。

同じ要求の再試行には同じ決定を返し、二度目の許可を生じさせないようにします。承認後はデバイスの識別情報を使って通信し、ペアリングコードは使用済みになります。Mac からスマートフォンの登録を取り消すこともできます。同じ iPhone が再びペアリングするときは以前の ID を伝え、Mac はそれらの古い項目を 2 件並存させずに削除します。スマートフォンを削除すると、Mac がそのスマートフォン宛てに iCloud に残していたメッセージも削除されます。起動時にも Mac は、ペアリングが解除されたスマートフォンを待ち続けている記録を消去します。設定 › 接続 › iPhone では、各スマートフォンは Mac がそこから認証済みのメッセージを初めて読み取るまで Connecting… と表示され、その後は Connected と最終接続時刻が表示されます。各デバイスの秘密鍵は、それぞれの Keychain に保存します。信頼の根拠は、一回限りのペアリング情報とユーザー確認の組み合わせであり、「同じ iCloud アカウントだから、どのメッセージも信頼できる」というものではありません。

メッセージの内容、出所、コンテキストを同時に検証する

新しいメッセージごとに一時的な X25519 鍵で共有秘密を確立し、HKDF-SHA256 で 32 バイトの鍵を導出します。ChaCha20-Poly1305 で認証付き暗号化を行い、さらに Ed25519 で署名します。ヘッダーには長さで区切る UTF-8 フィールドを使い、言語間の JSON の並び順の違いが検証に影響しないようにします。ヘッダーフィールドは署名と AEAD 認証の両方に結び付けます。これは CryptoKit の暗号プリミティブを使ったアプリケーションプロトコルであり、Signal の Double Ratchet は実装していません。一時鍵を使うことだけをもって、あらゆる状況での前方秘匿性を主張することもできません。

受信時の順序は明確です。形式と受信者を確認し、署名を検証してから復号します。その後、平文とヘッダーの一致を確かめ、ファイルがある場合は添付も検証します。どの段階で失敗しても、業務上の処理が部分的に反映されてはいけません。ファイルの上限は 20 MiB で、暗号文のダイジェスト、認証タグ、平文のサイズとダイジェストがすべて一致して初めて、キャッシュやプレビューが可能になります。

12 / テストと検証タスクが正しくできたかをどう判断するか

タスクが終了したこと、ファイルを開けること、報告書の内容が正しいことは、三つの異なる判断です。Arslan は実行記録で起きたことを示し、成果物と契約の検査で確定できる部分を検証し、さらに実タスクの評価でモデルの働きを観察します。どの層で合格しても、他の層の代わりにはなりません。

本節は、公開ソース、リリースノート、過去の実験記録をまとめたものです。数値はそれぞれのバージョンと環境に対応しており、本書執筆時にすべてのテストを再実行したことや、全機能を実機と実モデルで受け入れ検証したことを意味しません。

まず「完了」を確認可能な証拠に分ける

実行されたか

ツール呼び出しは結果を返したか。終了コードは何か。操作結果は明確な成功、明確な失敗、それとも不明か。モデルが「完了しました」と書いてもツールの証拠の代わりにはなりません。結果不明の副作用を、安全にもう一度実行できるものとして扱うこともできません。

成果物として成立しているか

ファイルが存在し、このタスクに属し、バイト数とハッシュが一致し、形式を解析できるか。表計算ファイルを開けてもデータが正しいとは限らず、画像の寸法が正しくてもレイアウトが適切とは限りません。

タスクの要件を満たしたか

有効な結果を十件求められているなら、六件では要件を満たしていません。引用元は結論に対応している必要があり、Web ページを読んだことだけでは、そのページが主張を裏付ける証拠になりません。この層には、タスク固有の検証と人の判断が引き続き必要です。

タスクの受け入れでは、ルールによる検査、モデルによる評価、人による再確認を区別します。テキスト、JSON、ファイルの完全性、画像の寸法、実際の実行結果には決定的な検査を使えます。モデル評価は適した項目だけを判断し、実行していない検査を成功扱いに変えてはいけません。成果物を解析できることは構造が読める証拠であり、出典の読み取り記録はシステムが内容を取得した証拠です。どちらも、事実の正しさや視覚的な品質を自動的に証明するものではありません。

15 / よくある質問Arslan を使い、理解するうえで混同しやすいこと

モデルの Web サイトで直接チャットする場合と、Arslan はどう違いますか？

Arslan はモデルに加え、ローカルファイル、ツール、タスク状態、記憶、承認、デスクトップ連携を提供します。モデルが判断と生成を担い、アプリがツール要求を制御された実行につなげ、結果を記録します。価値があるかどうかは、この一連の仕組みで具体的なタスクを完了できるかにかかっています。

一人で AI を使って開発しているプロジェクトですか？

はい。作者が独立して、AI の支援を受ける開発、いわゆる vibe coding により、Arslan の構築と改善を継続しています。製品にはオープンソースのフレームワーク、第三者のコンポーネント、外部モデルを使用しており、それぞれの出典とライセンスはプロジェクトの文書に記録されています。

すべての内容が自分の端末内に留まりますか？

主なデータ保存と実行の制御はローカルで行います。クラウドモデル、検索、リモート MCP などを利用すると、関連するリクエストが各サービスに送信されます。記憶には、クラウドでの使用許可と機密性に関する独立したルールもあります。ローカル優先は、全工程がオフラインであることを意味しません。

モデルを変更したり、ローカルモデルを接続したりできますか？

対応するプロバイダーや互換エンドポイントを設定できます。OpenAI 互換のローカルサービスも含まれます。エンドポイントに接続できても、確認できるのは通信が成立することだけです。ツール呼び出し、画像、推論の継続、コンテキスト長は、そのモデルとアダプターの経路が対応している必要があります。

初期の文書には多数のエキスパートが登場するのに、今は Arslan が一つだけなのはなぜですか？

製品の仕組みを統一してきたためです。0.1.44 でエキスパートの作成と割り当てを終了し、0.1.46 で旧来の自動進化ループを停止、0.1.48 で前段のルーターを削除しました。以前の手法は Skill に変換でき、過去のデータとの互換性も維持しています。制限付きの読み取り専用ワーカーは、独立した調査に引き続き使われます。

記憶、ナレッジベース、チャット履歴は同じものですか？

異なります。チャット履歴は会話を記録し、作業コンテキストはそこから最近の内容や要約を選びます。個人の記憶は、出典と権限を伴う好み、事実、ルールを保存します。知識検索は、取り込んだ資料から関連する部分を探します。三者では、保存、想起、削除の意味がそれぞれ異なります。

「経験の学習」はモデルを訓練したり、自動で権限を増やしたりしますか？

しません。現在の学習は、再利用できる手法を記録して後のタスクで呼び出すもので、基盤モデルの重みや実行の許可を変更しません。経験を取得、想起、適用できることは記録で確認されていますが、一般的な高速化や費用削減には、さらに比較実験が必要です。

すべてのコマンドはネット接続のないサンドボックスで実行されますか？

いいえ。標準の Python 計算サンドボックスはネットワークを拒否しますが、通常のターミナルのワークスペースサンドボックスは、一般にネットワークアクセスを維持し、独自のフォールバック動作を持ちます。ツールの権限、コマンドのポリシー、OS の権限、サンドボックスは別の層です。具体的な違いはセキュリティの章を参照してください。

チャットのウィンドウを閉じると、タスクはどうなりますか？

接続とタスクは別々に管理されます。アプリのサービスが動いていれば、バックグラウンドジョブは実行を続けられます。ウィンドウを閉じることは、必ずしもプロセスの終了を意味しません。サービスが終了したり Mac がスリープしたりすると、ローカル実行は継続できません。再起動後は記録から中断状況を確認し、対応する経路で明示的に再開します。

再開すると、以前の操作をすべて自動でやり直しますか？

いいえ。再開時には完了済みの手順と外部への影響を調べ、副作用が不明なら先に確認します。タスクの試行、操作の状態、チェックポイント、バージョンの制約は、古い結果による新しい状態の上書きを防ぐために役立ちます。ただし、すべての外部システムに対して厳密に一度だけの実行を保証することはできません。

Hands はどの Mac アプリでも操作できますか？

互換性は、アプリが公開する Accessibility の構造、OS の許可、Arslan の操作ルールに依存します。コントロールを読み取れることは、あらゆる業務操作を安全に完了できることを意味しません。機密性の高いボタンやキー操作には、より細かな確認が入り、一部のアプリやコントロールは未対応の場合があります。

Mac の電源が切れていても、iPhone が代わりにタスクを完了できますか？

Mac Bridge の経路では、実行を担うのは引き続き Mac です。Mac が利用できない間、メッセージは iCloud で待機します。v0.1.53 では Mac 側の Bridge がリリースされ、v0.1.54 ではそれを iPhone アプリ向けに整えましたが、それをもって iPhone クライアントの正式公開を判断することはできません。スマートフォンに受信済みと表示されても、タスクが完了したとは限りません。

テストがすべて通れば、どんな実タスクでも完了できますか？

テストが確認するのは、それぞれの条件の範囲だけです。ユニットテストは局所的なロジック、プロトコルテストは境界の整合性、インストール検証は配布物、実タスクの比較は特定のモデルとタスクでの成果を確認します。モデル、Web ページ、OS の権限、外部アプリによって結果は変わり得ます。

なぜバージョン番号がまだ 0.1.x なのですか？

プロジェクトは、v1 に至る前の継続的な改善段階にあります。50 を超える番号は、その改善の過程を表しています。成熟度は、具体的な機能、失敗への対処、テストの範囲、リリース状態を併せて判断すべきです。本書の完全なバージョン付録では、これらの違いを保持しています。
