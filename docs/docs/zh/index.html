01 / 项目概览让自然语言接上真实工作

Arslan 是一个开源、Mac 优先、本地优先的个人 AI 工作助手。用户描述想完成的任务，Arslan 组织上下文、调用模型、使用工具、记录执行过程，并交付可以检查的答案或文件。它把聊天、记忆、文件处理、终端、网页、部分原生应用操作与后台任务放在同一个工作入口中。

项目由作者独立通过 AI 辅助开发，也就是通常所说的 vibe coding，持续构建和迭代。本文从产品目标讲到实际代码边界，介绍它为什么这样设计、怎样运行，以及从最早原型到 v0.1.54 经历了哪些变化。

理解任务

结合本轮要求、近期对话、允许使用的个人记忆和相关资料，决定下一步需要什么信息与工具。

执行并观察

模型提出结构化动作，代码校验参数与权限，工具返回真实结果，再由模型决定继续、换方法或收尾。

交付可检查的结果

文件、工具返回、任务状态和来源构成结果依据。用户可以查看进度、处理审批、停止任务，或从已有记录继续工作。

一个入口，几类工作

任务类型典型工作使用条件与结果边界
研究与阅读搜索网页、提取内容、阅读附件、汇总带来源的资料受网页可访问性、提取完整性和模型能力影响；引用可供核对，但不自动证明结论正确
文件与产物处理工作区中的文本或数据，运行转换命令，生成可打开的结果文件读写范围取决于工具、工作区与授权；保存记录和实际文件应互相对应
Mac 上的操作通过系统接口、Shortcuts、Apple Events 或 Hands 读取与操作支持的应用路径各有系统权限和应用兼容要求；敏感动作可能需要额外确认
持续任务把耗时工作交到后台，按计划运行检查，接收进度与结果依赖本机进程可运行；Mac 休眠、离线或关机时，不能按云服务的可用性理解
个性化协作记住称呼、格式偏好、项目规则和这台机器上已验证的方法记忆有范围、敏感性、来源与使用许可；经验不会给工具追加权限

“本地优先”具体意味着什么

本地优先描述数据主存储和执行位置：桌面界面、本地服务、数据库、工作区及 Mac 工具主要运行在用户机器上。模型由用户配置；使用云模型时，请求中的对话、资料片段和获准使用的记忆会发送到相应模型供应商。兼容的本地模型端点也可以接入，但具体工具调用与视觉能力仍取决于模型和服务实现。

因此，Arslan 的架构需要同时回答两个问题：工作在哪台机器上发生，哪些内容会发往哪个模型端点。本地数据持久化、云端记忆许可和工具权限承担不同职责，不能用一个“本地”开关概括。

02 / 独立开发与开源一个人，借助 AI，把应用做成系统

Arslan 是我独立通过 AI 辅助开发做出来的项目，也就是通常所说的 vibe coding。从最初的原型到后续版本，项目一直由我独立推进。

这里的“独立开发”指项目整体由作者独立推进，AI 是实现过程中的协作工具。Arslan 同时建立在开源框架、系统 API、外部模型与第三方组件之上。开发方式、项目责任和组件来源各有清晰含义；下文讨论的，是最终进入产品的设计与实现。

从生成代码到维护一个可用产品

一段代码能运行，只覆盖产品的一小部分。桌面应用还要解决服务如何启动、窗口怎样连接、旧数据库怎样升级、进程被结束后如何清理、系统权限由谁持有，以及安装包在没有开发环境的机器上能否工作。Agent 又增加了新的不确定性：模型会超时、工具参数会截断、网页可能读不全，执行到一半也可能需要用户批准。

这些问题把 Arslan 的迭代逐渐推向四个方向：用明确契约约束输入与状态，用可观察的工具结果核对完成情况，用权限边界控制实际副作用，用测试与发布验收检查更改是否成立。AI 辅助可以加快实现与排查，但最终交付需要这些约束共同支撑。

敢于删掉早期假设

早期围绕专家分身组织能力，后来收敛到一个统一的 Arslan。工具和方法可以继续复用，用户入口与执行主路径则随着真实问题重新设计。

保留没有改善的证据

增加审阅层、学习经验或并行能力，并不必然提高任务效果。项目记录过审阅失败、研究任务落后和学习后未提速的结果，为下一轮修改提供具体方向。

为什么保留 Python 执行核心

Python 承担模型适配、文档处理、Agent 循环和任务服务，已有生态和现有实现能直接复用；Tauri 与 Rust 承担窗口、进程生命周期及原生集成。公开架构决策记录了保留这一执行核心的选择。将核心迁往另一种语言，会同时改变工具、数据迁移、打包和测试边界，不能只用“更原生”判断收益。

这种结构在逻辑上分层，在部署上仍以本地服务为主体。内部 Python 模块没有各自成为远端微服务，也不依赖 Redis、Celery 或 Kubernetes 才能运行。Hands、Bridge、MCP 服务和终端子进程在需要独立权限或独立运行环境的位置形成进程边界。

锁定依赖：前端锁文件；桌面锁文件；Python 锁文件。设计与归属：运行核心决策；第三方归属。

04 / 项目如何走到今天从生成专家，到一个能持续工作的 Arslan

Arslan 由作者以 AI 辅助的 vibe coding 方式持续独立开发。它的演进过程既有新能力，也有收回的设计：有些功能需要补齐运行条件，有些复杂度则需要删除。理解这些变化，比把所有历史功能并列在一张清单上，更能说明今天的架构。

这是一条有证据边界的时间线。早期日期取自保留的 Git 提交，正式版本日期取自公开 Release，并统一换算为北京时间。最早提交、开源准备、仓库变为公开和首次发布不是同一个时间点；现有记录不能确定仓库转为 Public 的准确日期；当前的公开仓库建立于 2026 年 7 月 26 日。

六月：先建立“通过对话生成 Agent”的闭环

2026 年 6 月 7 日最早保留的提交从数据模型开始。当时的方向是 Meta-Agent：让不熟悉技术的用户通过对话创建领域专家，再由这些专家完成任务。随后出现模型适配器、工具注册表、需求对话状态机、模板、Spawn Manager 和 CLI。6 月 8 日，FastAPI、异步数据库、认证、WebSocket 与 React 界面接起来，原型有了可交互、可保存和可恢复连接的入口。

随着工具开始真正运行，系统需要知道“执行过什么”，也需要给回答提供资料。6 月 23 日加入 Runs、Steps、Evaluations，以及文档分块和 SQLite FTS5；6 月 27 日接入 MCP 的 stdio 与 HTTP 传输。这些变化把项目从生成一段专家提示词，推进到管理一次完整执行：调用模型、运行工具、保存过程、检索资料，再把结果交回用户。

最早数据模型；Runs 数据模型；FTS5 知识索引；MCP HTTP 传输。

七月：把记忆和交付变成工程问题

7 月 5 日，Second Brain 加入 embedding 与按作用域过滤的混合检索，结合全文搜索、向量相似度和 RRF 排序融合。随后补上事实来源、有效状态、替代与撤销、整理提案和使用记录。记忆由此不只是聊天摘要：资料是否相关、是否仍有效、属于哪个范围，都要影响它能否进入模型上下文。

把更多历史放进上下文会带来新的取舍：检索范围过大可能混入无关资料，旧事实可能覆盖新事实，外部文本也可能影响长期行为。因此七月的实现开始给事实补来源和时序，区分自动追加、需要审阅的修改与敏感内容，并让整理结果进入提案收件箱。后续记忆功能沿着这些约束继续演进，用户能看见、纠正和撤回，成为比“记住更多”更明确的工程目标。

这一阶段也开始处理长期维护。7 月 14 日，数据库迁移切换到自有版本化 runner，移除 Alembic 依赖。7 月 10 日改用 Apache-2.0 许可证，并加入 NOTICE 与 SECURITY.md；7 月 25 日出现明确的开源准备提交；到 7 月 27 日，v0.1.0 作为首个桌面安装版发布，Tauri 外壳与冻结的 Python 后端一起交付，签名、公证、更新和首次安装检查进入发布链路。

真实安装环境随即暴露了开发测试看不到的缺口：v0.1.0–0.1.6 的安装包缺少 WebSocket 运行依赖，健康接口正常，聊天却无法建立连接。0.1.7 修复依赖层与 PyInstaller 隐式导入，并把真实握手加入安装验收。这个故障解释了为什么“后端启动了”必须进一步验证为“用户的整条路径可用”。

混合检索；版本化迁移；开源准备；安装包 WebSocket 故障复盘。

八月：能力可接入，还要让用户看懂

0.1.20 把凭据状态区分为未配置、可解密和不可解密，稳定盐与密钥迁移；搜索增加来源与错误说明，模型开始按任务分工。随后，MCP OAuth、OpenRouter 登录、首次引导、扩展清单、本地工作区读写、定时任务与 SSH 逐步加入。扩展能力变多后，系统也必须准确说明：当前连接能否调用工具、装备是否生效、哪次动作需要授权。

本地执行能力也开始分层。工作区读取与写入分开，写入需要相应授权；定时任务有自己的调度许可；SSH 可以记住机器，但每次远程执行仍需要确认。工具清单由此同时描述能力和使用条件。对用户而言，“已经连接”与“这次可以执行”是不同状态，界面与模型上下文都需要表达这个区别。

0.1.23 的 turn journal 让切换对话后正在生成的回答仍能接回来；安装版找到 npx 的修复则再次说明，桌面应用拿到的环境与终端不同。八月的主线不只是接更多服务，而是把连接、状态和授权变成用户能理解的操作。

九月：从一次回答，走向可追溯的工作

0.1.38 集中补可靠性：默认拒绝的 Python 执行沙箱、独立计算运行时、持久化 Runs、产物、检查点和共享执行预算。0.1.40 的预览与稳定化继续推进项目记忆、文档来源、任务延续和迁移前备份，同时保留跨语言、多文档比较的已知失败。来源可点击，只说明资料能被找到，并不能证明模型的结论正确。

更早一些，8 月 31 日到 9 月 3 日，语音从朗读（0.1.32）、按住说话（0.1.36）推进到半双工对话（0.1.37），同时修复麦克风权限与语言选择。与此同时，0.1.40 的研究验收没有把跨语言比较失败改写成成功；0.1.41 的来源审阅在校准不理想后保持默认关闭。这些记录限定了“系统做过检查”的含义，也让下一步改进可以围绕真实失败展开。

0.1.41 让关闭窗口变为留在菜单栏继续工作；0.1.42 把长任务放到后台，用户可以继续聊天；0.1.43 再区分预算软限与硬停：到达软限先利用已有材料收尾，避免研究做到一半却没有交付物。任务逐渐拥有独立于界面的生命周期，但这不意味着任意外部动作都能在崩溃后安全自动重放。

九月末到十月：收敛为一条执行循环

06 / 执行运行时让一次请求有过程、有边界、有结果

Arslan 的执行核心负责把用户意图变成一连串可观察的动作：准备上下文、调用模型、校验工具请求、执行获准的操作、读取真实结果，再决定继续还是交付。v0.1.54 的默认入口采用统一循环，EXPERTS_ENABLED=False；消息直接进入答复流程，长期事实的提取放在答复之后。历史专家系统仍留有兼容代码，当前主流程不再先经过一次模型路由。

图 2 · 执行闭环。纯文本读法：输入 → 上下文 → 模型 → 参数校验 → 授权 → 工具执行 → 结果回流，再继续循环；模型也可直接回答。答案与产物须经检查，再交付或如实说明未完成；禁止和拒绝不会被模型意愿覆盖。

模型负责提出下一步，运行时负责执行条件

模型看到的工具是一组名称、用途与参数 schema。它返回结构化 tool_calls 后，运行时先解析 JSON、验证参数，再重新确认工具是否仍可用、当前预算是否允许以及是否需要用户授权。内建工具由注册表映射到执行函数，mcp_ 前缀的工具转入 MCP 调用。一个工具出现在注册表中，并不意味着它会在每轮对话里开放。

一个关键边界是响应完整性：如果供应商因输出长度限制截断了工具调用，本批调用不会被执行，即使其中某项看起来已经完整。含有工具调用的模型文本只作为过程说明，不能提前充当最终交付。执行前后会记录检查点，真实工具结果带着对应调用身份返回模型；来自网页、文件或外部工具的内容仍作为数据处理。

因此，“我已经保存文件”要能对应实际保存结果和产物引用；一句自然语言承诺不会自动变成已经发生的操作。工具失败也会成为下一轮输入，循环可以调整路线，但须继续遵守相同的权限与预算。

以“读取指定目录并生成清单”为例，目录路径先作为输入进入任务范围；模型提出读取请求，工具返回实际文件信息，随后才有依据生成清单。若进一步要求移动或删除文件，运行时还要根据对应操作判断授权。最后的交付应指向已经生成的文件，并说明检查结果。这个过程中的文件列表、操作回执与产物引用，分别承担不同的证据作用。

临时协作者与后台任务各有职责

delegate_work 把独立研究拆给临时 worker：一批最多 4 项，最多同时运行 2 项。当前 worker 只开放 web_search 与 web_extract，不能写文件或个人记忆，也不能继续递归委派。主执行者接回材料后负责核对和整合。这个设计保留了并行研究的价值，同时让执行责任集中在原任务上。

后台 job 则用于较长的完整任务：它拥有独立上下文和预算，复用工具循环、产物检查与修复流程，进度通过任务卡回到会话，默认最多同时运行 3 个。网络连接、聊天窗口和后台执行有各自生命周期；切换会话不等于取消任务。本机休眠或进程退出时，后台工作也不会转交给云端继续运行。

先进入收尾，再触及硬限制

预算同时统计模型请求数、工具调用数、累计 token 与执行时间。达到 soft limit 时，循环应停止扩张研究范围并组织现有成果；hard limit 防止继续失控消耗。嵌套执行和重试也要计入任务预算，无进展的重复调用另有检测，避免反复尝试同一条失败路径。

任务、尝试与验收分别记录

TaskSpec 保存任务约定：指令、输入、范围、验收项与预算，并带有修订版本。一个 task 可经历多次 attempt；attempt 是一次具体执行尝试。修改约定、取消后返回的旧结果或恢复后的新尝试，不能互相混写状态。持久化更新同时检查 attempt 身份与 row version，防止过期执行覆盖新状态。

状态含义
queued / running等待开始 / 正在执行。
waiting_user需要用户操作或显式继续；状态本身不代表成果已完成。

验收结果区分通过、失败、未运行、不适用等情形。判定需要对应证据，不能漏掉约定的检查，也不能全部只依靠模型自评。文件存在性、所属任务与摘要等可以确定性校验，主观质量才适合补充模型或人工评价。仍有准备中、进行中或效果未知的动作时，仓库层也会阻止任务直接变成成功。

这也解释了为什么任务修订必须保留身份：针对旧要求生成的结果，不能自动证明新要求已经满足。验收要对应同一版任务约定、同一次有效尝试，以及该任务拥有的证据。关键检查不能随意标成“不适用”；只有符合契约规则的非关键项才有这种处理空间。缺少证据时，应保留未验证或未完成的结果，等待补充检查。

恢复从已有证据继续

检查点保存进度、已用预算、证据与产物引用，运行事件供界面重连后查看。进程内的 run registry 持有实际异步任务和取消入口，并把事件分发给已连接窗口；重连时同步取得快照并附着事件流，减少连接交接处的丢帧或重复。

进程重启后，尚未结束的执行会被识别为中断，由用户显式继续。已经发送出去、却没有收到回执的外部动作，其效果属于未知，必须先核对，不能直接重复提交。恢复备份还会撤销旧动作授权、把相关动作标成不确定。检查点解决的是“从哪里安全继续”，并不能撤回已经产生的外部结果。

停止也有两个层面：运行注册表负责取消正在等待或执行的异步工作，持久化状态负责阻止迟到结果继续提交。对外部系统已经接受的请求，取消本地等待无法证明对方没有执行。因此动作表区分准备、已开始、已确认、失败、效果未知与已取消等状态，恢复流程先处理这些状态，再决定哪些步骤可以再次尝试。

源码：任务与验收契约；持久化状态与并发检查；产物校验；执行与显式继续；连接与运行分离；备份恢复边界。

07 / 数据与记忆保留可用的上下文，也保留清晰的数据边界

Arslan 把主要状态保存在本机 SQLite：会话、运行记录、任务、个人记忆、模型配置及用量都有对应数据模型。文件产物写在磁盘；过长的工具输出全文另存于应用数据目录（保留 7 天），模型按结果里给出的路径分段读取。这样，关闭一个窗口不会抹掉任务过程；也能分别管理“当时说了什么”“实际做了什么”和“以后可以记住什么”。

数据访问采用异步 SQLAlchemy 与 aiosqlite。连接启用 WAL、外键检查、5 秒忙等待，并使用 synchronous=NORMAL。这些选择服务于本机单用户应用：减少部署依赖，并改善读写并存时的体验。数据目录还有协作式进程锁，避免遵守同一协议的实例同时使用同一份数据。

工作上下文：控制本轮输入，保留原始历史

模型每次能接收的内容有限，Arslan 会用有上限的滚动摘要加上近期消息构成工作上下文。该历史窗口的默认估算预算为 3,000 token，摘要本身也受长度限制。这是历史装配的预算，不代表整个模型请求只有 3,000 token：系统指令、工具 schema、资料和结果还会占用其他空间。

对话变长后，旧消息可以被概括为摘要，近期消息保留原文。压缩影响下一次装配哪些内容，不等于删除数据库中的完整会话；压缩失败也会保留原始记录。过长工具输出另有落盘机制：模型得到头尾摘要和文件路径，需要时再分段读取，完整输出按保留策略清理。

这种分层让模型优先看到当前任务所需的信息，同时给后续核对留下原始依据。摘要只是已有内容的压缩表示，不能代替某个外部动作的真实回执。

“关于你”和“Mac 笔记”有受限的基础注入，其余内容按相关性选择。自 v0.1.52 起，默认开启的“记住我并在对话中使用”可允许普通、cloud_allowed 条目用于已配置的云模型。敏感内容还需要额外许可；local_only 不会因为总开关开启而变成可上云内容。

ContextReceipt 记录使用了哪些条目和修订、为何使用以及估算计数，不复制记忆正文。用户能追溯一次上下文选择的依据，系统也不必为此再制造一份敏感内容副本。

编辑记忆会产生新的修订，条目的当前修订指针随之更新；来源记录继续说明这版内容是如何形成的。暂停、过期、被替代和删除等状态，也会影响是否进入后续上下文。版本化有利于核对变化，但删除流程会清除需要抹去的正文，所以不能把它理解成所有历史内容永久不可删除的事件库。

源码：历史与摘要；长工具输出；会话许可；范围与隐私过滤、回执。

资料检索：关键词与向量可以组合使用

知识资料的检索模块支持 SQLite FTS5 全文搜索和向量余弦相似度搜索。前者找词面匹配，后者利用 embedding 寻找语义相关片段；两路都可用时，通过 RRF 把排名融合。RRF 比较的是排名位置，不直接混用不同量纲的原始分数。未配置 embedding 或缺少向量时，仍可走全文检索。

检索所得片段附带来源进入模型上下文，由模型结合当前问题组织答复，这就是此处的 RAG。记忆 v2 启用后，资料检索只在绑定了资料集的项目中进行；使用云模型时，还需该对话单独开启云端记忆许可（默认的“记住我”开关不覆盖资料）。结果作为 recall 工具的返回值进入上下文。它无需修改基础模型权重，也不依赖单独部署的向量数据库。个人记忆 v2 的选择主要使用权限过滤、全文与本地相关性逻辑，不能据此推断所有记忆都经过同一套向量管线。

经验学习：把纠正变成可审阅的规则

Lesson 用于保存用户纠正、失败后成功的绕行方法以及机器环境特点。例如，某个命令在当前 Mac 上需要不同参数，可以形成有来源的经验，供相似任务参考。召回最多 5 条、总计约 800 字符，放入动态的 agent status，不污染稳定系统前缀；召回、遵循、成功与失败都有计数。

是否值得保存、是否与已有内容重复或冲突，可以由 judgment 层提出范围很小的判断，并记录概率与后续结果。用户纠正或未受外部内容影响的经验，在设置允许且判断有价值时可以直接生效；其他需要审阅的内容进入提案。含凭证的候选会被直接丢弃；“推断出的敏感信息需要审阅”这条规则属于个人记忆，而不是经验。判断缺失或超时时有回退路径。

这些机制修改应用保存与召回的知识，不训练模型权重。judgment 的启用范围也各不相同：例如工具审批判断处于 shadow 模式时只记录建议，仍由真实授权流程决定能否执行。

源码：混合资料检索；经验提取与召回；小判断与运行模式。

删除需要跨过摘要和旧备份

删除一条记忆时，系统会提高 deletion epoch，清除该条的旧修订正文与来源，并清空所有会话的滚动摘要和运行记录中缓存的提示词，防止旧的派生内容把已删记忆带回来。删除记录只保留用于匹配的内容指纹（本地密钥 HMAC）和范围等元数据，避免在账本里重新保存已删除正文；suppression 记录防止仍在聊天历史中的同一来源再次自动生成这条记忆。删除记忆与删除原始会话是不同的数据操作。

独立删除账本和删除清单用于在启动及恢复路径继续落实删除。恢复旧备份前，系统检查存储身份，在激活数据前对照删除信息整理暂存数据，降低旧备份让已删除记忆重新出现的可能。这个保证依赖恢复流程与可用删除记录，不能解释成能撤回所有已经导出到外部的副本。

备份里的其余记忆也不会立即恢复全部使用许可：恢复处理会将其隔离待审，收紧使用策略，清掉缓存上下文，停用全部定时任务，并收回会话级的云端与敏感许可、归档进行中的项目。恢复数据与重新批准使用数据分开完成，避免旧会话许可在新的运行环境中静默生效。

迁移先完成，应用再开始使用数据

当前数据库升级使用显式迁移 runner：检查 schema 版本、准备升级备份、创建缺少的表、按顺序执行待运行迁移，然后处理密钥兼容和记忆 v2 激活。未知或过新的 schema 会被拒绝，避免较旧程序盲目修改较新数据。v0.1.54 的显式登记已到 0061；早期 Alembic 历史不应当作当前运行机制。

记忆 v2 激活时，旧事实与学习表改名为 legacy 表并加只读触发器，兼容视图将旧读入口映射到新结构，全文索引也在这一过程中建立。模型 API 密钥、MCP 环境变量与 OAuth 令牌、SSH 密钥等秘密字段使用 Fernet 字段级加密（PBKDF2 + 每次安装独立的盐值）；普通会话和任务表并未因此变成整库加密。持久化、秘密保护与备份恢复各有具体边界。

源码：记忆删除与版本；删除账本；恢复前删除核对；备份恢复协调；恢复数据隔离；存储启动顺序；显式迁移；记忆结构激活；密钥字段保护。

08 / 工具、Skill 与扩展让能力可复用，也让执行有边界

Arslan 把“能够做什么”和“知道怎样做”分开组织。工具负责实际动作，Skill 保存方法和参考，MCP 连接外部能力，插件清单把这些资源组合起来。模型拿到的是本轮可用的能力集合；某个工具存在于源码注册表中，并不代表它默认启用或已经获得执行许可。

扩展服务是新的信任边界

本地 stdio MCP 通常意味着启动一个独立进程，HTTP MCP 则可能连接远端服务。Arslan 需要分别管理连接、主助手是否可用、工具是否暴露，以及凭证怎样保存和展示。插件清单中声明的 HTTP MCP 服务 URL 必须使用 HTTPS；secret 槽位声明参数形状，不在清单中内嵌真实凭证。已配置环境值会加密保存，读取显示时掩码处理。

这些约束降低了意外暴露和误执行的机会，但实际 MCP 服务仍可能访问它获得的资源。工具来源、所需权限、发送到远端的数据和操作副作用，都属于扩展能力需要解释的部分。

并行研究为何仍然存在

统一 Agent 循环保留了受限的临时只读 workers。v0.1.54 中，一批最多 4 项，最多同时运行 2 个；工具限定为搜索与网页提取，不写入文件和个人记忆，也不能递归创建更多 workers。主助手负责检查并综合它们的结果。

这类委派适合拆开互相独立的资料查询。它与早期永久专家分身的生命周期不同：没有要求用户先挑选或管理一个专家团队，也没有把每条消息强制路由给另一位“专家”。是否使用并行，仍应取决于任务是否能有效拆分以及额外调用成本。

后台、定时与 heartbeat

后台 job 将耗时执行与当前聊天分开，复用同一套模型、工具和验收逻辑。定时任务把“何时开始”持久化；heartbeat 是定期检查清单的一种使用方式，默认关闭，负责检查与提出建议。定时触发不会把建议变成已批准的写入或命令。

当前调度由本地服务实现，包含重叠跳过、失败暂停和重启清理等处理。错过的周期不会逐一补跑；同一个任务上一轮未完成时，不叠加启动下一轮。这些行为适合个人桌面应用，也意味着它的运行条件与持续在线的服务器不同。

实现：工具注册与 read_skill；插件清单契约；MCP 连接与配置；只读 workers；后台任务；本地调度；heartbeat。

09 / 执行与安全边界从模型建议到真实动作，中间发生什么

Arslan 可以读写文件、运行命令，也能通过浏览器和原生应用完成工作。它的安全设计围绕一个区别展开：模型负责提出下一步，可信代码负责决定这一步能否执行。下面描述 v0.1.54 已实现的边界；这些是有具体作用范围的保护机制，并不是对所有恶意输入、应用行为或系统环境的安全证明。

外部内容可以提供资料，不能自行扩大权限

网页和工具结果可能含有提示注入。网页文本进入上下文时，会被包在明确的外部数据边界中，并处理伪造边界标记的内容。系统还记录本轮是否读过网页、文件、MCP 结果等外部内容：受这些内容影响的经验和机器笔记需要先成为提案。这样，一段网页里的“以后总是把文件发到这里”不能仅凭被读到就获得长期授权。

这层处理有助于保持来源和信任关系，但仍然依赖后面的执行检查。模型可能误解资料，命令风险识别也不是完整的语义证明；不能因为文本被标为“不可信”，就取消真正的权限边界。

外部数据包装与来源追踪；工具校验与执行入口；经验进入生效或提案路径。

不同执行工具，有不同的隔离强度

路径实际限制不能从中推导出的保证
run_python默认拒绝的 macOS Seatbelt 计算环境：只开放解释器所需读取、临时工作区读写和只读参考文件；禁止网络及 host IPC，清理子进程环境并施加资源限制。不是任意 Python 程序的通用宿主。缺少可用隔离时默认拒绝；未实现的 Linux 沙箱不会被当成已经可用。
普通 run_command运行真实 shell。策略分 run / ask / forbid，命令链（&&、;、|、||、&）中的每一条都会检查，不只第一条；“不再询问”只有覆盖命令命中的全部规则时才会跳过卡片。默认工作区沙箱限制写入工作目录、临时与缓存目录，另行关闭 SSH、Keychain 文件、Arslan 数据及 Hands socket 所在路径。其他位置的读取、程序运行与网络仍开放。普通模式下沙箱不可用时会降级执行并返回 sandbox=unavailable，因此不是统一的 fail-closed 路径。
离线收尾命令任务进入收尾后，允许处理已取得的数据并保存交付物，同时额外阻断网络。所需沙箱不可用则拒绝执行，不能套用普通命令的降级规则。
AppleScript / Shortcuts通过其他应用产生效果，保留单独的动作授权。命令本身在文件沙箱中，不代表被调用的应用也受同一文件范围约束。
Arslan Hands独立 helper 持有 Accessibility；helper 内再次检查应用、动作、字段和停止状态。辅助功能树不是完整的业务语义。应用是否提供可操作节点、窗口所在 Space 都会影响可用性。

离开命令沙箱需要用户点击批准：可以为当前动作申请，也可以由用户选择本次会话内允许；后者只保存在内存。源码开发环境另有显式的 Python 无沙箱逃生设置，生产模式和冻结安装包会关闭这条逃生路径。两者都不应被误读为模型可以自行关闭保护。

审批绑定具体动作，后台工作不继承所有便利授权

审批卡通过 call_id 与动作种类关联，错误种类的回复不能批准另一张卡。Mac 窗口和手机共同看到的卡采用首个有效回答，并向其余视图广播关闭结果；无人回答在 300 秒后过期。后台任务不继承连接的会话授权，也不提供“记住这条命令”；自 0.1.54 起，这也包括聊天窗口的“本次会话内在沙箱外运行”，后台任务的命令无论窗口允许过什么，都从沙箱内开始。模型建议连上 MCP、登记远程机器或访问其他执行入口时，提案与真正启用连接分开处理。

对于外部副作用，发送请求也不等于完成动作。任务恢复会把结果不明的在途动作标为不确定，不能仅因为进程重启就自动重放。这里的目标是让重试与恢复有明确语义，而不是许诺任意外部系统都能撤销。

卡片关联、过期和多端回答；恢复时的不确定副作用；连接提案和授权入口。

Hands 将系统权限收在一个更小的进程中

Accessibility 授予 Arslan Hands.app，而非主 App。签名发行包通过受保护 Unix socket、每次启动生成的 token 和 peer 签名检查接收请求。helper 自己执行规则，底层 agent-desktop 不单独持有该权限。读取按会话及应用批准；动作只在后台任务中进行，并按任务及应用批准。删除、发送、支付、购买、转账和提交等敏感按钮按实际标签每次询问；密码字段不输入，密码管理器、系统安全界面等应用在禁用名单中。

停止入口会设置停止闩锁，后续动作要经过该检查；活动记录保留操作线索，输入文字只记录长度。限制同样公开：仅能看到当前 Space 的窗口，大窗口读取可能需要 10–20 秒；Stop 截断的调用可能没有对应 trace 行，审计记录并非对所有中断情况的完整取证保证。

本地服务也有边界。发行包为 REST 和 WebSocket 生成访问 token，并在安装验收中检查未认证请求被拒绝。显示 token 的设置接口只把它交给已经带着该 token 的直接本机调用方（0.1.54）；仅凭本机来源不够，因为沙箱里的命令同样能打开本机 socket。源码开发模式允许 localhost 无 token 的便利路径；“只监听本机”与“已经通过认证”不是同一件事。与当前用户同权限且已被攻陷的宿主环境，也不能靠一个本地 token 自动变成可信环境。

CloudKit 是信箱，设备身份仍由协议确认

v1 使用同一 Apple ID 下的 CloudKit 私有数据库。Mac 必须开机、在线并处于可运行状态；否则消息等待处理，手机并不能让一台已经关机的 Mac 继续工作。局域网 Bonjour 是后续方向，不是本版的备用直连通道。Mac helper 是随应用运行的独立 ArslanBridge.app，通过 stdin 获得本地 API token，再连接后端；手机不持有该 token，也不接收模型 API key。

扫描二维码只是配对的开始

二维码携带一次性 pairing_id、Mac 的签名与交换公钥、32 字节配对密钥、固定容器标识和期限。有效期不超过 600 秒；手机拒绝过期信息、错误容器和不符合约束的内容，并固定二维码里的 Mac 公钥。随后手机生成自己的身份与交换密钥，发出加密配对请求。Mac 验证请求后仍要展示给用户，由 Mac 上的点击决定接受或拒绝。

同一请求重试应得到相同决定，不能产生第二次授权。接受后使用设备身份通信，配对码被消耗；Mac 可以撤销手机。同一台 iPhone 再次配对时会带上它以前的 ID，Mac 移除这些旧条目，而不是并存两条。移除手机还会删除 Mac 留在 iCloud 里给它的消息；启动时 Mac 也会清理仍在等待已不再配对的手机的记录。设置 › iPhone 中，每台手机在 Mac 读到它的第一条已认证消息前显示正在连接…，之后显示已连接及最后在线时间。设备私钥由各自 Keychain 保存。这里的信任来自一次性配对材料与用户确认的组合，而非“同在一个 iCloud 账户，所以任何消息都可信”。

消息同时校验内容、来源与上下文

每条新消息使用临时 X25519 密钥协商共享秘密，以 HKDF-SHA256 派生 32 字节密钥，由 ChaCha20-Poly1305 加密认证，再以 Ed25519 签名。消息头使用按长度编码的 UTF-8 字段，避免跨语言 JSON 排序差异影响验证；头字段同时被签名和 AEAD 认证绑定。这是以 CryptoKit 原语实现的应用协议，没有实现 Signal 双棘轮，也不应仅凭临时密钥就宣称所有场景的前向保密。

接收顺序有明确要求：检查形状与收件人，验证签名，再解密；随后检查明文与头字段是否一致，有文件时再验证附件。任一步失败都不应留下部分业务效果。文件上限为 20 MiB，密文摘要、认证标签、明文大小和摘要都要匹配后才能缓存或预览。

配对、密码套件和验证顺序；Mac 编解码与密码协议；一次性配对与用户决定。

12 / 测试与验证如何判断任务做得对

一个任务结束、一份文件能打开、一份报告内容正确，是三种不同的判断。Arslan 用运行记录说明发生了什么，用产物与契约检查验证能够确定的部分，再用真实任务评测观察模型表现。任何一层通过，都不能替代其他层。

本节汇总公开源码、发布说明与历史实验记录。数字对应各自版本和环境，不表示这些测试在本文编写时全部重跑，也不表示全部功能都经过真实设备和真实模型验收。

先把“完成”拆成可检查的证据

执行是否发生

工具调用有没有返回？退出码是什么？动作结果是明确成功、明确失败，还是未知？模型写下“已完成”不能替代工具证据；结果未知的副作用也不能当作可以安全再执行一次。

交付物是否成立

文件是否存在、属于本任务、字节数与哈希是否匹配、格式能否解析？表格能打开不等于数据正确，图片尺寸正确也不等于排版合格。

要求十条有效结果，六条就没有满足要求。引用来源必须与结论对应；读过网页不能证明其中支持某个说法。这一层仍需要任务专用校验与人工判断。

0.1.41 来源审阅校准中，13 份报告产生 14 个提示：1 个正确、2 个边缘、11 个错误，同时漏掉两项预先登记的已知错误。该能力因此保持默认关闭。调用另一个模型并没有自动获得可靠的事实核查器；格式合法、锚点存在，也不能保证批评内容成立。

0.1.52 的经验学习验证则呈现另一种边界：一次 AppleScript 被拒后，经验被保存、召回，下一次直接选择 EventKit，证明经验能够影响执行。但是后续脚本编辑与检查产生更多调用，没有测出提速。要判断经验本身是否提高效率，需要在相同任务上进行有经验／无经验的配对重复实验；当时的记录明确说明这项公平速度对照尚未运行。

更强的质量结论需要预先冻结任务、交付物和检查标准，记录模型与配置、调用轨迹、实际费用及失败原因，并用独立人工标注校准模型评分。格式不合法的评分、没有运行的检查、无法取得的证据，都应保留自己的状态，不能为了汇总好看而计为通过。

来源审阅公开校准结果；经验学习的通过项与未证明项；更强质量结论所需的评测条件。

13 / 工程方向从已有能力，走向更可靠的交付

Arslan 已建立执行、持续任务与记忆三条基础。下一阶段值得验证的，是这些能力在更复杂场景中能否保持正确状态、给出可靠结果，并让用户保有控制。下图将已有实现、需要继续验证的环节和可选工程方向分开；它是一份技术讨论，不是带日期的发布承诺。

图 4 · 能力蓝图。纯文本：已有执行、持续任务、记忆三条基础 → 跨设备和可靠性验收 → 以真实完成率、恢复契约、学习对照实验为优先建议。建议不是已上线承诺。

真实任务效果

固定任务集应覆盖搜索完整性、引用与结论对应、文件可打开性、系统操作的真实落点，以及失败后是否诚实收尾。已有对照暴露了研究任务的差距；扩大工具列表之前，先定位“没找到、没读全、没验证、没正确交付”分别发生在哪一步，更有助于改善完成率。

恢复与跨设备一致性

网络重试、消息重复、应用重启和用户取消可能同时发生。后续验证可以围绕稳定业务 ID、终态不可被旧消息覆盖、审批取消后的行为，以及副作用未知时的核对路径展开。通过崩溃注入与协议负例，明确哪些情况可自动处理，哪些必须回到用户确认。

可测量的学习收益

经验被记住只是起点。需要在相同任务和模型条件下，反复比较有经验与无经验的完成率、调用成本、耗时和错误行为。也要检验过时经验是否会被纠正、外部文本是否可能污染经验，以及删除后是否仍被召回。

平台与扩展的代价

Tauri 提供跨平台宿主基础，但 Seatbelt、Vision、Accessibility、Apple Events 与 CloudKit 都有平台特性。扩展到其他桌面系统，需要替换并验证这些能力，不能把一次跨平台编译当成产品功能已经迁移。更多外部工具同样意味着更多凭证、权限和失败模式。

以上为基于现有实现与测试结果整理的工程方向。具体优先级和排期，以后续正式发布说明为准。

15 / 常见问题使用与理解 Arslan 时，最容易混淆什么

Arslan 与直接在模型网页里聊天有什么区别？

Arslan 在模型之外提供本地文件、工具、任务状态、记忆、授权和桌面集成。模型负责判断与生成，应用负责把工具请求变成受控执行，并记录结果。它的价值取决于整个过程能否完成具体任务。

项目是一个人用 AI 做的吗？

是。Arslan 由作者独立通过 AI 辅助开发，也就是 vibe coding，持续构建和迭代。产品使用开源框架、第三方组件和外部模型，相关来源与许可分别记录在项目文档中。

所有内容都留在本机吗？

数据主存储和执行编排在本机。使用云模型、搜索、远端 MCP 等能力时，相关请求会发往对应服务。记忆还有独立的云端使用许可和敏感性规则；本地优先不等于全程断网。

可以换模型或接本地模型吗？

可以配置支持的供应商或兼容端点，包括 OpenAI 兼容的本地服务。端点可连接只证明传输可用；工具调用、图片、推理延续和上下文长度还要符合该模型与适配路径的能力。

为什么早期文档里有很多专家分身，现在只看到一个 Arslan？

项目经历了产品收敛。0.1.44 停止专家创建与调度，0.1.46 关闭旧自动演进循环，0.1.48 移除前置路由。旧方法可转为 Skill，历史数据保留兼容，受限只读 workers 仍用于独立研究。

记忆、知识库和聊天历史是一回事吗？

不是。聊天历史记录对话，工作上下文选取近期内容与摘要；个人记忆保存带来源和权限的偏好、事实与规则；知识检索从导入资料中找相关片段。三者的存储、召回与删除语义不同。

“学习经验”会训练模型，或者让它自行获得更多权限吗？

不会。当前学习记录可复用的方法并在后续任务中召回，不修改基础模型权重，也不改变执行授权。已有记录显示经验可以被捕获、召回和遵循；普遍提速或节省成本仍需要更多对照实验。

所有命令都在断网沙箱里执行吗？

不是。默认 Python 计算沙箱拒绝网络；普通终端的工作区沙箱通常保留网络访问，并有单独的降级行为。工具权限、命令策略、系统权限和沙箱是不同层，具体差异见安全章节。

关掉聊天窗口后，任务会怎样？

连接和任务分开管理，后台 job 可以在应用服务继续运行时执行；窗口关闭也不能直接等同于进程退出。若服务退出或 Mac 休眠，任务不能继续依赖本地执行。重启后通过记录检查中断情况，再按支持的路径显式恢复。

恢复会自动重新执行先前的每个动作吗？

不会。恢复需要检查已有步骤与外部效果，未知副作用先核对。任务尝试、动作状态、检查点和版本约束帮助防止旧结果覆盖新状态，但不能为所有外部系统提供恰好执行一次的保证。

Hands 可以操作任何 Mac 应用吗？

兼容性依赖应用暴露的 Accessibility 结构、系统授权和 Arslan 的动作规则。可读取控件不等于可安全完成所有业务操作。敏感按钮与按键会触发更细的确认，部分应用或控件仍可能不支持。

iPhone 能在 Mac 关机时替它完成任务吗？

Mac Bridge 路径仍由 Mac 执行，Mac 不可用时消息会在 iCloud 等待。v0.1.53 发布了 Mac 侧 Bridge，v0.1.54 为 iPhone App 做好了准备，不能据此认定 iPhone 客户端已经正式上架。手机显示消息已收到，也不等于任务已做成。

测试都通过，就意味着任意真实任务都能完成吗？

测试只覆盖各自的条件：单元测试检查局部逻辑，协议测试检查边界一致性，安装验收检查产物，真实任务对照检查指定模型与任务下的效果。模型、网页、系统权限和外部应用都可能改变结果。

为什么版本号还在 0.1.x？

项目仍处于 pre-v1 的持续迭代阶段。五十多个编号反映了迭代历程；判断成熟度应结合具体能力、失败处理、测试范围与发布状态。本文的完整版本附录保留了这些差别。
