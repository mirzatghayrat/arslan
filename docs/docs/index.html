01 / OverviewConnecting plain language to real work

Arslan is an open-source, Mac-first, local-first personal AI assistant for getting work done. You describe what you want done; Arslan assembles the context, calls a model, uses tools, records what it did, and delivers an answer or a file you can check. Chat, memory, file handling, the terminal, the web, some native Mac apps and background work all sit behind one entry point.

The author builds and iterates on it alone, with AI assistance — what is often called vibe coding. This document goes from the product's goals down to the actual code boundaries: why it is designed this way, how it runs, and how it changed from the first prototype to v0.1.53.

Understand the task

From this turn's request, recent conversation, the personal memory it is allowed to use and relevant material, work out what information and tools the next step needs.

Act and observe

The model proposes a structured action, code validates its arguments and permissions, the tool returns a real result, and the model decides whether to continue, change approach or wrap up.

Deliver a result you can check

Files, tool returns, task state and sources are the evidence for the result. You can watch progress, handle approvals, stop a task, or carry on from what is already recorded.

What "local-first" actually means

Local-first describes where data is primarily stored and where work runs: the desktop interface, the local service, the database, the workspace and the Mac tools run mainly on your machine. You configure the model. With a cloud model, the conversation, excerpts of material and any memory you allowed for that use are sent to that model provider. A compatible local model endpoint can also be connected, but tool calling and vision still depend on the model and how the service implements them.

So Arslan's architecture has to answer two questions at once: which machine the work happens on, and what is sent to which model endpoint. Local persistence, permission for cloud use of memory and tool permissions do different jobs; one "local" switch cannot describe them.

02 / Independent and open sourceOne person, with AI, turning an app into a system

Arslan is a project I built on my own with AI-assisted development — what is often called vibe coding. From the first prototype to every later version, I have driven it on my own.

"Independent" here means the author drives the project as a whole, with AI as a collaborator in the implementation. Arslan also stands on open-source frameworks, system APIs, external models and third-party components. How it was built, who is responsible for it and where its components come from are separate questions; what follows is about the design and implementation that actually shipped.

From generating code to maintaining a usable product

Code that runs is a small part of a product. A desktop app also has to settle how its service starts, how the window connects, how an old database is upgraded, how things are cleaned up when a process is killed, who holds system permissions, and whether the installer works on a machine with no development environment. An agent adds more uncertainty: models time out, tool arguments get truncated, pages are read incompletely, and a run may need the user's approval halfway through.

These problems pushed Arslan's iteration in four directions: explicit contracts for inputs and state, observable tool results to check what was actually done, permission boundaries around real side effects, and tests plus release acceptance to check that a change holds. AI assistance speeds up implementation and debugging, but the delivered product rests on these constraints together.

Willing to delete early assumptions

Early on, capabilities were organised around expert personas; later it converged on a single Arslan. Tools and methods could be reused, while the user's entry point and the main execution path were redesigned around real problems.

Keeping evidence of what did not improve

Adding a review layer, learned practices or parallelism does not automatically make tasks go better. The project recorded a failed review layer, research tasks that lagged behind, and learning that did not speed things up — each a concrete direction for the next round.

Why the Python core stays

Python handles model adapters, document processing, the agent loop and task services, where an existing ecosystem and the current implementation can be reused directly; Tauri and Rust handle windows, process lifecycle and native integration. A public architecture decision records the choice to keep this core. Moving it to another language would change tools, data migration, packaging and test boundaries all at once — "more native" alone is not a measure of the gain.

The structure is layered logically but deployed mainly as one local service. Internal Python modules are not separate remote microservices, and nothing needs Redis, Celery or Kubernetes to run. Hands, Bridge, MCP servers and terminal subprocesses form process boundaries where they need separate permissions or a separate runtime.

04 / How it got hereFrom generating experts to one Arslan that keeps working

Arslan has been developed continuously by its author alone, with AI-assisted vibe coding. Its history includes new capabilities and withdrawn designs: some features needed their missing conditions filled in, some complexity needed deleting. Understanding those changes explains today's architecture better than listing every historical feature side by side.

A timeline with stated limits of evidence. Early dates come from preserved Git commits; release dates come from public Releases; all are in Beijing time (UTC+8). The first commit, open-source preparation, the repository going public and the first release are different moments. The records cannot establish exactly when the repository became public; the current public repository was created on 26 July 2026.

June: first, a loop that generates agents through conversation

The earliest preserved commit, on 7 June 2026, starts with data models. The direction then was a Meta-Agent: let non-technical users create domain experts by talking, and have those experts do the work. Model adapters, a tool registry, a requirements-dialogue state machine, templates, a Spawn Manager and a CLI followed. On 8 June, FastAPI, an async database, authentication, WebSocket and a React interface were connected, giving the prototype an interactive entry point that could save its state and resume connections.

Once tools really ran, the system needed to know "what was executed" and needed material to ground answers in. On 23 June, Runs, Steps and Evaluations arrived, together with document chunking and SQLite FTS5; on 27 June, MCP's stdio and HTTP transports were connected. These changes moved the project from generating an expert prompt to managing a whole run: call the model, run tools, save the process, retrieve material, and hand the result back.

earliest data models; Runs data model; FTS5 knowledge index; MCP HTTP transport.

July: memory and delivery become engineering problems

On 5 July, the Second Brain gained embeddings and scope-filtered hybrid retrieval, combining full-text search, vector similarity and RRF rank fusion. Provenance, validity, supersession and retraction, curation proposals and usage records followed. Memory became more than a chat summary: whether material is relevant, still valid and in scope all decide whether it may enter the model's context.

Putting more history into context brings new trade-offs: retrieval that is too broad pulls in unrelated material, old facts can override new ones, and external text can influence long-term behaviour. So July's work gave facts provenance and timing, separated automatic appends from edits that need review and from sensitive content, and sent curation results to a proposal inbox. Later memory work followed these constraints; letting the user see, correct and withdraw what is remembered became a clearer engineering goal than "remember more".

This stage also began to address long-term maintenance. On 14 July, database migrations moved to a home-grown versioned runner, dropping the Alembic dependency. On 10 July, the licence changed to Apache-2.0 and NOTICE and SECURITY.md were added; on 25 July an explicit open-source preparation commit appeared; and on 27 July v0.1.0 shipped as the first desktop installer, with the Tauri shell and a frozen Python backend delivered together, and signing, notarisation, updates and first-install checks part of the release path.

Real installs soon exposed gaps that development testing could not see: the v0.1.0–0.1.6 installers lacked WebSocket runtime dependencies, so the health endpoint was fine but chat could not connect. 0.1.7 fixed the dependency layer and PyInstaller's hidden imports, and added a real handshake to installer acceptance. That failure is why "the backend started" has to be checked further as "the user's whole path works".

hybrid retrieval; versioned migrations; open-source preparation; installer WebSocket post-mortem.

August: capabilities that connect, and that users can understand

0.1.20 distinguished credentials as not configured, decryptable or not decryptable, and stabilised the salt and key migration; search gained sources and error explanations, and models began to divide work by task. MCP OAuth, OpenRouter sign-in, first-run onboarding, extension manifests, local workspace reading and writing, scheduled tasks and SSH followed. With more extensions, the system also had to say precisely whether the current connection can call tools, whether equipment is in effect, and which action needs permission.

Local execution was layered too. Reading and writing the workspace were separated, with writes needing the matching permission; scheduled tasks have their own scheduling permission; SSH can remember a machine, but each remote execution still needs confirmation. The tool list now describes both capability and conditions of use. For the user, "connected" and "allowed to run this time" are different states, and both the interface and the model's context have to express that.

0.1.23's turn journal let an answer still being generated reconnect after switching conversations; the fix that let the installed app find npx showed again that a desktop app gets a different environment from a terminal. August's thread was less about connecting more services than about turning connections, states and permissions into operations users can understand.

September: from a single answer to traceable work

0.1.38 concentrated on reliability: a default-deny Python sandbox, a separate compute runtime, persistent Runs, artifacts, checkpoints and a shared execution budget. The 0.1.40 previews and stabilisation advanced project memory, document sources, task continuation and pre-migration backups, while keeping known failures in cross-language, multi-document comparison on record. A clickable source shows that material can be found; it does not prove the model's conclusion is right.

Somewhat earlier, from 31 August to 3 September, voice went from read-aloud (0.1.32) and push-to-talk (0.1.36) to half-duplex conversation (0.1.37), with fixes to microphone permissions and language selection. Meanwhile, 0.1.40's research acceptance did not rewrite the cross-language comparison failure as a success, and 0.1.41's source review stayed off by default after a disappointing calibration. These records bound what "the system checked it" means, and let the next improvements centre on real failures.

0.1.41 made closing the window leave Arslan working from the menu bar; 0.1.42 moved long tasks to the background so the user can keep chatting; 0.1.43 separated a soft budget limit from a hard stop — at the soft limit it wraps up with what it has, so research does not stop halfway without a deliverable. Tasks gradually gained a lifecycle independent of the interface, but that does not mean any external action can be safely replayed automatically after a crash.

Late September into October: converging on one execution loop

The early design treated experts as long-lived roles, and both user and system had to deal with choosing, inviting and routing. 0.1.44 stopped creating and dispatching experts, and old experts' methods can be converted into Skills; 0.1.46 stopped background expert evolution, which no longer had any consumer; 0.1.48 removed the front router, so every message goes straight into the agent loop. The release notes point out that some fixed "I can't do that" answers came from the routing decision rather than from real capability. This convergence put tool choice back inside the execution process that actually has the tools and the state.

After that, improvements concentrated on the shared execution layer: 0.1.49 completed the native tool protocol and truncation and failure recovery; 0.1.50 added the current working state, plans and alternative routes; 0.1.51 added the command sandbox and the Island; 0.1.52 brought user memory and learned practices into later work. "Learning" here means saving and using manageable practices, not updating a foundation model's weights.

0.1.53 goes further: a separate Hands helper reads accessibility trees and operates Mac apps, and the Mac side of the iPhone Bridge is included. The old expert orchestration is history, and accessibility-based operation cannot be extrapolated to "every app is reliably controllable". The current version still constrains what the model can actually do through visible state, explicit permissions and results you can check.

reliability foundations; scope of the stable research assistant; background work; the single agent loop; Hands and Bridge.

05 / ArchitectureWho is responsible for interface, execution and permissions

In one sentence: React is the workbench you see, Tauri is the shell that connects to macOS, Python is the engine that coordinates the work, the model supplies judgement, tools produce the real actions, and the database and disk keep the process and its results. These parts make up one desktop product, but they are not one process.

How one launch wires these processes together

  1. Tauri starts the frozen Python sidecar and shows a launch screen until the service is ready.
  2. The sidecar prefers local port 47317, falls back to an ephemeral port if it is taken, and reports the port back on standard output with an ARSLAN_PORT handshake.
  3. Once the shell has the port, the system WebView loads the React page served by the local service. Preferring a fixed port keeps the WebKit origin and local UI storage stable; the server-side conversation directory lets history be found again after a port change.
  4. The interface manages resources over HTTP and receives text streams, tool status, approvals and task progress over WebSocket. Local connections still need a token and an origin check.
  5. The shell keeps the standard-input pipe as a lifeline; when the parent exits and the pipe reaches EOF, the sidecar can clean up and exit. The output pipe must also be drained, so nothing blocks or is left as an orphan after the connection drops.

Together these details keep the window, service and database lifecycles consistent. A successful HTTP health check alone does not prove that WebSocket, attachments, static assets and the native helpers work; release acceptance checks each of them separately.

06 / Execution runtimeGiving every request a process, limits and a result

Arslan's execution core turns what you want into a series of observable actions: prepare the context, call the model, validate tool requests, execute what is allowed, read the real results, then decide whether to continue or deliver. In v0.1.53 the default entry point is the single loop, with EXPERTS_ENABLED=False; a message goes straight into answering, and long-term facts are extracted after the answer. Compatibility code from the historical expert system remains, but the main flow no longer starts with a model routing call.

Figure 2 · The execution loop. As text: input → context → model → argument validation → authorisation → tool execution → result back, then loop again; the model can also answer directly. Answers and files are checked before delivery, or the result honestly says what is not done; forbid and deny cannot be overridden by the model.

The model proposes the next step; the runtime sets the conditions

To the model, tools are a set of names, purposes and argument schemas. When it returns structured tool_calls, the runtime parses the JSON, validates the arguments, then re-checks that the tool is still available, that the budget allows it and whether the user must authorise it. Built-in tools map to executor functions through the registry; tools prefixed mcp_ go to MCP. A tool being in the registry does not mean it is offered in every turn.

One key boundary is response completeness: if the provider truncated a tool call at its output limit, none of that batch runs, even if one call looks complete. Model text that comes with tool calls is narration of the process; it cannot stand in for the final deliverable. Checkpoints are recorded before and after execution, and real tool results return to the model tagged with the call they answer; content from web pages, files or external tools is still handled as data.

So "I saved the file" has to correspond to an actual save result and a reference to the file; a sentence of promise does not turn into something that happened. A failed tool becomes input to the next round too; the loop can change route, but under the same permissions and budget.

Take "read this folder and make a list": the folder path enters the task's scope as input; the model asks to read it, the tool returns the real file information, and only then is there a basis for the list. If you then ask to move or delete files, the runtime decides authorisation for that operation separately. The delivery should point at the file actually produced and say how it was checked. The file listing, the action receipts and the file reference each serve as different evidence.

One entry point, different model protocols underneath

LLMAdapter provides one calling interface; each provider handles request formats, streaming events, tool calls and usage. Providers send HTTP requests with httpx; an OpenAI-compatible endpoint can also point at a local model server. With a cloud model, the request context goes to the provider the user configured.

Temporary helpers and background jobs have different jobs

delegate_work splits independent research across temporary workers: at most 4 per batch, at most 2 running at once. Workers currently get only web_search and web_extract; they cannot write files or personal memory, and cannot delegate further. The main executor takes the material back and is responsible for checking and combining it. Parallel research stays useful while responsibility for the work stays with the original task.

A background job is for a longer, complete task: it has its own context and budget, reuses the tool loop, deliverable checks and repair flow, reports progress back to the conversation through a task card, and by default at most 3 run at once. The network connection, the chat window and background execution each have their own lifecycle; switching conversations does not cancel a task. If the Mac sleeps or the process exits, background work is not handed to the cloud to continue.

Wrap up first, before the hard limit

The budget counts model requests, tool calls, cumulative tokens and running time together. At the soft limit, the loop should stop widening its research and organise what it has; the hard limit stops runaway consumption. Nested runs and retries count toward the task budget, and repeated calls that make no progress are detected separately, so the same failing route is not tried over and over.

Tasks, attempts and acceptance are recorded separately

TaskSpec holds the task contract — instructions, inputs, scope, acceptance checks and budget — with a revision number. A task can go through several attempts; an attempt is one concrete run. A changed contract, an old result returning after cancellation, and a new attempt after resuming must never write over each other's state. Persistent updates check both the attempt identity and the row version, so a stale run cannot overwrite newer state.

Acceptance results distinguish passed, failed, not run, not applicable and similar cases. A verdict needs matching evidence; agreed checks cannot be skipped, and not everything can rest on the model's self-assessment. File existence, which task a file belongs to and its digest can be checked deterministically; only subjective quality is suited to model or human review. While any action is still prepared, started or of unknown effect, the repository layer also stops the task from becoming a success.

This is also why a revised task must keep its identity: results produced for an old requirement do not automatically prove the new one is met. Acceptance must match the same contract revision, the same valid attempt and evidence owned by that task. Key checks cannot casually be marked "not applicable"; only non-key items that fit the contract's rules can be. When evidence is missing, the result stays unverified or incomplete until it is checked.

Resuming continues from existing evidence

Checkpoints keep progress, budget used, evidence and file references; run events let the interface catch up after reconnecting. The in-process run registry holds the actual async tasks and their cancel handles and dispatches events to connected windows; on reconnect it takes a snapshot and attaches the event stream in one synchronous step, to avoid dropped or duplicated frames at the handover.

After a process restart, unfinished runs are recognised as interrupted and continue only when the user explicitly resumes them. An external action that was sent but never acknowledged has an unknown effect; it must be checked before anything is resubmitted. Restoring a backup also revokes old action grants and marks the affected actions as uncertain. A checkpoint answers "where can we safely continue from"; it cannot undo external results that already happened.

Stopping also has two layers: the run registry cancels async work that is waiting or running, and persistent state stops late results from being committed. For a request an external system already accepted, cancelling the local wait does not prove the other side did nothing. So the action table distinguishes prepared, started, confirmed, failed, uncertain and cancelled, and resuming deals with those states before deciding which steps may be retried.

07 / Data and memoryKeeping useful context, and clear data boundaries

Arslan keeps its main state in SQLite on your Mac: conversations, run records, tasks, personal memory, model configuration and usage each have a data model. Deliverables are written to disk; the full text of very long tool output is stored separately in the app's data folder (kept for 7 days), and the model reads it in parts from the path given in the result. Closing a window therefore does not erase a task's process, and "what was said", "what was actually done" and "what may be remembered later" can be managed separately.

Data access uses async SQLAlchemy with aiosqlite. Connections enable WAL, foreign-key checks, a 5-second busy timeout and synchronous=NORMAL. These choices suit a single-user local app: fewer deployment dependencies and better behaviour when reads and writes overlap. The data folder also has a cooperative process lock, so instances that follow the same protocol do not use the same data at once.

Working context: control this turn's input, keep the raw history

A model can only take in so much at a time, so Arslan builds the working context from a bounded rolling summary plus recent messages. This history window has a default estimated budget of 3,000 tokens, and the summary itself is length-limited too. That is the budget for assembling history, not the size of the whole request: system instructions, tool schemas, material and results take up other space.

As a conversation grows, older messages can be folded into the summary while recent messages stay verbatim. Compaction changes what is assembled next time; it does not delete the full conversation from the database, and if compaction fails the original record is kept. Very long tool output is stored separately: the model gets the head and tail plus a file path and reads more in parts when needed, and the full output is cleaned up under its retention policy.

This layering lets the model see what the current task needs first, while keeping the originals for later checking. A summary is a compressed view of what exists; it cannot replace the real receipt of an external action.

Personal memory: first whether it may be used, then whether it is relevant

A memory entry has a type, scope, sensitivity level, use policy, state, confidence and version. The scope can be global or a project (with internal scopes such as domain and expert), and each entry also has an owner; use policies such as local_only further decide whether content may go into a cloud model request. Each turn's trusted context loads conversation settings from the database; ordinary user text, web pages or model output cannot rewrite these permissions.

Retrieval: keywords and vectors can be combined

The knowledge retrieval module supports SQLite FTS5 full-text search and vector cosine-similarity search. The first finds word matches; the second uses embeddings to find semantically related passages; when both are available, their rankings are fused with RRF. RRF compares rank positions rather than mixing raw scores on different scales. Without embeddings, or without vectors, full-text search still works.

Retrieved passages enter the model's context with their sources, and the model uses them to answer the current question — that is what RAG means here. With memory v2 active, material retrieval runs only in projects that have bound collections; with a cloud model, the conversation's own cloud-memory permission must also be on (the default "Remember me" switch does not cover material). Results enter the context as the return value of the recall tool. None of this changes the foundation model's weights or needs a separately deployed vector database. Personal-memory v2 selection mainly uses permission filtering, full-text and local relevance logic; it does not follow that every memory goes through the same vector pipeline.

Learned practices: turning corrections into reviewable rules

A Lesson records a user correction, a detour that worked after a failure, or a quirk of this machine. For example, if a command needs different arguments on this Mac, that can become a practice with its source, for similar tasks to consult. Recall takes at most 5 items, about 800 characters in all, placed in the dynamic agent status rather than the stable system prefix; recalls, follows, successes and failures are each counted.

Whether something is worth saving, or duplicates or conflicts with what exists, can be put to the judgement layer as a narrowly scoped question, with the probability and later outcome recorded. User corrections, and practices not influenced by external content, can take effect directly when settings allow and the judgement finds them valuable; anything else needing review becomes a proposal. Candidates containing credentials are dropped outright; the rule that inferred sensitive information needs review belongs to personal memory, not to practices. There are fallbacks when the judgement is missing or times out.

These mechanisms change what the app saves and recalls; they do not train model weights. Judgements are enabled to different extents: for example, when the tool-approval judgement runs in shadow mode it only records a suggestion, and the real authorisation flow still decides whether something runs.

Source: hybrid retrieval; extracting and recalling practices; small judgements and their modes.

Deletion has to reach summaries and old backups

When a memory is deleted, the system raises the deletion epoch, erases that entry's old revision text and sources, and clears every conversation's rolling summary and the prompts cached in run records, so old derived content cannot bring the deleted memory back. The deletion record keeps only a content fingerprint for matching (an HMAC with a local key) plus metadata such as scope, so the deleted text is not saved again in the ledger; a suppression record stops the same source, still in the chat history, from automatically recreating the memory. Deleting a memory and deleting the original conversation are different operations.

A separate deletion ledger and deletion manifest keep deletions applied on start-up and restore paths. Before an old backup is restored, the system checks the store's identity and reconciles the staged data against the deletion records before activating it, reducing the chance that an old backup resurrects deleted memories. This depends on the restore flow and the deletion records available; it cannot recall copies already exported elsewhere.

The rest of the memories in a backup do not regain all their permissions immediately either: restoring quarantines them for review, tightens use policies, clears cached context, disables all scheduled tasks, revokes per-conversation cloud and sensitive permissions, and archives active projects. Restoring data and re-approving its use are done separately, so old conversation permissions do not silently take effect in a new environment.

Migrations finish before the app starts using data

Database upgrades use an explicit migration runner: check the schema version, prepare an upgrade backup, create missing tables, run pending migrations in order, then handle key compatibility and memory v2 activation. Unknown or newer schemas are refused, so an older program never blindly modifies newer data. In v0.1.53 the explicit registry goes up to 0061; the early Alembic history is not the current mechanism.

When memory v2 activates, the old fact and learning tables are renamed to legacy tables with read-only triggers, compatibility views map old read paths to the new structure, and the full-text index is built at the same time. Secret fields — model API keys, MCP environment variables and OAuth tokens, SSH keys and the like — use Fernet field-level encryption (PBKDF2 plus a salt unique to each install); ordinary conversation and task tables are not thereby encrypted as a whole database. Persistence, secret protection and backup-restore each have specific boundaries.

Extensions are a new trust boundary

A local stdio MCP server usually means starting a separate process; an HTTP MCP server may connect to a remote service. Arslan manages separately whether a connection exists, whether the main assistant can use it, whether its tools are exposed, and how its credentials are stored and shown. Configured environment values are stored encrypted and masked when shown.

These constraints reduce accidental exposure and mistaken execution, but a real MCP server can still access whatever it is given. Where a tool comes from, what it needs, what data goes to a remote service and what side effects it has are all part of what an extension must explain.

Why parallel research still exists

The single agent loop keeps constrained, temporary read-only workers. In v0.1.53 a batch has at most 4, and at most 2 run at once; their tools are limited to search and web extraction, they write no files or personal memory, and they cannot create more workers. The main assistant checks and combines their results.

This kind of delegation suits splitting up independent lookups. Its lifecycle differs from the early permanent expert personas: you are not asked to pick or manage a team of experts first, and messages are not forced through to another "expert". Whether to use parallelism should still depend on whether the task splits well, and on the cost of the extra calls.

Background, scheduled and heartbeat

A background job separates long execution from the current chat, reusing the same model, tools and acceptance logic. A scheduled task persists "when to start"; the heartbeat is one way of periodically working through a checklist — off by default, it checks and suggests. A scheduled trigger never turns a suggestion into an approved write or command.

Scheduling is implemented in the local service, with overlap skipping, pausing after failures and clean-up after a restart. Missed runs are not replayed one by one; if the previous run of the same task has not finished, the next one does not start on top of it. This suits a personal desktop app, and it also means its operating conditions differ from a server that is always online.

Approval is bound to the exact action; background work does not inherit every convenience

An approval card is tied to its call_id and action kind, so a reply of the wrong kind cannot approve a different card. A card shown in both the Mac window and on the phone takes the first valid answer and broadcasts the closed result to the other views; unanswered, it expires after 300 seconds. Background jobs do not inherit a connection's session grants and never offer "remember this command". For external side effects, sending a request is not the same as completing an action. Hands keeps the system permission in a smaller process

Accessibility is granted to Arslan Hands.app, not the main app. The signed release accepts requests over a protected Unix socket, with a token generated at each launch and a peer signature check. The limits are public too: only windows on the current Space are visible, reading a large window can take 10–20 seconds, and a call cut short by Stop may have no matching trace row — the audit trail is not a complete forensic record of every interruption.

A host environment that is already compromised with the current user's permissions does not become trustworthy because of a local token.

CloudKit is a mailbox; the protocol still establishes device identity

v1 uses the CloudKit private database under the same Apple ID. The Mac must be on, online and able to run; otherwise messages wait, and the phone cannot make a Mac that is switched off keep working. Scanning the QR code only starts pairing

The QR code carries a one-time pairing_id, the Mac's signing and exchange public keys, a 32-byte pairing key, the fixed container identifier and an expiry. It is valid for at most 600 seconds; the phone rejects expired codes, the wrong container and anything outside the constraints, and pins the Mac's public keys from the code. The phone then creates its own identity and exchange keys and sends an encrypted pairing request. Even after the Mac verifies the request, it shows it to the user, and a click on the Mac accepts or rejects it.

Retrying the same request must get the same decision, never a second grant. Once accepted, the devices communicate by identity and the pairing code is consumed; the Mac can revoke the phone. Each device keeps its private keys in its own Keychain. Trust here comes from one-time pairing material combined with the user's confirmation, not from "same iCloud account, so any message is trusted".

Every message is checked for content, sender and context

Each new message agrees a shared secret with an ephemeral X25519 key, derives a 32-byte key with HKDF-SHA256, encrypts and authenticates with ChaCha20-Poly1305, and is signed with Ed25519. The header uses length-prefixed UTF-8 fields, so differences in JSON ordering across languages cannot affect verification; header fields are bound by both the signature and the AEAD authentication. This is an application protocol built on CryptoKit primitives; it does not implement the Signal double ratchet, and forward secrecy in every scenario should not be claimed from ephemeral keys alone.

The receiving order is fixed: check the shape and the recipient, verify the signature, then decrypt; then check the plaintext against the header fields, and verify any attachment. A failure at any step must leave no partial business effect. Files are limited to 20 MiB, and the ciphertext digest, authentication tag, plaintext size and digest must all match before a file is cached or previewed.

12 / Testing and evaluationHow to tell whether a task was done right

A task that finished, a file that opens and a report whose content is correct are three different judgements. Arslan uses run records to show what happened, checks deliverables and contracts to verify what can be determined, and uses real-task evaluations to observe how models perform. Passing one layer cannot stand in for the others.

This section brings together the public source, release notes and past experiment records. The numbers belong to their own versions and environments; they do not mean every test was re-run while this was written, or that every feature has been accepted on real devices with real models.

First, break "done" into checkable evidence

Did it actually run?

Did the tool call return? What was the exit code? Did the action clearly succeed, clearly fail, or is the outcome unknown? A model writing "done" cannot replace tool evidence, and a side effect with an unknown outcome cannot be treated as safe to run again.

Does the deliverable hold up?

Does the file exist, belong to this task, match its byte count and hash, and parse? A spreadsheet that opens does not mean its data is right; an image of the right size does not mean its layout is acceptable.

Was the requirement met?

If ten valid results were asked for, six do not meet it. Citations must match conclusions; having read a page does not prove it supports a claim. This layer still needs task-specific checks and human judgement.

The task acceptance system keeps rule checks, model evaluation and human review distinct. Text, JSON, file integrity, image size and actual execution results can be checked deterministically; model evaluation covers only what it is suited to judge, and cannot turn a check that never ran into a pass. A deliverable that parses proves its structure is readable, and a record of reading a source proves the system got the content; neither automatically proves facts or visual quality.

13 / Engineering directionsFrom what exists to more reliable delivery

Arslan has three foundations: execution, ongoing work and memory. What is worth verifying next is whether these hold correct state, give reliable results and leave the user in control in more complex situations. The diagram separates what is implemented, what still needs verifying and optional engineering directions; it is a technical discussion, not a dated release commitment.

Figure 4 · Capability blueprint. As text: three foundations — execution, ongoing work, memory → cross-device and reliability acceptance → suggested priorities: real completion rate, a recovery contract, controlled learning trials. Suggestions are not shipped commitments.

Real-task results

A fixed task set should cover search completeness, citations matching conclusions, files that open, where system operations actually land, and whether a failure is wrapped up honestly. The existing comparison exposed gaps in research tasks; before widening the tool list, locating at which step "not found, not fully read, not verified, not delivered correctly" happens does more for the completion rate.

Recovery and consistency across devices

Network retries, duplicate messages, app restarts and user cancellation can happen at the same time. Further verification can centre on stable business IDs, final states that old messages cannot overwrite, behaviour after an approval is cancelled, and the checking path when a side effect is unknown. Crash injection and protocol negative cases can make clear which cases can be handled automatically and which must go back to the user.

Measurable gains from learning

A practice being remembered is only the start. Completion rate, call cost, time and wrong behaviour need comparing repeatedly, with and without the practice, on the same tasks and models. It also needs checking whether stale practices get corrected, whether external text can contaminate practices, and whether a deleted practice is still recalled.

The cost of platforms and extensions

Tauri provides a cross-platform host, but Seatbelt, Vision, Accessibility, Apple Events and CloudKit are all platform-specific. Moving to another desktop system means replacing and verifying these capabilities; a cross-platform compile is not the same as the product's features having moved. More external tools likewise mean more credentials, permissions and failure modes.

These directions are drawn from the current implementation and test results. Actual priorities and dates are whatever later release notes say.

15 / FAQWhat is easiest to mix up when using and understanding Arslan

How is Arslan different from chatting with a model on its website?

Beyond the model, Arslan provides local files, tools, task state, memory, permissions and desktop integration. The model judges and generates; the app turns tool requests into controlled execution and records the results. Its value depends on whether the whole process gets a specific task done.

Was it built by one person with AI?

Yes. The author builds and iterates on Arslan alone with AI-assisted development — vibe coding. The product uses open-source frameworks, third-party components and external models, whose sources and licences are recorded in the project documents.

Does everything stay on my Mac?

Data is primarily stored, and execution orchestrated, on your Mac. When you use a cloud model, search, a remote MCP server or similar, the relevant requests go to that service. Memory also has its own cloud-use permission and sensitivity rules; local-first does not mean always offline.

Can I switch models, or use a local one?

You can configure a supported provider or a compatible endpoint, including an OpenAI-compatible local server. An endpoint connecting only proves the transport works; tool calling, images, reasoning continuation and context length still depend on that model and its adapter path.

Early docs mention many expert personas — why is there only one Arslan now?

The product converged. 0.1.44 stopped creating and dispatching experts, 0.1.46 turned off the old automatic evolution loop, and 0.1.48 removed the front router. Old methods can be converted into Skills, historical data stays compatible, and constrained read-only workers are still used for independent research.

Are memory, the knowledge base and chat history the same thing?

No. Chat history records conversations, and the working context picks recent content plus a summary; personal memory keeps preferences, facts and rules with their sources and permissions; knowledge retrieval finds relevant passages in imported material. The three differ in how they are stored, recalled and deleted.

Does "learning" train the model, or let it give itself more permissions?

No. Learning today records reusable methods and recalls them in later tasks; it does not change foundation-model weights or execution permissions. The records show practices can be captured, recalled and followed; a general speed-up or cost saving still needs more controlled experiments.

Do all commands run in an offline sandbox?

No. The default Python compute sandbox denies the network; the ordinary terminal's workspace sandbox usually keeps network access and has its own fallback behaviour. Tool permissions, command policy, system permissions and sandboxes are different layers; the security chapter has the details.

What happens to a task when I close the chat window?

Connections and tasks are managed separately, and a background job can run while the app's service keeps running; closing the window is not the same as quitting the process. If the service exits or the Mac sleeps, the task cannot keep relying on local execution. After a restart, interruptions are checked from the records, and the task resumes explicitly along a supported path.

Does resuming automatically re-run every earlier action?

No. Resuming checks the steps already taken and their external effects, and unknown side effects are checked first. Task attempts, action states, checkpoints and version constraints help stop old results overwriting new state, but they cannot guarantee exactly-once execution for every external system.

Can Hands operate any Mac app?

Compatibility depends on the Accessibility structure the app exposes, system permissions and Arslan's action rules. Being able to read a control does not mean every business operation can be completed safely. Sensitive buttons and keys trigger finer-grained confirmation, and some apps or controls may still not be supported.

Can the iPhone get work done while the Mac is off?

On the Mac Bridge path the Mac still does the work; when it is unavailable, messages wait in iCloud. v0.1.53 shipped the Mac side of Bridge, which does not mean the iPhone app is on the App Store. The phone showing a message as received does not mean the task is done either.

If all tests pass, can any real task be done?

Each test only covers its own conditions: unit tests check local logic, protocol tests check boundary consistency, installer acceptance checks the artifact, and real-task comparisons check results for a given model and task. Models, web pages, system permissions and external apps can all change the outcome.

Why is the version still 0.1.x?

The project is still in pre-v1 continuous iteration. More than fifty version numbers reflect that history; judge maturity by specific capabilities, failure handling, test coverage and release status. The full version appendix in this document keeps those distinctions.

Summaries combine the official release notes with the commits between neighbouring tags, and never describe something that exists only in a planning document as delivered. To check a specific implementation, pin to that version's tag or release commit, rather than reading the past through the ever-changing main branch.
