11 / 验证与软件交付从能运行的源码，到可以安装和更新的应用

桌面软件的交付单位是应用包。源码环境中存在的 Python 模块、系统工具和旧数据库，都可能让一个缺少资源的安装包看起来正常。Arslan 将验证分成源码、平台、冻结产物、全新用户环境和分发几个层次。本章记录 v0.1.55 的流程及对应发布证据。

CI 同时检查行为、平台与依赖边界

检查组主要内容设计目的
Linux 后端Python 3.11、uv frozen lock、Ruff、pytest；显式安装并检查 OCR 测试依赖。执行完整后端测试，保留“缺少 macOS 隔离时必须拒绝”的平台负例。
macOSSwift 语音 helper 类型检查、Bridge 构建与测试、Rust fmt/test/clippy、Hands 检查、原生 Python 用例。让最终交付平台上的 Vision、Seatbelt 和宿主代码进入常规验证。
前端Node 22、npm ci、TypeScript 类型检查、Vitest、生产构建。覆盖状态与组件行为，并确认生产资源可以生成。
历史与供应链gitleaks 扫完整 Git 历史并脱敏输出；Hands 固定上游 commit、校验 vendored 文件，以 cargo-deny 检查依赖。避免只检查最新 diff，或让构建悄然使用变动的外部源码。

其中 macOS 测试并不只接受 pytest 的退出码。流水线解析 JUnit，要求 49 个指定平台用例实际执行、零跳过且无失败；缺依赖导致全部跳过也会拒绝通过。Python 与 Rust 共享 Hands 契约样例，Mac、iOS 与独立 Python 参考实现共享 Bridge 向量，使参数映射、签名、收件人、篡改和重放的边界可以跨语言核对。

这些结果仍有范围：Swift 类型检查不验证麦克风授权，Linux 单元测试不验证 macOS 内核，模拟信箱不验证生产 CloudKit。测试数量也不是整体覆盖率；重叠套件不能相加成独立场景数。

Release workflow 查询将发布的 SHA 是否有成功 CI，另一个提交通过不能替代。构建使用受锁文件约束的依赖；Python 明确选择 uv 管理的独立解释器，防止 runner 偶然选中 framework build。后端以 PyInstaller onedir 冻结，前端静态资源和 Swift/Rust helper 随 Tauri 应用一起装配。

签名与公证各有作用。内嵌 Mach-O 需要先签名，再由外层应用封装；Developer ID、hardened runtime 和时间戳用于发行。DMG 提交 Apple 公证，随后 staple 票据并用 Gatekeeper 检查。构建脚本保留无签名开发包以及缺少部分凭据时的警告路径，所以“能构建”不自动等于“已经满足公开分发条件”；正式发布应核对真正得到的产物。

更新清单还有独立约束：tag 必须与 Tauri 版本一致；有 updater 签名才生成对应 manifest。流程生成 GitHub Draft Release，正式发布后，已安装应用才会在后续检查中看到该更新。

全新安装验收直接启动应用包

fresh_install_check.py 使用临时 HOME 和最小环境启动包内真正的 arslan-desktop，不是在源码 venv 中替它启动服务。检查包含包内没有混入用户数据库或秘密文件、首启初始化、token 的生成与文件权限、未认证请求拒绝、真实 WebSocket 101 握手，以及前端 JavaScript 能被正确取得。HTTP 200 可能只是 SPA 的兜底页面，因此资源检查不能只看状态码。

同一脚本还检查原生 OCR、嵌入 helper、Bridge 自检和相关签名。历史上冻结包曾漏掉动态加载的 WebSocket 依赖：健康接口正常，聊天却不能升级连接。这个问题说明，导入成功、服务存活和核心功能随包交付是三种不同的证据。

更新由用户触发安装，并验证下载内容

Tauri updater 从公开的 latest.json 发现更新，用编译在应用中的公钥验证归档签名。应用启动检查一次，菜单也可以手动检查；本版没有周期检查 timer。发现新版本显示提示，用户点击安装后才下载、验签、替换并重启。自动检查失败可以是暂时离线，安装失败则需要向用户明确反馈。

早期 0.1.0/0.1.1 只注册了 updater 插件，没有主动调用检查函数，不能自动发现版本。当前实现把检查、可安装状态、下载失败与重启串成显式流程；有签名配置并不等于流程已经被触发。

0.1.55 的交付证据对应哪个对象

发布提交的 GitHub Actions 记录显示：发布源码为 81c0028c；该提交的 CI 首次尝试即通过（run 37729747101），其中 macOS 任务的 49 个指定平台用例零跳过，后端测试 6,324 项通过、119 项跳过。发布流程（run 37729747033）的源码验证、构建和发布步骤通过；DMG 公证被接受并 staple，Gatekeeper 接受。发布应用的 fresh-install 检查 89 项通过、0 项失败，包括 Hands 接受签名后端的连接和 Bridge 自检。0.1.54 在同一检查中为 87 项通过、0 项失败，CI 同样首次即通过。

验证对象各不相同，记录也要分开说。0.1.55 的公开说明中没有真实 Mac 上的手工实测记录，因此本文不声称这份精确的 0.1.55 DMG 被手动安装并完整操作过，也不声称用发布版完成过 iPhone 到 Mac 的完整链路。作为对照，0.1.53 的 Verification 记录过一次真实 Mac 实测：通过 Hands 创建并读回 Notes、审批等待 36 秒——用的是 43751254 的 build-only 包，而非最终 DMG。自动包验收、较早构建的功能实测与精确发行包手工验收应分别陈述，不能互相替代。
