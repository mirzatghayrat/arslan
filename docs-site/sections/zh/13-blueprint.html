13 / 工程方向从已有能力，走向更可靠的交付

Arslan 已建立执行、持续任务与记忆三条基础。下一阶段值得验证的，是这些能力在更复杂场景中能否保持正确状态、给出可靠结果，并让用户保有控制。下图将已有实现、需要继续验证的环节和可选工程方向分开；它是一份技术讨论，不是带日期的发布承诺。本章反映 v0.1.63；计划在 0.1.64 中做的事会标明是计划，而不是已经做成。

计划在 0.1.64 中做（只是计划，尚未实现；来自已批准的 0.1.64 计划）：先做一个默认拒绝的沙箱，管住命令、Python 和安装的工具。然后恢复“只在有风险时问”。再之后是一个可选的“自动”模式：由一个审查模型替你回答一部分卡片；它默认关闭，只有达到事先定好的合格线才会发布，而且绝不批准任何离开沙箱、向外发送或联网的操作。届时会有五种模式，在输入框旁按对话选择：计划、每步都问、自动编辑、完全访问和自动；设置里只保留新对话的默认模式。定时任务会重新可以运行只读命令。在此之前，每条新命令都先询问，定时任务不运行命令。一个列出并可撤销已记住回答的页面，以及一个允许文件夹的设置，目前仍在考虑中，不在计划里。0.1.63 的说明还列出了针对已知限制的两项修复：在同一条命令里切换文件夹之后再删除，被错误地当作在工作文件夹之内；以及对长文件的一行改动是通过终端而不是编辑工具完成的。

图 4 · 能力蓝图。纯文本：已有执行、持续任务、记忆三条基础 → 跨设备和可靠性验收 → 以真实完成率、恢复契约、学习对照实验为优先建议。建议不是已上线承诺。

真实任务效果

固定任务集应覆盖搜索完整性、引用与结论对应、文件可打开性、系统操作的真实落点，以及失败后是否诚实收尾。已有对照暴露了研究任务的差距，而 0.1.63 的发布前运行（九个任务，每个跑三次，在 DeepSeek 和 Claude 上）错过了自己的两项标准：被拒绝的删除之后另找办法（Claude 3 次中 0 次，因为在“只在有风险的命令时询问”下，工作文件夹内的删除不出卡片直接运行）以及对同一份文档做三次后续编辑（DeepSeek 3 次中 1 次，Claude 0 次）；扩大工具列表之前，先定位“没找到、没读全、没验证、没正确交付”分别发生在哪一步，更有助于改善完成率。

恢复与跨设备一致性

网络重试、消息重复、应用重启和用户取消可能同时发生。后续验证可以围绕稳定业务 ID、终态不可被旧消息覆盖、审批取消后的行为，以及副作用未知时的核对路径展开。通过崩溃注入与协议负例，明确哪些情况可自动处理，哪些必须回到用户确认。有一块已经做出：自 0.1.63 起，一个回合第一次改动工作文件夹之前会保存一个检查点，“撤回这一轮”会恢复文件并把这一回合移除。它有局限：只保存最多 20,000 个文件、5 GB 的文件夹（不计 Python 环境、node_modules、构建输出和 Python 缓存），保存不了时显示“未保存”；它只覆盖工作文件夹，不覆盖其外的效果。

可测量的学习收益

经验被记住只是起点。需要在相同任务和模型条件下，反复比较有经验与无经验的完成率、调用成本、耗时和错误行为。也要检验过时经验是否会被纠正、外部文本是否可能污染经验，以及删除后是否仍被召回。

平台与扩展的代价

Tauri 提供跨平台宿主基础，但 Seatbelt、Vision、Accessibility、Apple Events 与 CloudKit 都有平台特性。扩展到其他桌面系统，需要替换并验证这些能力，不能把一次跨平台编译当成产品功能已经迁移。更多外部工具同样意味着更多凭证、权限和失败模式。

以上为基于现有实现与测试结果整理的工程方向。具体优先级和排期，以后续正式发布说明为准。
