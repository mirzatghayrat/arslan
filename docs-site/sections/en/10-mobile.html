10 / iPhone and Mac BridgeThe phone asks and watches; the Mac does the work

The mobile bridge lets a paired iPhone see the Mac's tasks, start work, answer approvals and read results. Execution still happens in Arslan on the Mac; the phone is neither a separate cloud agent service nor something that exposes or calls the Mac's HTTP interface directly. This chapter is based on the public protocol and source of Mac v0.1.55. That release includes the Mac Bridge; its public release notes still describe the iPhone app as coming to the App Store, and this document does not claim an App Store release or full production end-to-end acceptance on that basis.

CloudKit is a mailbox; the protocol still establishes device identity

v1 uses the CloudKit private database under the same Apple ID. The Mac must be on, online and able to run; otherwise messages wait, and the phone cannot make a Mac that is switched off keep working. Bonjour on the local network is a later direction, not a fallback direct channel in this release. The Mac helper is a separate ArslanBridge.app that runs with the app, receives the local API token on stdin and then connects to the backend; the phone never holds that token or receives model API keys.

The envelope fields visible in the cloud index include the sending and receiving devices, sequence number, a coarse kind, a notification flag and time. The real message type, body and file content are inside application-level ciphertext. So "end-to-end encrypted" describes protection of messages between paired devices; it does not mean there is no metadata, nor that backend model calls bypass the AI service the user configured.

Scanning the QR code only starts pairing

The QR code carries a one-time pairing_id, the Mac's signing and exchange public keys, a 32-byte pairing key, the fixed container identifier and an expiry. It is valid for at most 600 seconds; the phone rejects expired codes, the wrong container and anything outside the constraints, and pins the Mac's public keys from the code. The phone then creates its own identity and exchange keys and sends an encrypted pairing request. Even after the Mac verifies the request, it shows it to the user, and a click on the Mac accepts or rejects it.

Retrying the same request must get the same decision, never a second grant. Once accepted, the devices communicate by identity and the pairing code is consumed; the Mac can revoke the phone. When the same iPhone pairs again it names its earlier ids, and the Mac removes those entries instead of keeping two. Removing a phone also deletes the messages the Mac had left for it in iCloud, and at start-up the Mac clears what still waits for phones no longer paired. Settings › iPhone shows each phone as Connecting… until the Mac has read an authenticated message from it, then Connected with when it was last seen. Each device keeps its private keys in its own Keychain. Trust here comes from one-time pairing material combined with the user's confirmation, not from "same iCloud account, so any message is trusted".

Every message is checked for content, sender and context

Each new message agrees a shared secret with an ephemeral X25519 key, derives a 32-byte key with HKDF-SHA256, encrypts and authenticates with ChaCha20-Poly1305, and is signed with Ed25519. The header uses length-prefixed UTF-8 fields, so differences in JSON ordering across languages cannot affect verification; header fields are bound by both the signature and the AEAD authentication. This is an application protocol built on CryptoKit primitives; it does not implement the Signal double ratchet, and forward secrecy in every scenario should not be claimed from ephemeral keys alone.

The receiving order is fixed: check the shape and the recipient, verify the signature, then decrypt; then check the plaintext against the header fields, and verify any attachment. A failure at any step must leave no partial business effect. Files are limited to 20 MiB, and the ciphertext digest, authentication tag, plaintext size and digest must all match before a file is cached or previewed.

Delivered, done and final on screen are three different things

MechanismResponsible forLimit
Persistence and same-packet retryA retry reuses the same envelope ID, seq and ciphertext; sequence numbers and other key state are saved first, so a network failure cannot roll state back.A delivery log cannot stand in for an external business system's transaction.
Replay windowPer sender, the last 1,024 sequence numbers are kept; new out-of-order packets inside the window are accepted, duplicates and packets that are too old are dropped.A valid new sequence number does not necessarily mean a business-state update; old progress may also be sent late.
ACKConfirms an envelope was delivered; a duplicate can be ACKed again. The original record is deleted once acknowledged, and ACKs themselves are not ACKed.An ACK does not mean the task succeeded or that an approved action was carried out.
Business IDs and resultsclient_msg_id and client_task_id prevent duplicates; approval.result, task events and results carry business state.In v0.1.55 the business-ID mapping has in-memory state, so global exactly-once across arbitrary crashes cannot be promised.

The Mac's status snapshot lists only tasks still running; the normal heartbeat is every 60 seconds, and the phone treats a Mac it has not heard from for 90 seconds as offline. Progress is throttled and merged; final states should be sent promptly. The client must therefore handle duplicate and out-of-order messages while making the task list, approval cards and history converge — "the last text received overwrites the previous one" is not enough to maintain state.

Approving on the phone reuses the Mac's authorisation and execution path

The phone shows the exact action, target and risk. Approving requires the phone's biometrics; denying does not. After answering, the phone waits for the Mac's approval.result. The Mac checks that the card is still valid and maps the answer to the original confirm / cancel operation; the phone can never grant a command "always allow". The voice entry can produce text awaiting confirmation; it cannot stand in for approval.

Version boundary: since v0.1.54 the Mac counts an approval only with the faceid or touchid marker (Touch ID for iPhone SE), and says so in its capabilities; any other marker is a no. Before 0.1.54 a Touch ID yes was treated as a cancel. The protocol's high_risk_mac_only is fixed at false in this release and is not yet a user setting. Shared protocol and test vectors can verify interoperability and negative cases; they cannot replace end-to-end acceptance of the final distributed app with real iCloud, push and device authentication.
