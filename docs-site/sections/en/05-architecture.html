05 / ArchitectureWho is responsible for interface, execution and permissions

In one sentence: React is the workbench you see, Tauri is the shell that connects to macOS, Python is the engine that coordinates the work, the model supplies judgement, tools produce the real actions, and the database and disk keep the process and its results. These parts make up one desktop product, but they are not one process.

Figure 1 · Current architecture. As text: workbench ↔ local service → single agent loop ↔ model; execution loop → tools → system / files; state in SQLite and on disk. The iPhone talks to the Mac Bridge through CloudKit, not to a public API on the Mac.

Why these layers

BoundaryWhat it buysWhat it costs
React ↔ local serviceChat, settings, graph and other UI are separated from execution logic; model streams and tool events show liveA protocol, reconnection, streaming state and authentication to maintain; an open page does not mean a task is still alive
Tauri ↔ Python sidecarKeeps Python's model and document ecosystem while giving a normal Mac install experienceMulti-language packaging, dynamic dependencies, port discovery, process exit and signing all need handling
Model ↔ tool executorThe model proposes actions; deterministic code validates, authorises, executes and records themMalformed arguments, unknown tools, truncated responses, repeated failures and cancellation must be handled
Separate Hands helperA separate process holds the Accessibility permission, with app-level and action-level rulesCode signing, process identity, system permissions and app differences become extra maintenance
Mac ↔ iPhoneWhile the Mac is on, online and awake, you can make requests, see results and handle supported approvals away from itWhen the Mac is unavailable, messages wait in iCloud; retries, reordering, recovery and consistent final states must be handled

How one launch wires these processes together

  1. Tauri starts the frozen Python sidecar and shows a launch screen until the service is ready.
  2. The sidecar prefers local port 47317, falls back to an ephemeral port if it is taken, and reports the port back on standard output with an ARSLAN_PORT handshake.
  3. Once the shell has the port, the system WebView loads the React page served by the local service. Preferring a fixed port keeps the WebKit origin and local UI storage stable; the server-side conversation directory lets history be found again after a port change.
  4. The interface manages resources over HTTP and receives text streams, tool status, approvals and task progress over WebSocket. Local connections still need a token and an origin check.
  5. The shell keeps the standard-input pipe as a lifeline; when the parent exits and the pipe reaches EOF, the sidecar can clean up and exit. The output pipe must also be drained, so nothing blocks or is left as an orphan after the connection drops.

Together these details keep the window, service and database lifecycles consistent. A successful HTTP health check alone does not prove that WebSocket, attachments, static assets and the native helpers work; release acceptance checks each of them separately.

Old and new architecture: reuse what works, retire expert dispatch

History

Multiple experts / Meta-Agent

User → front router → choose or create a Spawn → expert runs → summarise; expert prompts could go through held-out evaluation and a human Promote. The product required users to understand expert identity, equipment, the roster and evolution.

0.1.56 main path

One Arslan / single loop

User → one agent loop → load Skills and call tools as needed → result; ordinary facts are extracted after the answer. Old experts can be converted into Skills and their history is kept, but expert routing is no longer the main execution path.

"Single loop" does not mean "everything is serial" or "never delegates". The code still has constrained read-only workers; they are not the early expert product with its own personas, equipment, evolution and routing.
