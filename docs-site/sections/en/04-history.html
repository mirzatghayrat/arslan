04 / How it got hereFrom generating experts to one Arslan that keeps working

Arslan has been developed continuously by its author alone, with AI-assisted vibe coding. Its history includes new capabilities and withdrawn designs: some features needed their missing conditions filled in, some complexity needed deleting. Understanding those changes explains today's architecture better than listing every historical feature side by side.

A timeline with stated limits of evidence. Early dates come from preserved Git commits; release dates come from public Releases; all are in Beijing time (UTC+8). The first commit, open-source preparation, the repository going public and the first release are different moments. The records cannot establish exactly when the repository became public; the current public repository was created on 26 July 2026.

June: first, a loop that generates agents through conversation

The earliest preserved commit, on 7 June 2026, starts with data models. The direction then was a Meta-Agent: let non-technical users create domain experts by talking, and have those experts do the work. Model adapters, a tool registry, a requirements-dialogue state machine, templates, a Spawn Manager and a CLI followed. On 8 June, FastAPI, an async database, authentication, WebSocket and a React interface were connected, giving the prototype an interactive entry point that could save its state and resume connections.

Once tools really ran, the system needed to know "what was executed" and needed material to ground answers in. On 23 June, Runs, Steps and Evaluations arrived, together with document chunking and SQLite FTS5; on 27 June, MCP's stdio and HTTP transports were connected. These changes moved the project from generating an expert prompt to managing a whole run: call the model, run tools, save the process, retrieve material, and hand the result back.

earliest data models; Runs data model; FTS5 knowledge index; MCP HTTP transport.

July: memory and delivery become engineering problems

On 5 July, the Second Brain gained embeddings and scope-filtered hybrid retrieval, combining full-text search, vector similarity and RRF rank fusion. Provenance, validity, supersession and retraction, curation proposals and usage records followed. Memory became more than a chat summary: whether material is relevant, still valid and in scope all decide whether it may enter the model's context.

Putting more history into context brings new trade-offs: retrieval that is too broad pulls in unrelated material, old facts can override new ones, and external text can influence long-term behaviour. So July's work gave facts provenance and timing, separated automatic appends from edits that need review and from sensitive content, and sent curation results to a proposal inbox. Later memory work followed these constraints; letting the user see, correct and withdraw what is remembered became a clearer engineering goal than "remember more".

This stage also began to address long-term maintenance. On 14 July, database migrations moved to a home-grown versioned runner, dropping the Alembic dependency. On 10 July, the licence changed to Apache-2.0 and NOTICE and SECURITY.md were added; on 25 July an explicit open-source preparation commit appeared; and on 27 July v0.1.0 shipped as the first desktop installer, with the Tauri shell and a frozen Python backend delivered together, and signing, notarisation, updates and first-install checks part of the release path.

Real installs soon exposed gaps that development testing could not see: the v0.1.0–0.1.6 installers lacked WebSocket runtime dependencies, so the health endpoint was fine but chat could not connect. 0.1.7 fixed the dependency layer and PyInstaller's hidden imports, and added a real handshake to installer acceptance. That failure is why "the backend started" has to be checked further as "the user's whole path works".

hybrid retrieval; versioned migrations; open-source preparation; installer WebSocket post-mortem.

August: capabilities that connect, and that users can understand

0.1.20 distinguished credentials as not configured, decryptable or not decryptable, and stabilised the salt and key migration; search gained sources and error explanations, and models began to divide work by task. MCP OAuth, OpenRouter sign-in, first-run onboarding, extension manifests, local workspace reading and writing, scheduled tasks and SSH followed. With more extensions, the system also had to say precisely whether the current connection can call tools, whether equipment is in effect, and which action needs permission.

Local execution was layered too. Reading and writing the workspace were separated, with writes needing the matching permission; scheduled tasks have their own scheduling permission; SSH can remember a machine, but each remote execution still needs confirmation. The tool list now describes both capability and conditions of use. For the user, "connected" and "allowed to run this time" are different states, and both the interface and the model's context have to express that.

0.1.23's turn journal let an answer still being generated reconnect after switching conversations; the fix that let the installed app find npx showed again that a desktop app gets a different environment from a terminal. August's thread was less about connecting more services than about turning connections, states and permissions into operations users can understand.

September: from a single answer to traceable work

0.1.38 concentrated on reliability: a default-deny Python sandbox, a separate compute runtime, persistent Runs, artifacts, checkpoints and a shared execution budget. The 0.1.40 previews and stabilisation advanced project memory, document sources, task continuation and pre-migration backups, while keeping known failures in cross-language, multi-document comparison on record. A clickable source shows that material can be found; it does not prove the model's conclusion is right.

Somewhat earlier, from 31 August to 3 September, voice went from read-aloud (0.1.32) and push-to-talk (0.1.36) to half-duplex conversation (0.1.37), with fixes to microphone permissions and language selection. Meanwhile, 0.1.40's research acceptance did not rewrite the cross-language comparison failure as a success, and 0.1.41's source review stayed off by default after a disappointing calibration. These records bound what "the system checked it" means, and let the next improvements centre on real failures.

0.1.41 made closing the window leave Arslan working from the menu bar; 0.1.42 moved long tasks to the background so the user can keep chatting; 0.1.43 separated a soft budget limit from a hard stop — at the soft limit it wraps up with what it has, so research does not stop halfway without a deliverable. Tasks gradually gained a lifecycle independent of the interface, but that does not mean any external action can be safely replayed automatically after a crash.

Late September into October: converging on one execution loop

The early design treated experts as long-lived roles, and both user and system had to deal with choosing, inviting and routing. 0.1.44 stopped creating and dispatching experts, and old experts' methods can be converted into Skills; 0.1.46 stopped background expert evolution, which no longer had any consumer; 0.1.48 removed the front router, so every message goes straight into the agent loop. The release notes point out that some fixed "I can't do that" answers came from the routing decision rather than from real capability. This convergence put tool choice back inside the execution process that actually has the tools and the state.

After that, improvements concentrated on the shared execution layer: 0.1.49 completed the native tool protocol and truncation and failure recovery; 0.1.50 added the current working state, plans and alternative routes; 0.1.51 added the command sandbox and the Island; 0.1.52 brought user memory and learned practices into later work. "Learning" here means saving and using manageable practices, not updating a foundation model's weights.

0.1.53 goes further: a separate Hands helper reads accessibility trees and operates Mac apps, and the Mac side of the iPhone Bridge is included. 0.1.54 readies that Mac side for the iPhone app (Touch ID approvals, one entry per phone, clean-up when a phone is removed) and closes four gaps in the terminal gate, each of them asking more, not less. 0.1.55 gives everything that asks one look and one queue: cards can be answered from the Inbox and, unless the step is risky, from the Island. 0.1.56 adds projects in two layers: a board for all of them, and levels with checkpoints that Arslan ticks only from evidence it can name. The old expert orchestration is history, and accessibility-based operation cannot be extrapolated to "every app is reliably controllable". The current version still constrains what the model can actually do through visible state, explicit permissions and results you can check.
