07 / Data and memoryKeeping useful context, and clear data boundaries

Arslan keeps its main state in SQLite on your Mac: conversations, run records, tasks, personal memory, model configuration and usage each have a data model. Deliverables are written to disk; the full text of very long tool output is stored separately in the app's data folder (kept for 7 days), and the model reads it in parts from the path given in the result. Closing a window therefore does not erase a task's process, and "what was said", "what was actually done" and "what may be remembered later" can be managed separately.

Data access uses async SQLAlchemy with aiosqlite. Connections enable WAL, foreign-key checks, a 5-second busy timeout and synchronous=NORMAL. These choices suit a single-user local app: fewer deployment dependencies and better behaviour when reads and writes overlap. The data folder also has a cooperative process lock, so instances that follow the same protocol do not use the same data at once.

Working context: control this turn's input, keep the raw history

A model can only take in so much at a time, so Arslan builds the working context from a bounded rolling summary plus recent messages. This history window has a default estimated budget of 3,000 tokens, and the summary itself is length-limited too. That is the budget for assembling history, not the size of the whole request: system instructions, tool schemas, material and results take up other space.

As a conversation grows, older messages can be folded into the summary while recent messages stay verbatim. Compaction changes what is assembled next time; it does not delete the full conversation from the database, and if compaction fails the original record is kept. Very long tool output is stored separately: the model gets the head and tail plus a file path and reads more in parts when needed, and the full output is cleaned up under its retention policy.

This layering lets the model see what the current task needs first, while keeping the originals for later checking. A summary is a compressed view of what exists; it cannot replace the real receipt of an external action.

Personal memory: first whether it may be used, then whether it is relevant

A memory entry has a type, scope, sensitivity level, use policy, state, confidence and version. The scope can be global or a project (with internal scopes such as domain and expert), and each entry also has an owner; use policies such as local_only further decide whether content may go into a cloud model request. Each turn's trusted context loads conversation settings from the database; ordinary user text, web pages or model output cannot rewrite these permissions.

"About you" and "Mac notes" get a capped base injection; everything else is chosen by relevance. Since v0.1.52, "Remember me and use it in conversations", on by default, lets ordinary cloud_allowed entries be used with a configured cloud model. Sensitive content needs a further permission; local_only never becomes cloud-eligible because the main switch is on.

ContextReceipt records which entries and revisions were used, why, and an estimated count, without copying the memory text. You can trace why a context was chosen, and the system does not have to create another copy of sensitive content to do so.

Editing a memory creates a new revision and moves the entry's current-revision pointer; source records continue to explain how that revision came about. Paused, expired, superseded and deleted states also affect whether an entry enters later contexts. Versioning helps with checking changes, but deletion erases the text that must go — so it is not an event store where history can never be deleted.

Retrieval: keywords and vectors can be combined

The knowledge retrieval module supports SQLite FTS5 full-text search and vector cosine-similarity search. The first finds word matches; the second uses embeddings to find semantically related passages; when both are available, their rankings are fused with RRF. RRF compares rank positions rather than mixing raw scores on different scales. Without embeddings, or without vectors, full-text search still works.

Retrieved passages enter the model's context with their sources, and the model uses them to answer the current question — that is what RAG means here. With memory v2 active, material retrieval runs only in projects that have bound collections; with a cloud model, the conversation's own cloud-memory permission must also be on (the default "Remember me" switch does not cover material). Results enter the context as the return value of the recall tool. None of this changes the foundation model's weights or needs a separately deployed vector database. Personal-memory v2 selection mainly uses permission filtering, full-text and local relevance logic; it does not follow that every memory goes through the same vector pipeline.

Learned practices: turning corrections into reviewable rules

A Lesson records a user correction, a detour that worked after a failure, or a quirk of this machine. For example, if a command needs different arguments on this Mac, that can become a practice with its source, for similar tasks to consult. Recall takes at most 5 items, about 800 characters in all, placed in the dynamic agent status rather than the stable system prefix; recalls, follows, successes and failures are each counted.

Whether something is worth saving, or duplicates or conflicts with what exists, can be put to the judgement layer as a narrowly scoped question, with the probability and later outcome recorded. User corrections, and practices not influenced by external content, can take effect directly when settings allow and the judgement finds them valuable; anything else needing review becomes a proposal. Candidates containing credentials are dropped outright; the rule that inferred sensitive information needs review belongs to personal memory, not to practices. There are fallbacks when the judgement is missing or times out.

These mechanisms change what the app saves and recalls; they do not train model weights. Judgements are enabled to different extents: for example, when the tool-approval judgement runs in shadow mode it only records a suggestion, and the real authorisation flow still decides whether something runs.

Deletion has to reach summaries and old backups

When a memory is deleted, the system raises the deletion epoch, erases that entry's old revision text and sources, and clears every conversation's rolling summary and the prompts cached in run records, so old derived content cannot bring the deleted memory back. The deletion record keeps only a content fingerprint for matching (an HMAC with a local key) plus metadata such as scope, so the deleted text is not saved again in the ledger; a suppression record stops the same source, still in the chat history, from automatically recreating the memory. Deleting a memory and deleting the original conversation are different operations.

A separate deletion ledger and deletion manifest keep deletions applied on start-up and restore paths. Before an old backup is restored, the system checks the store's identity and reconciles the staged data against the deletion records before activating it, reducing the chance that an old backup resurrects deleted memories. This depends on the restore flow and the deletion records available; it cannot recall copies already exported elsewhere.

The rest of the memories in a backup do not regain all their permissions immediately either: restoring quarantines them for review, tightens use policies, clears cached context, disables all scheduled tasks, revokes per-conversation cloud and sensitive permissions, and archives active projects. Restoring data and re-approving its use are done separately, so old conversation permissions do not silently take effect in a new environment.

Migrations finish before the app starts using data

Database upgrades use an explicit migration runner: check the schema version, prepare an upgrade backup, create missing tables, run pending migrations in order, then handle key compatibility and memory v2 activation. Unknown or newer schemas are refused, so an older program never blindly modifies newer data. In v0.1.54 the explicit registry goes up to 0061; the early Alembic history is not the current mechanism.

When memory v2 activates, the old fact and learning tables are renamed to legacy tables with read-only triggers, compatibility views map old read paths to the new structure, and the full-text index is built at the same time. Secret fields — model API keys, MCP environment variables and OAuth tokens, SSH keys and the like — use Fernet field-level encryption (PBKDF2 plus a salt unique to each install); ordinary conversation and task tables are not thereby encrypted as a whole database. Persistence, secret protection and backup-restore each have specific boundaries.
