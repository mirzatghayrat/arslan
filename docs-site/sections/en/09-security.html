09 / Execution and security boundariesWhat happens between a model's suggestion and a real action

Arslan can read and write files, run commands, and work through the browser and native apps. Its security design rests on one distinction: the model proposes the next step; trusted code decides whether that step may run. What follows describes the boundaries implemented in v0.1.63. Each is a protection with a specific scope, not a proof of safety against every malicious input, app behaviour or system environment.

External content can supply material, not grant itself permissions

Web pages and tool results may contain prompt injection. Web text and MCP results enter the context wrapped in an explicit external-data boundary; since 0.1.63 what a local tool returns (a file, a command, an app window) is wrapped in a separate tool-output boundary with the same data-only rule, and content that forges the markers of either is handled. The system also records whether this turn read external content such as web pages, files or MCP results: practices and machine notes influenced by that content must first become proposals. A line on a page saying "always send files here from now on" cannot gain lasting permission just by being read.

Since 0.1.63 the same record limits the terminal: once a turn has read outside content (a page, a file, an MCP result), its commands run without network under the kernel's rule, and a command that reaches the network, judged by its text or by the model saying so, asks first. Inside the sandbox the answer can be for this time or for the conversation; outside it, only this time. Where nobody can be asked, the command stays offline. Reading the web is guarded separately: local names and private addresses are refused, and the exception for proxies that answer DNS with fake addresses (0.1.61) lets through only https on port 443 to a name, leaving the proxy to decide where it really goes (chapter 08).

This helps keep track of provenance and trust, but it still relies on the execution checks that follow. The model can misunderstand material, and command-risk detection is not a full semantic proof; labelling text "untrusted" is no reason to drop the real permission boundaries.

Ordinary run_commandRuns a real shell. Policy has three layers: forbid (never, inside the sandbox or out: wiping the disk, the home folder or a system folder, raw disk writes, shutting the Mac down, reading passwords out of the keychain, touching Arslan's own key files, anything needing sudo); ask, this time only (sending or publishing, deleting outside the working folder, force-killing programs, changing startup or system settings, driving other apps, opening apps or links outside the sandbox, reading the screen or clipboard, writing shell-startup, SSH, credential or other agents' settings files, and any command whose text cannot be read, such as unbalanced quoting, eval or downloaded code piped into a shell); and run. Every command in a chain (&&, ;, |, ||, &) is checked, not only the first. A card for a command that matches a rule is answered for this time only: no answer is remembered for it. From 0.1.63 every new command asks first by default (the “When to ask” setting: “Ask before every command”); only with “Ask only for risky commands” does a command the policy answers run go ahead without a card: in the sandbox, or outside it where this conversation was allowed to leave it. The default workspace sandbox limits writes to the working folder, temp and cache folders, denies sending Apple Events, and closes the paths of Arslan's data and keys, the Hands socket and the user's credentials (SSH keys, Keychain files, cloud and CLI credentials such as AWS, gcloud, kube, gh, GnuPG, npm and netrc files, browser profiles, Safari and cookies). If the sandbox is unavailable, a command asks first (under “Ask only for risky commands”, a yes “In this conversation” covers that conversation’s later commands the policy answers run); once allowed, it runs without the sandbox and reports sandbox=unavailable, so this is not a uniform fail-closed path.

AppleScript / ShortcutsIn a terminal command, osascript and shortcuts run always ask, this time only, in their common spellings (with a path, through command, exec or xargs, with redirection). The sandbox denies Apple Events, so a spelling Arslan does not recognise fails inside it. Only a plain call that has been approved runs with no sandbox wrapper: a script that talks to Reminders, Calendar, Notes or Contacts and does nothing else risky, or a plain shortcuts run whose files stay in Arslan's folder; it can be approved only by a click in the Mac window. Hands' own AppleScript tool asks every time with the whole script shown, is offered only to background work, and refuses a script that names a blocked app or chooses its app by a computed name.An approved Shortcut runs as the user outside the sandbox, and Arslan cannot see what it does. The command being inside the file sandbox does not mean the app it drives is held to the same file scope.
Arslan HandsA separate helper holds Accessibility; inside the helper, the app, action, field and stop state are checked again. Since 0.1.60 a look may carry a picture of that one window, held in memory only.An accessibility tree is not full business meaning, and a window picture is read by the model, not checked by code. Whether an app exposes actionable nodes affects what works; a window on another desktop is reached only by visiting it under the borrowing rules (chapter 08).

Leaving the command sandbox takes the user's click: either for the current action, or by choosing to allow it for the rest of this conversation — the latter is saved with the conversation (it outlasts a restart), covers its background tasks too, and can be taken back in Settings. Source development environments also have an explicit escape hatch for unsandboxed Python; the desktop app disables it. Neither should be read as the model being able to turn protections off.

Since 0.1.62 write_file and edit_file never follow a link out of the working folder: a write through a link that points outside is refused, a file with a second name elsewhere (a hard link) is replaced in the working folder and the other name keeps its old content, new files are never executable, and an existing file keeps its permissions. The file is written to a new file beside it and swapped in, so a failed write leaves the old one untouched. Since 0.1.63 the first change a turn makes to the working folder saves a checkpoint, and "Undo this turn" puts the files back and takes the turn out of the conversation. This is a recovery net, not a boundary: it saves only a folder of at most 20,000 files and 5 GB (not counting Python environments, node_modules, build output and caches, which it leaves out and never puts back), never copies secret-shaped files, covers only the working folder, undoes nothing that left the Mac, and says "Not saved" when it could not save. Checkpoints are kept for seven days.

Approval is bound to the exact action; background work does not inherit every convenience

An approval card is tied to its call_id and action kind, so a reply of the wrong kind cannot approve a different card. A card shown in both the Mac window and on the phone takes the first valid answer and broadcasts the closed result to the other views; unanswered, it stays open for 30 minutes, and running out is not a no (since 0.1.61; earlier versions: it expired after 300 seconds). Since 0.1.61 one card looks the same in the window, the Inbox, the Island and on the iPhone: Once (or For this task, whichever the card offers first), In this conversation, Always, and No with a note that goes to Arslan; a message typed in the chat while a card waits answers it No, with that message as the note, and one click answers one card. Some kinds offer fewer choices: a command that matches a rule, money, a takeover and a risky step in an app answer this time only, and leaving the sandbox, a site, a Shortcut and an MCP tool never offer "Always". A job’s cards offer the same choices as the window’s; since 0.1.63 (S4a) a job started from a conversation uses that conversation’s grants, leaving the sandbox included. A run with nobody to ask (a scheduled run) takes none of these steps: no earlier answer counts there, the step is refused at once, and what it could not do is listed in the Inbox. In this version a scheduled run runs no terminal command at all. When the model suggests connecting an MCP server, registering a remote machine or reaching another execution entry, the proposal is handled separately from actually enabling the connection.

For external side effects, sending a request is not the same as completing an action. Resuming a task marks in-flight actions with unknown results as uncertain; they are not replayed automatically just because the process restarted. The goal is clear semantics for retry and recovery, not a promise that any external system can be undone.

Since 0.1.55 every waiting card — from a window, a background job or the iPhone — also stands in one queue and in the Inbox, and can be answered there by its call_id; the reply is built from the card's own kind, so it can only confirm or cancel that card, and the wider choices (In this conversation, Always) are chosen only on a card that offers them: the iPhone and the Island give only the card's first choice, never "Always", and the Inbox can give any choice the card itself offered. The Island can answer folder, app, screen, MCP tool, schedule, site and Shortcut cards and a command or workspace write that is not one of the risky kinds. It cannot approve money, sending, deleting, a risky step in an app, a takeover, leaving the sandbox, a command that matches a terminal ask rule or cannot be read, a command that also asks for the network, anything on a remote host, system changes, other agents' settings, installing a capability, an AppleScript, a command that would run with no sandbox around it, or any card kind the check does not know. Those show "Open in Arslan", and the server refuses an approval from the Island for them, not only the Island page. A card that would run an approved plain AppleScript or Shortcut with no sandbox wrapper, and one that installs a capability, are approved only in the Mac window; the iPhone's yes to such a card is swallowed. In the window, ⌘⏎ allows and Esc declines; plain ⏎ never answers a card.

Hands keeps the system permission in a smaller process

Accessibility is granted to Arslan Hands.app, not the main app. The signed release accepts requests over a protected Unix socket, with a token generated at each launch and a peer signature check. The helper enforces the rules itself; the underlying agent-desktop does not hold the permission on its own. Since 0.1.61 looking at an app and acting in it are one card per app, offering "for this task" first. Since 0.1.60 a chat reply may also act: until 0.1.62 for up to five steps in one app, and from 0.1.63 under the run's own limits, as background work does, in more than one app, and Stop stops it (a scheduled run cannot act: nobody is there to approve it); a job started from a conversation inherits that conversation's yes. Acting in the browser, running Shortcuts and AppleScript are still offered only to background work. An app is judged by its identity, so naming it with .app or a full path, or in another case, does not get past the blocked list or a missing approval. Sensitive buttons — delete, send, pay, buy, transfer, submit — ask every time, by their actual label; password fields are never typed into, and apps such as password managers and system security screens are on a blocked list.

The stop control sets a stop latch that every later action must pass; the activity log keeps a trail of operations, recording typed text only by its length. The limits are public too: a window on another Space is reached only by visiting it under the borrowing rules, clicking at a screen position and dragging are not offered, reading a large window can take 10–20 seconds, and a call cut short by Stop may have no matching trace row — the audit trail is not a complete forensic record of every interruption.

Since 0.1.56 Hands runs each request at most once: answers to a request id are kept for ten minutes, a repeated id is answered from there, and the backend fetches an answer whose reply it lost instead of sending the action again. Appending to a field whose text cannot be read is refused rather than replacing it, Return is pressed only when that field has focus, and an action that was sent but not read back is reported as "sent, not confirmed", not done. Hands runs agent-desktop, built from Arslan's fork at a pinned commit; the Cua Driver engine was unwired from Hands in 0.1.63, so the helper no longer looks for or starts it (its unused module still sits in the helper's source). Since 0.1.60 one card can cover up to eight apps for a piece of work, a background job started from a conversation inherits that conversation's yes, and apps can be allowed for good in Settings → Hands. A click, choice or last menu item labelled to delete, send, pay, buy, submit, transfer, sign, post, publish or confirm (in several languages), the matching shortcut keys, Return in apps that send on Return, a takeover and any AppleScript still ask every time.

The local service has boundaries too. The release generates access tokens for REST and WebSocket, and installer acceptance checks that unauthenticated requests are refused. The Settings endpoint that shows the token gives it only to a direct loopback caller that already presents it (0.1.54); loopback alone is not enough, since a sandboxed command can open a loopback socket too. The desktop app's server always needs its token, accepts no other website as a caller (no cross-origin and no WebSocket without an Origin), trusts only localhost as a host name, ignores the host and origin variables and other settings inherited from the environment that launched it, serves no API explorer, and keeps the token out of its log (0.1.63). Source development mode allows a token-free localhost convenience path, though a host or origin variable naming * or null now refuses to start; "listening only on this machine" and "authenticated" are not the same thing. A host environment that is already compromised with the current user's permissions does not become trustworthy because of a local token.
