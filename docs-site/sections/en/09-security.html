09 / Execution and security boundariesWhat happens between a model's suggestion and a real action

Arslan can read and write files, run commands, and work through the browser and native apps. Its security design rests on one distinction: the model proposes the next step; trusted code decides whether that step may run. What follows describes the boundaries implemented in v0.1.61. Each is a protection with a specific scope, not a proof of safety against every malicious input, app behaviour or system environment.

External content can supply material, not grant itself permissions

Web pages and tool results may contain prompt injection. Web text enters the context wrapped in an explicit external-data boundary, and content that forges boundary markers is handled. The system also records whether this turn read external content such as web pages, files or MCP results: practices and machine notes influenced by that content must first become proposals. A line on a page saying "always send files here from now on" cannot gain lasting permission just by being read.

This helps keep track of provenance and trust, but it still relies on the execution checks that follow. The model can misunderstand material, and command-risk detection is not a full semantic proof; labelling text "untrusted" is no reason to drop the real permission boundaries.

Reading a page or opening the browser also passes a network guard: local names and real private addresses are refused. Since 0.1.61, on a Mac whose proxy or VPN answers DNS with fake addresses, the proxy resolves the name and the guard accepts it only for https on port 443, and only when a proxy carries the request or the system DNS is fake-IP for a public name too; a proxy setting that cannot be parsed is refused rather than bypassed. A page read now says who is reading, so sites that turn away unnamed clients answer, and when a site still refuses, Arslan is told that the site blocks automated reading, not that a key was rejected.

Leaving the command sandbox takes the user's click: either for the current action, or by choosing to allow it for the rest of this conversation — the latter is kept only in memory. Source development environments also have an explicit escape hatch for unsandboxed Python; production mode and the frozen installer disable it. Neither should be read as the model being able to turn protections off.

Approval is bound to the exact action; background work does not inherit every convenience

An approval card is tied to its call_id and action kind, so a reply of the wrong kind cannot approve a different card. A card shown in both the Mac window and on the phone takes the first valid answer and broadcasts the closed result to the other views; unanswered, it stays open for 30 minutes, and running out is not a no (since 0.1.61; earlier versions: it expired after 300 seconds). Background jobs do not inherit a connection's session grants and never offer "remember this command"; since 0.1.54 that includes the chat window's "run outside the sandbox for the rest of this conversation", so a job's command starts inside the sandbox whatever the window allowed. When the model suggests connecting an MCP server, registering a remote machine or reaching another execution entry, the proposal is handled separately from actually enabling the connection.

For external side effects, sending a request is not the same as completing an action. Resuming a task marks in-flight actions with unknown results as uncertain; they are not replayed automatically just because the process restarted. The goal is clear semantics for retry and recovery, not a promise that any external system can be undone.

Since 0.1.55 every waiting card — from a window, a background job or the iPhone — also stands in one queue and in the Inbox, and can be answered there by its call_id; the reply is built from the card's own kind, so it can only confirm or cancel that card, and "remember this" is chosen only on the card itself. The Island can answer too, except a step that deletes, sends, publishes, pays or reaches another machine: any AppleScript (since 0.1.61), a terminal command matching those rules or a Hermes danger rule, anything outside the sandbox or on a remote host, and any card kind the check does not know. Those show "Open in Arslan", and the server refuses an approval from the Island for them, not only the Island page. In the window, ⌘⏎ allows and Esc declines; plain ⏎ never answers a card.

Since 0.1.61 every card has the same shape in the chat window, the Inbox, the Island and on the iPhone, and one decision function (permissions.decide) builds it: a card offers Once or For this task (whichever it lists first), In this conversation, Always, and No… with a note that goes to Arslan. A message typed in the chat while a card waits answers it No, with that message as the note. "In this conversation" says what it covers: a kind of command, any scheduled task, any file in the folder. A "for this task" yes ends with its task, also after a restart or a resume. Always cards for sites and Shortcuts are hidden for now, and "In this conversation" cannot yet be taken back from a list. The Island and the iPhone show the card's own question, say what their yes means, and answer only once, or for this task where that is the card's first choice, never "Always". One click answers one card: for 500 ms after a card leaves the top, nothing answers the one that comes up, and a held key answers one card.

What could not be asked while nobody was there (a card that never opened, and most of what a scheduled task was refused) is listed in the Inbox with exactly what "Always allow" would store, one rule to a line, and that answer can be undone for 10 seconds. Rules, grants and a ledger of every decision are stored in migration 0067.

Hands keeps the system permission in a smaller process

Accessibility is granted to Arslan Hands.app, not the main app. The signed release accepts requests over a protected Unix socket, with a token generated at each launch and a peer signature check. The helper enforces the rules itself; the underlying agent-desktop does not hold the permission on its own. Reading is approved per conversation and app. Since 0.1.60 a chat reply may also act, for up to five steps in one app, and longer work runs as a background job; actions are approved per conversation or job and app, and a job started from a conversation inherits its yes. Sensitive buttons — delete, send, pay, buy, transfer, submit — ask every time, by their actual label; password fields are never typed into, and apps such as password managers and system security screens are on a blocked list.

The stop control sets a stop latch that every later action must pass; the activity log keeps a trail of operations, recording typed text only by its length. The limits are public too: a window on another Space is reached only by visiting it under the borrowing rules, clicking at a screen position and dragging are not offered, reading a large window can take 10–20 seconds, and a call cut short by Stop may have no matching trace row — the audit trail is not a complete forensic record of every interruption.

Since 0.1.56 Hands runs each request at most once: answers to a request id are kept for ten minutes, a repeated id is answered from there, and the backend fetches an answer whose reply it lost instead of sending the action again. Appending to a field whose text cannot be read is refused rather than replacing it, Return is pressed only when that field has focus, and an action that was sent but not read back is reported as "sent, not confirmed", not done. Hands runs agent-desktop, built from Arslan's fork at a pinned commit; the Cua Driver path stays in the code behind a development-only build switch and is not in releases. Since 0.1.60 one card can cover up to eight apps for a piece of work, a background job started from a conversation inherits that conversation's yes, and apps can be allowed for good in Settings → Hands. A click, choice or last menu item labelled to delete, send, pay, buy, submit, transfer, sign, post, publish or confirm (in several languages), the matching shortcut keys, Return in apps that send on Return, a takeover and any AppleScript still ask every time. Since 0.1.61 an AppleScript is no longer covered by an app's yes, a Settings → Hands "always" or a task grant: each script is asked once, never remembered, with the whole script shown, and answered in Arslan.

The local service has boundaries too. The release generates access tokens for REST and WebSocket, and installer acceptance checks that unauthenticated requests are refused. The Settings endpoint that shows the token gives it only to a direct loopback caller that already presents it (0.1.54); loopback alone is not enough, since a sandboxed command can open a loopback socket too. Source development mode allows a token-free localhost convenience path; "listening only on this machine" and "authenticated" are not the same thing. A host environment that is already compromised with the current user's permissions does not become trustworthy because of a local token.
