08 / Tools, Skills and extensionsReusable capabilities, with limits on execution

Arslan keeps "what it can do" separate from "knowing how to do it". Tools perform real actions, Skills hold methods and references, MCP connects external capabilities, and a plugin manifest combines these resources. The model receives the set of capabilities available this turn; a tool existing in the source registry does not mean it is on by default or allowed to run.

How the four concepts fit together

Built-in tools are handled by registered executors; calls prefixed mcp_ go to the MCP proxy. Tool results return to the single loop, where the model can fill in arguments, choose another method or finish. Even after the model has read a Skill, files, commands and app operations still pass through their own permission boundaries.

Since 0.1.63 a request no longer carries every tool. It carries a resident set of everyday tools (web search and page reading, file read, write and edit, the terminal, planning, background work, memory, read_skill, the capabilities list, and the desktop tools of Hands) plus two finders: find_tools ranks the tools this turn may call but was not shown, and use_tool calls one under its real name, so the arguments are checked against that tool's own parameters and the same approval, trace and receipts apply as for a direct call. MCP tools, attach_file and the browser tools are reached this way. A tool used on demand joins that conversation's list from the next turn (at most 12 per conversation, kept in memory, so after a restart the model searches again). Text from an MCP server that find_tools hands back is wrapped as outside data, never as instructions.

When the model asks for several reads in a row, up to four run at the same time: web search and page reads, read_skill, file reads, listings and the like, and MCP tools whose server marks them read-only (one per server in a group). Each call still passes every gate in the reply's order and each result stays paired with the call that asked for it; anything that is not a read runs alone, in its place.

Skills are read on demand: an index tells the model which methods exist, and read_skill fetches the body from a registered SkillPack or an allowed reference path. The library of methods can grow while each turn's context stays small. Arslan ships two skills of its own, a designed HTML report and the skill creator. Since 0.1.63 the expert-era seeds, the preset MCP connector list and the model's connector-suggestion tool are gone (finding a new MCP server goes through find_capability, below), and a skill you imported under a retired name is no longer removed.

Since 0.1.55 the Capabilities page lists what Arslan can do as switches, each on, off, one step away or not possible here, with the reason. Off means the model is not offered it at all, and read_skill refuses a switched-off skill. The rows are read from the same gates that decide which tools a turn gets, so a row cannot say "on" while its tools are missing. A whats_new tool answers "which version are you, what changed" from the release notes shipped with the app, never from the model's memory.

Extensions are a new trust boundary

A local stdio MCP server usually means starting a separate process; an HTTP MCP server may connect to a remote service. Arslan manages separately whether a connection exists, whether the main assistant can use it, whether its tools are exposed, and how its credentials are stored and shown. HTTP MCP server URLs declared in a plugin manifest must use HTTPS; secret slots declare the shape of a parameter and never embed a real credential in the manifest. Configured environment values are stored encrypted and masked when shown.

Since 0.1.61 every MCP server you switched on starts in the background when Arslan opens, at most four at a time, and a chat never waits for one. Each server has one state that the Capabilities page and the model both read, and the model is offered only the servers that are ready right now; a call to any other is answered with its state and the reason, with keys and tokens masked. A first start gets 120 seconds; a failed server is tried again after 30 seconds, then less often (at most every 10 minutes).

Since 0.1.62 Arslan reshapes the parameter descriptions of MCP tools into a form Anthropic, OpenAI-compatible providers and Gemini accept before sending them; built-in tools are sent as written. If a provider still refuses one, that tool is left out for the rest of the reply and the reply goes on (if the refusal names no tool, or a second one is refused, all MCP tools are left out for that reply).

Since 0.1.63 an MCP call asks according to what the server says the tool does: a tool the server marks read-only runs without a card; one it marks destructive asks every time, this time only; any other asks, this time or for the conversation, never "Always". A call whose arguments are too long for a card to show in full is refused, never cut. These marks are the server's own statement, which Arslan does not verify. Where nobody can be asked (a scheduled run), only read-only tools run.

These constraints reduce accidental exposure and mistaken execution, but a real MCP server can still access whatever it is given. Where a tool comes from, what it needs, what data goes to a remote service and what side effects it has are all part of what an extension must explain.

Capabilities that grow: find, ask, install, scan, test

Since 0.1.57, when a step needs something Arslan cannot do, find_capability searches the official MCP Registry, GitHub and reviewed skill libraries together. propose_capability may only name a candidate this conversation was shown, and the card is built on the server from that search result, never from the model's words: what it would add, where it comes from, its license read from the project's own license file, how it would run, which folders it may use and any key it needs. Only the Arslan window that asked can approve; a background job, or a turn with nobody to ask, records the find under "Arslan found" on the Capabilities page instead.

After approval it is installed pinned and switched off: a lock with hashes, a published checksum or a commit, on Arslan's own pinned uv or Node, with no package code running during the install (wheels only, npm without install scripts). A scan looks for known dangerous patterns — hidden instructions in a skill, code that fetches and runs more code, writes to where macOS starts programs — and a high finding removes it again; the scan cannot prove anything safe, which is why the server then runs in its own sandbox (chapter 09). It must start and list at least one tool before it is switched on, and the tool loop re-reads its tools so the failed step can be retried in the same reply. Skills imported from GitHub are pinned to one commit with a checksum per file, and their text is read as outside content that cannot grant permissions.

Files come back as files: the workbench reader

Since 0.1.58 a file written during a turn shows under the reply as a card, and paths in a reply open in Arslan or in the file browser. The reader in the workbench reads only where Arslan's own read tools may: the workspace, Desktop, Documents and Downloads when default read is on, active project folders and Arslan's own outputs. Symlinks are resolved first, hidden files and credential-shaped names are never listed or read, file bytes are sent as an attachment with nosniff, and HTML is shown in an iframe with an empty sandbox, so its scripts cannot run.

Since 0.1.63, when you ask for a file (a screenshot, chart, export or document), attach_file attaches it to the answer: a file card in the window, and the file itself on a paired iPhone. It takes no card of its own because it only reads where the reader may, and the same rules apply: no hidden or credential-shaped names, no link leading out of the readable folders. It also never takes anything under Arslan's own data, keychains or SSH keys, a file over 20 MB, or more files than one run can hold.

Hands v2: one window's picture, batches, borrowing the front, taking over

Hands still reads a window as its accessibility tree. Since 0.1.60 each look can also attach a JPEG of that one window — never the whole screen — held in memory and sent only to the model; it is not written to disk, to the trace or to the interface, and when the model cannot take images, macOS Vision reads the text locally instead. It can be turned off in Settings → Hands, or kept to text for apps you list. Several steps in one app run as one batch of up to eight, menu items are chosen directly even when the app is not in front, and apps are opened in the background. Until 0.1.62 a chat reply could take at most five actions, all in one app; from 0.1.63 it has no Hands limit of its own and acts under the run's limits, as background work does. A scheduled run cannot act on the Mac at all: nobody is there to approve it.

Some things only work with the app in front, such as a pop-up menu. Hands then waits for a one-second pause in typing, borrows the front for about a second while the edges of every display glow blue, holds the keys pressed meanwhile and replays them when the user's app is back. If the app's window is on another desktop, Hands goes there under the same rules and comes back when the work ends, after 15 seconds without action or at the user's first input. For longer work a background job can ask to take over the screen for up to 30 minutes; any keyboard or mouse input pauses it until the user continues. "While I'm away" is off by default; when on, a takeover may start without a card after three minutes without input. Borrowing can be turned off, and Hands then refuses instead.

Search and reading the web

Since 0.1.63 web_search uses the search of the model this turn runs on first: Anthropic's own web search for a Claude conversation on Anthropic's own API, DeepSeek's for a DeepSeek model. A conversation on a local model never sends its queries to a provider's own search. Tavily or a self-hosted SearXNG chosen in Settings is either the only search or a backup after the model's own; with no deliberate choice, a best-effort DuckDuckGo scrape comes last. When a search service refuses Arslan, the result says the search was blocked and that nothing was searched, never "no results".

Page reads and the browser keep the outbound guard: local names, real private addresses and hosts with control characters are refused. Since 0.1.61, on a Mac whose proxy or VPN answers DNS with fake addresses (198.18.0.0/15), a name asked for over https on port 443 whose addresses all lie in that block is let through, and plain http or another port to such a name is refused. For such a name the proxy decides where the request really goes; what still holds is TLS, checked against the real name.

Why parallel research still exists

The single agent loop keeps constrained, temporary read-only workers. In v0.1.63 a batch has at most 4, and at most 2 run at once; their tools are limited to search and web extraction, they write no files or personal memory, and they cannot create more workers. The main assistant checks and combines their results.

This kind of delegation suits splitting up independent lookups. Its lifecycle differs from the early permanent expert personas: you are not asked to pick or manage a team of experts first, and messages are not forced through to another "expert". Whether to use parallelism should still depend on whether the task splits well, and on the cost of the extra calls.

Background, scheduled and heartbeat

A background job separates long execution from the current chat, reusing the same model, tools and acceptance logic. A scheduled task persists "when to start"; the heartbeat is one way of periodically working through a checklist — off by default, it checks and suggests. A scheduled trigger never turns a suggestion into an approved write or command. Since 0.1.63 every scheduled run is an ordinary Arslan turn with nobody to ask: in this version it runs no terminal command at all, whatever was allowed before, writes only in Arslan's own folder, cannot act on the Mac, and runs only MCP tools their server marks read-only; a step that needs more is refused and listed in the Inbox.

Chat replies and background tasks stop at a dollar limit per task (on by default, $2; they start wrapping up at about two thirds of it; only models with a known price count), changeable in Settings. A chat reply is no longer pushed into the background for long work: background work is the same work done elsewhere, when you or the model choose it.

Scheduling is implemented in the local service, with overlap skipping, pausing after failures and clean-up after a restart. Missed runs are not replayed one by one; if the previous run of the same task has not finished, the next one does not start on top of it. This suits a personal desktop app, and it also means its operating conditions differ from a server that is always online.
