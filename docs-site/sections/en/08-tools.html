08 / Tools, Skills and extensionsReusable capabilities, with limits on execution

Arslan keeps "what it can do" separate from "knowing how to do it". Tools perform real actions, Skills hold methods and references, MCP connects external capabilities, and a plugin manifest combines these resources. The model receives the set of capabilities available this turn; a tool existing in the source registry does not mean it is on by default or allowed to run.

How the four concepts fit together

Built-in tools are handled by registered executors; calls prefixed mcp_ go to the MCP proxy. Tool results return to the single loop, where the model can fill in arguments, choose another method or finish. Even after the model has read a Skill, files, commands and app operations still pass through their own permission boundaries.

Skills are read on demand: an index tells the model which methods exist, and read_skill fetches the body from a registered SkillPack or an allowed reference path. The library of methods can grow while each turn's context stays small. Converting historical experts into Skills follows the same direction: keep the methods and material, simplify the way in.

Since 0.1.55 the Capabilities page lists what Arslan can do as switches, each on, off, one step away or not possible here, with the reason. Off means the model is not offered it at all, and read_skill refuses a switched-off skill. The rows are read from the same gates that decide which tools a turn gets, so a row cannot say "on" while its tools are missing. A whats_new tool answers "which version are you, what changed" from the release notes shipped with the app, never from the model's memory.

Extensions are a new trust boundary

A local stdio MCP server usually means starting a separate process; an HTTP MCP server may connect to a remote service. Arslan manages separately whether a connection exists, whether the main assistant can use it, whether its tools are exposed, and how its credentials are stored and shown. HTTP MCP server URLs declared in a plugin manifest must use HTTPS; secret slots declare the shape of a parameter and never embed a real credential in the manifest. Configured environment values are stored encrypted and masked when shown.

These constraints reduce accidental exposure and mistaken execution, but a real MCP server can still access whatever it is given. Where a tool comes from, what it needs, what data goes to a remote service and what side effects it has are all part of what an extension must explain.

Capabilities that grow: find, ask, install, scan, test

Since 0.1.57, when a step needs something Arslan cannot do, find_capability searches the official MCP Registry, GitHub and reviewed skill libraries together. propose_capability may only name a candidate this conversation was shown, and the card is built on the server from that search result, never from the model's words: what it would add, where it comes from, its license read from the project's own license file, how it would run, which folders it may use and any key it needs. Only the Arslan window that asked can approve; a background job, or a turn with nobody to ask, records the find under "Arslan found" on the Capabilities page instead.

After approval it is installed pinned and switched off: a lock with hashes, a published checksum or a commit, on Arslan's own pinned uv or Node, with no package code running during the install (wheels only, npm without install scripts). A scan looks for known dangerous patterns — hidden instructions in a skill, code that fetches and runs more code, writes to where macOS starts programs — and a high finding removes it again; the scan cannot prove anything safe, which is why the server then runs in its own sandbox (chapter 09). It must start and list at least one tool before it is switched on, and the tool loop re-reads its tools so the failed step can be retried in the same reply. Skills imported from GitHub are pinned to one commit with a checksum per file, and their text is read as outside content that cannot grant permissions.

Why parallel research still exists

The single agent loop keeps constrained, temporary read-only workers. In v0.1.57 a batch has at most 4, and at most 2 run at once; their tools are limited to search and web extraction, they write no files or personal memory, and they cannot create more workers. The main assistant checks and combines their results.

This kind of delegation suits splitting up independent lookups. Its lifecycle differs from the early permanent expert personas: you are not asked to pick or manage a team of experts first, and messages are not forced through to another "expert". Whether to use parallelism should still depend on whether the task splits well, and on the cost of the extra calls.

Background, scheduled and heartbeat

A background job separates long execution from the current chat, reusing the same model, tools and acceptance logic. A scheduled task persists "when to start"; the heartbeat is one way of periodically working through a checklist — off by default, it checks and suggests. A scheduled trigger never turns a suggestion into an approved write or command.

Scheduling is implemented in the local service, with overlap skipping, pausing after failures and clean-up after a restart. Missed runs are not replayed one by one; if the previous run of the same task has not finished, the next one does not start on top of it. This suits a personal desktop app, and it also means its operating conditions differ from a server that is always online.
