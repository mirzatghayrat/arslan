11 / Verification and deliveryFrom source that runs to an app you can install and update

A desktop app is delivered as an app bundle. Python modules, system tools and old databases in a source environment can all make an installer that is missing resources look fine. Arslan splits verification into layers: source, platform, the frozen artifact, a brand-new user environment, and distribution. This chapter records v0.1.54's process and the matching release evidence.

The macOS tests do not just accept pytest's exit code. The pipeline parses the JUnit report and requires 49 named platform cases to actually run, with zero skips and no failures; if missing dependencies skip everything, it fails. Python and Rust share Hands contract samples, and the Mac, iOS and an independent Python reference implementation share Bridge vectors, so argument mapping, signatures, recipients, tampering and replay can be checked across languages.

These results still have a scope: Swift type-checking does not verify microphone authorisation, Linux unit tests do not verify the macOS kernel, and a simulated mailbox does not verify production CloudKit. Test counts are not overall coverage either; overlapping suites cannot be added up into independent scenarios.

The release workflow checks that the SHA being released has successful CI; another commit passing does not count. The build uses lock-file-pinned dependencies; Python explicitly uses a uv-managed standalone interpreter so the runner cannot accidentally pick a framework build. The backend is frozen with PyInstaller onedir, and the frontend assets and Swift/Rust helpers are assembled into the Tauri app.

Signing and notarisation do different jobs. Embedded Mach-O binaries are signed first, then wrapped by the outer app; Developer ID, hardened runtime and timestamps are for distribution. The DMG is submitted to Apple for notarisation, then the ticket is stapled and Gatekeeper checks it. The build script keeps an unsigned development path and a warning path for missing credentials, so "it builds" does not automatically mean "it meets the conditions for public distribution"; a real release must check the artifact it actually produced.

The update manifest has its own constraints: the tag must match the Tauri version, and a manifest is generated only when there is an updater signature. The workflow creates a GitHub draft release; only after it is published do installed apps see the update on their next check.

Fresh-install acceptance launches the real app bundle

fresh_install_check.py launches the real arslan-desktop inside the bundle with a temporary HOME and a minimal environment, rather than starting the service from a source venv on its behalf. It checks that no user database or secret files were bundled, first-launch initialisation, token generation and file permissions, that unauthenticated requests are refused, a real WebSocket 101 handshake, and that the frontend JavaScript can actually be fetched. An HTTP 200 may just be the SPA's fallback page, so asset checks cannot rely on status codes alone.

The same script also checks native OCR, the embedded helpers, the Bridge self-test and the relevant signatures. A frozen bundle once missed a dynamically loaded WebSocket dependency: the health endpoint was fine, but chat could not upgrade its connection. That is why a successful import, a live service and core features shipping in the bundle are three different kinds of evidence.

Updates install when you choose, and downloads are verified

The Tauri updater finds updates from the public latest.json and verifies the archive's signature with a public key compiled into the app. The app checks once at launch, and you can check manually from the menu; this release has no periodic check timer. When a new version is found it shows a notice; only when you click Install does it download, verify, replace and restart. An automatic check failing may just mean you are offline; a failed install must be reported clearly.

The early 0.1.0 and 0.1.1 only registered the updater plugin and never called the check, so they could not discover new versions. The current implementation chains checking, installable state, download failure and restart into an explicit flow; having a signing configuration does not mean the flow has been triggered.

Which object 0.1.54's delivery evidence applies to

The GitHub Actions runs for the release commit show: the release source is ebf438dc; CI for that commit passed on its first attempt (run 37663596194), including the macOS job's 49 named platform cases with zero skips. The release workflow (run 37663596043) passed source verification, build and publish; the DMG was accepted by notarisation, stapled, and accepted by Gatekeeper. The shipped app's fresh-install check had 87 passed and 0 failed, including Hands accepting the signed backend's connection and the Bridge self-test. The 0.1.53 release had the same 87/0 result after CI passed on its second attempt; that order-dependent flake was traced to tests sharing a database session and fixed in 0.1.54.

The objects differ, and the records say so. 0.1.54's public notes contain no hand-run on a real Mac, so this document does not claim that the exact 0.1.54 DMG was installed and walked through by hand, nor a full iPhone-to-Mac run with the shipped app. For comparison, 0.1.53's Verification section recorded a real-Mac run in which Hands created and read back a note in Notes, with an approval left waiting for 36 seconds — on the build-only bundle of 43751254, not the final DMG. Automated bundle acceptance, feature runs on an earlier build, and manual acceptance of the exact release bundle are stated separately; none substitutes for another.
