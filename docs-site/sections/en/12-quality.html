12 / Testing and evaluationHow to tell whether a task was done right

A task that finished, a file that opens and a report whose content is correct are three different judgements. Arslan uses run records to show what happened, checks deliverables and contracts to verify what can be determined, and uses real-task evaluations to observe how models perform. Passing one layer cannot stand in for the others.

This section brings together the public source, release notes and past experiment records. The numbers belong to their own versions and environments; they do not mean every test was re-run while this was written, or that every feature has been accepted on real devices with real models.

First, break "done" into checkable evidence

Did it actually run?

Did the tool call return? What was the exit code? Did the action clearly succeed, clearly fail, or is the outcome unknown? A model writing "done" cannot replace tool evidence, and a side effect with an unknown outcome cannot be treated as safe to run again.

Does the deliverable hold up?

Does the file exist, belong to this task, match its byte count and hash, and parse? A spreadsheet that opens does not mean its data is right; an image of the right size does not mean its layout is acceptable.

Was the requirement met?

If ten valid results were asked for, six do not meet it. Citations must match conclusions; having read a page does not prove it supports a claim. This layer still needs task-specific checks and human judgement.

The task acceptance system keeps rule checks, model evaluation and human review distinct. Text, JSON, file integrity, image size and actual execution results can be checked deterministically; model evaluation covers only what it is suited to judge, and cannot turn a check that never ran into a pass. A deliverable that parses proves its structure is readable, and a record of reading a source proves the system got the content; neither automatically proves facts or visual quality.

For example, the September 2026 reliability work provided 30 fixed contracts with zero external model cost; they really exercise storage, cancellation, deliverables, backup and permission code, but use a deterministic provider stand-in. That is engineering-contract evidence, not 30 end-to-end tasks with a real model. The later paid evaluations are a different layer of evidence, and the two cannot be blended into one success rate.

Tests also have to prove they actually ran. v0.1.54's macOS CI parses the JUnit report and requires 49 named platform cases to actually run with zero skips. Hands' Python and Rust sides share contract samples; both ends of Bridge share protocol vectors. For key protections, mutation checks temporarily break a rule and confirm the tests turn red, exposing tests that only check how something is implemented rather than constraining what it does.

Real-task data: keep the comparison, and the weak spots

The 0.1.51 evaluation on 3 October 2026 used deepseek-v4-pro, compared against Hermes in the same round, with three runs of each of four tasks. "Passed acceptance" means checker score = 3, which is not the same as the run's status being done. Cost and time are the mean of each task's three runs, including failures; cost is at that round's off-peak prices. Time is the span from the first model request starting to the last one ending — neither the full end-to-end task time nor pure model inference time.

The public experiment record keeps these conditions, and they should be read together with the summary.

Comparisons between versions need the same restraint: the Reminders sample went from 1/3 in 0.1.49 to 3/3 in 0.1.50, a stage in which alternative routes and context state improved. But several things changed between those versions, and the whole difference cannot be strictly attributed to one prompt or one module.

Model review needs reviewing too

In 0.1.41's source-review calibration, 13 reports produced 14 hints: 1 correct, 2 borderline, 11 wrong — and it missed both pre-registered known errors. So the feature stays off by default. Calling another model does not automatically give you a reliable fact-checker; valid format and existing anchors do not guarantee a critique holds.

0.1.52's learned-practice validation shows a different limit: after an AppleScript was refused once, the practice was saved and recalled, and next time it went straight to EventKit — showing practices can influence execution. But later script editing and checking made more calls, and no speed-up was measured. To judge whether a practice itself improves efficiency needs paired, repeated runs of the same task with and without it; the record at the time states plainly that this fair speed comparison had not been run.

Stronger quality claims need tasks, deliverables and checks frozen in advance; the model and configuration, call trajectories, real costs and failure reasons recorded; and model scores calibrated against independent human labels. A malformed score, a check that never ran and evidence that could not be obtained each keep their own status, rather than being counted as passes to make the summary look better.
