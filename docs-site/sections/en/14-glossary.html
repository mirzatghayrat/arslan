14 / GlossaryFrom terms back to the implementation

Terms here distinguish different mechanisms. The tables give a short definition and place each concept back in Arslan's implementation; historical mechanisms are marked as such.

AI and context

TermIn plain wordsHow Arslan uses it
LLMA large model that understands and generates languageFrom the provider the user configures; Arslan provides the app and the execution system
AgentA process that decides its next step from resultsCall the model, run tools, look at results, continue or wrap up
OrchestratorA coordinator that brings different capabilities togetherCoordinates the model, context, tools, permissions and task state
Tool callingThe model requests a tool in a structured wayTool name and JSON arguments are validated before anything runs
Native tool protocolThe tool message format a provider officially definesKeeps tool call IDs, results and reasoning continuation correctly matched
TrajectoryA structured record of the model's interaction with toolsOpenAI-compatible providers use native history; other providers keep their own paths
Context windowHow much a model can see at onceAll history, all memory and full long output cannot be stuffed in without limit
CompactionCompressing old context into a bounded summaryControls request size while keeping recent content; it does not delete the original conversation
RAGFind relevant material first, then let the model answerRetrieves passages from imported knowledge, with their sources
FTS5SQLite's full-text searchGood at word matches; material can be searched even without vectors
EmbeddingTurning the meaning of text into a numeric vectorHelps find content that is worded differently but means something similar
Cosine similarityComparing whether vectors point the same wayOne way of measuring similarity for semantic search
RRFMerging several retrieval results by rankFuses FTS and vector rankings without mixing scores in different units
SkillA reusable "how to do it" guideSKILL.md with optional scripts and references; not another model
MCPA standard interface between an agent and external toolsConnects external capabilities over stdio or HTTP; the app still controls authorisation
BYOKBring your own model API keyYou choose the provider and pay for the model calls
Prompt injectionWeb or tool content disguised as new instructions for the agentExternal content is treated as data, and practices influenced by it without confirmation usually become proposals; this is not proof of immunity
Learned practiceA method noted down from a correction or a detour that worked"AppleScript doesn't work on this Mac — try EventKit"; model weights are not changed
Shadow modeRecording a judgement without letting it change behaviour yetThe judgement layer can record an approval suggestion; the real card still waits for your click
Held-out evaluationTesting on questions not used to tune the promptA historical design from early expert evolution, not a fixed step in today's turns

Software architecture, state and reliability

TermIn plain wordsHow Arslan uses it
SPASwitching pages and state inside one web appThe local service serves the React workbench's static assets
SidecarA helper process launched alongside the main appThe local Python backend running next to Tauri
IPCCommunication between processes on the same computerPipes, Unix sockets; not every module talks through the cloud
REST / HTTPOne request reads or changes one resourceSettings, history, task and file management APIs
WebSocketA two-way connection that keeps pushing updatesReply streams, tool status, approvals and progress events
Async I/OYielding the event loop while waiting on I/O so other work can proceedPython asyncio, async APIs and database access; not unlimited parallel CPU work
Schema / ContractAn explicit agreement on inputs, outputs and valid statesPydantic, tool arguments and task acceptance contracts
State machineDescribing how far a process has got with a finite set of statesqueued, running, waiting_user, verifying, succeeded and so on
CheckpointA record of where things are, what was done and what is leftResuming uses references, evidence and budget; unknown side effects are not blindly replayed
AttemptOne run of a taskResuming creates a new attempt; old async results cannot overwrite the new round's state
Optimistic concurrencyChecking before writing that the data is still the version you sawRow version and attempt ID stop old results overwriting a cancellation or update
IdempotencyA repeated request should not cause an unintended repeated actionMessage and task IDs prevent duplicates; unknown external effects still need checking
ACKThe receiver saying "I got this packet"Does not mean the task succeeded or that an approval took effect
Single-flightNot starting the same thing again until the last run finishesScheduled tasks avoid piling up repeated runs
BackoffWaiting longer between retries after failuresBacks off on rate limits and server errors, honouring Retry-After; authentication errors are not blindly retried
WALSQLite writes a log first, so reads and writes coexist betterLocal persistence; write concurrency still has limits
MigrationSafely upgrading an old database structure to a new oneAn explicit versioned runner, a backup before upgrading, unknown schemas refused
ProvenanceWhere a piece of information came fromDocument sources, memory sources, real run trajectories
ObservabilityBeing able to see what happened when something goes wrongRuns/Steps, Activity, usage, errors linked to deliverables

Operating system, security and delivery

TermIn plain wordsHow Arslan uses it
Sandbox / SeatbeltThe operating system limits what a process can reachThe compute sandbox and the command sandbox have different rules; network and fallback behaviour are described separately
Fail-closedRefuse to run when the protection is unavailableApplies to the default Python sandbox and the offline wrap-up path; not to every ordinary command
Accessibility treeThe structure of windows, buttons and text that the system exposesHands reads and locates controls with it, not by recognising screenshot pixels
TCCmacOS's privacy permission systemAccessibility, microphone, Apple Events and others are not granted by the app flipping its own switch
SSRFTricking a service into reaching internal addresses it shouldn'tWeb extraction and external URLs need their target, redirects and network boundary checked
AEADEncryption that protects both secrecy and integrityBridge uses ChaCha20-Poly1305; tampering makes verification fail
Key agreement / SignatureThe first agrees encryption material; the second verifies who sent itX25519 and Ed25519 do different jobs and should not be conflated
Replay protectionStopping an attacker from re-sending an old message to make it count againSignatures, recipients, a sliding sequence window and persistent de-duplication work together
CI / CDAutomating build, checks and distributionSuccessful CI must belong to the SHA being released, and the final artifact is checked too
Contract testChecking both sides of a boundary follow the same protocolPython/Rust and Mac/iPhone share positive and negative vectors
Mutation testingDeliberately breaking a protection to see whether tests catch itShows a specific assertion actually discriminates; not just a unit test under another name
Code signingVerifying where software came from and that it was not modifiedThe app and its embedded helpers all need correct signatures
Notarization / StapleApple checks the release, then the ticket is attached to itDifferent from signing; Gatekeeper also checks the result
Fresh-install acceptanceSimulating a new user with no development environment and no old dataVerifies authentication, WebSocket, assets and helpers in the real installer

Today's system is mainly a layered local monolith plus separate helpers. SQLite and in-process async scheduling suit how a personal desktop product is installed and run; read these terms at that deployment scale.
