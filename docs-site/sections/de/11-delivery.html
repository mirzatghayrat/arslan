11 / Prüfung und SoftwareauslieferungVon lauffähigem Quellcode zur installierbaren und aktualisierbaren App

Die Auslieferungseinheit einer Desktopsoftware ist das Anwendungspaket. Python-Module, Systemwerkzeuge und alte Datenbanken aus der Entwicklungsumgebung können ein Paket mit fehlenden Ressourcen scheinbar funktionsfähig machen. Arslan trennt die Prüfung deshalb in Quellcode, Plattform, gebündelte Artefakte, frische Nutzerumgebung und Distribution. Dieses Kapitel dokumentiert den Ablauf von v0.1.63 und die zugehörigen Release-Belege.

Bei macOS genügt nicht allein der pytest-Exitcode. Die Pipeline wertet JUnit aus und verlangt, dass 60 festgelegte Plattformfälle tatsächlich ausgeführt werden – ohne übersprungene oder fehlgeschlagene Tests. Fehlen Abhängigkeiten und werden dadurch alle Fälle übersprungen, wird die Prüfung ebenfalls nicht bestanden. Python und Rust teilen Hands-Vertragsbeispiele. Mac, iOS und eine unabhängige Python-Referenz verwenden gemeinsame Bridge-Testvektoren. So lassen sich Parameterabbildung, Signaturen, Empfängerprüfung, Manipulation und Replay sprachübergreifend abgleichen.

Die Aussagekraft bleibt begrenzt: Eine Swift-Typprüfung validiert keine Mikrofonberechtigung, ein Linux-Unit-Test keinen macOS-Kernel und ein simuliertes Postfach kein produktives CloudKit. Testzahlen sind auch keine Gesamtdeckungsquote. Überlappende Testsuiten dürfen nicht zu einer Zahl unabhängiger Szenarien addiert werden.

Der Release-Workflow fragt ab, ob für genau die zu veröffentlichende SHA eine erfolgreiche CI vorliegt. Der Erfolg eines anderen Commits genügt nicht. Der Build verwendet durch Lockdateien gebundene Abhängigkeiten. Python wird ausdrücklich als eigenständiger, von uv verwalteter Interpreter gewählt, damit der Runner nicht zufällig einen Framework-Build verwendet. PyInstaller bündelt das Backend als onedir; statische Frontendressourcen sowie Swift- und Rust-Helper werden mit der Tauri-App zusammengestellt.

Signierung und Notarisierung erfüllen unterschiedliche Aufgaben. Eingebettete Mach-O-Dateien müssen zuerst signiert werden, bevor die äußere App sie umschließt. Für die Distribution werden Developer ID, Hardened Runtime und Zeitstempel verwendet. Das DMG wird bei Apple zur Notarisierung eingereicht, anschließend wird das Ticket per staple angeheftet und Gatekeeper prüft das Ergebnis. Das Buildskript erlaubt weiterhin unsignierte Entwicklungspakete und Warnpfade bei teilweise fehlenden Zugangsdaten. Ein erfolgreicher Build erfüllt deshalb nicht automatisch alle Voraussetzungen öffentlicher Distribution; beim offiziellen Release müssen die tatsächlichen Artefakte geprüft werden.

Für das Updatemanifest gelten eigene Bedingungen: Tag und Tauri-Version müssen übereinstimmen. Ein entsprechendes Manifest entsteht nur mit Updater-Signatur. Der Ablauf erzeugt zunächst ein GitHub Draft Release. Erst nach der offiziellen Veröffentlichung sehen installierte Apps das Update bei einer späteren Prüfung.

Die Neuinstallationsabnahme startet unmittelbar das Anwendungspaket

fresh_install_check.py startet mit temporärem HOME und minimaler Umgebung das tatsächliche arslan-desktop im Paket. Es startet nicht stellvertretend den Dienst aus einer Quellcode-venv. Geprüft werden unter anderem, dass keine Nutzerdatenbank oder geheimen Dateien im Paket liegen, die Erstinitialisierung, Tokenerzeugung und Dateirechte, Ablehnung nicht authentifizierter Anfragen, ein echter WebSocket-101-Handshake sowie korrekter Abruf des Frontend-JavaScripts. HTTP 200 kann lediglich die SPA-Fallbackseite sein; eine Ressourcenprüfung darf sich daher nicht auf den Statuscode beschränken.

Dasselbe Skript prüft native OCR, eingebettete Helper, Bridge-Selbsttest und zugehörige Signaturen. In einem früheren gebündelten Paket fehlte eine dynamisch geladene WebSocket-Abhängigkeit: Der Health-Endpunkt funktionierte, der Chat konnte die Verbindung jedoch nicht hochstufen. Erfolgreicher Import, laufender Dienst und mitgelieferte Kernfunktion sind also drei unterschiedliche Nachweise.

Nutzer starten die Updateinstallation; der Download wird verifiziert

Der Tauri-Updater findet Updates über die öffentliche latest.json und prüft die Archivsignatur mit dem in die App einkompilierten öffentlichen Schlüssel. Einmal beim Start wird geprüft; zusätzlich ist eine manuelle Prüfung im Menü möglich. Diese Version besitzt keinen Timer für regelmäßige Prüfungen. Bei einer neuen Version erscheint ein Hinweis. Erst nach dem Installationsklick folgen Download, Signaturprüfung, Austausch und Neustart. Eine fehlgeschlagene automatische Prüfung kann auf eine vorübergehend fehlende Verbindung zurückgehen; ein Installationsfehler muss dem Nutzer dagegen klar gemeldet werden.

Die frühen Versionen 0.1.0/0.1.1 registrierten nur das Updater-Plugin, riefen die Prüffunktion aber nicht aktiv auf und konnten deshalb neue Versionen nicht automatisch entdecken. Die aktuelle Implementierung verbindet Prüfung, Installationsbereitschaft, Downloadfehler und Neustart zu einem ausdrücklichen Ablauf. Eine vorhandene Signaturkonfiguration bedeutet noch nicht, dass dieser Ablauf ausgelöst wurde.

Auf welche Artefakte sich die Auslieferungsbelege von 0.1.63 beziehen

Die GitHub-Actions-Läufe zum Release-Commit zeigen: Der Release-Quellstand ist 9bbb6ad6 auf main; die CI auf main bestand beim ersten Versuch (Run 40502155919), einschließlich der 60 festgelegten Plattformfälle des macOS-Jobs ohne übersprungene Tests; im Backend bestanden 9.469 Tests, 124 wurden übersprungen. Das Pushen des Tags startete keinen eigenen CI-Lauf, deshalb nutzte das Gate den Lauf auf main für denselben Commit. Der Release-Workflow (Run 40505601007) bestand Quellprüfung, Build und Veröffentlichung; das DMG wurde zur Notarisierung angenommen, das Ticket angeheftet und von Gatekeeper akzeptiert. Der Fresh-Install-Test der ausgelieferten App meldet 92 bestandene und 0 fehlgeschlagene Prüfungen, einschließlich der Annahme der Verbindung des signierten Backends durch Hands und des Bridge-Selbsttests.

Die beiden Releases davor: 0.1.61 wurde aus main bei fb6d7230 erstellt (CI auf main Run 38489348597, Tag-CI Run 38498094635, Release Run 38498094628; 54 Plattformfälle; Backend 8.466 bestanden und 124 übersprungen; Fresh-Install 89/0). 0.1.62 wurde aus release/0.1.62 bei a4fca23b erstellt (Branch-CI Run 39112567104, Tag-CI Run 39114206598, Release Run 39114206588; 55 Plattformfälle; Backend 8.747 bestanden und 125 übersprungen; Fresh-Install 89/0). Beide bestanden beim ersten Versuch, wurden notarisiert, mit dem Ticket versehen und von Gatekeeper akzeptiert.

Die geprüften Objekte unterscheiden sich, und die Aufzeichnungen benennen das. Die öffentlichen Notes zu 0.1.63 sagen, dass auf einem Release Candidate eine kurze Liste von Prüfungen von Hand durchgegangen wurde und dass zwei davon nicht bestanden (eine dritte Folgebearbeitung, die mehr änderte als verlangt, und eine einzeilige Änderung in einer langen Datei über das Terminal); sie sagen nicht, dass genau das DMG von 0.1.63 von Hand installiert und vollständig bedient wurde, und dieses Dokument tut es auch nicht, ebenso wenig einen vollständigen Durchlauf vom iPhone zum Mac mit der ausgelieferten App. Die Notes zu 0.1.61 und 0.1.62 enthalten keinen manuellen Durchlauf auf einem echten Mac, auf den sich dieses Dokument stützt. Zum Vergleich: Die Verification von 0.1.53 dokumentierte einen Durchlauf auf einem echten Mac, bei dem Hands eine Notiz in Notes erstellte und wieder las, während eine Freigabe 36 Sekunden lang wartete – mit dem Build-only-Paket von 43751254, nicht mit dem finalen DMG. Automatische Paketabnahme, Funktionstest eines früheren Builds und manuelle Abnahme des exakten Distributionspakets müssen getrennt benannt werden und ersetzen einander nicht.
