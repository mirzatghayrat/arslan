02 / 個人開発とオープンソースAI とともに、一人でアプリをシステムへ育てる

Arslan は、私が AI の支援を受けて単独で開発したプロジェクトです。いわゆる vibe coding にあたります。最初のプロトタイプからその後の各バージョンまで、一貫して私一人で開発を進めてきました。

ここでいう「個人開発」とは、プロジェクト全体を作者が単独で進めており、AI が実装過程の協働ツールであるという意味です。同時に Arslan は、オープンソースのフレームワーク、システム API、外部モデル、サードパーティのコンポーネントを基盤としています。開発方法、プロジェクトの責任、コンポーネントの出所は、それぞれ別の意味を持ちます。以下では、最終的に製品に組み込まれた設計と実装について説明します。

コードの生成から、使える製品の保守へ

コードが動くことは、製品に必要なことのごく一部です。デスクトップアプリでは、サービスの起動方法、ウィンドウの接続方法、古いデータベースの移行方法、プロセス終了後の後処理、システム権限を持つ主体、開発環境のないマシンで配布パッケージが動くかどうかも解決しなければなりません。Agent にはさらに不確実性があります。モデルのタイムアウト、ツール引数の欠落、Web ページの読み取り不足が起こり得ますし、実行の途中でユーザーの承認が必要になることもあります。

こうした課題を受け、Arslan の改良は次第に四つの方向へ進みました。明示的な契約で入力と状態を制約すること、観察可能なツール結果で完了状況を照合すること、権限の境界で実際の副作用を制御すること、そしてテストとリリース時の受け入れ確認で変更の妥当性を確かめることです。AI の支援は実装や原因調査を速められますが、最終的な製品の提供には、これらの制約がそろっている必要があります。

初期の前提を捨てる判断

初期は専門家の分身を中心に機能を組み立てていましたが、後に一つの Arslan へ統合しました。ツールや手順は再利用しながら、ユーザーの入口と主要な実行経路を、実際に生じた課題に合わせて設計し直しています。

改善しなかった結果も残す

レビュー層、経験学習、並列処理を追加しても、必ずしもタスクの結果は改善しません。プロジェクトでは、レビューの失敗、調査タスクでの劣後、学習後も高速化しなかった結果を記録し、次の修正につながる具体的な手がかりとしています。

Arslan 自体の役割と、依存コンポーネントの役割

構成要素プロジェクト内での役割
アプリケーションと実行システムArslan は、UI、モデルアダプター、統一ループ、タスク状態、記憶、ツール権限、デスクトップへの配布をまとめ、インストール可能な個人向けアプリを構成します。
基盤フレームワークReact、Tauri、FastAPI、SQLAlchemy、SQLite などが、汎用的な UI、ホスト、サービス、永続化を担います。
モデルユーザーが設定したエンドポイントを通じてモデルを呼び出します。Arslan が提供するのはアプリの実行環境と実行経路であり、このプロジェクトで新たな基盤モデルを学習しているわけではありません。
デスクトップ自動化コンポーネントHands は未改変の agent-desktop 0.9.4（Apache-2.0）を使用します。Arslan はその外側に、独立した helper、認証、権限ポリシーを実装しています。
ターミナルルールの出所破壊的なコマンドの検出や基本的な安全規則の一部には、MIT ライセンスの Hermes Agent のコードを再利用し、Arslan の外部への操作および認証情報に関するルールを組み合わせています。
