04 / これまでの歩み専門家を生成する仕組みから、仕事を続けられる一つの Arslan へ

Arslan は、作者が AI を活用した vibe coding により、単独で開発を続けているプロジェクトです。その歩みには新機能の追加だけでなく、設計の撤回もあります。実行条件を整える必要がある機能もあれば、複雑さを取り除くべき部分もありました。過去の機能をすべて並べるより、こうした変化を理解するほうが、現在のアーキテクチャをよく説明できます。

この年表には、根拠から確認できる範囲があります。初期の日付は残存する Git コミット、正式バージョンの日付は公開 Release に基づき、すべて北京時間に換算しています。最初のコミット、オープンソース化の準備、リポジトリの公開、初回リリースは、それぞれ別の時点です。現在の記録からは、リポジトリを Public に切り替えた正確な日付は確定できません。現在の公開リポジトリは 2026 年 7 月 26 日に作成されました。

6 月：まず「会話を通じて Agent を生成する」一連の流れを作る

現存する最初のコミットは 2026 年 6 月 7 日のデータモデルです。当時の方向性は Meta-Agent でした。技術に詳しくないユーザーが会話を通じて分野ごとの専門家を作り、その専門家がタスクを遂行するという構想です。その後、モデルアダプター、ツールレジストリ、要件を聞き取る会話の状態機械、テンプレート、Spawn Manager、CLI が加わりました。6 月 8 日には、FastAPI、非同期データベース、認証、WebSocket、React UI が接続され、操作、保存、再接続ができるプロトタイプになりました。

ツールが実際に動き始めると、システムは「何を実行したか」を把握し、回答に使う資料も供給する必要が生じました。6 月 23 日には Runs、Steps、Evaluations、文書の分割、SQLite FTS5 が追加され、6 月 27 日には MCP の stdio と HTTP トランスポートが導入されました。これにより、専門家向けのプロンプトを生成するだけの段階から、モデルの呼び出し、ツールの実行、過程の保存、資料の検索、ユーザーへの結果の返却まで、一回の実行全体を管理する段階へ進みました。

最初のデータモデル；Runs データモデル；FTS5 の知識インデックス；MCP HTTP トランスポート。

7 月：記憶と製品の提供を、技術的な課題として捉える

7 月 5 日、Second Brain に embedding とスコープで絞り込むハイブリッド検索が追加されました。全文検索、ベクトル類似度、RRF による順位融合を組み合わせたものです。その後、事実の出所、有効性、置き換えと取り消し、整理提案、利用記録が加わりました。記憶は単なるチャットの要約ではなくなり、資料の関連性、現在も有効かどうか、どの範囲に属するかが、モデルのコンテキストに入れられるかどうかを左右するようになりました。

多くの履歴をコンテキストに取り込むと、新たなトレードオフが生まれます。検索範囲が広すぎると無関係な資料が混ざり、古い事実が新しい事実を上書きし、外部の文章が長期的な動作に影響する可能性があります。そのため、7 月の実装では事実に出所と時系列を付け、自動追加、レビューが必要な変更、機微な内容を区別し、整理結果を提案の受信箱へ送るようにしました。その後の記憶機能もこうした制約に沿って発展しています。「より多くを覚える」ことよりも、ユーザーが確認し、訂正し、取り消せることが、明確な技術目標になりました。

この時期には長期保守への対応も始まりました。7 月 14 日、データベース移行を独自のバージョン管理 runner に切り替え、Alembic への依存を削除しました。7 月 10 日にはライセンスを Apache-2.0 に変更し、NOTICE と SECURITY.md を追加しました。7 月 25 日には明示的なオープンソース化準備のコミットが記録されています。7 月 27 日には、初のデスクトップインストール版として v0.1.0 を公開しました。Tauri のシェルと実行ファイル化した Python バックエンドを一緒に配布し、署名、公証、更新、初回インストールの検査がリリース工程に入りました。

実際のインストール環境では、すぐに開発時のテストでは見えなかった欠落が明らかになりました。v0.1.0–0.1.6 のパッケージには WebSocket の実行時依存関係が不足しており、health API は正常でもチャットには接続できませんでした。0.1.7 で依存関係と PyInstaller の hidden import を修正し、実際のハンドシェイクをインストール時の受け入れ確認に追加しました。この不具合は、「バックエンドが起動した」だけでなく、「ユーザーの操作経路全体が使える」ことまで検証すべき理由を示しています。

ハイブリッド検索；バージョン管理された移行；オープンソース化の準備；配布パッケージの WebSocket 障害の振り返り。

8 月：接続できる機能を、ユーザーにも分かるものにする

0.1.20 では、認証情報の状態を「未設定」「復号可能」「復号不可能」に分け、salt と鍵の移行を安定させました。検索には出典とエラーの説明が加わり、モデルはタスクごとに役割を分担するようになりました。その後、MCP OAuth、OpenRouter ログイン、初回案内、拡張機能一覧、ローカルワークスペースの読み書き、定期タスク、SSH が順次追加されました。拡張機能が増えるにつれ、現在の接続でツールを呼び出せるのか、設定したツール類が有効なのか、どの操作に許可が必要なのかを、システムが正確に伝える必要も生じました。

ローカルでの実行機能も分離が進みました。ワークスペースの読み取りと書き込みを分け、書き込みには対応する許可を必要としました。定期タスクには専用の実行スケジュールの許可を設けました。SSH では接続先を記憶できますが、リモートでの実行には毎回確認を求めます。こうしてツールの一覧は、能力と利用条件の両方を示すものになりました。ユーザーにとって「接続済み」と「今回は実行できる」は異なる状態であり、UI とモデルのコンテキストの両方で、その違いを表す必要があります。

0.1.23 の turn journal により、会話を切り替えても生成中の回答を再び受け取れるようになりました。一方、インストール版が npx を見つけられない問題の修正は、デスクトップアプリが受け取る環境とターミナルの環境が異なることを、改めて示しました。8 月の主題は接続先の追加だけでなく、接続、状態、許可を、ユーザーが理解できる操作へ変えることでした。

9 月：一回の回答から、追跡できる仕事へ

0.1.38 では信頼性を集中的に強化しました。既定で実行を拒否する Python サンドボックス、独立した計算ランタイム、永続化された Runs、成果物、チェックポイント、共有の実行予算が加わりました。0.1.40 のプレビューと安定化では、プロジェクト記憶、文書の出典、タスクの継続、移行前のバックアップが進む一方、言語をまたぐ複数文書の比較に関する既知の失敗も記録に残しました。出典をクリックできることは資料を見つけられることを示すだけで、モデルの結論の正しさを証明するものではありません。

それより少し前の 8 月 31 日から 9 月 3 日にかけて、音声機能は読み上げ（0.1.32）、押している間だけの音声入力（0.1.36）から、半二重の音声会話（0.1.37）へ進み、マイク権限と使用言語の選択も修正されました。その一方で、0.1.40 の調査機能の受け入れ確認では、異なる言語間の比較の失敗を成功扱いに変更していません。0.1.41 の出典レビューも、判定の調整が十分でなかったため、既定では無効のままにしました。こうした記録は「システムが検査した」ことの意味を限定し、実際の失敗に沿って次の改善を進める基盤となっています。

0.1.41 では、ウィンドウを閉じてもメニューバーに残って作業を続けるようになりました。0.1.42 では長いタスクをバックグラウンドへ移し、ユーザーがチャットを続けられるようにしました。0.1.43 ではさらに、予算のソフト上限と強制停止を区別しました。ソフト上限に達したら、手元の資料を使ってまず成果をまとめ、調査が途中で止まって何も届けられない事態を避けます。タスクは次第に UI から独立したライフサイクルを持つようになりましたが、任意の外部操作をクラッシュ後に安全に自動再実行できるという意味ではありません。

9 月末から 10 月：一つの実行ループへ集約する

初期設計では専門家を長期的に存在する役割として扱い、ユーザーとシステムの双方が、選択、招待、振り分けを扱う必要がありました。0.1.44 では専門家の作成とディスパッチを停止し、既存の専門家の手順を Skill に変換できるようにしました。0.1.46 では、利用経路がなくなった専門家のバックグラウンド進化を停止しました。0.1.48 では前段の router を取り除き、すべてのメッセージが直接 Agent ループに入るようにしました。リリースノートによれば、「できません」という一部の定型回答は、実際の能力ではなくルーティングの判定に由来していました。この集約により、ツールの選択を、実際のツールと状態を持つ実行過程に戻しました。

集約後の改善は、共通の実行層に集中しています。0.1.49 はネイティブなツールプロトコル、応答の途切れ、失敗からの復旧を改善しました。0.1.50 では現在の作業状態、計画、代替経路が加わり、0.1.51 ではコマンドサンドボックスと Island、0.1.52 ではユーザーの記憶と learned practices が後続の作業で使われるようになりました。ここでの「学習」は、管理可能な経験を保存して利用することであり、基盤モデルの重みを更新することではありません。

0.1.53 では、独立した Hands helper によってアクセシビリティツリーを読み取り、Mac アプリを操作できるようになり、Mac 側の iPhone Bridge も含まれました。0.1.54 では、この Mac 側を iPhone アプリに対応できる状態に整え（Touch ID による承認、スマートフォン 1 台につき 1 項目、スマートフォンを削除したときの後片付け）、ターミナルゲートの 4 つの抜け穴を塞ぎました。いずれも確認を増やす方向の変更で、減らすものではありません。以前の専門家オーケストレーションは、すでに過去の仕組みです。また、アクセシビリティ経由の操作ができるからといって、すべてのアプリを確実に制御できるとは限りません。現在も、目に見える状態、明確な権限、確認できる結果によって、モデルが実際に行える仕事を制約しています。

信頼性の基盤；安定版の調査アシスタントの範囲；バックグラウンド作業；統一 Agent ループ；Hands と Bridge。
