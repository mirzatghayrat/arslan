10 / iPhone と Mac Bridge依頼と確認はスマートフォンで、実行は Mac で

モバイル連携により、ペアリング済みの iPhone から Mac のタスクを確認し、作業を依頼し、承認に回答し、結果を読むことができます。実行するのは引き続き Mac 上の Arslan です。スマートフォンは別のクラウド Agent サービスではなく、Mac の HTTP インターフェースを直接公開したり呼び出したりすることもありません。本章は、Mac v0.1.54 の公開プロトコルとソースコードを基準にしています。この版には Mac Bridge が含まれていますが、公開リリースノートでは iPhone App は引き続き公開予定とされています。そのため、本書では App Store での公開や、本番環境における一連の経路の受け入れ確認が完了したとは述べません。

CloudKit はメールボックスであり、デバイスの本人性はプロトコルで確認する

v1 は、同じ Apple ID の CloudKit 非公開データベースを使います。Mac は電源が入り、オンラインで、実行可能な状態である必要があります。そうでなければメッセージは処理待ちとなり、スマートフォンから電源の切れた Mac を動かすことはできません。LAN 内の Bonjour は今後の方向性であり、この版の代替直結経路ではありません。Mac helper は、アプリに伴って動く独立した ArslanBridge.appで、stdin 経由でローカル API token を受け取ってバックエンドに接続します。スマートフォンはこの token を持たず、モデルの API key も受け取りません。

エンベロープのクラウド側で見える索引フィールドには、送信元・送信先のデバイス、シーケンス番号、大まかな kind、通知フラグ、時刻があります。実際のメッセージ種別、本文、ファイル内容は、アプリ層の暗号文に含まれます。したがって、「エンドツーエンド暗号化」は、ペアリングされたデバイス間のメッセージ保護を指します。メタデータが存在しないことや、バックエンドのモデル呼び出しがユーザー設定の AI サービスを一切経由しないことを意味しません。

QR コードの読み取りは、ペアリングの始まりにすぎない

QR コードには、一回限りの pairing_id、Mac の署名用・鍵交換用の公開鍵、32 バイトのペアリング鍵、固定のコンテナ識別子、有効期限が含まれます。有効期間は最大 600 秒です。スマートフォンは、期限切れ、誤ったコンテナ、制約に合わない内容を拒否し、QR コード内の Mac 公開鍵を固定します。その後、自身の識別用・鍵交換用の鍵を生成し、暗号化されたペアリング要求を送ります。Mac は要求を検証した後もユーザーに提示し、Mac 上でのクリックによって承認または拒否を決めます。

同じ要求の再試行には同じ決定を返し、二度目の許可を生じさせないようにします。承認後はデバイスの識別情報を使って通信し、ペアリングコードは使用済みになります。Mac からスマートフォンの登録を取り消すこともできます。同じ iPhone が再びペアリングするときは以前の ID を伝え、Mac はそれらの古い項目を 2 件並存させずに削除します。スマートフォンを削除すると、Mac がそのスマートフォン宛てに iCloud に残していたメッセージも削除されます。起動時にも Mac は、ペアリングが解除されたスマートフォンを待ち続けている記録を消去します。設定 › iPhone では、各スマートフォンは Mac がそこから認証済みのメッセージを初めて読み取るまで Connecting… と表示され、その後は Connected と最終接続時刻が表示されます。各デバイスの秘密鍵は、それぞれの Keychain に保存します。信頼の根拠は、一回限りのペアリング情報とユーザー確認の組み合わせであり、「同じ iCloud アカウントだから、どのメッセージも信頼できる」というものではありません。

メッセージの内容、出所、コンテキストを同時に検証する

新しいメッセージごとに一時的な X25519 鍵で共有秘密を確立し、HKDF-SHA256 で 32 バイトの鍵を導出します。ChaCha20-Poly1305 で認証付き暗号化を行い、さらに Ed25519 で署名します。ヘッダーには長さで区切る UTF-8 フィールドを使い、言語間の JSON の並び順の違いが検証に影響しないようにします。ヘッダーフィールドは署名と AEAD 認証の両方に結び付けます。これは CryptoKit の暗号プリミティブを使ったアプリケーションプロトコルであり、Signal の Double Ratchet は実装していません。一時鍵を使うことだけをもって、あらゆる状況での前方秘匿性を主張することもできません。

受信時の順序は明確です。形式と受信者を確認し、署名を検証してから復号します。その後、平文とヘッダーの一致を確かめ、ファイルがある場合は添付も検証します。どの段階で失敗しても、業務上の処理が部分的に反映されてはいけません。ファイルの上限は 20 MiB で、暗号文のダイジェスト、認証タグ、平文のサイズとダイジェストがすべて一致して初めて、キャッシュやプレビューが可能になります。

配信成功、操作完了、UI の最終状態は別のもの

永続化と同じパケットの再試行再試行では同じエンベロープ ID、seq、暗号文を使います。シーケンス番号などの重要な状態を先に保存し、ネットワーク障害で状態が後戻りするのを防ぎます。配信ログは、外部の業務システムのトランザクションの代わりにはなりません。
リプレイウィンドウ送信者ごとに直近 1,024 個のシーケンス番号を保持します。ウィンドウ内の新しいパケットは順不同でも受け取り、重複または古すぎるものは拒否します。有効な新しい番号でも、業務状態が新しいとは限りません。古い進捗が後から送られることもあります。
ACKエンベロープの配信を確認します。重複パケットにも再び ACK を返せます。元の記録は確認後に削除し、ACK 自体には ACK を返しません。ACK はタスクの成功でも、承認した操作の実行完了でもありません。
業務上の識別子と結果client_msg_id、client_task_id は重複防止に使い、approval.result、タスクイベント、結果が業務上の状態を伝えます。v0.1.54 の業務 ID の対応付けにはメモリ内の状態があるため、任意のクラッシュでも全体で exactly-once が成立するとは約束できません。

Mac の状態スナップショットは、まだ実行中のタスクだけを含みます。通常の heartbeat 間隔は 60 秒で、スマートフォンは 90 秒間更新がなければオフラインと判断します。進捗は頻度を制限してまとめ、最終状態は速やかに送る必要があります。そのためクライアントは、メッセージの重複と順序の乱れを処理しながら、タスク一覧、承認カード、履歴を整合させなければなりません。「最後に受け取ったテキストで前を上書きする」だけでは状態を維持できません。

スマートフォンの承認は、Mac の許可と実行経路を再利用する

スマートフォンには具体的な action、target、risk を表示します。承認には端末内の生体認証が必要ですが、拒否には不要です。回答を送信した後も、Mac からの approval.resultを待ちます。Mac はカードがまだ有効かを確認し、元の confirm / cancel 操作へ対応付けます。スマートフォンからコマンドに「常に許可」を与えることはありません。音声入力は確認待ちのテキストを作れますが、承認の代わりにはなりません。

バージョンの境界：v0.1.54 以降、Mac は faceid または touchid マーカー（iPhone SE では Touch ID）が付いている場合にのみ回答を承認として扱い、そのことを capabilities でスマートフォンに伝えます。それ以外のマーカーはすべて拒否として扱います。0.1.54 より前は、Touch ID による承認はキャンセルとして扱われていました。プロトコル内の high_risk_mac_only は、この版では false に固定されており、ユーザーが設定できるスイッチではありません。共有プロトコルとテストベクトルは相互運用や異常系を検証できますが、最終配布パッケージ、実際の iCloud、プッシュ通知、デバイス認証を含むエンドツーエンドの受け入れ確認の代わりにはなりません。
