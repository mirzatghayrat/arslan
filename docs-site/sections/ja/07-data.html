07 / データと記憶役立つコンテキストを残し、データの境界も明確にする

Arslan は、主な状態をマシン上の SQLite に保存します。会話、実行記録、タスク、個人の記憶、モデル設定、使用量には、それぞれ対応するデータモデルがあります。ファイルの成果物はディスクに書き込みます。非常に長いツール出力の全文はアプリのデータフォルダーに別途保存され（保持期間は 7 日間）、モデルは結果に示されたパスから分割して読み取ります。そのため、ウィンドウを閉じてもタスクの過程は消えず、「そのとき何を話したか」「実際に何をしたか」「今後何を覚えてよいか」を別々に管理できます。

データへのアクセスには、非同期 SQLAlchemy と aiosqliteを使います。接続では WAL、外部キー検査、5 秒のビジータイムアウトを有効にし、 synchronous=NORMALを設定しています。これらはローカルの単一ユーザー向けアプリに合わせた選択で、配備時の依存を減らし、読み書きが並行する場合の使い勝手を改善します。データディレクトリには協調型のプロセスロックも設け、同じプロトコルを守るインスタンスが同じデータを同時に使うことを防ぎます。

図 3 · 記憶の循環。テキストで表すと、出所 → 判断 → 有効化／提案 → 保存 → 範囲と権限による絞り込み → 呼び出し → 利用記録となります。「EventKit を使う」と覚えても、リマインダーへのアクセス権限を得られるわけではありません。

作業用コンテキスト：今回の入力を制御し、元の履歴を残す

モデルが一度に受け取れる量には限りがあるため、Arslan は長さに上限のある逐次更新の要約と最近のメッセージで、作業用コンテキストを構成します。この履歴ウィンドウの既定の推定予算は 3,000 token で、要約そのものにも長さの制限があります。これは履歴を組み立てるための予算であり、モデルリクエスト全体が 3,000 token という意味ではありません。システム指示、ツール schema、資料、結果も別の領域を使います。

会話が長くなると、古いメッセージは要約にまとめ、最近のメッセージは原文を保てます。圧縮が変えるのは次回の入力に含める内容であり、データベース内の完全な会話を削除するわけではありません。圧縮に失敗しても元の記録は残ります。長すぎるツール出力には、別途ディスクへ保存する仕組みがあります。モデルには先頭と末尾の抜粋とファイルパスを渡し、必要に応じて分割して読み取ります。完全な出力は保持ポリシーに従って削除します。

この層構造により、モデルには現在のタスクに必要な情報を優先して見せながら、後の照合に使う元の根拠を残せます。要約は既存の内容を圧縮した表現にすぎず、外部操作の実際の応答記録の代わりにはなりません。

個人の記憶：関連性より先に、利用できるかを判断する

記憶の項目には、種類、範囲、機密度、利用ポリシー、状態、信頼度に関する情報、改訂番号を持たせます。範囲はグローバルまたは特定のプロジェクトで（ほかにドメインや専門家などの内部的な範囲もあります）、各項目には所有者もあります。local_only などの利用ポリシーが、クラウドモデルへの要求に含めてよいかをさらに決定します。各ターンの信頼できるコンテキストは、データベースから会話設定を読み込みます。通常のユーザーテキスト、Web ページ、モデル出力が、これらの権限を勝手に書き換えることはできません。

「あなたについて」と「Mac ノート」は、量を制限した基本情報として挿入し、その他の内容は関連性で選びます。v0.1.52 以降は、既定で有効な「自分のことを覚え、会話で使う」により、通常の項目で、cloud_allowed のものを、設定済みのクラウドモデルで使えます。機微な内容には追加の許可が必要です。local_only の内容は、全体のスイッチを有効にしてもクラウドに送れるようにはなりません。

ContextReceipt は、使った項目と改訂、利用理由、推定量を記録し、記憶の本文は複製しません。ユーザーはコンテキストの選択根拠を追跡でき、システムもそのために機微な内容のコピーを新たに作らずに済みます。

記憶を編集すると新しい改訂が作られ、項目の現在の改訂を指すポインターも更新されます。出所の記録は、その版がどのように形成されたかを引き続き示します。停止、期限切れ、置換済み、削除などの状態も、後続のコンテキストに含めるかに影響します。バージョン管理は変更の照合に役立ちますが、削除処理では消す必要のある本文を消去します。したがって、すべての履歴が永久に削除できないイベントストアではありません。

資料検索：キーワードとベクトルを組み合わせる

知識資料の検索モジュールは、SQLite FTS5 の全文検索と、ベクトルのコサイン類似度検索に対応しています。前者は語句の一致を、後者は embedding を使って意味の近い断片を探します。両方を利用できる場合は、RRF で順位を統合します。RRF が比べるのは順位であり、尺度の異なる生のスコアを直接混ぜません。embedding が未設定、またはベクトルがない場合も、全文検索を利用できます。

検索された断片は出典とともにモデルのコンテキストに入り、モデルが現在の質問と合わせて回答を組み立てます。ここでいう RAG は、この仕組みを指します。記憶 v2 が有効な場合、資料の検索は資料コレクションが紐付けられたプロジェクトでのみ行われます。クラウドモデルを使う場合は、その会話自体のクラウド記憶の許可も有効である必要があります（既定の「Remember me」スイッチは資料を対象にしません）。結果は recall ツールの戻り値としてコンテキストに入ります。基盤モデルの重みを変更する必要はなく、別途配備したベクトルデータベースにも依存しません。個人の記憶 v2 の選択には、主に権限による絞り込み、全文検索、ローカルの関連性ロジックを使います。すべての記憶が同じベクトル処理を通ると解釈することはできません。

経験からの学習：訂正を、レビューできるルールにする

Lesson は、ユーザーの訂正、失敗の後に成功した回避策、マシン環境の特徴を保存します。たとえば、現在の Mac であるコマンドに別の引数が必要なら、出所のある経験として残し、類似タスクの参考にできます。呼び出すのは最大 5 件、合計約 800 文字で、動的な agent status に入れ、固定のシステムプレフィックスには混ぜません。呼び出し、遵守、成功、失敗をそれぞれ計数します。

保存する価値があるか、既存の内容と重複または矛盾するかについては、judgment 層が狭い範囲の判断を提示し、確率と後の結果を記録できます。ユーザーの訂正や、外部コンテンツの影響を受けていない経験は、設定で許可され、有用と判断されれば直接有効にできます。その他のレビューが必要な内容は提案へ送ります。認証情報を含む候補はその場で破棄されます。「推測された機微情報はレビューが必要」というルールは個人の記憶に適用されるもので、経験には適用されません。判断が得られない場合やタイムアウト時には、フォールバック経路があります。

これらの仕組みは、アプリが保存して呼び出す知識を変更するもので、モデルの重みを学習するものではありません。judgment の有効範囲も用途ごとに異なります。たとえば、ツール承認の判断が shadow モードのときは提案を記録するだけで、実行の可否は引き続き本来の許可フローが決めます。

削除を、要約と古いバックアップにも反映する

記憶を削除すると、システムは deletion epoch を進め、その項目の古い改訂の本文と出所を消去し、すべての会話の逐次要約と、実行記録にキャッシュされたプロンプトを消去します。これにより、古い派生コンテンツが削除済みの記憶を呼び戻すことはありません。削除記録には照合用のコンテンツ指紋（ローカル鍵による HMAC）と範囲などのメタデータだけを残し、削除済みの本文を台帳に再保存することを避けます。suppression 記録は、チャット履歴に残る同じ出所から記憶が再び自動生成されるのを防ぎます。記憶の削除と元の会話の削除は、別々のデータ操作です。

独立した削除台帳と削除マニフェストにより、起動時と復元時にも削除を引き続き適用します。古いバックアップを復元する前には、ストレージの識別情報を検証し、データを有効にする前に、削除情報と照合して一時領域のデータを整理します。これにより、古いバックアップから削除済みの記憶が戻る可能性を抑えます。この保証は復元手順と利用可能な削除記録に依存し、外部に出力済みのすべてのコピーを取り消せるという意味ではありません。

バックアップ内の他の記憶も、すべての利用許可がすぐに復元されるわけではありません。復元処理はそれらをレビュー待ちとして隔離し、利用ポリシーを厳しくし、キャッシュされたコンテキストを消去し、すべての定期タスクを無効にし、会話単位のクラウド利用と機微情報の許可を取り消し、進行中のプロジェクトをアーカイブします。データの復元と利用の再承認を分けることで、古い会話の許可が新しい実行環境で知らないうちに有効になることを防ぎます。

移行を完了してから、アプリがデータを使い始める

現在のデータベース更新は、明示的な移行 runner を使います。schema のバージョン検査、更新前バックアップの準備、不足するテーブルの作成、未実行の移行の順次実行を行い、その後に鍵の互換性処理と記憶 v2 の有効化を行います。不明な schema や新しすぎる schema は拒否し、古いプログラムが新しいデータを不用意に変更することを防ぎます。v0.1.54 の明示的な登録は 0061まで進んでいます。初期の Alembic の履歴を、現在の実行方式と混同しないでください。

記憶 v2 の有効化では、旧来の事実テーブルと学習テーブルを legacy テーブルに改名し、読み取り専用のトリガーを追加します。互換ビューが旧来の読み取り口を新構造に対応付け、全文インデックスもこの過程で作成します。モデルの API キー、MCP の環境変数と OAuth トークン、SSH 鍵などの秘密フィールドには、フィールド単位の Fernet 暗号化（PBKDF2 とインストールごとに独立した salt）を使いますが、通常の会話やタスクのテーブルまで含めたデータベース全体の暗号化ではありません。永続化、秘密情報の保護、バックアップからの復元には、それぞれ固有の境界があります。
