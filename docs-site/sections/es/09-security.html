09 / Ejecución y límites de seguridadQué ocurre entre la propuesta del modelo y la acción real

Arslan puede leer y escribir archivos, ejecutar comandos y trabajar mediante navegadores y aplicaciones nativas. Su diseño de seguridad parte de una distinción: el modelo propone el siguiente paso y el código de confianza decide si puede ejecutarse. A continuación se describen los límites implementados en v0.1.63. Son protecciones con ámbitos concretos, no una demostración de seguridad frente a cualquier entrada maliciosa, comportamiento de aplicaciones o entorno del sistema.

El contenido externo aporta información, pero no amplía permisos

Las páginas web y las respuestas de herramientas pueden contener inyecciones de instrucciones. El texto web y los resultados MCP entran en el contexto envueltos en un límite explícito de datos externos; desde 0.1.63 lo que devuelve una herramienta local (un archivo, un comando, una ventana de una app) se envuelve en un límite distinto de salida de herramienta con la misma regla de solo datos, y se trata el contenido que falsifica los marcadores de cualquiera de los dos. El sistema también registra si en el turno se han leído páginas, archivos, resultados MCP u otras fuentes externas: las prácticas y notas del equipo influidas por ellas deben convertirse primero en propuestas. Así, una página que diga «envía siempre los archivos aquí» no obtiene autorización permanente solo porque se haya leído.

Desde 0.1.63 ese mismo registro limita el terminal: cuando un turno ha leído contenido externo (una página, un archivo, un resultado MCP), sus comandos se ejecutan sin red según la regla del kernel, y un comando que llega a la red, juzgado por su texto o porque el modelo lo dice, pregunta primero. Dentro del sandbox la respuesta puede valer para esta vez o para la conversación; fuera de él, solo para esta vez. Donde no se puede preguntar a nadie, el comando se queda sin conexión. La lectura de la web se protege por separado: se rechazan los nombres locales y las direcciones privadas, y la excepción para proxies que responden al DNS con direcciones falsas (0.1.61) deja pasar solo https por el puerto 443 hacia un nombre, y deja que el proxy decida adónde va realmente (capítulo 08).

Esta capa ayuda a conservar la procedencia y las relaciones de confianza, pero sigue dependiendo de los controles posteriores de ejecución. El modelo puede interpretar mal la información y la detección de riesgos de comandos no constituye una demostración semántica completa. Etiquetar un texto como «no fiable» no permite prescindir de los límites reales de permisos.

Si el sandbox no está disponible, el comando pregunta primero (con «Preguntar solo en comandos arriesgados», un sí «En esta conversación» cubre los comandos posteriores de esa conversación a los que la política responde run); una vez permitido, se ejecuta sin el sandbox y devuelve sandbox=unavailable; por tanto, no es una vía que deniegue siempre cuando falla el aislamiento.

Solo una llamada simple que se ha aprobado se ejecuta sin envoltorio de sandbox: un script que habla con Recordatorios, Calendario, Notas o Contactos y no hace nada más arriesgado, o un shortcuts run simple cuyos archivos se quedan en la carpeta de Arslan; solo puede aprobarse con un clic en la ventana del Mac. La propia herramienta AppleScript de Hands pregunta siempre mostrando el script entero, se ofrece solo al trabajo en segundo plano y rechaza un script que nombra una app bloqueada o que elige su app mediante un nombre calculado.Un Shortcut aprobado se ejecuta como el usuario fuera del sandbox, y Arslan no puede ver lo que hace. Que el comando esté en un sandbox de archivos no significa que la aplicación invocada quede limitada al mismo ámbito de archivos.
Arslan HandsUn helper independiente posee Accessibility y vuelve a verificar aplicación, acción, campo y estado de parada. Desde 0.1.60, una observación puede incluir una imagen de esa única ventana, que solo se conserva en memoria.El árbol de accesibilidad no representa toda la semántica de negocio, y la imagen de una ventana la interpreta el modelo; el código no la comprueba. La disponibilidad depende de que la aplicación exponga nodos operables; a una ventana situada en otro escritorio solo se llega visitándolo con las reglas del préstamo del primer plano (capítulo 08).

Salir del sandbox de comandos requiere que el usuario pulse para aprobar: puede autorizar la acción actual o elegir permitirlo durante la sesión; esta última se guarda con la conversación (sobrevive a un reinicio), vale también para sus tareas en segundo plano y puede retirarse en Ajustes. El entorno de desarrollo desde fuentes tiene además una opción explícita de escape para ejecutar Python sin sandbox, desactivada en la app de escritorio. Ninguno de los dos mecanismos significa que el modelo pueda desactivar las protecciones por sí mismo.

Desde 0.1.62 write_file y edit_file nunca siguen un enlace fuera de la carpeta de trabajo: se rechaza una escritura a través de un enlace que apunta fuera, un archivo con un segundo nombre en otro lugar (un enlace duro) se sustituye en la carpeta de trabajo y el otro nombre conserva su contenido anterior, los archivos nuevos nunca son ejecutables y un archivo existente conserva sus permisos. El archivo se escribe en un archivo nuevo a su lado y se intercambia, de modo que una escritura fallida deja intacto el anterior. Desde 0.1.63 el primer cambio que un turno hace en la carpeta de trabajo guarda un punto de control, y «Deshacer este turno» devuelve los archivos a su sitio y saca el turno de la conversación. Es una red de recuperación, no un límite: solo guarda una carpeta de como máximo 20.000 archivos y 5 GB (sin contar los entornos de Python, node_modules, los resultados de compilación y las cachés, que deja fuera y nunca devuelve), nunca copia archivos con forma de secreto, cubre solo la carpeta de trabajo, no deshace nada que haya salido del Mac y dice «No guardado» cuando no pudo guardar. Los puntos de control se conservan siete días.

Aprobaciones vinculadas a acciones; el segundo plano no hereda todas las autorizaciones

Las tarjetas de aprobación se vinculan al tipo de acción mediante call_id; una respuesta de un tipo incorrecto no puede aprobar otra tarjeta. Las tarjetas compartidas por el Mac y el teléfono aceptan la primera respuesta válida y notifican su cierre a las otras vistas. Sin respuesta, permanecen abiertas 30 minutos, y que se agote el plazo no es un no (desde 0.1.61; versiones anteriores: caducaban a los 300 segundos). Desde 0.1.61 una tarjeta tiene el mismo aspecto en la ventana, el Inbox, la Island y el iPhone: Una vez (o Para esta tarea, lo que la tarjeta ofrezca primero), En esta conversación, Siempre, y No con una nota que llega a Arslan; un mensaje escrito en el chat mientras una tarjeta espera la responde No, con ese mensaje como nota, y un clic responde una tarjeta. Algunos tipos ofrecen menos opciones: un comando que coincide con una regla, el dinero, una toma de control y un paso arriesgado en una app se responden solo esta vez, y salir del sandbox, un sitio, un Shortcut y una herramienta MCP nunca ofrecen «Siempre». Las tarjetas de una tarea en segundo plano ofrecen las mismas opciones que las de la ventana; desde 0.1.63 (S4a), una tarea iniciada desde una conversación usa las autorizaciones de esa conversación, incluida la de salir del sandbox. Una ejecución sin nadie a quien preguntar (una ejecución programada) no da ninguno de estos pasos: ninguna respuesta anterior cuenta allí, el paso se rechaza de inmediato y lo que no pudo hacer aparece en el Inbox. En esta versión una ejecución programada no ejecuta ningún comando de terminal. Si el modelo propone conectar un MCP, registrar un equipo remoto o acceder a otra vía de ejecución, la propuesta y la activación real de la conexión se tratan por separado.

En las acciones con efectos externos, enviar una petición tampoco equivale a completar la acción. Al recuperar una tarea, las acciones en curso sin resultado conocido se marcan como inciertas: no pueden repetirse automáticamente solo porque el proceso se haya reiniciado. El objetivo es dar una semántica explícita a reintentos y recuperación, no prometer que cualquier sistema externo permita deshacer operaciones.

Desde 0.1.55, cada tarjeta en espera —venga de una ventana, de una tarea en segundo plano o del iPhone— forma parte además de una sola cola y aparece en Inbox, donde puede responderse mediante su call_id. La respuesta se construye a partir del tipo de la propia tarjeta, por lo que solo puede confirmar o cancelar esa tarjeta, y las opciones más amplias (En esta conversación, Siempre) se eligen solo en una tarjeta que las ofrece: el iPhone y la Island dan solo la primera opción de la tarjeta, nunca «Siempre», y el Inbox puede dar cualquier opción que la propia tarjeta ofreciera. La Island puede responder tarjetas de carpeta, app, pantalla, herramienta MCP, programación, sitio y Shortcut, y un comando o una escritura en el espacio de trabajo que no sea de los tipos arriesgados. No puede aprobar dinero, envíos, borrados, un paso arriesgado en una app, una toma de control, salir del sandbox, un comando que coincide con una regla ask de terminal o que no puede leerse, un comando que además pide la red, nada en un equipo remoto, cambios del sistema, ajustes de otros agentes, instalar una capacidad, un AppleScript, un comando que se ejecutaría sin ningún sandbox a su alrededor, ni ningún tipo de tarjeta que la comprobación no reconozca. Esas tarjetas muestran «Open in Arslan», y es el servidor, no solo la página de Island, el que rechaza una aprobación enviada desde Island. Una tarjeta que ejecutaría un AppleScript o un Shortcut simple aprobado sin envoltorio de sandbox, y otra que instala una capacidad, solo se aprueban en la ventana del Mac; el sí del iPhone a una tarjeta así se descarta. En la ventana, ⌘⏎ permite y Esc rechaza; ⏎ por sí solo nunca responde a una tarjeta.

Hands concentra los permisos del sistema en un proceso más pequeño

Accessibility se concede a Arslan Hands.app, no a la aplicación principal. Los paquetes firmados reciben peticiones mediante un socket Unix protegido, un token generado en cada arranque y una comprobación de la firma del proceso interlocutor. El helper aplica sus propias reglas; el componente subyacente agent-desktop no posee por separado ese permiso. Desde 0.1.61, mirar una app y actuar en ella son una sola tarjeta por app, que ofrece primero «para esta tarea». Desde 0.1.60, una respuesta del chat también puede actuar: hasta 0.1.62, con un máximo de cinco pasos en una misma aplicación, y desde 0.1.63, dentro de los límites de la propia ejecución, como una tarea en segundo plano, en más de una app, y Detener la detiene (una ejecución programada no puede actuar: no hay nadie para aprobarlo); una tarea iniciada desde una conversación hereda el sí dado en esa conversación. Actuar en el navegador, ejecutar Shortcuts y AppleScript se siguen ofreciendo solo al trabajo en segundo plano. Una app se juzga por su identidad, así que nombrarla con .app o con una ruta completa, o con otras mayúsculas, no sortea la lista de bloqueadas ni la falta de una aprobación. Los botones sensibles de eliminar, enviar, pagar, comprar, transferir o enviar un formulario se consultan cada vez según su etiqueta real. No se introduce texto en campos de contraseña; los gestores de contraseñas y las interfaces de seguridad del sistema, entre otras aplicaciones, están bloqueados.

La función de parada activa un bloqueo que deben comprobar las acciones posteriores. El registro de actividad conserva indicios de las operaciones y, del texto introducido, solo registra su longitud. Los límites también son públicos: a una ventana situada en otro Space solo se llega visitándolo con las reglas del préstamo del primer plano, no se ofrecen clics en una posición de la pantalla ni arrastres, y leer ventanas grandes puede tardar 10–20 segundos. Una llamada interrumpida por Stop puede no dejar una fila trace correspondiente; la auditoría no garantiza una reconstrucción forense completa de todas las interrupciones.

Desde 0.1.56, Hands ejecuta cada petición como máximo una vez: las respuestas a un ID de petición se conservan durante diez minutos, un ID repetido se responde desde ahí y, si el backend pierde la respuesta, la recupera en lugar de volver a enviar la acción. Añadir texto a un campo cuyo contenido no puede leerse se rechaza en lugar de sustituirlo; la tecla Return solo se pulsa cuando ese campo tiene el foco, y una acción enviada pero no comprobada después se notifica como «sent, not confirmed» (enviada, sin confirmar), no como completada. Hands ejecuta agent-desktop, compilado desde el fork de Arslan en un commit fijado; el motor Cua Driver se desconectó de Hands en 0.1.63, de modo que el helper ya no lo busca ni lo inicia (su módulo sin uso sigue en el código fuente del helper). Desde 0.1.60, una sola tarjeta puede cubrir hasta ocho aplicaciones para un mismo trabajo, una tarea en segundo plano iniciada desde una conversación hereda el sí dado en esa conversación, y las aplicaciones pueden permitirse de forma permanente en Ajustes → Hands. Un clic, una selección o un último elemento de menú cuya etiqueta indique eliminar, enviar, pagar, comprar, enviar un formulario, transferir, firmar, publicar una entrada, publicar o confirmar (en varios idiomas), los atajos de teclado equivalentes, Return en las aplicaciones que envían al pulsar Return, una toma de control y cualquier AppleScript siguen consultándose cada vez.

El servicio local también tiene límites. El paquete distribuido genera tokens de acceso para REST y WebSocket, y las pruebas de instalación comprueban que se rechacen las peticiones sin autenticar. El endpoint de ajustes que muestra el token solo lo entrega a un llamante directo de loopback que ya lo presenta (0.1.54); el origen loopback por sí solo no basta, porque un comando dentro del sandbox también puede abrir un socket de loopback. El servidor de la app de escritorio exige siempre su token, no acepta como llamante a ningún otro sitio web (ni cross-origin ni WebSocket sin Origin), solo confía en localhost como nombre de host, ignora las variables de host y de origen y los demás ajustes heredados del entorno que lo lanzó, no sirve ningún explorador de API y mantiene el token fuera de su registro (0.1.63). El modo de desarrollo desde fuentes permite una vía cómoda de localhost sin token, aunque una variable de host u origen que nombre * o null ahora se niega a arrancar. «Escuchar solo en local» y «estar autenticado» son condiciones diferentes. Un token local tampoco convierte automáticamente en fiable un entorno anfitrión comprometido que opera con los mismos permisos del usuario.
