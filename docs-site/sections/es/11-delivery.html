11 / Validación y distribución del softwareDel código que funciona a una aplicación instalable y actualizable

En una aplicación de escritorio, la unidad de entrega es el paquete de la aplicación. Los módulos Python, las herramientas del sistema y las bases de datos antiguas presentes en el entorno de desarrollo pueden hacer que parezca correcto un instalador al que le faltan recursos. Arslan divide la validación en código fuente, plataforma, ejecutables empaquetados, entorno de usuario nuevo y distribución. Este capítulo recoge el proceso de v0.1.55 y sus evidencias de publicación.

En macOS no basta con aceptar el código de salida de pytest. El flujo analiza JUnit y exige que 49 casos específicos de la plataforma se ejecuten realmente, sin omisiones ni fallos; también rechaza un resultado en el que falten dependencias y se omitan todas las pruebas. Python y Rust comparten ejemplos de contrato de Hands; Mac, iOS y una implementación Python de referencia independiente comparten vectores de Bridge. Esto permite contrastar entre lenguajes los límites de mapeo de parámetros, firma, destinatarios, manipulación y repetición.

Los resultados siguen teniendo un alcance concreto: comprobar tipos Swift no valida el permiso de micrófono; las pruebas unitarias Linux no validan el kernel de macOS; y un buzón simulado no valida CloudKit en producción. El número de pruebas tampoco representa la cobertura total; las baterías solapadas no pueden sumarse como escenarios independientes.

El workflow de publicación comprueba si el SHA que se va a distribuir tiene una CI satisfactoria; no sirve que la haya superado otro commit. La compilación utiliza dependencias fijadas por archivos de bloqueo. Python selecciona explícitamente un intérprete independiente gestionado por uv para evitar que el runner elija accidentalmente un framework build. El backend se empaqueta con PyInstaller onedir y los recursos estáticos del frontend y los helpers Swift/Rust se integran en la aplicación Tauri.

La firma y la notarización tienen funciones distintas. Los Mach-O internos deben firmarse antes de empaquetarlos en la aplicación exterior; la distribución utiliza Developer ID, hardened runtime y sello de tiempo. El DMG se envía a Apple para notarización; después se adjunta el ticket con staple y se comprueba con Gatekeeper. El script de compilación conserva rutas para paquetes de desarrollo sin firma y avisos cuando faltan algunas credenciales. Por eso, «se puede compilar» no implica «cumple las condiciones de distribución pública»: hay que comprobar los entregables reales.

El manifiesto de actualización tiene restricciones adicionales: el tag debe coincidir con la versión de Tauri y solo se genera el manifest correspondiente si existe firma del updater. El proceso crea una GitHub Draft Release. Las aplicaciones instaladas solo descubrirán la actualización en comprobaciones posteriores cuando se publique oficialmente.

La aceptación de una instalación nueva inicia directamente la aplicación empaquetada

fresh_install_check.py inicia el verdadero arslan-desktop incluido en el paquete con un HOME temporal y un entorno mínimo; no arranca el servicio desde el venv del código fuente en su lugar. Comprueba que no se hayan incluido bases de datos o secretos del usuario, la inicialización del primer inicio, la generación del token y los permisos de su archivo, el rechazo de peticiones sin autenticar, un handshake WebSocket 101 real y la descarga correcta del JavaScript del frontend. Un HTTP 200 puede corresponder a la página de fallback de la SPA, por lo que comprobar recursos exige algo más que mirar el estado HTTP.

El mismo script comprueba el OCR nativo, los helpers incluidos, la autocomprobación de Bridge y las firmas correspondientes. Históricamente, un paquete omitió una dependencia de WebSocket cargada dinámicamente: el endpoint de salud respondía, pero el chat no podía establecer la conexión. Esto demuestra que importar correctamente, mantener un servicio activo y distribuir las funciones esenciales en el paquete son evidencias diferentes.

El usuario inicia la instalación de actualizaciones y se verifica la descarga

Tauri updater descubre actualizaciones en el latest.json público y verifica la firma del archivo con una clave pública integrada en la aplicación. Se comprueba una vez al arrancar y también de forma manual desde el menú; esta versión no tiene un temporizador de comprobación periódica. Al detectar una versión nueva se muestra un aviso. Solo cuando el usuario pulsa instalar se descarga, verifica, sustituye y reinicia. Un fallo de comprobación automática puede deberse a una desconexión temporal; un fallo de instalación debe comunicarse claramente.

Las versiones iniciales 0.1.0/0.1.1 solo registraban el plugin updater, sin llamar activamente a la función de comprobación, por lo que no descubrían versiones de forma automática. La implementación actual enlaza comprobación, disponibilidad para instalar, errores de descarga y reinicio en un flujo explícito. Tener configurada una firma no implica haber iniciado ese flujo.

A qué entregable corresponden las evidencias de 0.1.55

Las ejecuciones de GitHub Actions del commit de publicación muestran que el código publicado es 81c0028c; la CI de ese commit pasó en el primer intento (run 37729747101), incluidos los 49 casos específicos de la plataforma sin ninguna omisión del job de macOS y, en el backend, 6,324 pruebas superadas y 119 omitidas. El workflow de publicación (run 37729747033) superó la validación del código, la compilación y la publicación; el DMG fue aceptado por notarización, recibió staple y fue aceptado por Gatekeeper. La aplicación distribuida obtuvo en la comprobación fresh-install 89 comprobaciones superadas y 0 fallidas, incluidas la aceptación por Hands de una conexión del backend firmado y la autocomprobación de Bridge. La 0.1.54 obtuvo 87 superadas y 0 fallidas en esa misma comprobación, también después de que su CI pasara en el primer intento.

Los objetos verificados son distintos, y los registros lo indican. Las notas públicas de 0.1.55 no contienen ninguna prueba manual en un Mac real, por lo que este documento no afirma que el DMG exacto de 0.1.55 se haya instalado y recorrido a mano, ni que se haya completado con la aplicación distribuida un recorrido completo del iPhone al Mac. Como comparación, la sección Verification de 0.1.53 registró una prueba en un Mac real en la que Hands creó y volvió a leer una nota en Notes, con una aprobación en espera durante 36 segundos; se hizo con el paquete build-only de 43751254, no con el DMG final. La aceptación automática del paquete, las pruebas funcionales de una compilación anterior y la aceptación manual del paquete exacto deben describirse por separado: no se sustituyen entre sí.
