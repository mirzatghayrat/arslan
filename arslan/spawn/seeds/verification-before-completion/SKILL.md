## Trigger

在即将声称工作"完成/修好/通过"、即将表达满意、即将提交或建 PR、即将转下一个任务或委派给代理之前激活。核心原则：证据先于断言。没在本条消息里跑过验证命令，就不能声称它通过。

## 决策规则

- **铁律：没有新鲜验证证据，不下任何完成结论**。声称成功前先跑那条能证明它的命令。
- **门控流程**：先问"哪条命令能证明这个断言" → 完整跑一遍（新鲜、完整）→ 读全部输出、看退出码、数失败数 → 输出是否确认了断言（否→如实报告真实状态并附证据；是→带着证据下结论）→ 才做断言。跳任何一步 = 撒谎而非验证。
- **各类断言的充分证据**：测试通过 = 测试命令输出 0 失败（不是上次跑的/"应该过"）；构建成功 = 构建退出码 0（linter 过 ≠ 编译过）；bug 修好 = 原始症状的测试现在过；代理完成 = 看版本控制 diff 有实际改动（不是代理自报"成功"）；需求满足 = 逐条对照清单。
- **红旗词就停**：用了"应该/大概/看起来"、验证前先说"太好了/完美/搞定"、没验证就要提交/推送/建 PR、信代理的成功自报、只做了部分验证 —— 全停下先跑验证。
- **拆穿借口**："应该好了"→去跑；"我很有信心"→信心≠证据；"就这一次"→无例外；"linter 过了"→linter≠编译器；"代理说成功了"→独立核实；"我累了"→疲惫不是借口；"换了措辞规则就不适用"→精神高于字面。
- **适用于一切措辞**：不只精确原话，同义改写、暗示成功、任何传达"完成/正确"的表达都算。
- **底线**：跑命令、读输出、然后才声称结果 —— 不可协商。
