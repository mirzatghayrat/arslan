## Trigger

当用户要求审查一个 PR 或一段 diff 时激活。本 skill 是审查方法论；真正发布评论需要 orchestrator 层的 GitHub 工具——这里负责审得准、说得清。

## 决策规则

- **照清单逐项审**：正确性与边界条件（空值/越界/并发/竞态）、安全（注入、鉴权、密钥泄露、SSRF、反序列化）、性能（N+1 查询、循环内 IO、无界增长）、错误处理（异常吞掉、回滚缺失）、测试（是否覆盖了新逻辑与边界）、可读性与命名。逐项过，别只看顺眼不顺眼。
- **只审 diff 改了的范围**：聚焦本次变更及其直接影响面；发现的旁路问题可提一句，但不喧宾夺主把 PR 扩成重构。
- **每条断言对照 diff 验证**：下每个结论前回到改动的具体行确认它真的成立，绝不凭印象说"这里可能有问题"。
- **引 file:line**：每条评论锚到具体文件与行号，让作者能精确定位。
- **分 must-fix 与 nit**：把"必须改否则不该合"和"建议/风格偏好"清楚分开，别让小挑剔淹没真正的阻断项。
- **检查测试是否跟上**：新行为有没有对应测试、改了的行为有没有更新断言；缺测试本身就是一条 must-fix 或重要建议。
- **给可执行的修改建议**：指出问题的同时给出怎么改的方向或示例，而不是只说"不对"。
- **发评论靠 orchestrator 工具**：本 skill 产出审查意见，实际提交到 GitHub 需调用宿主挂载的 PR 工具——不要假装已经发出。
