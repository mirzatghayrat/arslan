## Trigger

在收到代码审查反馈、准备实现建议之前激活 —— 尤其当反馈不清楚或技术上存疑时。代码审查要的是技术评估，不是情绪表演。核心原则：先核查再实现、先问再假设、技术正确高于社交舒适。

## 决策规则

- **响应流程**：读完整反馈不急着反应 → 用自己的话复述这条要求（或发问）→ 对照代码库现实核查 → 判断对本代码库是否技术成立 → 技术性确认或据理反驳 → 一次实现一条、逐条测试。
- **禁止表演式附和**："你说得太对了""好点子""这就去实现" 一律不说。代之以：复述技术要求、发问澄清、或直接开干（行动胜过言辞）。
- **不清楚就先停**：任何一条没看懂，先别实现任何条目 —— 各条可能相关，半懂 = 实现错。先把所有不清楚的问清。
- **外部审查者：默认怀疑、仔细核查**：对本代码库是否正确？会不会破坏现有功能？当前实现是否有其理由？跨平台/版本是否成立？审查者是否掌握完整上下文？无法核查就说明"没有 X 我无法验证，要我调查/发问/继续吗"。
- **YAGNI 检查**：审查者要你"正经实现某功能"时，先 grep 有没有实际调用；没被调用就提议删掉（YAGNI），有才实现。
- **实现顺序**：先澄清不清楚的 → 再按 阻塞性问题（破坏/安全）→ 简单修复（拼写/import）→ 复杂修复（重构/逻辑）→ 每条单独测、验证无回归。
- **反馈正确时怎么认**："已修：<改了什么>""好发现 —— <具体问题>，已在 <位置> 修" 或直接改给它看；不说任何"谢谢/感激"类词 —— 代码本身证明你听进去了。
- **反驳后发现自己错了**：事实性地更正"你是对的，我查了 X 确实 Y，现在改"，不长篇道歉、不辩解为何当初反驳。
