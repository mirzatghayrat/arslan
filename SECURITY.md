# Security Policy

Arslan is a local-first personal AI orchestrator. By design it runs powerful, potentially dangerous machinery on your machine, so it is worth understanding its threat model before you deploy it beyond localhost.

## What Arslan runs

- **A Python computation sandbox.** On macOS, generated Python uses a default-deny Seatbelt profile: read-only interpreter libraries, a per-run read/write workspace, read-only staged inputs, and denied network/host IPC. Other tool classes have different boundaries; this is not an app-wide jail.
- **Stored BYOK secrets.** Your LLM provider API keys are stored on disk, encrypted at rest.
- **An MCP client.** Arslan can launch configured MCP servers as **stdio subprocesses** — i.e. it runs arbitrary local commands that you configure.

## Safe-by-default posture

- **Two ways to run.** The desktop app is the supported way to run Arslan. A source checkout's dev server on **localhost is unauthenticated by design** — zero friction for local, single-user use, intended only for a loopback bind on a machine you control. There is no separate production mode (removed in v0.1.63): a dev server refuses to start if `ARSLAN_ENV` is set to anything but `dev`; the desktop app ignores it.
- **Auth enforced where it matters.** In the desktop app (its server always runs with `ARSLAN_PACKAGED=1`, which an inherited value cannot override) or on a **non-loopback bind**, Arslan requires a bearer token. If `ARSLAN_API_TOKEN` is empty in those modes, a token is **auto-generated on first run**, persisted to `<data_dir>/api_token` (owner-only), and viewable/resettable from Settings. It is kept out of the server log: the first-run notice gives only the file's path, and a `token=` in a request URL is redacted. Minting or disabling the inbound-MCP token needs the current access token, not just a loopback connection. The desktop window gives the token only to its own server's page and cannot navigate away from it.
- **Inherited configuration does not move the desktop app.** It ignores the configuration variables an inherited environment could use to move it: its data, spawns and web folders, the host and origin allowlists, the sandbox's Python, the file tools' folder, the run budgets and the sidecar's port, among others. `ARSLAN_SECRET_KEY` and `ARSLAN_SECRET_KEY_FILE` are kept on purpose (a power-user choice; a mismatch is warned about).
- **Cross-site protections.** TrustedHost, CORS, and WebSocket-Origin checks block cross-site drive-by requests. The desktop app's server allows no cross-origin caller (it ignores `ARSLAN_ALLOWED_ORIGINS` and `ARSLAN_ALLOWED_HOSTS`) and refuses a WebSocket without an `Origin`; a non-localhost dev bind must configure `ARSLAN_ALLOWED_HOSTS` and `ARSLAN_ALLOWED_ORIGINS`.
- **Secrets encrypted, public key refused.** BYOK secrets are **Fernet-encrypted** with a key derived via **PBKDF2-HMAC-SHA256** (per-install random salt stored in the database since migration 0039). The app **refuses to write secrets under the built-in public dev key** — the desktop app creates and saves a real one on first run (`~/.arslan/secret_key`) and refuses to start if it cannot, and a dev run auto-generates one too (the `ARSLAN_ALLOW_INSECURE_SECRETS` escape hatch exists for dev testing only, is ignored by the desktop app, and must never be used for real keys).
- **Sandbox fails closed.** Where the kernel sandbox is unavailable, code execution fails closed rather than silently running unsandboxed.
- **Child output cannot weaken policy on its own.** A failed child is never retried outside its sandbox automatically. When a terminal command's output shows the sandbox stopped it, the result goes back to the model with a note and no card is shown. To run a command outside the sandbox the model has to ask, with a reason, and only your click on that card does that (that card can also allow the rest of the conversation); unattended, there is nobody to click, so nothing runs outside. The development unsandboxed escape valve is disabled in the desktop app.
- **Actual-peer authentication guard.** With no active API token, HTTP and WebSocket middleware reject non-loopback or unknown peers, even when a bare server launcher hides its bind address from configuration. A reverse proxy must still use a token: loopback proxying is not authentication.

## Known boundaries

Please read these before exposing Arslan beyond a trusted local machine:

- **The kernel sandbox is macOS seatbelt only.** On non-macOS platforms it is unavailable and fails closed. The dev-only `ARSLAN_ALLOW_UNSANDBOXED_PY=1` escape hatch runs generated Python with the server's full privileges and network access — only enable it on a machine you fully trust.
- **Do not expose the server to an untrusted network without a token + allowlist.** An unauthenticated instance grants full control of the orchestrator, its stored secrets, and code execution to anyone who can reach it. Always set `ARSLAN_API_TOKEN` (or rely on the auto-generated token) **and** the host/origin allowlists for any non-loopback dev bind (the desktop app's server binds to loopback and ignores them).
- **The MCP client runs arbitrary configured stdio commands by design.** Only configure MCP servers you trust; a malicious server definition can run arbitrary local commands. An MCP server Arslan installs for you runs in Arslan's default-deny sandbox (v0.1.64, SBX-4): its own folder, the folders you granted and no other app's services. When it declared that it needs the network, it reaches the network only through Arslan's local proxy, under the same rules as a sandboxed command online (SBX-6); Arslan's own ports are read when the server starts. Otherwise it has no network. A server you added by hand runs as you configured it, unsandboxed.
- **MCP environment passing is allowlisted.** Runtime basics and explicitly configured server credentials are passed, not the parent's Arslan secret, provider-key variables, SSH agent or runtime injection flags. This reduces accidental credential exposure; a trusted local MCP process is still not filesystem-isolated.
- **Credentials an MCP server takes in its environment or arguments are not secret from other programs running as you.** On macOS a process can read the arguments and environment of another process of the same user, so a key handed to an MCP server that way (the usual convention for stdio servers, and the only way most of them accept one) is readable by other code running as you.
- **Terminal commands are only partly isolated.** On macOS a command runs under a default-deny Seatbelt profile (v0.1.64, SBX-3). It may write only to the working folder, its run's own temp folder and Arslan's own cache folder for its tools (v0.1.64, SBX-5: your `~/.npm`, `~/.cache` and `~/Library/Caches` are read-only to it, so a package it plants there can't be installed later by something unsandboxed). It can't read or write the skill and plugin folders (`~/.agents/skills`), and neither can a command you let out of the sandbox; an MCP server can't write them either, and each installed MCP server writes only its own cache. When a folder it may write holds them, a sandboxed command or an MCP server can't move out of the way, remove or replace with a link the folders above the skill and plugin folders, Arslan's data, your credential folders and your caches (for a command, also the folders closed to it, such as Mail's), nor the skill or plugin folder itself when it is a link. A command you let out of the sandbox is held that way only above the skill and plugin folders and Arslan's own folders, not above your credential folders or caches. Writing beside those folders still works. Arslan's file tools (write and edit) refuse the skill and plugin folders and Arslan's data folder by any spelling (letter case, Unicode form, another path to the same folder), and refuse a path they can't check; credential-shaped file names are a separate rule, and they don't refuse your caches or credential folders as such. What a path rule can't catch: a hard link to one of those files, made by something else running as you in a folder a command, an MCP server or `run_python` may write, reaches the original (an MCP server's folder is checked for such links when it starts, and the server doesn't start when one is found or the check can't read a folder or entry, but a link added while or after it checks isn't caught); `run_python` closes the skill and plugin folders by name but not Arslan's data or your caches, so one whose parent something else turned into a link into its fresh workspace before it started is reachable; and a folder something else renames between the file tools' check and their write isn't caught. It can't read or write Arslan's own data and keys, your credential folders (SSH, keychains, cloud CLIs, browser profiles, Claude Code's and Codex's config and sign-ins) or Mail, Messages and Photos data. It reaches only a short list of macOS services and sockets (file events always; DNS and certificate checks when online), so it can't ask launchd, LaunchServices, Shortcuts or the pasteboard to act for it outside the sandbox. It can't listen on a port, send Apple Events or use POSIX shared memory and semaphores (a stock Python multiprocessing pool fails inside it). It can still read elsewhere and run programs. Online (v0.1.64, SBX-6), it reaches the network only through Arslan's own local proxy, which has no site list yet: it refuses a name that resolves to a private or loopback address (a LAN device you list under trusted local devices is the one exception: that host or address only, its name pinned to the address it had when you added it, never loopback, link-local or this Mac's own addresses; trusting a device trusts every port on it. Only you list one: in Settings, where Arslan resolves a name and refuses a public address, this Mac's own and a name that doesn't resolve, or with "Trust this device" on the card a refused LAN connection shows, which lists exactly the device that card names; nothing the model can call lists a device or turns on certificate checks. A listed name's answers that no entry could hold, such as its IPv6 link-local address, don't stop it; any other answer does) and connects to the address it checked. With a system HTTP proxy on this Mac it goes through that proxy, still to the address it checked, except that a tunnel to port 443 goes by name (the system proxy resolves the name and picks the real destination, so the address check is delegated to it there, and a name that resolves differently for it could reach a local address on port 443); it can also reach other loopback ports for local dev servers, but not the ports Arslan itself listens on or a proxy set on this Mac; it has no DNS of its own and no UDP, and it can't reach macOS's certificate trust service unless you allow system certificate checks in the sandbox (needed by Swift, Xcode and Go tools; off by default, since that service fetches certificate data itself, round the proxy). Offline, it has no network at all. Arslan's own ports are read when the command starts, so a port Arslan opens later is reachable from a command already running, and a local proxy this Mac doesn't announce (Tor, `ssh -D`) is reachable like a dev server. By default Arslan asks before every new command (the Terminal setting *When to ask*: "Ask before every command"); answering a card "In this conversation" lets exactly that command text run again in the same conversation without asking. The upgrade to v0.1.63 moves every install to it once, including one that had chosen "Ask only for risky commands" (a stored setting cannot show whether it was chosen); a choice made after that is kept. "Ask only for risky commands" can still be selected: under it, a command Arslan judges harmless (one its rules do not flag) runs in the sandbox without asking, edits and builds as well as reads. Its judgement of which commands are risky is completed only in v0.1.64: until then its rules ask before some of the programs that reach those services, not all, so it can run some commands it should ask about in the sandbox without a card. Until v0.1.64, a run with nobody to ask (a scheduled task, the heartbeat) runs no terminal command at all, whatever rules or grants exist: the step is refused and listed in your Inbox. Such a run can still read the web in Arslan's own browser (its own persistent profile; pages run their JavaScript), call MCP tools that their server marks read-only (the server's own claim), and use Arslan's fixed-argument helpers (listing your Shortcuts and, when you have switched them on, the local-network scan and the SSH host-key probe). The network stays open until the turn has read outside content (a web page, a file, an MCP tool's answer); after that, commands run offline, and one that needs the network asks first with a card. A command you let out of the sandbox runs with your full privileges, under the same network rule. Do not treat this as the Python computation sandbox.
- **The hard rules are written down once** (v0.1.64, HR-0: `server/services/hard_rules.py`). Each rule names the layer that holds it and the test that proves it, and a test fails when a rule has no row or a row's test isn't collected. There are four categories:
  - *Direct*: what a command's text alone decides. Its forbid rules never run, inside the sandbox or out, and no card is shown for them. Its this-time-only rules (sending, publishing, deleting outside the working folder, changing the system, driving other apps, a command Arslan can't read) are answered by your click each time. The exception is a command whose only rule is that Arslan can't read it: under "Ask only for risky commands" it runs offline in the sandbox with no card (v0.1.64, S2a-3), and it asks only when it would run outside the sandbox. Both are held by the command parser, and the tool loop's gate also refuses a few shapes before any card.
  - *Run later*: writes into files that make something run later. These rules are not held yet; the next v0.1.64 changes add them to the sandbox's profiles and to the file tools.
  - *Never automatic*: payments, installing capabilities, another machine, leaving the sandbox, the network after outside content and the other once-only kinds, what full access still asks (sending, opening a site, a Hands shortcut), plus any command with a this-time-only rule. Nothing automatic answers these: not Arslan's own judgement of a request (a classifier, when one is added) and not a full-access mode. Your own standing answers are the exception, as before: a grant you gave answers a site, a Hands shortcut or a send; an "Always" rule you set answers a send; this conversation's grant to run commands outside the sandbox lets a command out with no card; and a grant in this conversation answers the network card for a command in the sandbox after outside content. They are held by the permission ladder, and an unknown kind fails closed.
  - *Absolute*: held even under the least strict settings ("Ask only for risky commands", a grant to run commands outside the sandbox, the sandbox switched off). The forbid rules, Arslan's own data, the skill and plugin folders, Apple Events, payments, capabilities and the network cut after outside content stay in force there. They are held by the outside profile, the gate and the permission ladder. The profile's part holds only where macOS's sandbox can start; where it can't, a command outside the sandbox has only the gate and the ladder. One plain AppleScript or `shortcuts run` call that you approve with a click in the asking window (U11's bare run) runs with no profile, so it can send Apple Events.

  Hard links that already exist inside a folder you granted, pointing at a file elsewhere, are accepted and not detected: a write through such a link reaches the original.
- **BYOK secret confidentiality depends on the secret key and `crypto_salt`.** In the desktop app the key is the file `~/.arslan/secret_key`, kept outside the data folder: anything running as you can read it (sandboxed commands cannot), so encryption protects a copied data folder or backup, not against software already running on your Mac.
- **SSRF protection is delegated to your proxy for `https` + proxy.** Outbound fetches normally resolve the hostname once, reject any non-global address, and pin the connection to that IP — so a name that re-resolves to a private address between the check and the connection cannot be reached. That guarantee **cannot** be carried over an HTTP proxy on `https`: httpcore's CONNECT tunnel ignores the `sni_hostname` extension and hands the tunnel's own origin host to TLS, so pinning would make certificate validation fail against an IP literal. In that one combination Arslan degrades to *the proxy decides where the request goes* and **logs a warning** rather than failing silently. Plain `http` through a proxy, and every non-proxied request, still pin. If `HTTPS_PROXY`/`https_proxy` is set in your environment, your `https` fetches run in this delegated mode — point it at a proxy you trust, or unset it for the pinned path.

- **Generic secret detection is CI-side, not GitHub-side.** GitHub's non-provider-pattern scanning (the one that catches private keys and other non-vendor secrets) requires an organization-owned repository on GitHub Team with Secret Protection; this repository is personal, so that setting cannot be enabled — the API silently accepts and ignores it. The defenses that ARE in place: CI runs `gitleaks detect` over the **full history** on every push (a diff-mode scan would permanently miss anything that slipped in once), Apple signing material never enters the repository (it lives in GitHub Actions secrets, is `.gitignore`d, and is recoverable from the Apple Developer portal — see `docs/RELEASE_KEYS.md`), and no `pull_request`-triggered workflow references secrets — asserted by a test, not by convention.
- **An update is code you chose to trust once, at install time.** Auto-updates are minisign-signed; the public key is compiled into the app and the private key lives in GitHub Actions secrets — which are **write-only**, so the CI copy can never be read back out. The maintainer keeps the only recoverable copy offline; losing it would strand every existing install on its current version (custody, backup, and rotation: `docs/RELEASE_KEYS.md`). Publishing a GitHub release IS pushing an update to every install, which is why releases are created as drafts and published by a human. If the signing key were compromised together with repository write access, an attacker could ship a malicious update — the same trust model as every self-updating desktop app, stated here rather than implied.

## Backup & durability

The PBKDF2 salt now lives in the **database**, beside the ciphertext (migration 0039). A legacy `crypto_salt` file is only a recovery candidate, not the active derivation source. The external `ARSLAN_SECRET_KEY` remains essential: keep it separately from the data archive. Never publish either private data or keys.

Stop the app before taking a backup. `python -m scripts.backup_data create` uses SQLite's backup API (including committed WAL data), checksums files, and excludes access tokens, the external secret and rebuildable caches. Restore validates checksums, paths and database integrity **into a new directory only**. See [Recovery and execution contracts](docs/RELIABILITY.md). Checksums detect damage, not authenticity: only restore archives you trust.

Run text is checkpointed periodically and interrupted runs are marked at boot. This is partial-output recovery, not transparent replay of external effects. Task recipes retain completed-step outputs; retrying unfinished steps requires explicit confirmation and can repeat effects that completed before a crash.

## Reporting a vulnerability

Please report security issues **privately** — do not open a public issue for a vulnerability.

- **Primary channel:** use GitHub's private vulnerability reporting — the **"Report a vulnerability"** button on the repository's **Security** tab (`https://github.com/mirzatghayrat/arslan/security/advisories/new`). This opens a private security advisory visible only to the maintainers.
- **That button is the only channel.** Private vulnerability reporting is enabled on this
  repository, so a report filed there reaches the maintainers privately and keeps the whole
  exchange in one place. There is deliberately no email address here: an address in a public
  file is scraped, and a second channel is a second place for a report to be missed.

Please include a description, reproduction steps, affected version/commit, and impact. We will acknowledge your report and coordinate a fix and disclosure timeline with you.

## Supported versions

Arslan is **pre-v1**. Only the `main` branch is supported; security fixes land there. There are no backported release branches yet.
