# Security Policy

Arslan is a local-first personal AI orchestrator. By design it runs powerful, potentially dangerous machinery on your machine, so it is worth understanding its threat model before you deploy it beyond localhost.

## What Arslan runs

- **A Python computation sandbox.** On macOS, generated Python uses a default-deny Seatbelt profile: read-only interpreter libraries, a per-run read/write workspace, read-only staged inputs, and denied network/host IPC. Other tool classes have different boundaries; this is not an app-wide jail.
- **Stored BYOK secrets.** Your LLM provider API keys are stored on disk, encrypted at rest.
- **An MCP client.** Arslan can launch configured MCP servers as **stdio subprocesses** — i.e. it runs arbitrary local commands that you configure.

## Safe-by-default posture

- **Two ways to run.** The desktop app is the supported way to run Arslan. A source checkout's dev server on **localhost is unauthenticated by design** — zero friction for local, single-user use, intended only for a loopback bind on a machine you control. There is no separate production mode (removed in v0.1.63): a dev server refuses to start if `ARSLAN_ENV` is set to anything but `dev`; the desktop app ignores it.
- **Auth enforced where it matters.** In the desktop app (its server always runs with `ARSLAN_PACKAGED=1`, which an inherited value cannot override) or on a **non-loopback bind**, Arslan requires a bearer token. If `ARSLAN_API_TOKEN` is empty in those modes, a token is **auto-generated on first run**, persisted to `<data_dir>/api_token` (owner-only), and viewable/resettable from Settings. It is kept out of the server log: the first-run notice gives only the file's path, and a `token=` in a request URL is redacted. Minting or disabling the inbound-MCP token needs the current access token, not just a loopback connection. The desktop window gives the token only to its own server's page and cannot navigate away from it.
- **Inherited configuration does not move the desktop app.** It ignores the configuration variables an inherited environment could use to move it: its data, spawns and web folders, the host and origin allowlists, the sandbox's Python, the file tools' folder, the run budgets and the sidecar's port, among others. `ARSLAN_SECRET_KEY` and `ARSLAN_SECRET_KEY_FILE` are kept on purpose (a power-user choice; a mismatch is warned about).
- **Cross-site protections.** TrustedHost, CORS, and WebSocket-Origin checks block cross-site drive-by requests. The desktop app's server allows no cross-origin caller (it ignores `ARSLAN_ALLOWED_ORIGINS` and `ARSLAN_ALLOWED_HOSTS`) and refuses a WebSocket without an `Origin`; a non-localhost dev bind must configure `ARSLAN_ALLOWED_HOSTS` and `ARSLAN_ALLOWED_ORIGINS`.
- **Secrets encrypted, public key refused.** BYOK secrets are **Fernet-encrypted** with a key derived via **PBKDF2-HMAC-SHA256** (per-install random salt stored in the database since migration 0039). The app **refuses to write secrets under the built-in public dev key** — the desktop app creates and saves a real one on first run (`~/.arslan/secret_key`) and refuses to start if it cannot, and a dev run auto-generates one too (the `ARSLAN_ALLOW_INSECURE_SECRETS` escape hatch exists for dev testing only, is ignored by the desktop app, and must never be used for real keys).
- **The Python sandbox fails closed.** Where the kernel sandbox is unavailable, `run_python` refuses to run rather than running unsandboxed. A terminal command does not fail closed (a sub-session's does): it waits for your click, unless this conversation's grant covers it, then runs with no sandbox, and its result says `sandbox: unavailable` (or `off`). A command that has to run without network is refused, since nothing can cut its network.
- **Child output cannot weaken policy on its own.** A failed child is never retried outside its sandbox automatically. When a terminal command's output shows the sandbox stopped it, the result goes back to the model with a note and no card is shown. To run a command outside the sandbox the model has to ask, with a reason, and only your click on that card does that (that card can also allow the rest of the conversation); unattended, there is nobody to click, so nothing runs outside. The development unsandboxed escape valve is disabled in the desktop app.
- **Actual-peer authentication guard.** With no active API token, HTTP and WebSocket middleware reject non-loopback or unknown peers, even when a bare server launcher hides its bind address from configuration. A reverse proxy must still use a token: loopback proxying is not authentication.

## Known boundaries

Please read these before exposing Arslan beyond a trusted local machine:

- **The kernel sandbox is macOS seatbelt only.** On non-macOS platforms it is unavailable: `run_python` fails closed, while a terminal command runs with no sandbox after your click or this conversation's grant (marked `sandbox: unavailable` or `off`). The dev-only `ARSLAN_ALLOW_UNSANDBOXED_PY=1` escape hatch runs generated Python with the server's full privileges and network access — only enable it on a machine you fully trust.
- **Do not expose the server to an untrusted network without a token + allowlist.** An unauthenticated instance grants full control of the orchestrator, its stored secrets, and code execution to anyone who can reach it. Always set `ARSLAN_API_TOKEN` (or rely on the auto-generated token) **and** the host/origin allowlists for any non-loopback dev bind (the desktop app's server binds to loopback and ignores them).
- **The MCP client runs arbitrary configured stdio commands by design.** Only configure MCP servers you trust; a malicious server definition can run arbitrary local commands. An MCP server Arslan installs for you runs in Arslan's default-deny sandbox (v0.1.64, SBX-4): its own folder, the folders you granted and no other app's services. When it declared that it needs the network, it reaches the network only through Arslan's local proxy, under the same rules as a sandboxed command online (SBX-6); Arslan's own ports are read when the server starts. Otherwise it has no network. A server you added by hand runs as you configured it, unsandboxed.
- **MCP environment passing is allowlisted.** Runtime basics and explicitly configured server credentials are passed, not the parent's Arslan secret, provider-key variables, SSH agent or runtime injection flags. This reduces accidental credential exposure; a trusted local MCP process is still not filesystem-isolated.
- **Credentials an MCP server takes in its environment or arguments are not secret from other programs running as you.** On macOS a process can read the arguments and environment of another process of the same user, so a key handed to an MCP server that way (the usual convention for stdio servers, and the only way most of them accept one) is readable by other code running as you.
- **Terminal commands are only partly isolated.** On macOS a command runs under a default-deny Seatbelt profile (v0.1.64, SBX-3). It may write only to the working folder, its run's own temp folder and Arslan's own cache folder for its tools (v0.1.64, SBX-5: your `~/.npm`, `~/.cache` and `~/Library/Caches` are read-only to it, so a package it plants there can't be installed later by something unsandboxed). It can't read or write the skill and plugin folders (`~/.agents/skills`), and neither can a command you let out of the sandbox; an MCP server can't write them either, and each installed MCP server writes only its own cache. When a folder it may write holds them, a sandboxed command or an MCP server can't move out of the way, remove or replace with a link the folders above the skill and plugin folders, Arslan's data, your credential folders and your caches (for a command, also the folders closed to it, such as Mail's), nor the skill or plugin folder itself when it is a link. A command you let out of the sandbox is held that way only above the skill and plugin folders and Arslan's own folders, not above your credential folders or caches. Writing beside those folders still works. Arslan's file tools (write and edit) refuse the skill and plugin folders and Arslan's data folder by any spelling (letter case, Unicode form, another path to the same folder), and refuse a path they can't check; credential-shaped file names are a separate rule, and they don't refuse your caches or credential folders as such. What a path rule can't catch: a hard link to one of those files, made by something else running as you in a folder a command, an MCP server or `run_python` may write, reaches the original (an MCP server's folder is checked for such links when it starts, and the server doesn't start when one is found or the check can't read a folder or entry, but a link added while or after it checks isn't caught); `run_python` closes the skill and plugin folders by name but not Arslan's data or your caches, so one whose parent something else turned into a link into its fresh workspace before it started is reachable; and a folder something else renames between the file tools' check and their write isn't caught. It can't read or write Arslan's own data and keys, your credential folders (SSH, keychains, cloud CLIs, browser profiles, Claude Code's and Codex's config and sign-ins) or Mail, Messages and Photos data. It reaches only a short list of macOS services and sockets (file events always; DNS and certificate checks when online), so it can't ask launchd, LaunchServices, Shortcuts or the pasteboard to act for it outside the sandbox. It can't listen on a port, send Apple Events or use POSIX shared memory and semaphores (a stock Python multiprocessing pool fails inside it). It can still read elsewhere and run programs. Online (v0.1.64, SBX-6), it reaches the network only through Arslan's own local proxy, which has no site list yet: it refuses a name that resolves to a private or loopback address (a LAN device you list under trusted local devices is the one exception: that host or address only, its name pinned to the address it had when you added it, never loopback, link-local or this Mac's own addresses; trusting a device trusts every port on it) and connects to the address it checked. With a system HTTP proxy on this Mac it goes through that proxy, still to the address it checked, except that a tunnel to port 443 goes by name (the system proxy resolves the name and picks the real destination, so the address check is delegated to it there, and a name that resolves differently for it could reach a local address on port 443); it can also reach other loopback ports for local dev servers, but not the ports Arslan itself listens on or a proxy set on this Mac; it has no DNS of its own and no UDP, and it can't reach macOS's certificate trust service unless you allow system certificate checks in the sandbox (needed by Swift, Xcode and Go tools; off by default, since that service fetches certificate data itself, round the proxy). Offline, it has no network at all. Arslan's own ports are read when the command starts, so a port Arslan opens later is reachable from a command already running, and a local proxy this Mac doesn't announce (Tor, `ssh -D`) is reachable like a dev server. By default Arslan asks before every new command (the Terminal setting *When to ask*: "Ask before every command"); answering a card "In this conversation" lets exactly that command text run again in the same conversation without asking. The upgrade to v0.1.63 moves every install to it once, including one that had chosen "Ask only for risky commands" (a stored setting cannot show whether it was chosen); a choice made after that is kept. "Ask only for risky commands" can still be selected: under it, a command Arslan judges harmless (one its rules do not flag) runs in the sandbox without asking, edits and builds as well as reads. Its judgement of which commands are risky is completed only in v0.1.64: until then its rules ask before some of the programs that reach those services, not all, so it can run some commands it should ask about in the sandbox without a card. Until v0.1.64, a run with nobody to ask (a scheduled task, the heartbeat) runs no terminal command at all, whatever rules or grants exist: the step is refused and listed in your Inbox. Such a run can still read the web in Arslan's own browser (its own persistent profile; pages run their JavaScript), call MCP tools that their server marks read-only (the server's own claim), and use Arslan's fixed-argument helpers (listing your Shortcuts and, when you have switched them on, the local-network scan and the SSH host-key probe). The network stays open until the turn has read outside content (a web page, a file, an MCP tool's answer); after that, commands run offline, and one that needs the network asks first with a card. A command you let out of the sandbox runs with your full privileges, under the same network rule. Do not treat this as the Python computation sandbox.
- **The hard rules are written down once** (v0.1.64, HR-0: `server/services/hard_rules.py`). Each rule names the layer that holds it and the test that proves it, and a test fails when a rule has no row or a row's test isn't collected. There are four categories:
  - *Direct*: what a command's text alone decides. Its forbid rules never run, inside the sandbox or out, and no card is shown for them. Its this-time-only rules (sending, publishing, deleting outside the working folder, changing the system, driving other apps, a command Arslan can't read) are answered by your click each time. The exception is a command whose only rule is that Arslan can't read it: under "Ask only for risky commands" it runs offline in the sandbox with no card (v0.1.64, S2a-3), and it asks only when it would run outside the sandbox. Both are held by the command parser, and the tool loop's gate also refuses a few shapes before any card.
  - *Run later*: writes into files that another program runs or loads as configuration later (v0.1.64, HR-1: `server/services/run_later.py`). The sandbox refuses them to a command in the sandbox and to an installed MCP server, even inside the working folder or a folder you granted, and at any depth: git's hooks and config (`.git/hooks/`, `.git/config` and its worktree config, a submodule's hooks and config one level under `.git/modules/`, `.gitmodules`, and the folder the repository's `core.hooksPath` names, which Arslan reads but never runs; a config it can't read means the command or the server doesn't start), `.envrc`, editor tasks and settings (`.vscode/tasks.json`, `launch.json`, `settings.json` and `mcp.json`, `*.code-workspace`), agents' settings (`.claude/settings*.json` and `.claude/launch.json`, `.mcp.json`, `.codex/config.toml`, `.gemini/settings.json`, the JSON files directly in `.cursor/`), package managers' settings (`.npmrc`, `.yarnrc`, `.yarnrc.yml`, `pip.conf`, `uv.toml`) and commit hooks (`.pre-commit-config.yaml`, `.husky/`). Instruction files (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.cursorrules` and the like) are ordinary files, as in Claude Code and Codex. So are CI files (`.github/workflows/`, `.gitlab-ci.yml`, `.circleci/`, `azure-pipelines.yml`, `Jenkinsfile`, `bitbucket-pipelines.yml`): a CI job runs on the CI service only after a push, so Arslan recognises them but doesn't refuse them, and their guard is the card before a push (the next v0.1.64 changes; until then a sandboxed command can change them, and a push you approve sends that change). So are these names inside a `node_modules` folder (matched as a folder on the real path), where installed packages ship their own and nothing runs or loads them from there; but when the working folder (for an MCP server, its own folder or a folder you granted) already lies inside a `node_modules` folder, there is no such exception and every name stays held. Nor is there when one of these files or folders is a link whose real path leaves its own folder (into `node_modules` or anywhere else; found by the walk below, so also not past its limits or inside the folders it doesn't list): then the exception is off for that run, and the link's target and the folders above it stay in place. A new link can't be made at one of these names or folder names during the run, by `ln -s` or by renaming a link made elsewhere onto it (an ordinary file or folder of that name can). A file or folder of one of these names that is already a link, including one a repository checks out (git stores links), has its target held the same way, whatever the target is named and wherever it is: `.envrc` linked to `envrc.real` holds `envrc.real`; `.vscode` linked to `vsc` holds `vsc/settings.json`, `tasks.json`, `launch.json` and `mcp.json` but not the rest of `vsc`; `.husky` linked to a folder holds all of it; `.git` linked to a folder holds its hooks and configs, not its objects. The target stays in place; a link inside it at one of these names is followed the same way; and when the target doesn't exist yet (a broken link), it can't be made. This rests on the same walk as below, so inside the folders it doesn't list, and in the parts of a working folder too large to map (past its 50,000 entries or 32 folders deep), a link is not followed; its limit on held folders doesn't stop it. Past 256 links at these names (links at other names, such as a `node_modules` full of them, don't count; macOS's sandbox is slow to start, or refuses, a profile holding many more), the command doesn't start in the sandbox, nor under the outside profile that holds them, nor does the MCP server start: Arslan says the working folder has too many links at protected names. A command you let out of the sandbox under this conversation's grant, with no click on its own card, is held the same way (anywhere on disk), with the same note for git as below; a click on that command's own card lifts it. With the sandbox switched off or unable to start, nothing holds them. Arslan's file tools don't refuse them yet (the next v0.1.64 change).
    The cost inside the sandbox: `git init`, `git clone`, `git remote add`, setting an upstream and any `git config` write fail (husky's install too, which sets `core.hooksPath` and writes `.husky/_/`), and so does `npm config set --location=project`. Three of them exit 0: `git checkout -b <branch> origin/<branch>` (or checking out a branch that exists only on the remote) and `git push -u` do the rest with no upstream, and `git branch --set-upstream-to` changes nothing. Whenever a line of git's output (on either stream, so `2>&1` too) names one of these files and says the change was refused ("Operation not permitted"), Arslan tells the model that git didn't update them, to check `git status`, to tell you, and not to commit over them, even at exit 0; a line that only names such a file (a hook printing its own path, a hint, a pathspec error, a diff) doesn't count. It looks for the path, which git never translates, and for that refusal text, which macOS never translates, so this holds in any language git speaks. A step that fails outright on the repository's own config or hooks (`clone`, `init`, `remote add`, a `git config` write) gets the ordinary note for a command the sandbox stopped instead, since nothing in the work tree moved. Fetch, pull, push, commit and switching branches work. When the repository tracks one of these files (`.gitmodules`, `.vscode/settings.json`, `.pre-commit-config.yaml`, `.npmrc`, `.envrc`), git can't change it: `git checkout` or `git switch` to a branch where it differs, is deleted, or is new in a folder that exists moves HEAD and exits 0 but leaves the file as it was (a changed one then shows as a local change, and a `commit -a` would undo the branch's change; the note above covers it, even at exit 0); one where it is new in a folder that doesn't exist yet fails. `merge` (fast-forward or not), `pull`, `rebase`, `cherry-pick`, `reset --hard`, `restore`, `stash` and `stash pop` fail when they must change it, some with the work tree half updated (`stash` keeps its entry and the edit). These were measured under the real sandbox; `revert`, `am`, `worktree add` and `submodule update` write the same way and should fail the same, not measured. Status, diff, add, commit, branch, log, and checkout, stash and merge that don't touch such a file keep working. Letter case doesn't matter to the rule (macOS's disk ignores it). Not covered yet: a `.git` file that names a git folder elsewhere (a worktree, `--separate-git-dir`), a bare repository, a submodule nested deeper, a `core.hooksPath` set in an included config file, and the user's home-level files (shell startup, global git config, LaunchAgents) when the working folder is your home.
    Git's settings (v0.1.64, HR-1b): when git needs to update a repository's config, the model may ask, and one card ("Let git update this repository's settings?") answers for the rest of the conversation; it offers no other scope, the island never answers it, nothing automatic does, and with nobody to ask it is refused and listed in your Inbox. Under it, a command in the sandbox may write `.git/config`, its worktree config and a submodule's config, at any depth under the working folder, and `clone` and `init` run with no template folder (so they make no hooks folder, which stays held). A config reached through a link (a `.git` or a config that is a link) stays held at the link's target, as above, and so do the configs inside the folders the walk below doesn't list. Before each such command Arslan saves those files (finding repositories by walking the working folder, skipping `node_modules` and those folders; when it can't, the command runs with them held); afterwards git's own reader compares each changed one, and every change to a key other than remotes (`url`, `fetch`, `pushurl`), branch tracking (`remote`, `merge`, `rebase`), `user.name`, `user.email`, `submodule.<name>.url` and `.active`, `pull.rebase`, `push.default`, `init.defaultBranch` and the format keys git writes on init (`core.repositoryformatversion`, `filemode`, `bare`, `logallrefupdates`, `ignorecase`, `precomposeunicode`) is put back, a new repository's included: `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, a pager or editor, filters, `diff.external`, aliases, credential helpers, includes and URL rewrites among them. The step and the model name the keys put back, never their values. When the check fails, the file goes back to what it was before the command whole (a new repository's config is removed). The hooks, `.gitmodules`, the `core.hooksPath` folder, `.husky/`, `.envrc`, editor, agent and package settings stay held under it, and a command outside the sandbox never gets it. Git's sample hooks (`.git/hooks/*.sample`, which git never runs) may be written in the sandbox with or without it; renaming one to a hook's name is refused, and so is making a link at a hook's name. When the walk finds a link at a hook's name (`pre-commit -> pre-commit.sample`, wherever it points) or a hooks folder that is a link, it counts as a link out of its folder: that exception and the `node_modules` one are off for the run, and the link's target is held. What a command leaves running in its process group is ended before the check. A process that leaves the group (a session of its own) can still change a config after the check, so once any folder has had this permission, every later command, in any conversation or sub-session, with or without the permission and in or out of the sandbox, first has those folders' configs checked the same way against what the last check left (a config removed in a run is written back too); when a folder can't be looked through completely or a config can't be written back, the command doesn't start and says why. Arslan keeps this while it runs, not across a restart. Not covered, named residuals: a process that left the group and writes after that check, while the next command runs (closing it fully would need a shadow copy of the config; it takes a command run under this permission that deliberately escapes its process group, and the permission itself, asked once per conversation, is the main defence: mainstream agents have no put-back at all, so this is an extra layer); and git run outside Arslan, or by a plugin hook or an MCP server, before the next command.
    The folders around them stay in place (HR-1's ancestor hold). The names are matched by path, so a command could otherwise rename `.git`, `.git/hooks`, `.vscode` or `.husky` (or a folder above one), write inside it under the new name and rename it back. So when a command or an MCP server starts, every existing held folder (`.git` and its `hooks`, `worktrees` and `modules`, `.vscode`, `.claude`, `.codex`, `.gemini`, `.cursor`, `.husky`, and the folder `core.hooksPath` names) and every folder above it, up to the working folder (an MCP server's own and granted folders; up to the root of the disk for a command let out under this conversation's grant), can't be renamed, removed or replaced; files inside are created, written and removed as before. For a command let out, only the held folders inside the working folder are held in place: elsewhere on disk their files are held by name, but the folders themselves can move. Arslan finds them by walking the working folder: links aren't followed, `node_modules` is skipped under the same exception as above, and the walk stops at 50,000 entries, 32 folders deep, or 256 held folders (or 128 KiB of their paths and the paths above them), which keeps the sandbox's rules small enough to start a command. The walk never lists the folders you keep closed or the home folders macOS's privacy controls protect (`~/Desktop`, `~/Documents`, `~/Downloads`, `~/Library`, `~/Pictures`, `~/Movies`, `~/Music`), so it can't raise a privacy prompt or look into a closed folder when the working folder is your home or contains them; inside those folders it holds every folder with one of those names by its name instead (so no new `.git` can be made there in that run), and the folder itself stays in place. A working folder that is one of them, or inside one, is walked as usual. Past the walk's limits, or on a folder it can't list, every folder with one of those names is held by its name wherever it is (closed, not open), so no new one (a `.git`, a first `.vscode`) can be made in that run, and the note for a stopped command says the working folder was too large to map; links in the parts of a working folder too large to map aren't held (past the limit on held folders alone, the walk goes on for them). The cost inside the sandbox: `rm -rf .git` fails (after removing what isn't held), and so does renaming or removing a folder that holds a repository or one of these folders, or the working folder itself. A held folder that doesn't exist yet isn't held, by design: `git init`, `git clone` and a first `.vscode` make one. The accepted residual is a folder prepared elsewhere, under no held name, and renamed into a fresh place where another program would load it: an editor's `.vscode`, `.husky`, an agent's or a package manager's settings. For git, a check of what git itself would read follows in the next change (HR-1b). For comparison, as documented by those projects: Claude Code's sandbox runtime denies writes to a list of named dangerous paths, matched by path with a similar residual; Codex makes `.git` read-only, which holds git at the cost of a card for every commit.
  - *Never automatic*: payments, installing capabilities, another machine, leaving the sandbox, the network after outside content, git updating a repository's settings (HR-1b) and the other once-only kinds, what full access still asks (sending, opening a site, a Hands shortcut), plus any command with a this-time-only rule. Nothing automatic answers these: not Arslan's own judgement of a request (a classifier, when one is added) and not a full-access mode. Your own standing answers are the exception, as before: a grant you gave answers a site, a Hands shortcut or a send; an "Always" rule you set answers a send; this conversation's grant to run commands outside the sandbox lets a command out with no card; and a grant in this conversation answers the network card for a command in the sandbox after outside content. They are held by the permission ladder, and an unknown kind fails closed.
  - *Absolute*: held even under the least strict settings ("Ask only for risky commands", a grant to run commands outside the sandbox, the sandbox switched off). The forbid rules, Arslan's own data, the skill and plugin folders, Apple Events, payments, capabilities and the network cut after outside content stay in force there. They are held by the outside profile, the gate and the permission ladder. The profile's part holds only where macOS's sandbox can start; where it can't, a command outside the sandbox has only the gate and the ladder. One plain AppleScript or `shortcuts run` call that you approve with a click in the asking window (U11's bare run) runs with no profile, so it can send Apple Events.

  Hard links that already exist inside a folder you granted, pointing at a file elsewhere, are accepted and not detected: a write through such a link reaches the original. The same holds for the run-later files: a hard link made before the command ran, under an ordinary name, to one of them (a git hook, an editor's settings) is written through.
- **BYOK secret confidentiality depends on the secret key and `crypto_salt`.** In the desktop app the key is the file `~/.arslan/secret_key`, kept outside the data folder: anything running as you can read it (sandboxed commands cannot), so encryption protects a copied data folder or backup, not against software already running on your Mac.
- **SSRF protection is delegated to your proxy for `https` + proxy.** Outbound fetches normally resolve the hostname once, reject any non-global address, and pin the connection to that IP — so a name that re-resolves to a private address between the check and the connection cannot be reached. That guarantee **cannot** be carried over an HTTP proxy on `https`: httpcore's CONNECT tunnel ignores the `sni_hostname` extension and hands the tunnel's own origin host to TLS, so pinning would make certificate validation fail against an IP literal. In that one combination Arslan degrades to *the proxy decides where the request goes* and **logs a warning** rather than failing silently. Plain `http` through a proxy, and every non-proxied request, still pin. If `HTTPS_PROXY`/`https_proxy` is set in your environment, your `https` fetches run in this delegated mode — point it at a proxy you trust, or unset it for the pinned path.

- **Generic secret detection is CI-side, not GitHub-side.** GitHub's non-provider-pattern scanning (the one that catches private keys and other non-vendor secrets) requires an organization-owned repository on GitHub Team with Secret Protection; this repository is personal, so that setting cannot be enabled — the API silently accepts and ignores it. The defenses that ARE in place: CI runs `gitleaks detect` over the **full history** on every push (a diff-mode scan would permanently miss anything that slipped in once), Apple signing material never enters the repository (it lives in GitHub Actions secrets, is `.gitignore`d, and is recoverable from the Apple Developer portal — see `docs/RELEASE_KEYS.md`), and no `pull_request`-triggered workflow references secrets — asserted by a test, not by convention.
- **An update is code you chose to trust once, at install time.** Auto-updates are minisign-signed; the public key is compiled into the app and the private key lives in GitHub Actions secrets — which are **write-only**, so the CI copy can never be read back out. The maintainer keeps the only recoverable copy offline; losing it would strand every existing install on its current version (custody, backup, and rotation: `docs/RELEASE_KEYS.md`). Publishing a GitHub release IS pushing an update to every install, which is why releases are created as drafts and published by a human. If the signing key were compromised together with repository write access, an attacker could ship a malicious update — the same trust model as every self-updating desktop app, stated here rather than implied.

## Backup & durability

The PBKDF2 salt now lives in the **database**, beside the ciphertext (migration 0039). A legacy `crypto_salt` file is only a recovery candidate, not the active derivation source. The external `ARSLAN_SECRET_KEY` remains essential: keep it separately from the data archive. Never publish either private data or keys.

Stop the app before taking a backup. `python -m scripts.backup_data create` uses SQLite's backup API (including committed WAL data), checksums files, and excludes access tokens, the external secret and rebuildable caches. Restore validates checksums, paths and database integrity **into a new directory only**. See [Recovery and execution contracts](docs/RELIABILITY.md). Checksums detect damage, not authenticity: only restore archives you trust.

Run text is checkpointed periodically and interrupted runs are marked at boot. This is partial-output recovery, not transparent replay of external effects. Task recipes retain completed-step outputs; retrying unfinished steps requires explicit confirmation and can repeat effects that completed before a crash.

## Reporting a vulnerability

Please report security issues **privately** — do not open a public issue for a vulnerability.

- **Primary channel:** use GitHub's private vulnerability reporting — the **"Report a vulnerability"** button on the repository's **Security** tab (`https://github.com/mirzatghayrat/arslan/security/advisories/new`). This opens a private security advisory visible only to the maintainers.
- **That button is the only channel.** Private vulnerability reporting is enabled on this
  repository, so a report filed there reaches the maintainers privately and keeps the whole
  exchange in one place. There is deliberately no email address here: an address in a public
  file is scraped, and a second channel is a second place for a report to be missed.

Please include a description, reproduction steps, affected version/commit, and impact. We will acknowledge your report and coordinate a fix and disclosure timeline with you.

## Supported versions

Arslan is **pre-v1**. Only the `main` branch is supported; security fixes land there. There are no backported release branches yet.
